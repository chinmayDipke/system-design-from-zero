Building a toy town from Lego

You get a big box of Lego and a request: "Build me a railway station." You do not start by snapping bricks. First you ask: "How many platforms? Do trains go both ways?" Then you pick the pieces: platform, train, signal. Then you decide which piece connects to which. Only then do you build.

Low-level design interviews work the same way. The interviewer says "Design a parking lot." You ask questions, pick the classes, connect them, and then write the important methods. Talking through the steps matters as much as the final code.

The LLD interview flow, then five problems

Use these seven steps every time. In a 45-minute round, spend about 5 on requirements, 10 on entities and relationships, 5 on the diagram, 20 on key methods and patterns, and 5 on edge cases.

  1. Requirements: ask questions and write down what is in and out of scope.
  2. Entities: list the nouns. They become classes.
  3. Relationships: who owns whom, who uses whom, and how many (see UML class diagrams).
  4. Class diagram: draw it.
  5. Key methods: write the two or three methods that carry the real logic.
  6. Patterns: use one only where behaviour varies (see design patterns and SOLID).
  7. Edge cases: full, empty, invalid, and concurrency.

Every skeleton below is plain TypeScript, kept small on purpose, with time passed in as a number so the output is the same every run. They compile with tsc --strict and the outputs are real. They keep data in memory; a real system would save it in a database.

Concurrency: these skeletons are safe only because one Node process runs one piece of code at a time. As soon as two servers or two database calls can race (two people picking the last parking spot or the same cinema seat), you need a database transaction, a row lock or a unique constraint. The system-design version of this problem is in Ticket booking.

1. Parking lot

Clarifying questions: What vehicle types (bike, car, truck)? One floor or many? Fixed spot sizes? Fee: per hour, flat, or by vehicle type? Pay at exit or at a machine? Multiple entrances? Is a lost ticket in scope?

Classes and relationships: ParkingLot owns many Spots (composition) and creates Tickets. A Ticket refers to a Vehicle and a spot. A fee rule sits behind an interface.

Patterns: Strategy for the fee (hourly, flat, weekend rates) and for how to pick a spot (nearest to the gate, lowest floor). Factory to create vehicles or spots from a type. The lot is often a Singleton in the answer, but passing it in is cleaner.

type VehicleType = "bike" | "car";
interface Vehicle { plate: string; type: VehicleType }
interface Ticket { id: number; plate: string; spotId: string; inTime: number }

class Spot {
  vehicle?: Vehicle;
  constructor(public id: string, public type: VehicleType) {}
  get free(): boolean { return !this.vehicle; }
}

const RATE_PER_HOUR: Record<VehicleType, number> = { bike: 10, car: 30 };
const HOUR = 3_600_000;

class ParkingLot {
  private tickets = new Map<number, Ticket>();
  private nextId = 1;
  constructor(private spots: Spot[]) {}

  park(v: Vehicle, now: number): Ticket {
    const spot = this.spots.find((s) => s.free && s.type === v.type);
    if (!spot) throw new Error(`Lot full for ${v.type}`);
    spot.vehicle = v;
    const t: Ticket = { id: this.nextId++, plate: v.plate, spotId: spot.id, inTime: now };
    this.tickets.set(t.id, t);
    return t;
  }

  unpark(ticketId: number, now: number): number {
    const t = this.tickets.get(ticketId);
    if (!t) throw new Error("Invalid ticket");
    const spot = this.spots.find((s) => s.id === t.spotId)!;
    const hours = Math.max(1, Math.ceil((now - t.inTime) / HOUR));
    spot.vehicle = undefined;
    this.tickets.delete(ticketId);
    return hours * RATE_PER_HOUR[spot.type];
  }
}

const lot = new ParkingLot([new Spot("C1", "car"), new Spot("B1", "bike")]);
const t = lot.park({ plate: "MH12AB1234", type: "car" }, 0);
console.log("Ticket", t.id, "spot", t.spotId);
try {
  lot.park({ plate: "MH14XY9999", type: "car" }, 0);
} catch (e) {
  console.log((e as Error).message);
}
console.log("Fee:", lot.unpark(t.id, 2.5 * HOUR));
Ticket 1 spot C1
Lot full for car
Fee: 90

Edge cases: lot full (shown above), unknown or already-used ticket, a car parked past the time, two gates picking the same spot at once (needs a lock or unique constraint, see the warning above), and what to do with a bigger vehicle in a smaller-only lot.

2. Splitwise (expense sharing)

Clarifying questions: Equal splits only, or also exact amounts and percentages? Groups? Do we need "simplify debts"? Currency? Should we notify people?

Classes and relationships: User, Group (many users), Expense (paid by one user, shared by several), and a balance sheet (ExpenseBook) that tracks "who owes whom". Each expense has a Split rule.

Patterns: Strategy for split types (equal, exact, percent), so adding "by shares" is one new class. Observer to notify members when an expense is added.

type UserId = string;

class ExpenseBook {
  // owes.get(a)?.get(b) = paise that a owes to b
  private owes = new Map<UserId, Map<UserId, number>>();

  private get(from: UserId, to: UserId): number {
    return this.owes.get(from)?.get(to) ?? 0;
  }
  private set(from: UserId, to: UserId, paise: number): void {
    if (!this.owes.has(from)) this.owes.set(from, new Map());
    this.owes.get(from)!.set(to, paise);
  }
  private add(from: UserId, to: UserId, paise: number): void {
    const back = this.get(to, from);
    if (back >= paise) {
      this.set(to, from, back - paise); // cancel against what they owed us
    } else {
      this.set(to, from, 0);
      this.set(from, to, this.get(from, to) + paise - back);
    }
  }

  addEqualExpense(paidBy: UserId, totalPaise: number, users: UserId[]): void {
    const share = Math.floor(totalPaise / users.length);
    let leftover = totalPaise - share * users.length; // spread odd paise
    for (const u of users) {
      const mine = share + (leftover-- > 0 ? 1 : 0);
      if (u !== paidBy) this.add(u, paidBy, mine);
    }
  }

  print(): void {
    for (const [from, row] of this.owes)
      for (const [to, p] of row)
        if (p > 0) console.log(`${from} owes ${to}: Rs ${(p / 100).toFixed(2)}`);
  }
}

const book = new ExpenseBook();
book.addEqualExpense("Asha", 90000, ["Asha", "Ravi", "Meera"]);
book.addEqualExpense("Ravi", 10000, ["Ravi", "Meera", "Asha"]);
book.print();
Ravi owes Asha: Rs 266.67
Meera owes Asha: Rs 300.00
Meera owes Ravi: Rs 33.33

Check the second line by hand: Ravi owed Asha Rs 300; then Ravi paid Rs 100 shared by three, so Asha now owes Ravi Rs 33.33, which cancels against the 300, leaving Rs 266.67.

Edge cases: money is stored in paise (whole numbers), never floats, because 0.1 + 0.2 is not 0.3 in floating point. Odd paise are spread across people so the total always matches. Also: a person paying for an expense they are not part of, settle-up payments, and "simplify debts" (a greedy match of the biggest debtor to the biggest creditor).

3. Elevator

Clarifying questions: One elevator or a bank of them? How many floors? Do we handle weight limits, emergency stops, doors? Is the algorithm part of the question or just "works correctly"?

Classes and relationships: Elevator (floor, direction, stops), Request (hall call or cabin call), Controller (chooses which elevator takes a hall call), Door, Button.

Patterns: State for the elevator (Idle, MovingUp, MovingDown, Maintenance), and Strategy for scheduling (nearest car, or SCAN: keep going in one direction while there are stops, then reverse; this is the idea below).

type Direction = "UP" | "DOWN" | "IDLE";

class Elevator {
  floor = 0;
  direction: Direction = "IDLE";
  private stops = new Set<number>();

  request(floor: number): void {
    if (floor !== this.floor) this.stops.add(floor);
  }

  step(): void {
    if (this.stops.size === 0) { this.direction = "IDLE"; return; }
    const above = [...this.stops].some((f) => f > this.floor);
    const below = [...this.stops].some((f) => f < this.floor);
    if (this.direction === "IDLE") this.direction = above ? "UP" : "DOWN";
    else if (this.direction === "UP" && !above) this.direction = "DOWN";
    else if (this.direction === "DOWN" && !below) this.direction = "UP";
    this.floor += this.direction === "UP" ? 1 : -1;
    if (this.stops.delete(this.floor)) console.log(`Door opens at floor ${this.floor}`);
  }
}

const lift = new Elevator();
lift.request(5);
lift.request(2);
for (let i = 0; i < 5; i++) lift.step();
lift.request(1);
for (let i = 0; i < 5; i++) lift.step();
console.log(lift.floor, lift.direction);
Door opens at floor 2
Door opens at floor 5
Door opens at floor 1
1 IDLE

Edge cases: a request for the current floor, new requests while moving, no requests (idle), overload, emergency stop, and with many elevators, which one takes a call. The skeleton handles one elevator and serves 5 and 2 on the way up, then comes back for 1.

4. BookMyShow (classes only)

Clarifying questions: Only seat booking, or food too? Seat types and prices? How long can a person hold seats before paying? Cancellation and refunds? Do we model many cities and theatres?

Classes and relationships: City has many Theatres; a Theatre has many Screens (composition); a Screen has Seats. A Show ties a Movie, a Screen and a start time together. A Booking ties a user, a Show and a set of seats, and has a Payment.

Patterns: State for a booking (Pending, Confirmed, Expired, Cancelled), Strategy for pricing (weekday, weekend, premium seat), Observer to send confirmation messages. The key method below is "hold, then confirm".

type SeatState =
  | { status: "HELD"; userId: string; until: number }
  | { status: "BOOKED"; userId: string };

class Show {
  private state = new Map<string, SeatState>();
  constructor(public id: string, public movie: string, public seatIds: string[]) {}

  holdSeats(userId: string, ids: string[], now: number, holdMs = 300_000): boolean {
    for (const id of ids) {
      const s = this.state.get(id);
      if (s && (s.status === "BOOKED" || s.until > now)) return false; // taken
    }
    for (const id of ids) this.state.set(id, { status: "HELD", userId, until: now + holdMs });
    return true;
  }

  confirm(userId: string, ids: string[], now: number): boolean {
    const ok = ids.every((id) => {
      const s = this.state.get(id);
      return s?.status === "HELD" && s.userId === userId && s.until > now;
    });
    if (!ok) return false;
    for (const id of ids) this.state.set(id, { status: "BOOKED", userId });
    return true;
  }
}

const show = new Show("S1", "Some Movie", ["A1", "A2", "A3"]);
console.log(show.holdSeats("asha", ["A1", "A2"], 0));
console.log(show.holdSeats("ravi", ["A2", "A3"], 1000));
console.log(show.confirm("asha", ["A1", "A2"], 2000));
console.log(show.holdSeats("ravi", ["A2"], 600_000));
true
false
true
false

Read the four lines in order: Asha holds A1 and A2 (true); Ravi tries A2 and A3 and is refused because A2 is held (false); Asha confirms (true); much later Ravi tries A2 again and is refused because it is now booked, not just held (false).

Edge cases: a hold that expires and frees the seat, paying after the hold expired, the same user double-clicking, partial group seats (all or nothing, as the code does), and above all two people clicking the same seat at the same moment. In memory, one process handles one call at a time. In real life with many servers this must be a database transaction or a unique constraint on (show, seat); read Ticket booking for the full design.

5. Vending machine

Clarifying questions: Which coins and notes? Does it give change? What if an item is sold out? Can the user cancel and get money back? Does an operator refill stock?

Classes and relationships: VendingMachine holds the stock (Slots with price and quantity), the credit, and a current State. States: Idle, HasMoney, Dispensing.

Patterns: State is the star. Each state answers "what happens if the user inserts money / selects an item?" in its own class, so there is no giant if (state === ...). This is the pattern that separates it from Strategy: the object moves between states by itself.

interface State {
  insert(m: VendingMachine, rupees: number): void;
  select(m: VendingMachine, code: string): void;
}

class VendingMachine {
  credit = 0;
  stock = new Map([["A1", { price: 20, qty: 1 }]]);
  state: State = new Idle();
  insert(rupees: number): void { this.state.insert(this, rupees); }
  select(code: string): void { this.state.select(this, code); }
}

class Idle implements State {
  insert(m: VendingMachine, rupees: number): void {
    m.credit += rupees;
    m.state = new HasMoney();
  }
  select(): void { console.log("Insert money first"); }
}

class HasMoney implements State {
  insert(m: VendingMachine, rupees: number): void { m.credit += rupees; }
  select(m: VendingMachine, code: string): void {
    const item = m.stock.get(code);
    if (!item || item.qty === 0) return console.log("Sold out");
    if (m.credit < item.price) return console.log(`Need Rs ${item.price - m.credit} more`);
    item.qty--;
    console.log(`Dispensed ${code}, change Rs ${m.credit - item.price}`);
    m.credit = 0;
    m.state = new Idle();
  }
}

const vm = new VendingMachine();
vm.select("A1");
vm.insert(10);
vm.select("A1");
vm.insert(20);
vm.select("A1");
vm.insert(20);
vm.select("A1");
Insert money first
Need Rs 10 more
Dispensed A1, change Rs 10
Sold out

Edge cases: note the last line. The item was sold out, but the Rs 20 stays as credit with no way out. A real machine needs a cancel() that refunds. Also consider: not enough change in the machine, a jam, power cut in the middle, and invalid codes.

Practice (about 45 minutes)

A. Run a skeleton and break it on purpose (10 minutes)

  1. Open typescriptlang.org/play in Chrome. Click the left editor, press Ctrl + A, then Delete.
  2. Click Copy on the parking-lot code, paste it, and press Ctrl + Enter (or click Run). In the Logs tab you should see Ticket 1 spot C1, Lot full for car and Fee: 90.
  3. Change the first line to type VehicleType = "bike" | "car" | "truck";. A red wavy line appears under RATE_PER_HOUR: the compiler tells you that you forgot the price for trucks. Hover to read it. Add truck: 60 to fix it. This is how TypeScript helps you cover every case.
  4. Change the time in the last line from 2.5 * HOUR to 0.2 * HOUR and run. The fee should be 30 (the minimum charge is one hour).

Quick quiz

What are the seven steps of the LLD interview flow?

Requirements, entities, relationships, class diagram, key methods, patterns, edge cases.

Why does the Splitwise skeleton store paise instead of rupees?

Whole numbers avoid floating-point errors (0.1 + 0.2 is not 0.3). Odd paise are spread over people so that the total always matches.

Why is State a better fit for the vending machine than Strategy?

The machine changes its own behaviour as it moves between Idle, HasMoney and Dispensing. With Strategy the caller picks the behaviour from outside.

In the BookMyShow skeleton, why does confirm() check that the hold has not expired?

Otherwise someone could pay after their hold ran out and take a seat that was already given to another person.

The interviewer says "two people try to book the last seat at the same moment". What do you say?

In memory this works only inside one process. With many servers I need an atomic step in the database: a transaction with a row lock, or a unique constraint on show and seat so the second insert fails. I also keep a short hold with an expiry so unpaid seats are released. The full design is in the Ticket booking lesson.

You must add "by percentage" splits to Splitwise. Which class do you change?

Ideally none of the existing ones. With a Split strategy interface you add one new class, PercentSplit, and the rest of the code is untouched (Open/Closed).

Say it in the interview

Before I draw anything, let me ask a few questions to fix the scope, and I will note what I am assuming.
I will start with the entities, draw the relationships with multiplicities, then write the two or three methods that hold the real logic.
I use a pattern only where behaviour varies: Strategy for pricing, State for a machine that changes mode. Otherwise I keep it plain.

Common follow-up question: "How would you make this thread-safe or work across many servers?"

Inside one process I would guard the shared state with a lock or a queue. Across servers a lock in memory is useless, so I move the rule into the database: a transaction with a row lock, or a unique constraint so a duplicate booking fails. Holds get a time limit so seats are not stuck forever.
