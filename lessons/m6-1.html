The tiffin box and the dabbawala

A dabbawala picks up your tiffin, and he does not open it. He does not know what is inside. He only knows: "pick up here, drop there." The tiffin is closed. The dabbawala uses it only through its handle and its tag.

Now think of a school with many kinds of teachers: maths, science, drawing. The principal says "Everyone, take attendance." Each teacher does it in her own way, but the principal does not care how. She just says one sentence and each teacher does the right thing.

Object-oriented programming (OOP) is built from these two ideas: closed boxes with a small handle, and one command that many things answer in their own way.

The four ideas, in plain words

So far in this course you drew big boxes (servers, databases). Low-level design (LLD) zooms inside one box and asks: "which classes, with which methods, talking to each other how?" Interviewers use it to see if you write code that is easy to change. This lesson refreshes the vocabulary; the next ones build on it.

Class and object

A class is a blueprint (the design of a bank account). An object is one real thing made from it (Asha's account). A class holds data (fields) and actions (methods).

1. Encapsulation: keep the data safe behind methods

Hide the fields. Let outsiders change them only through methods that check the rules. Then a balance can never become negative by accident, because the only door is deposit(), and the door has a guard.

class Account {
  #balance = 0; // truly private: code outside the class cannot touch it

  constructor(public readonly owner: string) {}

  deposit(amount: number): void {
    if (amount <= 0) throw new Error("Amount must be positive");
    this.#balance += amount;
  }

  get balance(): number {
    return this.#balance;
  }
}

const acc = new Account("Asha");
acc.deposit(500);
console.log(acc.owner, acc.balance);
try {
  acc.deposit(-5);
} catch (e) {
  console.log("Rejected:", (e as Error).message);
}
// acc.balance = 1_000_000;   // compile error: balance is read-only

Real output:

Asha 500
Rejected: Amount must be positive

In TypeScript, private is only checked while compiling. A #name field is private at run time too. Use # when it really must be hidden.

2. Abstraction: say what, not how

An abstract class or interface describes what something can do without saying how. The caller needs only the "what". Like the Start button of a washing machine: you do not need to know about the motor.

3. Inheritance: a child class reuses its parent

class EmailNotifier extends Notifier means "an EmailNotifier is a Notifier". It gets the parent's code for free and adds or replaces some.

4. Polymorphism: one call, many behaviours

Code written against the parent type works with any child. The loop below calls send() on each item and each one does its own thing.

abstract class Notifier {
  constructor(protected readonly to: string) {}

  // Abstraction: say WHAT must happen, not HOW.
  abstract send(message: string): string;

  // Inheritance: every child gets this for free.
  describe(): string {
    return `Notifier for ${this.to}`;
  }
}

class EmailNotifier extends Notifier {
  send(message: string): string {
    return `EMAIL to ${this.to}: ${message}`;
  }
}

class SmsNotifier extends Notifier {
  send(message: string): string {
    return `SMS to ${this.to}: ${message}`;
  }
}

// Polymorphism: one loop, many behaviours.
const list: Notifier[] = [new EmailNotifier("a@x.in"), new SmsNotifier("98xxxxxx01")];
for (const n of list) {
  console.log(n.send("Your order is out for delivery"));
}
console.log(list[0]!.describe());
EMAIL to a@x.in: Your order is out for delivery
SMS to 98xxxxxx01: Your order is out for delivery
Notifier for a@x.in

Composition over inheritance

Inheritance is tempting, but it glues the child to the parent forever. If you write class UserService extends Logger just to reuse log(), you are lying: a user service is not a logger. Changes to Logger can break UserService, and a class can extend only one parent.

The usual advice is: prefer "has-a" over "is-a". Put the helper inside as a field and pass it in. You can swap it later without touching the class.

class Logger {
  log(msg: string): void {
    console.log("[log]", msg);
  }
}

interface Store {
  save(key: string, value: string): void;
}

class MemoryStore implements Store {
  data = new Map<string, string>();
  save(key: string, value: string): void {
    this.data.set(key, value);
  }
}

// Has-a, not is-a: UserService HAS a logger and a store.
class UserService {
  constructor(private logger: Logger, private store: Store) {}

  register(name: string): void {
    this.store.save(name, "active");
    this.logger.log(`registered ${name}`);
  }
}

const store = new MemoryStore();
new UserService(new Logger(), store).register("Ravi");
console.log([...store.data.entries()]);
[log] registered Ravi
[ [ 'Ravi', 'active' ] ]

Trade-offs: when to use which

Inheritance (is-a)Composition (has-a)
Good forA true "kind of" relation, shared behaviour in a small, stable familyReusing behaviour, swapping parts, testing with fakes
CouplingTight: child depends on parent's inner workingsLoose: only the small interface is shared
Change laterHard: the family tree is fixedEasy: swap one part
Watch outDeep trees (3+ levels), children that break the parent's promiseMore small classes and some wiring code
Do not worry about getting OOP "perfect". If an interviewer sees small classes, clear names, private data and an interface where behaviour varies, you are already ahead of most candidates.

Run it yourself (about 20 minutes)

A. Open the TypeScript Playground

  1. In Chrome press Ctrl + T, type typescriptlang.org/play and press Enter.
  2. You see an editor on the left and results on the right. No install and no account needed.
  3. Click inside the left editor, press Ctrl + A to select the sample text and press Delete.

B. Encapsulation

  1. In this lesson, click Copy on the first code block (the Account class) and paste it into the editor with Ctrl + V.
  2. Press Ctrl + Enter (or click the Run button at the top). Open the Logs tab on the right (it may be labelled slightly differently, or sit beside .JS and Errors).
  3. You should see Asha 500 and Rejected: Amount must be positive.
  4. Now delete the two slashes // at the start of the last line. A red wavy line appears under balance. Hover your mouse over it: it says you cannot assign to a read-only property. That is encapsulation protecting you before the code even runs.
  5. If you see no red line, click TS Config in the toolbar and tick strict.

C. Polymorphism

  1. Clear the editor and paste the Notifier block. Run it. Two different lines appear, from one loop.
  2. Add a third class at the bottom: class WhatsAppNotifier extends Notifier with its own send(), then add it to the list. Run again. You added behaviour without changing the loop.
  3. Delete the send() method from SmsNotifier. A red line appears: an abstract method must be implemented. Put it back.

D. Turn inheritance into composition (on paper or in the editor)

  1. Paste the UserService block. Run it and read the output.
  2. Write a second class FileStore implements Store whose save() just does console.log("file saved", key).
  3. Change the last two lines so UserService uses FileStore. You changed one part and left UserService alone. That is the payoff of composition.

Quick quiz

What is the difference between a class and an object?

A class is the blueprint. An object is one real thing built from it, with its own data.

What does encapsulation protect against?

Outside code putting an object into an invalid state. Data is hidden, and only methods that check the rules can change it.

What is polymorphism, in one sentence?

The same method call behaves differently depending on the actual object behind it, so code written for a parent type works with every child.

Why is "class UserService extends Logger" a smell?

A user service is not a kind of logger. It ties the two together, blocks other parents, and Logger changes can break it. Hold a Logger as a field instead.

You must model Car, Bike and Truck, all of which can start() and stop(). Would you choose inheritance or composition?

An interface (or small abstract class) Vehicle with start/stop is fine here because "a Car is a Vehicle" is a true, stable relation. If the differences grow (different engines, fuel, tyres), pull those out into parts such as Engine and compose them, so you do not end up with a deep tree.

Say it in the interview

I keep fields private and expose small methods that enforce the rules, so an object can never be in an invalid state.
Where behaviour varies, I code against an interface and inject the implementation, instead of hard-wiring a class.
I prefer composition over inheritance: I use inheritance only for a true, stable is-a relation.

Common follow-up question: "Why not just use inheritance everywhere to reuse code?"

Because the child becomes tied to the parent's internals. A change to the parent can break every child, trees get deep and hard to read, and a class can have only one parent. With composition I reuse code by holding a small helper behind an interface, which is easy to swap and easy to fake in a test.
