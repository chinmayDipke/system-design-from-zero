The restaurant waiter

You sit in a restaurant. You do not walk into the kitchen. You tell the waiter: "One paneer butter masala, two naan." The waiter goes to the kitchen, and comes back with your food.

You are the client: the one who asks. The kitchen is the server: the one who serves. What you say is the request. The food that comes back is the response.

The kitchen is open all day, ready for anyone who walks in. That is all a server is: a computer that stays on and waits for people to ask.

Client, server, request, response

Almost everything on the internet works like the restaurant. One side asks, the other side answers.

  • Client: the program that starts the conversation. Your Chrome browser, a mobile app, or even another server.
  • Server: the program that waits for requests and sends answers.
  • Request: "Please give me this page" or "Please save this order".
  • Response: "Here is the page" or "Done, order saved" or "Sorry, I could not find that".

A server is just a computer

There is nothing magic about a server. It is a normal computer with three special habits: it is always on, it has a fixed address so others can find it, and it runs a program that listens for requests. Big companies keep thousands of them in buildings called data centres. You can rent a small one for a few hundred rupees a month, or run one on your own laptop while developing (localhost:3000 is your laptop acting as a server).

"Client" and "server" are roles, not types of machine. When your Next.js backend calls the Supabase database, your backend is the client in that moment and the database is the server.

Rule to remember: never trust the client. Price checks, permission checks and payment checks must happen on the backend, because anyone can tamper with what runs in their own browser.

Stateless vs stateful (just the idea)

A server is stateful if it remembers you between requests, like a waiter who remembers "the table 4 guy wanted less spice". It is stateless if every request must carry everything needed, like a fast-food counter that treats each customer as new.

HTTP, the language of the web, is stateless by design: each request stands alone. Websites add memory on top using things like cookies and a session or a login token, so the server can say "ah, this is the same person". You will meet this again when we scale servers up, because stateless servers are much easier to copy and replace.

Trade-offs and when to use what

  • Put logic on the client when it is only about display or comfort (form hints, sorting a list already on screen). It is fast, with no waiting for the network.
  • Put logic on the server when it must be correct and safe (money, permissions, data rules). It is slower because it needs a network trip, but it cannot be tampered with.
  • Stateless servers are simple to scale and recover. Stateful servers feel natural but make it hard to add more machines, since the "memory" lives on one of them.
Beginner mistake: thinking the "server" is the whole company. In an interview, one box labelled "server" is fine at first, but later you will split it into many boxes. Always say which one you mean.

Do it yourself (about 20 minutes)

A. Watch the conversation between your browser and a server

  1. Open Chrome. Go to https://example.com (a tiny, plain website made for testing).
  2. Press F12. A panel opens on the right or bottom. If nothing happens, press Fn + F12, or right-click the page and choose Inspect.
  3. At the top of that panel, click the Network tab. If you do not see it, click the » arrows to reveal more tabs.
  4. With the panel open, reload the page: Ctrl + R. A list of rows appears. Each row is one request your browser (the client) made.
  5. Click the row named example.com (the first one). A detail pane opens.
  6. Click Headers. Find Request URL, Request Method (it says GET) and Status Code (it says 200). That is the request and the first part of the response.
  7. Click Response. You see the HTML the server sent back. That text is what your browser turned into the page.

B. Try a busier site

  1. In the same tab, go to a site you use, for example https://github.com. Keep the Network tab open (it keeps working across pages; if the list is empty, reload with Ctrl + R).
  2. Look at the bottom of the panel: it shows a count like "40 requests". One page made many requests: the HTML, then images, styles and scripts.
  3. Click the filter button Fetch/XHR. These are requests made by the page's own JavaScript to a backend. The names and numbers shown depend on the site.

C. Write it down

  1. In your notes, answer in one line each: who was the client, who was the server, what was one request, what was its response.

Quick quiz

What is a server, in one sentence?

A computer (or program) that is always on and waits for requests, then sends back responses.

Can the same machine be both client and server?

Yes. Client and server are roles. Your backend is a server to the browser and a client to the database.

Why must a price check happen on the backend and not only in the frontend?

Frontend code runs on the user's machine, so the user can change it. The backend is under your control.

What does "HTTP is stateless" mean?

Each request stands alone. The server does not automatically remember earlier requests; cookies or tokens are added to carry identity.

You have to validate an email field. Where do you validate, and why?

Both. In the frontend for quick, friendly feedback; in the backend because the frontend can be bypassed.

Say it in an interview

"A client sends a request and a server sends back a response. Client and server are roles, not machines."
"I never trust the client, so all validation and authorization are enforced on the backend."

Common follow-up question: What does it mean that HTTP is stateless, and how do apps still remember who I am?

Each HTTP request is independent, so the server keeps no memory of earlier ones by default. Apps add state on top: after login the server gives the browser a cookie or token, and the browser sends it with every request so the server can identify the user. Keeping the servers themselves stateless, with session data in a shared store or in the token, makes them easy to scale.
