Four shops, one checklist

A good shopkeeper opens four very different shops: a tea stall that serves a long queue, a help desk that answers from a thick rule book, a phone booth where every second of silence feels rude, and a sales team that writes letters to new customers. The goods differ, but the owner asks the same questions every time: who comes, how many, what must be fast, what can go wrong, and what does it cost?

AI interviews work the same way. "Design a chatbot" and "design a voice agent" sound different, but you answer with the same 7-step framework you already know. The new part is that the expensive, slow, unreliable box in the middle is a language model, and you now know how to handle it (tokens, RAG, scaling, agents, guardrails and evals).

Four AI design problems, compactly

Before reading each problem, set a 5-minute timer and write your own requirements and a rough box diagram. Then compare. In the real interview each of these would take 45 minutes; here every problem is a compact version of the same seven steps.

Example prices used below (invented, check real ones): Rs 200 per million input tokens and Rs 800 per million output tokens, as in the earlier lessons. A day is about 86,400 seconds.

Problem 1: a ChatGPT-like chat app

1. Requirements. Functional: sign in, start a chat, send a message and see the answer appear word by word, keep and reopen past chats, stop a reply midway. Non-functional: first words within about a second or two, a conversation that stays coherent when long, cost under control, safe content. Out of scope: image generation, voice, plugins.

2. Estimation. 100,000 daily users x 10 messages = 1,000,000 messages a day. 1,000,000 / 86,400 = about 12 per second on average; peak at 3x is about 35 per second. A streamed answer stays open about 15 seconds, so at peak about 35 x 15 = 525 open streams. Tokens: with history, say 2,000 input and 400 output per message: 2,000 x 200 / 1,000,000 = Rs 0.40, plus 400 x 800 / 1,000,000 = Rs 0.32, so Rs 0.72 a message and 1,000,000 x 0.72 = Rs 720,000 (7.2 lakh) a day. The model bill dwarfs servers and storage. Storage: about 2 KB of text per message pair x 1,000,000 = 2 GB a day, about 730 GB a year.

3. API.

POST /v1/chats                          -> { "chat_id": "c1" }
POST /v1/chats/{id}/messages            body: { "text": "..." }
     -> Server-Sent Events: token, token, ... , done { "message_id", "tokens_used" }
POST /v1/chats/{id}/stop                -> cancels the running reply
GET  /v1/chats                          -> list of the user's chats
GET  /v1/chats/{id}/messages?before=... -> older messages (paged)

4. Data model. users, chats(id, user_id, title, created_at), messages(id, chat_id, role, content, tokens_in, tokens_out, created_at). The only hot query is "latest messages of one chat", so PostgreSQL with an index on (chat_id, created_at) is fine. Partition or shard by chat_id at much larger scale (sharding).

5. High-level design. Browser, load balancer, stateless app servers (auth and rate limit per user and per token budget), a context builder that loads recent messages, the LLM provider call, then the answer streamed back over SSE. The app saves the full reply after the stream ends. Billing and analytics events go on a queue.

6. Deep dives.

Deep diveOptionsPick
Long conversations outgrow the context window and the budgetSend everything; sliding window of the last N turns; summarise old turns; retrieve old messages by meaning (RAG over the chat)Sliding window plus a running summary. Predictable cost, simple. Add retrieval only if users need to refer to old chats
Many long-lived streamsOne server holds each stream; or a gateway holds connections and workers produce tokensStateless servers behind a load balancer with long idle timeouts. Cancel the upstream model call when the client disconnects, so you stop paying for words nobody reads

7. Trade-offs. Streaming improves perceived speed but makes retries hard (see scaling). Cheap-model routing saves money but risks quality. Per-user daily token budgets protect the bill but annoy heavy users. At 10x: add provider fallbacks, prompt caching of the stable prompt prefix, regional servers, and move the message store to sharded storage.

Problem 2: a customer-support RAG bot

1. Requirements. Functional: answer customer questions from the company's help articles, cite the source, hand over to a human when unsure or on request, remember the current chat. Non-functional: answers grounded in the documents (no invention), reply starts within about 2 seconds, one company's data never shown to another, new or changed articles live within an hour. Out of scope: taking actions like refunds (a later step, with approval).

2. Estimation. 20,000 questions a day. If 80% fall in an 8-hour working window: 16,000 / 28,800 seconds = about 0.6 per second; peak at 3x is about 2 per second. Throughput is tiny, so cost and quality are the real problems. Tokens per question: 300 rules + 200 history + 100 question + 5 chunks x 300 = 1,500 of sources, so 2,100 input and 250 output. Cost: 2,100 x 200 / 1,000,000 = Rs 0.42, plus 250 x 800 / 1,000,000 = Rs 0.20, so Rs 0.62 a question and 20,000 x 0.62 = Rs 12,400 a day. If a cache answers 25%, then 15,000 x 0.62 = Rs 9,300. Storage: 50,000 chunks x (384 numbers x 4 bytes = 1.5 KB vector + about 2 KB text) = about 175 MB. It fits in one Postgres with pgvector (embeddings).

3. API.

POST /v1/conversations                       -> { "id": "k1" }
POST /v1/conversations/{id}/messages         body: { "text": "..." }
     -> stream: tokens ... done { "answer", "sources": [{ "title", "url" }], "handoff": false }
POST /v1/conversations/{id}/feedback         body: { "message_id", "helpful": true }
POST /v1/admin/documents                     (ingest or update an article)

4. Data model. documents(id, tenant_id, title, url, updated_at), chunks(id, document_id, tenant_id, text, embedding vector(384)) with an HNSW index, conversations, messages (with the chunk ids used), and feedback. The tenant_id filter is applied in SQL before ranking (multi-tenant design).

5. High-level design. Follow the numbered path in the picture below: the customer asks (1), the app server does auth, limits and input checks (2), the retriever embeds the question and fetches the top-k chunks for this tenant (3), the prompt is built with numbered sources (4), the model streams an answer (5), an output check requires a citation or hands off to a human (6), and the reply is streamed to the customer (7). A separate ingest pipeline keeps the vector store fresh.

6. Deep dives.

Deep diveOptionsPick
Retrieval quality and "I don't know"Vector only; hybrid (keyword + vector); add a re-ranker; similarity thresholdHybrid search, top 20 re-ranked to 5, plus a threshold. Below the threshold: no model answer, offer a human. Measure on a golden set (evals)
Freshness and safety of the knowledgeRe-embed everything nightly; re-embed only changed pages; delete on removalRe-ingest per changed article and delete old chunks. Treat documents as untrusted data because they can carry prompt injection, and give the bot no powerful tools on this path

7. Trade-offs. A bigger k finds more but costs more and distracts the model. Strict thresholds reduce wrong answers but send more chats to humans. Languages: Hindi and Hinglish queries need a multilingual embedding model, and need more tokens (lesson 1). At 10x: cache frequent questions, route easy ones to a cheaper model, move vectors to a dedicated store if Postgres slows, and shard by tenant.

Problem 3: a real-time voice agent

1. Requirements. Functional: the caller speaks, the agent answers in speech, the caller can interrupt ("barge-in"), the agent can look up an order, a full transcript is saved. Non-functional: the pause after the caller stops speaking must feel natural, so aim for about 1 second to the first sound; calls must not drop; many calls at once. Out of scope: building your own speech models, outbound dialling campaigns.

2. Estimation (latency first). A voice agent is a chain of three streaming services: speech-to-text (STT), the LLM, then text-to-speech (TTS). The latency budget is spent hop by hop. These are example targets, not measured figures:

HopBudget (ms)
Detect that the caller has stopped speaking200
STT finishes the last words150
LLM time to first token400
TTS makes the first audio chunk150
Network in and out100
Total to first sound1,000

Cost of one 5-minute call with invented prices: STT Rs 0.5 per audio minute (on all 5 minutes) = Rs 2.50. The agent speaks about half the call: 2.5 minutes x 150 words = 375 words, about 2,250 characters; with TTS at Rs 1 per 1,000 characters that is Rs 2.25. The LLM runs 20 turns, each about 1,500 input and 60 output tokens: 1,500 x 200 / 1,000,000 + 60 x 800 / 1,000,000 = 0.30 + 0.048 = Rs 0.348 a turn, so 20 x 0.348 = Rs 6.96. Total 2.50 + 2.25 + 6.96 = about Rs 12 a call. At 1,000 simultaneous calls you hold 1,000 open audio streams, each fanning out to three provider streams.

3. API.

POST /v1/calls                         body: { "phone": "...", "agent_id": "..." } -> { "call_id" }
WS   /v1/calls/{id}/audio              duplex: audio frames in, audio frames out, control events
webhook call.ended                     { "call_id", "duration", "transcript_url", "outcome" }
GET  /v1/calls/{id}/transcript         -> turns with timestamps

4. Data model. calls(id, started_at, ended_at, outcome), turns(call_id, n, speaker, text, t_start, t_end, ttfb_ms) for transcripts and per-turn latency, and actions(call_id, tool, args, result). Raw audio goes in object storage with a retention period.

5. High-level design. Caller phone or browser, a telephony or WebRTC gateway, a voice-activity detector (finds where speech starts and ends), streaming STT, the LLM (with a few allow-listed tools), streaming TTS, and audio back to the caller. A session server holds the call's state, and every stage streams into the next: partial text goes to the LLM, and the first complete sentence goes to TTS while the LLM is still writing.

6. Deep dives.

Deep diveOptionsPick
Hitting the latency budgetWait for each stage to finish; stream every stage; a speech-to-speech model that skips the text stepsStream every stage, send TTS sentence by sentence, keep prompts short, use a small fast model, place servers near the provider. A speech-to-speech model can be faster but gives you less control and weaker transcripts
Barge-in (caller interrupts)Ignore interruptions; stop audio only; stop audio, cancel the LLM call and fix the historyThe VAD detects speech while the agent talks: stop playback at once, cancel the LLM and TTS streams, and record in the history only what was actually spoken

7. Trade-offs. Fillers like "let me check" hide a slow tool call but must be honest. Tools lengthen the pause, so cache lookups and prefetch likely data. A cheaper small model is faster but handles complex requests worse. Provide a human handoff. At 10x: regional deployments (distance is latency), autoscaling on concurrent calls, and per-hop latency dashboards (observability).

Problem 4: an AI lead-outreach pipeline

1. Requirements. Functional: take a list of leads, enrich each with public company information, have an LLM draft a short personalised email, let a human review and approve, then send within limits and record replies and opt-outs. Non-functional: nothing is sent without approval, one lead is never emailed twice, sending is spread out within provider limits, unsubscribe requests are honoured at once. Out of scope: buying data, scraping private data. Follow the consent, spam and data-protection laws that apply to you; the design must make opt-out easy to respect.

2. Estimation. 500 leads a day, 3 enrichment lookups each = 1,500 external calls a day. Drafting at 800 input and 200 output tokens: 800 x 200 / 1,000,000 + 200 x 800 / 1,000,000 = 0.16 + 0.16 = Rs 0.32 a draft, so 500 x 0.32 = Rs 160 a day. A human review at 1 minute each is 500 minutes, about 8.3 hours: review, not the model, is the bottleneck. If each mailbox may send 100 a day (example limit; check your email provider), 500 sends need 5 mailboxes, spread over working hours.

3. API.

POST /v1/campaigns                       body: { "name", "template_rules", "daily_limit" }
POST /v1/campaigns/{id}/leads            body: [ { "email", "company", "name" } ] -> accepted count
GET  /v1/drafts?status=pending_review    -> drafts with the facts they used
POST /v1/drafts/{id}/approve | reject    body: { "edited_text"? }
POST /v1/unsubscribe                     (public link in every email)

4. Data model. leads(id, campaign_id, email, status, unique(campaign_id, email)), enrichment(lead_id, source, facts, fetched_at), drafts(id, lead_id, text, prompt_version, status, reviewer, reviewed_at), sends(id, draft_id, sent_at, provider_msg_id), and a suppression table of people who opted out, checked before every send.

5. High-level design. A lead enters a queue. An enrichment worker calls external APIs. A drafting worker builds a prompt from the enrichment facts and calls the LLM, and a guard checks the draft (no invented claims, no banned phrases, right length). The draft waits in a review queue for a human. On approval a sender worker checks the suppression list and the daily limit, then sends. Replies and bounces come back by webhook and update the lead's status. Each stage is a queue plus workers (message queues).

6. Deep dives.

Deep diveOptionsPick
Never send twice, never lose a leadAt-most-once; at-least-once with deduplicationAt-least-once queues, an idempotency key per lead and campaign, and a unique constraint on the sends table. Failed jobs go to a dead-letter queue (idempotency and DLQs)
Quality and safety of the draftsTrust the model; rules only; rules plus review with a sample auditThe draft may use only the enrichment facts you pass in (so it cannot invent), is checked by rules, and always passes human review. Track the approve, edit and reject rates per prompt version as your quality metric
Send limitsSend as fast as possible; fixed daily cap; token bucket per mailboxA token bucket per mailbox with a daily cap and random spacing. A rate limiter (rate limiter) protects sender reputation

7. Trade-offs. More automation means more risk to your sender reputation and brand. Human review is slow but is the right place to catch embarrassing drafts. Enrichment data can be stale or wrong, so store its source and date. At 10x: 5,000 leads a day needs about 83 hours of review, so use confidence-based sampling for low-risk segments, more workers, and per-campaign budgets for tokens and sends.

B. Variation questions

Try each on paper for 5 minutes before opening the answer.

1. The support bot must also issue refunds. What changes?

Add a refund tool and move from a pure Q and A bot to a small agent (agents and tools). Keep it behind an allow-list, validate the order id and amount, cap the amount, require human approval above a limit, make the call idempotent so a retry never refunds twice, and log every call as an audit trail. Add golden-set cases that try to trick the bot into refunding.

2. The voice agent's tool call (order lookup) takes 2 seconds. How do you keep the call natural?

Say a short honest filler ("Let me check that for you") while the tool runs, start the lookup early when the intent is clear, cache or prefetch likely data (for example the caller's last order when the call connects), and set a timeout with a spoken fallback ("I am having trouble, shall I transfer you?").

3. The chat app's monthly bill is double what you planned. Where do you look first?

Per-request token logs (traces with cost): input tokens per message usually grow with history length, so check the context window handling. Then the share of cached or routed requests, retry storms, and a few heavy users or bots. Fixes: summarise old turns, cap history and output length, add per-user budgets, route easy messages to a cheaper model.

Quick quiz

In the chat app estimate, why are 525 open streams a bigger worry than 35 requests per second?

A streamed answer holds a connection open for about 15 seconds, so concurrency is requests per second times duration. Servers, load balancers and provider limits must handle hundreds of simultaneous long-lived connections, and must not time them out.

What breaks if the support bot filters by tenant after ranking instead of in the SQL query?

The top-k can fill with another customer's chunks that then get removed, leaving too few or no results. Worse, a bug in the later filter can leak one company's data to another. Filter before ranking, in the query.

What breaks in the voice agent if the caller interrupts and you only stop the audio?

The LLM and TTS keep running and still bill you, and the saved history says the agent said things the caller never heard, so the next reply is confused. Cancel the streams and keep only what was actually spoken.

Why is human review, not the LLM, the bottleneck in the outreach pipeline, and what does it lead you to do?

500 drafts a day cost only Rs 160 in model calls but need about 8.3 hours of review at a minute each. So you design the review queue (fast approve and edit, show the facts used), track approval rates per prompt version, and sample low-risk segments only at larger scale.

Your latency budget is 1,000 ms but a test call takes 1,800 ms to the first sound. What is your debugging order?

Log the time spent in each hop for each turn. Compare with the budget table, find the hop that is over, and fix that one: slow end-of-speech detection, a large prompt, a slow LLM first token, or non-streaming TTS. Without per-hop timings you are guessing.

Which of the four problems would you design as a workflow, and which might need an agent? Why?

The outreach pipeline and the support RAG bot are workflows: the steps are known and fixed, with model calls inside. The chat app is a single model call with context management. The voice agent may use a small agent loop for tool lookups, with a strict step limit because the caller is waiting.

Say it in the interview

I treat the model as a slow, costly, unreliable dependency. So I do the token and rupee arithmetic first, then add streaming, caching, limits and fallbacks around it (scaling LLM apps).
For a support bot I put most effort into retrieval quality, a citation or "I don't know" path, tenant filtering in SQL, and a human handoff, and I measure it with a golden set before every change.
For a voice agent I work backwards from a latency budget per hop, stream every stage into the next, and handle interruption by cancelling the downstream streams.

Common follow-up question: "How would you evaluate this system before launch?"

Build a golden set of real questions with expected answers and sources, score with code checks, a human rubric and an LLM judge calibrated against humans, and run it on every prompt or model change. Add adversarial cases (prompt injection, out-of-scope, private data). After launch, sample live traffic, collect thumbs up or down, and turn failures into new test cases (evals and observability).

Common follow-up question: "How do you control cost?"

Measure cost per request in traces first. Then cap input and output tokens, summarise long history, cache repeated answers, route easy requests to a cheaper model, set per-user token budgets, and review the top few spenders each week.
