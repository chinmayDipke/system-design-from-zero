The helpful shopkeeper who finishes your sentence

You walk into a kirana shop and say "do..." and the shopkeeper already says "Dosa batter? Dove soap? Dolo?" He knows what most people in the colony ask for when they start with "do". You did not even finish the word, and your answer is ready.

How does he do it? He does not think hard each time. Over the years he noticed what people buy and remembers, for every first few letters, the five most popular things. Asking "do" or "dol" is just remembering, not searching the whole shop.

A search box with suggestions works the same way. The hard part is doing it for millions of people at once, in less than the blink of an eye, while you type. That is why the answers must be pre-made and kept close.

Design search autocomplete (typeahead)

Before reading on, set a 10-minute timer and write your own requirements and a rough diagram. Then compare. In your own words: if the user typed "iph", where could the answer "iphone 15" come from in under 100 ms?

We follow the 7-step framework. This design uses caching, sharding, database indexes and CDNs.

1. Requirements

Functional:

  • While the user types, return the top 5 (or 10) suggestions that start with the typed prefix, ranked by how often people search them.
  • Suggestions should reflect what people search, so trending topics appear after some time.
  • Bad or unsafe suggestions must be filtered out.

Non-functional:

  • Very fast: under about 100 ms end to end, because the user is typing and the result must appear as they type.
  • Highly available. If autocomplete is down, search still works, so this is not critical. A slightly stale list is fine (eventual consistency).
  • Read-heavy: every keystroke is a request; the data is updated only periodically.

Out of scope: spell correction, personalised suggestions, multi-language ranking, and the search results page itself.

2. Estimation

Assume 100 million daily active users, each making 10 searches a day. After the debouncing described below, each search triggers about 4 suggestion requests.

  • Searches: 100,000,000 x 10 = 1,000,000,000 a day.
  • Suggestion requests: 1,000,000,000 x 4 = 4,000,000,000 a day, divided by 100,000 s = 40,000 a second. Peak at 2x is 80,000 a second. (Without debouncing, one request per keystroke would be about 2 to 3 times more.)
  • Data size: keep 10 million distinct popular queries of about 20 characters each: 10,000,000 x 20 = 200 million characters. Many queries share beginnings, so say the trie has about 100 million nodes. If a node costs about 50 bytes (child links plus 5 suggestion ids), that is 100,000,000 x 50 = about 5 GB. That fits in the memory of one machine. We shard for traffic, not for size.
  • Writes: there are no writes on the request path. The data is rebuilt in a batch, for example every hour or every day.

Conclusion: a read-only, in-memory, cache-friendly problem. Most of the engineering goes into making answers cheap to compute and close to the user.

3. API

GET /suggest?q=iph&limit=5
  200 -> { "prefix": "iph", "suggestions": ["iphone 15", "iphone 15 pro", "iphone charger", "iphone 14", "iphone case"] }
  Cache-Control: public, max-age=300

Only one endpoint. The Cache-Control header is on purpose: the same prefix gives the same answer for everyone, so browsers and CDNs can store it (deep dive C).

4. Data model

Trie node:  { children: { 'h': node, ... }, top_k: ["iphone 15", ... 5 items with counts] }

Source of truth (batch):
search_logs      (query, searched_at)                    -- huge, append-only, in files or a warehouse
query_counts     (query, count)                          -- the result of the aggregation job
blocked_terms    (term)                                  -- filter list

Snapshot: the built trie, saved as a file in object storage, loaded by each suggestion server

Why: the trie is built offline and loaded into memory, so no database sits on the request path. Logs are written as files because they are just appended. You will try the simple "database only" version in the SQL exercise to feel why it is not enough at scale.

5. High-level design

Numbers match the picture.

  1. As the user types, the browser waits for a short pause (debounce) and checks its own cache of recent prefixes.
  2. On a miss, the request goes to the CDN / edge cache, which returns the stored answer if another user already asked for this prefix.
  3. On a miss there too, it reaches the suggestion API, which picks the right shard from the first letters of the prefix and asks the trie server.
  4. The trie server walks the tree to the node for the prefix and returns the top 5 saved at that node. No scanning is needed. The response is cached on the way back.
  5. Separately, the search service writes every submitted search into the query logs.
  6. A batch job (hourly or daily) counts queries, applies the blocklist, and the trie builder makes a new trie snapshot.
  7. New snapshots are published to the trie servers, which swap to the new trie without downtime.

6. Deep dives

Deep dive A: the trie with top-k at each node

A trie (say "try") is a tree of letters. Each step down a branch adds one letter, so walking "i", "p", "h" lands on the node for the prefix "iph". All words starting with "iph" are below that node.

ApproachLookup for prefix "iph"ProsCons
Database LIKE 'iph%' with a prefix indexFind all matching rows, sort by count, take 5Simple, no new system; works well for long prefixes and modest dataA short prefix such as "i" matches millions of rows to sort, which is slow; the database takes the load of every keystroke
Plain trieWalk to the node, then visit every word below it to find the best 5Fast walkThe search below the node is slow for short prefixes, the same problem
Trie with top-k cached at every nodeWalk to the node and read its saved top 5Lookup cost depends only on the prefix length (a handful of steps); no scanningMore memory (5 items per node); must be rebuilt to refresh the rankings

Pick: the trie with top-k at each node. We trade memory (cheap, we computed 5 GB) for time (the thing the user feels). A saved top 5 per node is exactly what the shopkeeper in the story remembers.

Deep dive B: building it, and keeping it fresh

ApproachHowProsCons
Offline batch buildEvery hour or day, aggregate the logs into query_counts, build a new trie, publish a snapshot, swap it inSimple and robust; servers are read-only; easy to roll back; the blocklist is applied in one placeNew trends take up to one cycle to appear
Real-time updatesStream each search into counters and update the affected nodes liveTrending queries appear in minutesMany writes to the top-k of nodes near the root (every search touches "i", "ip", "iph"...); locking and complexity; easier to poison with spam
HybridThe big trie is built daily; a small "trending" list updated every few minutes is merged into answersStable base, fresh trendsTwo sources to merge

Pick: start with the offline batch build. Add a small real-time "trending" layer only if the product needs breaking-news freshness. To update safely, each server loads the new snapshot beside the old one and switches a pointer, so there is no moment with an empty trie.

To avoid rewarding one-off or recent noise, count with a time decay (last week's searches count more than last year's) and ignore queries seen fewer than some minimum number of times.

Deep dive C: sharding, caching and the client

  • Sharding by prefix. One machine can hold 5 GB but not take 80,000 requests a second, so we copy the trie to several servers (replicas) for traffic. If the data grew too big, we would split by first letter: shard 1 handles a to f, shard 2 handles g to m, and so on. But letters are not equally popular ("s" is far busier than "x"), so choose the ranges from real counts, or hash the first two letters, and watch for hot shards (sharding).
  • Caching, layer by layer. The same prefix gives the same answer for everyone. So set Cache-Control: max-age=300, and let the browser and the CDN store answers. A few thousand short prefixes ("a", "ap", "app") receive a huge share of the traffic, and the CDN answers those without touching our servers. Keep also a small in-memory cache in the API.
  • Debouncing on the client. Do not send a request on every keystroke. After each key, wait about 150 to 300 ms; if another key arrives, reset the timer. Only send when the user pauses. Also cancel an older request when a newer one is sent, and ignore a response that arrives out of order (check that its prefix still equals what is in the box). Debouncing alone can cut requests by half or more.
  • Prefix on the client. Once the user has typed "iph" and you got 5 results, if the user types "ipho" you may filter those results on the device, before asking the server again.

Deep dive D: filtering bad suggestions

Suggestions appear on a public page, so they must not show offensive, hateful or illegal terms, or private data such as someone's phone number. Do it in three layers: (1) a blocklist (and pattern rules) applied in the batch job, so a blocked term never enters the trie; (2) a quick second check on the serving side, so an urgent removal can take effect without waiting for the next build (a small "remove now" list); (3) a report button and a review process. Also drop queries with too few distinct searchers, which protects against both spam and privacy leaks (a query typed by only one person may be personal).

7. Trade-offs, bottlenecks and wrap-up

  • Memory against speed: storing top-k at every node costs memory but removes all work at request time. Limit depth (say the first 20 characters) and skip very rare queries to keep the trie small.
  • Freshness against simplicity: an offline build is simple and stable but lags; real-time is fresh but complex and abusable.
  • Relevance against safety: pure popularity can promote spam or offensive terms, so filtering is part of the design, not an extra.
  • Bottlenecks: short prefixes are the hot keys (cache them hard), the batch job's runtime as logs grow (it is a big-data job, not a web request), and hot shards.
  • Monitor (observability): suggestion latency p99, cache hit rate at the CDN, trie build age, share of searches that used a suggestion.

At 10x scale: more CDN caching (suggestions per region and language), a trie per language or region, a distributed batch pipeline (a stream of logs aggregated in a data warehouse), and a layer that personalises results on top of the shared trie.

B. A prefix query and its index in the Supabase SQL Editor (20 to 25 minutes)

Use a scratch project. This creates one table called search_queries and 200,000 filler rows (a few tens of MB). You drop the table at the end. Run each block on its own: select all the old text with Ctrl + A, paste the new text, and press Run.

  1. Open your Supabase dashboard in Chrome, open a project, click SQL Editor in the left sidebar and then + New query (it may be a plus icon).
  2. Create the table and a few real-looking rows. Paste this and press Run (or Ctrl + Enter). You should see Success. No rows returned: 
    create table search_queries (
  query text not null,
  count int  not null
);

insert into search_queries (query, count) values
  ('iphone 15', 9800), ('iphone 15 pro', 7600), ('iphone charger', 5200),
  ('iphone 14', 4100), ('iphone case', 3900), ('iphone 13', 2500),
  ('ipad air', 3000), ('instagram', 12000), ('samsung phone', 6000);

alter table search_queries enable row level security;  -- good habit: no public API access
  3. Add 200,000 filler rows, so the table is big enough to make the difference visible. Every filler query starts with the word filler, so none of them matches "iph". Run: 
    insert into search_queries (query, count)
select 'filler ' || md5(g::text), (random() * 1000)::int
from generate_series(1, 200000) as g;
    You should see Success. No rows returned. (It may take a few seconds.)
  4. Run the autocomplete query: 
    select query, count
from search_queries
where query like 'iph%'
order by count desc
limit 5;
    You should see five rows: iphone 15 (9800), iphone 15 pro (7600), iphone charger (5200), iphone 14 (4100), iphone case (3900). That is the answer a user typing "iph" should see. iphone 13 is the sixth match and is cut off by limit 5.
  5. Now ask Postgres how it would run this, with no index yet. Run: 
    explain
select query, count
from search_queries
where query like 'iph%'
order by count desc
limit 5;
    The result is a few lines of text (one per row; if you see a table, read the QUERY PLAN column). You should see Seq Scan on search_queries and a line Filter: (query ~~ 'iph%'::text). Seq Scan means "read every row of the table". With 200,000 rows it is fast enough to hide, but it reads them all for every keystroke of every user.
  6. Create the index made for prefix search: 
    create index search_queries_prefix_idx
  on search_queries (query text_pattern_ops);

analyze search_queries;
    You should see Success. No rows returned. text_pattern_ops tells Postgres to order the index by plain character comparison, so a prefix like iph% becomes a range of the index (everything from iph up to just before ipi). analyze refreshes Postgres's statistics so it knows how big the table is. Gotcha: a normal index (without text_pattern_ops) is often not used for LIKE 'x%' when the database uses a language-aware sorting order, which is the common default; this special index class avoids that. (A varchar column would use varchar_pattern_ops.)
  7. Run the explain from step 5 again. You should now see an Index Scan using search_queries_prefix_idx (or a Bitmap Index Scan followed by a Bitmap Heap Scan), and a line like Index Cond: ((query ~>=~ 'iph'::text) AND (query ~<~ 'ipi'::text)). Read that line as "from iph up to before ipi". Postgres jumps straight into the right place in the index instead of reading every row. Above it you will see a Sort (Sort Key: count DESC) and a Limit: after finding the 6 matching rows it sorts them by count and keeps 5. The exact cost numbers differ on your database; what matters is the node name.
  8. When the index does not help. Try a very short prefix that nearly all rows share. The filler rows all start with f: 
    explain
select query, count
from search_queries
where query like 'f%'
order by count desc
limit 5;
    You should see a Seq Scan again (not the index), and a much larger cost number than before (in the thousands, against single digits for iph%). Postgres is right: the prefix f matches all 200,000 rows, so using the index would not save work, and then it must sort 200,000 rows by count just to pick 5. This is the exact problem of short prefixes like "i" or "s" in a real search box, and it is the reason big systems use a trie with the top 5 stored at each node instead of asking a database.
  9. The plan depends on table size. If you try the same thing on a table with only 9 rows, Postgres will pick a Seq Scan even when the index exists, because reading one small page is cheaper than visiting the index. That is why we added 200,000 rows. If you see Seq Scan in step 7, make sure you ran analyze and that you used iph% with the percent sign at the end.
  10. One more: a wildcard at the start cannot use this index: 
    explain
select query from search_queries
where query like '%phone'
limit 5;
    You should see Seq Scan with Filter: (query ~~ '%phone'::text). A prefix index only works for words that start with the typed letters. That is fine for autocomplete.
  11. Clean up. The editor may ask you to confirm a destructive query; confirm it: 
    drop table search_queries;
    Dropping the table also drops its index.

Honest note: in the steps above, "Seq Scan" versus "Index Scan" are what Postgres chose on this data; on your project the choice can differ in cost numbers and in "Bitmap" variants, but a prefix like iph% on 200,000 rows with this index should use the index.

C. Variation questions

1. Add personalised suggestions: a user's own recent searches should come first. What changes?

Keep the shared trie as it is. Add a small per-user list (their last 20 searches, stored on the device or in Redis keyed by user id). At request time (or on the client), merge: the user's matching recent searches first, then the global top-k, without duplicates. The shared answers stay cacheable at the CDN; only the small personal part is not.

2. A new event happens and people search a brand-new name. Your trie is updated daily. What do you do?

Add a small trending layer: a stream job counts searches in the last few minutes and publishes a short "trending now" list every minute. The suggestion API merges these few entries into the answer when their prefix matches. The big trie keeps its daily build, and the trending layer stays small and cheap.

3. Support another language (Hindi, written in Devanagari). What changes?

A trie works on any characters, so the structure stays. Build one trie per language or locale from that language's logs, route by the app's language setting or the typed script, and be careful with characters that are really combinations of code points (normalise the text the same way when building and when querying). Sizes per node and ranking are tuned per language.

Quick quiz

Why store the top 5 at each node of the trie?

So a lookup needs only to walk the prefix's few characters and read the answer. Without it you would have to visit every word below the node and rank them, which is slow for short prefixes.

Why is the trie built offline from logs instead of updated on every search?

Every search would touch the top-k of many nodes near the root, causing a flood of writes and locking, and spam could poison the results instantly. A batch build is simple, stable, easy to roll back, and applies the blocklist in one place. The cost is some delay.

What breaks if the client sends a request on every keystroke with no debouncing?

Requests multiply (two to three times more), many are wasted on prefixes the user has already typed past, and slow responses can arrive out of order and show suggestions for an old prefix. Debounce and ignore stale responses.

What breaks if you use a plain btree index on query and run LIKE 'iph%' on a database with a language-aware collation?

Postgres may not use the index for the prefix match, so it falls back to scanning the whole table. Create the index with text_pattern_ops (or varchar_pattern_ops), which compares plain characters.

What breaks if a trending hateful phrase is not filtered?

It appears as a public suggestion and harms users and the company. Filter in the batch job with a blocklist, keep a quick "remove now" list on the servers, and require a minimum number of distinct searchers for a query to appear.

Would you use a trie service or just a database prefix query for a small shop's product search with 50,000 products? Why?

A database prefix query with a text_pattern_ops index. At that size it answers in a millisecond or two and needs no new system. A trie service earns its place when the data and traffic are large and short prefixes match millions of rows.

Say it in an interview

"Suggestions are read-only and need to be under 100 ms, so I would precompute them: a trie where each node stores the top 5 queries for that prefix, built offline from the query logs and loaded into memory on each suggestion server."
"Most traffic should never reach the servers: the client debounces keystrokes, and answers for a prefix are cached in the browser and at the CDN, because every user typing 'iph' gets the same result."

Common follow-up question: How do you keep suggestions fresh?

Rebuild the trie on a schedule (hourly or daily) from aggregated logs with time decay, and swap it in with no downtime. For breaking trends, merge in a small real-time trending list updated every few minutes.

Common follow-up question: How do you scale it?

The data is small (a few GB), so replicate the trie across servers for traffic, cache at the CDN, and if it ever outgrows memory, shard by prefix ranges chosen from real traffic counts so that no shard is hot.
