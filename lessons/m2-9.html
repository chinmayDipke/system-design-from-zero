The class monitor and the photocopies

In a class, the teacher writes the day's homework on the board. Students copy it into their notebooks. Only the teacher writes on the board; everyone can read from their own copy. If the board is wiped, the notebooks still have the homework.

Now suppose the teacher adds a new line, "also page 40". Some students copy it quickly; a slow student still has the old version for a minute. If you ask that slow student, he will honestly tell you the older homework.

This is database replication: one leader takes all the changes, and followers keep copies. Copies protect you if one machine breaks, and many readers can share the reading work. The price is that copies can briefly be behind.

Copies of the same data

Why replicate

  • Availability: if the main database dies, a copy can take over.
  • Read scaling: most apps read far more than they write. Send reads to copies and the main database gets breathing room.
  • Closer to users: keep a copy in another region for faster reads.

Leader-follower (primary-replica)

One server is the leader (also called primary or master). All writes go to it. It records each change in a log and sends that log to followers (replicas, read replicas), which apply the same changes in the same order. Reads can go to any follower. This is the most common setup.

Synchronous vs asynchronous

SynchronousAsynchronous
Write is "done" whenThe follower has confirmed it tooThe leader has saved it; followers catch up later
Data loss if leader diesNone for confirmed writesPossible: recent writes not yet copied
Write speedSlower (waits for the follower)Fast
If a follower is downWrites may stallWrites carry on

A common compromise: one synchronous follower for safety, the rest asynchronous for speed.

Replication lag and "I posted but can't see my post"

With asynchronous replication, a follower can be milliseconds (sometimes seconds) behind. Replication lag causes odd experiences. You post a comment (it goes to the leader), the page reloads and reads from a follower that has not received it yet, and your comment seems to have vanished. You post again, and now there are two.

The guarantee we want is read-your-writes: after you write something, you must see it. Common fixes:

  • Read from the leader for a short time after the user writes (say 10 seconds), or for the user's own data.
  • Remember the position of the user's last write and only read from a follower that has caught up to it.
  • Show the new item on screen immediately from the client's own memory (optimistic UI).

Failover

If the leader dies, a follower is promoted to be the new leader. This can be manual or automatic (a monitor notices missing heartbeats and promotes the most up-to-date follower). Risks: with async replication, writes the old leader had not yet sent are lost; and if the old leader comes back believing it is still leader you get split brain (two leaders) unless it is fenced off. Failover is the thing that must be tested, not assumed.

Multi-leader and leaderless, in a paragraph each

Multi-leader: several nodes accept writes (for example one per region), and they sync with each other. Writes are fast everywhere and survive a region outage, but two leaders can change the same row at the same time, so you need conflict resolution (last write wins, or merge). Complex; use it only when you truly need writes in many regions.

Leaderless: any node can take a write. The client sends it to several nodes and counts it done when enough of them (a quorum) confirm; reads ask several nodes and take the newest. Used by Dynamo-style stores such as Cassandra. Very available, but you must accept eventual consistency and handle conflicts.

Trade-offs

  • Replicas scale reads, not writes. All writes still go to one leader. (Splitting writes is sharding, the next lesson.)
  • Async: fast but may lose recent writes and serve stale reads. Sync: safer but slower.
  • More replicas means more cost and more things to monitor.

Do it yourself (about 20 minutes, on paper)

A. Draw the replication setup

  1. Open excalidraw.com and press R. Draw one box labelled Leader (writes) on top and two boxes below it labelled Follower 1 (reads) and Follower 2 (reads).
  2. Draw a box on the left labelled App. Press A and draw an arrow from App to the Leader. Label it write.
  3. Draw arrows from the Leader to each follower. Label them copy changes. Make them dashed: select the arrow (V, click it) and choose the dashed Stroke style in the left panel.
  4. Draw arrows from each follower back to the App, labelled read.
  5. Add a small box Monitor with an arrow to the Leader labelled heartbeat, and a note: if no heartbeat, promote a follower.
  6. Save as m2-9 replication.excalidraw: ☰, Save to…, Save to disk.

B. A lag thought experiment

  1. Draw a timeline on paper, from 0 to 300 milliseconds. Mark three lanes: App, Leader, Follower.
  2. At 0 ms, the user posts "Hello". Draw an arrow App to Leader. The leader saves it at 10 ms and replies "done".
  3. The leader sends the change to the follower. Say the copy takes 200 ms to arrive and apply, so the follower has "Hello" only at 210 ms.
  4. At 50 ms the page reloads and reads the post list from the follower. What does the user see? (No "Hello": it has not arrived yet.) Write the symptom: "I posted but I cannot see my post."
  5. Now read the same list from the leader instead. What does the user see? (Hello.) What is the cost? (The leader carries read load again.)
  6. Write down two fixes in your own words. Suggested: read from the leader for 10 seconds after a write; or show the new post immediately on screen from the client's memory.
  7. Extra: the leader crashes at 100 ms with asynchronous replication, before sending "Hello". A follower is promoted. Is "Hello" lost? (Yes.) With a synchronous follower it would have been safe. Write which you would choose for a bank, and which for a "likes" counter.

Quick quiz

In leader-follower replication, which node takes writes and which take reads?

All writes go to the leader. Reads can go to any follower (and the leader).

What is the trade-off between synchronous and asynchronous replication?

Synchronous waits for the follower, so it is safer (no loss of confirmed writes) but slower. Asynchronous is faster but followers lag and recent writes can be lost if the leader dies.

What is replication lag and what bug does it cause?

Followers can be a little behind the leader. A user may write, then read from a lagging follower and not see their own change.

What is read-your-writes consistency and how can you provide it?

After a user writes, that user always sees the write. Read their data from the leader for a short time, or from a follower known to have caught up, or show it immediately in the UI.

Do read replicas help a write-heavy workload?

No. They only spread reads; every write still goes to the single leader. For writes you need sharding or a different design.

You run a social app that is 95% reads. Which replication and why?

Leader plus several asynchronous followers for the reads, with read-your-writes handling. Reads are the bottleneck, and slightly stale data in a feed is acceptable.

Say it in an interview

"I would use a leader with asynchronous read replicas: writes go to the leader and the read-heavy traffic is spread over the followers."
"To avoid users not seeing their own writes, I would read from the leader right after a write, and I would plan automatic failover with a promoted follower."

Common follow-up question: What happens when the leader fails?

A monitor detects it, picks the most up-to-date follower and promotes it, then repoints the app. With async replication a few recent writes may be lost, and the old leader must be fenced off when it returns to avoid two leaders. I would also test failover regularly.
