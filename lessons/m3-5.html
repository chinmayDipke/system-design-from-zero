One big kitchen or many small stalls

A family restaurant has one big kitchen. One team makes everything: dosa, biryani, sweets. It is easy: everything is in one place, everyone talks face to face. But as the menu grows, the kitchen gets crowded. If the sweet counter is on fire, the whole kitchen shuts.

Another option is a food court: separate stalls for dosa, biryani and sweets. Each stall has its own cook and can open late or hire more staff by itself. But now a thali order needs a runner to fetch from three stalls, the bill must be added up across stalls, and if one runner is slow the customer waits.

The big kitchen is a monolith. The food court is microservices. Neither is "better". Each has a price.

Three ways to organise one product

Monolith

The whole app is one program, deployed as one unit, usually with one database. Users, orders, payments, notifications: all one codebase. Function calls between parts are fast and reliable (they stay inside one process), and a database transaction can cover everything at once (ACID).

Modular monolith

Still one deployable program, but the code is split into clear modules with strict boundaries: each module owns its tables and exposes a small interface, and other modules may not reach into its insides. It gives most of the organisation benefit of microservices without the network.

Microservices

The app is split into many small services, each doing one business job, owning its own data, and deployed on its own. They talk over the network: HTTP/REST or gRPC (APIs) or by sending events through a queue (message queues).

The real costs of microservices

  • Network calls fail and are slow. A call that was a function is now a request with timeouts, retries and partial failure (retries, circuit breakers).
  • No easy transactions. Placing an order may touch orders, payments and stock in three databases. You cannot just BEGIN ... COMMIT across them.
  • Operations multiply. Many deploy pipelines, many logs, monitoring, versioned APIs between services.
  • Debugging is harder. One user click spans many services; you need tracing (observability).
  • Data is spread out. A report joining users and orders now needs service calls or copied data.

When to split

  • Many teams stepping on each other in one codebase (a rough rule of thumb: dozens of engineers, not five).
  • One part needs very different scaling (video processing versus a settings page) or a different technology.
  • Parts need independent release speed or isolation so a failure stays contained.

Do not split because it sounds modern, or with a team of five. Many well-known companies ran a monolith for years.

Strong advice: start with a modular monolith. Keep clean boundaries now, so that when a real reason appears, one module can be lifted out into a service.

Service discovery

In a food court of changing stalls, how does the runner know where the dosa stall is today? Service instances start, stop and move, so their addresses change. Service discovery keeps a live directory: services register themselves, and callers ask the directory (or a load balancer, load balancers) by name, like payments, instead of a fixed IP. Platforms like Kubernetes and cloud load balancers provide this for you.

The saga pattern, simply

A saga is a way to do one business action across several services without one big transaction. It is a chain of small local transactions. If a step fails, earlier steps are undone by compensating actions.

Example: place an order. (1) Order service saves the order as "pending". (2) Payment service charges the card. (3) Stock service reserves items. If stock fails, the saga runs the undo: refund the payment and mark the order "cancelled". Services coordinate either by events passed along (choreography) or by one coordinator telling each what to do (orchestration). Each step must be idempotent (idempotency).

Trade-offs in one line

Microservices trade simple code and easy transactions for team independence and targeted scaling. Only pay that price when the second matters.

You get an imaginary food-delivery app (think of a Swiggy-style app) built as one monolith. You will cut it into services, one decision at a time.

  2. Inside it draw 7 small boxes: Users and login, Restaurants and menus, Search, Cart and orders, Payments, Delivery tracking, Notifications.
  3. Under the big box draw a cylinder or rectangle labelled One Postgres database, with one arrow from the big box to it.

  1. Do not split everything. Pick the parts with a real reason:

Quick quiz

What is a modular monolith?

One deployable program whose code is divided into modules with strict boundaries and their own data, so it is organised like services without network calls.

Name three real costs of microservices.

Network calls that fail and are slower than function calls; no easy transactions across services; more operations work and harder debugging.

When would you use an asynchronous event instead of a REST call?

When the caller does not need the result now, like sending a confirmation email, or when you want to decouple services so one being slow does not block the other.

What does a saga do when step 3 of 4 fails?

It runs compensating actions for the completed steps (for example refund the payment), since there is no single transaction to roll back.

A startup with 4 engineers wants microservices from day one. What do you advise?

Start with a modular monolith. With a small team the network, operations and debugging costs outweigh the benefits. Keep module boundaries clean so a service can be extracted later if a real need appears.

Say it in an interview

"I would start with a modular monolith and extract a service only when there is a clear reason: team size, a very different scaling need, or isolation of failures."
"Between services I use synchronous calls when the user needs an answer now, and events for work that can happen later, with sagas for multi-step business actions."

Common follow-up question: How do you keep data consistent across services?

Each service owns its data. For a business action across services I use a saga with compensating steps, make each step idempotent, and publish events reliably using the outbox pattern. I accept eventual consistency between services.
