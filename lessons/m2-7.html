The water bottle on your desk

When you are thirsty you could walk to the water cooler at the end of the corridor every time. Or you can keep a bottle on your desk. Grabbing from the bottle takes one second; the cooler takes two minutes. The bottle holds less, and it may go stale or run out, but most sips come from it.

A cache is a bottle on the desk: a small, fast place that keeps copies of things you recently needed, so you do not repeat a slow trip. Computers have many bottles at many distances.

The hard part: if the cooler's water is changed (the original changes), your bottle may still hold the old water. Knowing when to throw yours away is the famous tricky bit.

Where caches live, and how they behave

Remember the latency numbers from Module 1: memory is thousands of times faster than a disk or a network trip. Caching trades a bit of memory and some freshness for a lot of speed and a lot less load on the database.

Where caches live

LayerWhereHolds
Browser cacheOn the user's deviceImages, CSS, JS, some API responses
CDNServers near the userStatic files, sometimes whole pages
App memoryInside one app server's processSmall hot data; lost on restart, not shared
Redis / MemcachedA separate shared cache serverQuery results, sessions, counters
Database buffer cacheInside the databaseRecently used disk pages (automatic)

A request walks outward from the user. At each layer, a hit (the copy is there) ends the trip. A miss goes on to the next layer, and the answer is saved on the way back.

Caching strategies

StrategyHow it worksProsCons
Cache-aside (lazy loading)App checks the cache; on a miss it reads the DB, then stores the result in the cacheSimple; only caches what is used; cache failure is survivableFirst request is slow; data can go stale
Read-throughThe cache itself loads from the DB on a miss; the app only talks to the cacheApp code is simplerNeeds a cache layer that supports it; first request slow
Write-throughWrites go to cache and DB together, and succeed when both are doneCache always freshEvery write is slower; may cache data never read
Write-behind (write-back)Write to cache first, save to the DB later in the backgroundVery fast writesIf the cache dies before saving, data is lost

Cache-aside is the one to know best. It is what most apps do.

TTL: a freshness timer

TTL (time to live) is how long a cached item lives before it is thrown away, such as 60 seconds. It is the simplest protection against stale data: even if you forget to clean up, the copy expires by itself. Short TTL = fresher but more misses. Long TTL = faster but staler.

Eviction: what to throw out when the cache is full

PolicyRemovesGood for
LRU (least recently used)The item not touched for the longest timeMost general uses
LFU (least frequently used)The item used the fewest timesStable popular items
FIFO (first in, first out)The oldest item addedVery simple cases

Cache invalidation

There is an old joke that the two hard problems in computer science are cache invalidation and naming things. Invalidation means removing or updating a cached copy when the original changes. Common approaches: let the TTL expire; delete the cache key whenever you update the database row; or put a version in the key (user:7:v3). No approach is perfect; each one trades freshness against effort.

Cache stampede (thundering herd)

A very popular item expires. In that instant, 5,000 requests all miss together and all hit the database to rebuild it. The database buckles. Fixes:

  • Locking: only one request rebuilds the value while the others wait or use the old copy.
  • Jitter: add a random few seconds to each TTL so items do not all expire together.
  • Refresh early: refresh a hot item in the background before it expires.

Hit ratio

Hit ratio = hits divided by total requests. At 95% only 1 in 20 requests reaches the database. It is the number that says whether your cache is worth it. A low ratio means you cache the wrong things, the TTL is too short, or the cache is too small.

Trade-offs

  • Caching gives speed and protects the database, but you accept stale data, extra complexity and one more component to run.
  • Do not cache data that changes constantly or must always be exact (an account balance), or data that is rarely read twice.
  • Design for the cache being empty or down: the system should still work, just slower.

Interviewers love "what do you cache, with what key, for how long, and how does it get invalidated?" Have a one-line answer for each.

Do it yourself (about 25 minutes)

A. See cache headers on a real page

  1. Open Chrome, go to https://www.wikipedia.org. Press F12 and click the Network tab.
  2. Make sure the Disable cache checkbox (near the top of the Network panel) is not ticked.
  3. Reload with Ctrl + R. Click any row of type png, svg, css or js (use the filter buttons Img, CSS or JS to find one).
  4. Open the Headers tab. Under Response Headers find cache-control. It may say something like max-age=... (seconds the copy stays fresh) or no-cache / no-store (do not reuse blindly or do not keep). Also look for etag and last-modified, which let the browser ask "has it changed?" cheaply.
  5. Write in your notes: the file, its cache-control value, and how many days or hours max-age means.

B. Catch the browser cache in the act

  1. Keep the Network panel open. Reload the page again with F5 (a normal reload).
  2. Look at the Size column. Some rows now say (memory cache) or (disk cache) instead of a size in kB. That means the browser did not go to the network: it used its own saved copy. The Time column shows about 0 ms for those rows. (The labels can differ a little by Chrome version.)
  3. Count how many rows came from cache and how many from the network. Write the two numbers down.
  4. Now tick the Disable cache checkbox at the top of the Network panel. (DevTools must stay open for it to work.)
  5. Reload with F5 again. The Size column now shows real sizes for almost everything, and the total transferred at the bottom of the panel is bigger. Count again: cached rows should be (almost) zero.
  6. Untick Disable cache, reload twice, and see the cache come back.
  7. Look at the status bar at the bottom of the Network panel: it shows "x requests, y kB transferred". Compare the transferred size with cache on and off. This is the speed and bandwidth that caching saves.

Developers tick Disable cache while testing so they always see their newest code. If a page looks "stuck on the old version", a stale cache is a classic reason: try Ctrl + Shift + R (hard reload).

C. Design a cache on paper

  1. Scenario: a product page shows details for 100,000 products. 90% of views go to 1,000 popular products. The database is slow under load.
  2. Write answers to: Which layer would you add first? (Redis cache-aside, plus CDN for images.) What is the key? (product:{id}.) What TTL? (Maybe 5 minutes; prices may need less.) How do you invalidate when the price changes? (Delete the key on update.) What if one hot product expires under load? (Use a lock or jittered TTL against a stampede.)

Quick quiz

Explain cache-aside in three steps.

The app checks the cache. On a hit it returns the value. On a miss it reads the database, stores the result in the cache with a TTL, and returns it.

What risk does write-behind have?

Data is only in the cache until the background save happens. If the cache crashes first, those writes are lost.

What is a cache stampede and how do you reduce it?

A hot item expires and many requests rebuild it at once, hammering the database. Use a lock so only one rebuilds, add random jitter to TTLs, or refresh before expiry.

Your hit ratio is 30%. What could be wrong?

Maybe the TTL is too short, the cache is too small and evicts items too soon, or you cache items that are rarely requested twice.

Would you cache a user's bank balance for 10 minutes? Why or why not?

No. It must be accurate, and stale values could mislead or allow overspending. Cache data that tolerates staleness, like product descriptions.

Say it in an interview

"I would use cache-aside with Redis: check the cache, on a miss read the database and store it with a TTL. I would invalidate by deleting the key on writes."
"To avoid a stampede on hot keys I would add jitter to the TTL and use a lock so only one request rebuilds the value."

Common follow-up question: How do you keep the cache consistent with the database?

Perfect consistency is costly. Usually I accept a short staleness bounded by a TTL, and on writes I update the database first and then delete the cache key so the next read reloads fresh data. For data that must be exact, I skip the cache or read from the primary.
