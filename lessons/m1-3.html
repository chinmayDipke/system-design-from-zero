The speed-post envelope

When you send a speed-post, the envelope has a fixed format: To, From, what is inside, and a stamp. Because the format is fixed, every post office in India can handle it without asking questions.

HTTP is that fixed format for the web. A request says what you want and to whom, and the reply starts with a number that says how it went. "200" means fine. "404" means we could not find it.

HTTPS is the same letter in a locked, sealed envelope, so the postman cannot read or change it.

HTTP in plain words

A request has three parts: a method and address (GET /products), headers (extra details, like a label on the envelope) and an optional body (the actual content, e.g. a form's data as JSON). A response has a status code, headers and a body.

Methods: what do you want to do?

MethodMeaningExample
GETRead something. Changes nothing.Open a product page
POSTCreate something newPlace an order
PUTReplace a thing completelyOverwrite a whole profile
PATCHChange only some fieldsUpdate just the phone number
DELETERemove somethingDelete a comment

Headers and body

Headers are name: value pairs. A few you will see a lot: Content-Type (what kind of body, e.g. application/json), Authorization (who you are, usually a token), Cache-Control (how long it may be saved), Set-Cookie and Cookie. A GET normally has no body; POST, PUT and PATCH usually do.

HTTPS and TLS

Plain HTTP travels as readable text. Anyone on the path (café Wi-Fi, a router) could read or change it. HTTPS is HTTP wrapped in TLS, which does two jobs: it encrypts the traffic and it proves the server's identity. The proof is a certificate, a digital ID card issued by a trusted authority, saying "this really is example.com". The padlock in the browser means the certificate checked out and the connection is encrypted. It does not mean the site itself is honest.

HTTP/1.1, HTTP/2, HTTP/3

HTTP/1.1 is simple and text-based; it handles essentially one request at a time per connection, so browsers open several connections. HTTP/2 sends many requests together over one connection, which is faster for pages with many files. HTTP/3 runs over a newer transport called QUIC (instead of TCP), which recovers better on shaky mobile networks. Your app code stays the same; the server and browser negotiate the version.

Cookies

A cookie is a small piece of text the server asks the browser to keep (Set-Cookie) and the browser then sends back with every request to that site (Cookie). That is how a stateless protocol "remembers" your login.

Trade-offs

  • Right method and status code make an API predictable for other developers and for caches. The cost is discipline: a lazy "always 200" API is easy to write and hard to debug.
  • HTTPS everywhere costs a tiny bit of CPU and certificate upkeep. Today there is no good reason to skip it; most hosts give certificates free.
  • Cookies vs tokens in headers: cookies are sent automatically (convenient, but need care against cross-site misuse); a token in the Authorization header is sent only by your code.

Do it yourself (about 25 minutes)

A. Look at a response with curl

  1. Press the ⊞ Win key, type cmd, press Enter. Command Prompt opens. (To paste: Ctrl + V, or right-click in the window.)
  2. Run this, then press Enter. The -I asks only for the headers. 
    curl.exe -I https://www.google.com
  3. The first line looks like HTTP/2 200 (it may be HTTP/1.1 or a 301 or 302 if Google redirects you). Below it you see headers such as content-type and date. Spot the status code and a few headers.

Type curl.exe, not curl. In PowerShell, plain curl is an alias for a different command and behaves differently. In Command Prompt either works, but curl.exe is safe in both.

B. Make a 404 on purpose

  1. Run: 
    curl.exe -i https://httpbin.org/status/404
  2. The lowercase -i shows headers plus the body. You should see 404 in the first line. The body is empty.
  3. Try other codes by changing the number: /status/200, /status/500, /status/429. httpbin.org is a free practice site that answers with whatever code you ask for. If it is slow or down, try again later.

C. See status codes in Chrome

  1. Open Chrome, go to any site (for example https://github.com), press F12, click the Network tab, then reload with Ctrl + R.
  2. Find the column Status. If it is hidden, right-click any column title and tick Status. Mostly you will see 200.
  3. Reload again with a normal Ctrl + R. You may now see some 304 rows, or sizes shown as "(disk cache)": your browser reused saved copies. Which you get depends on the site.
  4. Click one request, then the Headers tab. Find Request Method, Status Code, and under Response Headers look for content-type. Check whether the request has a cookie header too.
  5. To see padlock details: click the padlock (or settings icon) left of the address bar, then Connection is secure → Certificate is valid. A window shows who issued the certificate. Labels may differ by Chrome version.

Quick quiz

What is the difference between PUT and PATCH?

PUT replaces the whole thing; PATCH changes only some fields.

401 or 403: the user is logged in but is not an admin, trying an admin page. Which one?

403 Forbidden. The server knows who they are but they are not allowed. 401 is for "not logged in".

What does a 502 or 504 tell you about where to look?

There is a proxy or gateway in front of your app, and the app behind it sent a bad answer (502) or took too long (504). Look at the app.

What do the padlock and a certificate actually guarantee?

The traffic is encrypted and the server is really the owner of that domain. It does not prove the website is trustworthy.

Your API returns 200 with {"error": "not found"} for missing items. Would you change it, and why?

Yes, return 404. Caches, monitoring tools, clients and other developers all rely on status codes; a fake 200 hides failures.

Say it in an interview

"GET reads, POST creates, PUT replaces, PATCH updates part of a resource and DELETE removes it. I return 2xx for success, 4xx for client errors and 5xx for server errors."
"HTTPS is HTTP over TLS: it encrypts traffic and uses a certificate to prove the server's identity."

Common follow-up question: What is the difference between 401 and 403?

401 means the request has no valid identity, so the user must log in or send a valid token. 403 means we know who the user is, but they do not have permission for this action.
