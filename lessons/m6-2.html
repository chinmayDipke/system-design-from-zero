The wedding caterer who does everything

Imagine one caterer who cooks, serves, washes the dishes, does the decoration and collects the money. On the wedding day, if he falls ill, everything stops. If the family wants a new sweet, he has to rewrite his whole routine.

A smart wedding has many small teams: cooks, servers, decorators. Each has one job. To add a new sweet stall you hire a new team and nobody else changes. They agree on simple rules for handing over plates, so any server can work with any cook.

SOLID is five rules that make code behave like the smart wedding: small teams, one job each, easy to add new ones.

The five rules, each with a before and after

SOLID is a checklist of five habits. They are guides, not laws. They help most when code keeps changing. The goal is simple: when a requirement changes, you edit as little code as possible. Below, every rule has a "before" (the problem) and an "after" (the fix), and every block compiles in TypeScript strict mode.

S: Single Responsibility. One class, one reason to change.

If the print layout changes, the database changes and the tax rule changes, and all three force you to edit the same class, that class has three jobs.

// BEFORE: one class, three reasons to change
class InvoiceBefore {
  constructor(public items: number[]) {}
  total(): number {
    return this.items.reduce((a, b) => a + b, 0);
  }
  print(): string {
    return `Total: Rs ${this.total()}`; // changes when the layout changes
  }
  saveToDb(): void {
    console.log("INSERT INTO invoices ..."); // changes when the database changes
  }
}
console.log(new InvoiceBefore([100, 250]).print());

Split it. Now each change touches only one class:

// AFTER: one job per class
class Invoice {
  constructor(public items: number[]) {}
  total(): number {
    return this.items.reduce((a, b) => a + b, 0);
  }
}
class InvoicePrinter {
  print(inv: Invoice): string {
    return `Total: Rs ${inv.total()}`;
  }
}
class InvoiceRepository {
  save(inv: Invoice): void {
    console.log(`INSERT INTO invoices ... (${inv.items.length} items)`);
  }
}

const inv = new Invoice([100, 250]);
console.log(new InvoicePrinter().print(inv));
new InvoiceRepository().save(inv);
Total: Rs 350
INSERT INTO invoices ... (2 items)

O: Open/Closed. Open for new behaviour, closed for editing old code.

Before: every new customer type means opening the function and adding another if. Each edit can break the old cases.

// BEFORE: every new customer type means editing this function
function discountBefore(type: string, amount: number): number {
  if (type === "regular") return amount;
  if (type === "festival") return amount * 0.9;
  if (type === "student") return amount * 0.8;
  throw new Error("Unknown type");
}
console.log(discountBefore("festival", 1000));

After: each rule is its own class behind one interface. A new rule is a new class, and checkout never changes.

// AFTER: add a new class, change nothing that exists
interface DiscountRule {
  apply(amount: number): number;
}
class NoDiscount implements DiscountRule {
  apply(amount: number): number { return amount; }
}
class FestivalDiscount implements DiscountRule {
  apply(amount: number): number { return amount * 0.9; }
}
class StudentDiscount implements DiscountRule {
  apply(amount: number): number { return amount * 0.8; }
}

function checkout(amount: number, rule: DiscountRule): number {
  return rule.apply(amount);
}
console.log(checkout(1000, new FestivalDiscount()));
console.log(checkout(1000, new StudentDiscount()));
900
800

L: Liskov Substitution. A child must work wherever its parent works.

Before: Penguin extends Bird but cannot fly. Code that trusts any Bird to fly crashes. Real output:

// BEFORE: a child that breaks the parent's promise
class BirdBefore {
  fly(): string { return "flap flap"; }
}
class PenguinBefore extends BirdBefore {
  override fly(): string {
    throw new Error("Penguins cannot fly");
  }
}
function launch(b: BirdBefore): string {
  return b.fly();
}
console.log(launch(new BirdBefore()));
try {
  console.log(launch(new PenguinBefore()));
} catch (e) {
  console.log("Crash:", (e as Error).message);
}
flap flap
Crash: Penguins cannot fly

After: only birds that can fly promise fly(). The compiler now stops you from sending a penguin to launch.

// AFTER: only birds that can fly promise to fly
class Bird {
  walk(): string { return "step step"; }
}
class FlyingBird extends Bird {
  fly(): string { return "flap flap"; }
}
class Penguin extends Bird {}

function launch(b: FlyingBird): string {
  return b.fly();
}
console.log(launch(new FlyingBird()));
console.log(new Penguin().walk());
// launch(new Penguin());   // compile error: caught before running
flap flap
step step

I: Interface Segregation. Many small interfaces beat one fat one.

Before: a robot is forced to implement eat() and can only throw an error.

// BEFORE: a fat interface forces useless methods
interface WorkerBefore {
  work(): string;
  eat(): string;
}
class RobotBefore implements WorkerBefore {
  work(): string { return "welding"; }
  eat(): string {
    throw new Error("Robots do not eat"); // forced to write this
  }
}
console.log(new RobotBefore().work());

After: split the interface. Each class picks only what it really does.

// AFTER: small interfaces, take only what you need
interface Workable { work(): string; }
interface Eatable { eat(): string; }

class Robot implements Workable {
  work(): string { return "welding"; }
}
class Human implements Workable, Eatable {
  work(): string { return "typing"; }
  eat(): string { return "dal chawal"; }
}

function runShift(w: Workable): string {
  return w.work();
}
console.log(runShift(new Robot()), runShift(new Human()));
welding typing

D: Dependency Inversion. Depend on an interface, not on a concrete tool.

Before: OrderService builds its own mailer. You cannot swap it, and you cannot test it without sending a real email.

// BEFORE: the high-level class builds its own low-level tool
class SmtpMailer {
  send(to: string, body: string): void {
    console.log(`SMTP -> ${to}: ${body}`);
  }
}
class OrderServiceBefore {
  private mailer = new SmtpMailer(); // glued in: cannot swap, cannot test
  place(email: string): void {
    this.mailer.send(email, "Order placed");
  }
}
new OrderServiceBefore().place("a@x.in");

After: the service asks for "something that can send" and receives it from outside. This is called dependency injection. In a test you pass a fake.

// AFTER: depend on an interface, receive the tool from outside
interface Mailer {
  send(to: string, body: string): void;
}
class SmtpMailer implements Mailer {
  send(to: string, body: string): void {
    console.log(`SMTP -> ${to}: ${body}`);
  }
}
class FakeMailer implements Mailer {
  sent: string[] = [];
  send(to: string, body: string): void {
    this.sent.push(`${to}|${body}`);
  }
}

class OrderService {
  constructor(private mailer: Mailer) {}
  place(email: string): void {
    this.mailer.send(email, "Order placed");
  }
}
new OrderService(new SmtpMailer()).place("a@x.in");
const fake = new FakeMailer();
new OrderService(fake).place("test@x.in");
console.log(fake.sent);
SMTP -> a@x.in: Order placed
[ 'test@x.in|Order placed' ]

When to use SOLID, and when not to

Use it whenBe careful when
The code changes often and several people touch itIt is a small script or a one-week prototype: extra interfaces are just noise
You see a growing if/else chain on a "type" field (O)You create an interface with only one implementation and no reason to have a second
You need tests without real email, payments or a database (D)You split classes so finely that you cannot follow the flow any more

Rule of thumb: wait until something has changed twice for the same reason, then apply the rule. Do not design for changes that may never come.

Run it yourself (about 25 minutes)

A. Set up

  1. Open typescriptlang.org/play in Chrome. Click the left editor, press Ctrl + A then Delete.
  2. Run any code with Ctrl + Enter (or the Run button) and read the result in the Logs tab on the right.

B. Open/Closed: add a rule without editing old code

  1. Paste the "after" block from the O section. Run it. You should see 900 and 800.
  2. At the bottom of the interface and classes, add: class WeddingDiscount implements DiscountRule { apply(amount: number): number { return amount * 0.5; } }
  3. Add console.log(checkout(1000, new WeddingDiscount())); at the end and run. You should see 500. You did not touch checkout. That is Open/Closed.

C. Liskov: let the compiler catch the bug

  1. Clear the editor and paste the "after" block from the L section.
  2. At the very end, delete the // in front of launch(new Penguin());. A red wavy line appears. Hover: it says a Penguin is not assignable to a FlyingBird. The bug is found before running.

D. Dependency Inversion: test without sending anything

  1. Paste the "after" block from the D section and run it. You see one SMTP line, then the array printed by the fake mailer.
  2. Explain out loud why the second call needed no real email server.

E. Spot the violation (paper exercise)

  1. Think of a UserController that validates input, hashes the password, writes to Postgres and sends a welcome email.
  2. Write down which SOLID letter each of those four jobs breaks (S, and D for the email and database).
  3. Sketch the split: UserValidator, PasswordHasher, UserRepository, Mailer.

Quick quiz

What does the S in SOLID stand for, and what is its test?

Single Responsibility. Ask: "how many different reasons could make me edit this class?" More than one means it is doing too much.

How does Open/Closed help when a new discount type arrives?

You add a new class that implements the discount interface. The existing checkout code is not edited, so old cases cannot break.

What is wrong with Penguin extends Bird, where Bird has fly()?

It breaks Liskov Substitution. Code that works with any Bird crashes for a Penguin. Fix it by moving fly() into a FlyingBird type.

What is dependency injection, and why does it help testing?

The class receives its helpers (through the constructor) instead of creating them. In tests you pass a fake, so no real email, payment or database is used.

Your team has a 100-line script that runs once a month. Do you split it into interfaces and classes? Why or why not?

Probably not. SOLID pays off when code changes often. For a small, stable script, extra layers cost more than they save. Wait until it changes twice for the same reason.

Say it in the interview

I give each class one reason to change, so a new requirement touches one place.
I depend on interfaces and inject implementations, so I can swap a payment provider or use a fake in tests.
When I see a growing if/else on a type, I replace it with one interface and one class per case, which is Open/Closed.

Common follow-up question: "Can you over-apply SOLID?"

Yes. If you add an interface for everything, you get many tiny classes and indirection with no benefit. I apply it where I expect change: payment methods, notification channels, pricing rules. For simple, stable code I keep it plain.
