A map where meaning has an address

Imagine a huge shopping mall. Shops that sell similar things stand close together: all the sweet shops in one corner, all the phone shops on the second floor, all the clothes shops on the third. If you want "something to eat", you do not read every signboard. You walk to the food corner and look at the nearest shops.

An embedding is the address of a piece of text on such a map. A model reads a sentence and gives back a list of numbers, like map coordinates. The clever part: sentences with similar meaning get nearby addresses, even if they share no words. "How do I get my money back?" lands close to "Refund policy".

A vector database is a database that is good at one question: "which addresses are nearest to this one?"

Embeddings, similarity and vector indexes

What an embedding really is

An embedding is a fixed-length list of decimal numbers (a vector) produced by an embedding model. Real models give hundreds or thousands of numbers per text, for example 384 or 1536. The length is called the dimension. You cannot read the numbers, because the dimensions are not "food" or "travel": the model invented them while learning. Two rules matter:

  • Same model for everything. Documents and queries must be embedded by the same model. Vectors from two different models are not comparable.
  • Fixed dimension. A vector(384) column only accepts 384 numbers.

In this lesson you will type tiny 3-number vectors by hand so you can see the idea. In the next lesson a real model makes 384 numbers for you.

Measuring "nearby"

There are three common ways to measure how close two vectors are. pgvector gives each an operator:

OperatorMeasuresSmaller meansUse when
<=>Cosine distance (angle between the arrows)More similarSafe default for text
<->Euclidean distance (straight-line gap)More similarWhen size of the vector matters
<#>Negative inner productMore similarVectors already normalised (length 1); fastest

Cosine similarity looks only at the direction the arrow points, not its length. Same direction = 1, unrelated = about 0, opposite = -1. pgvector returns cosine distance, which is 1 - similarity, so smaller is better and ORDER BY embedding <=> query puts the best match first. Beginners often get this backwards.

Exact search vs approximate search

Without an index, the database compares your query to every row. That is exact (perfect recall) but its cost grows with the number of rows. For a few thousand rows, that is fine. For millions, too slow. So vector indexes do approximate nearest neighbour (ANN) search: they find results that are very probably the true nearest ones, much faster. You trade a little accuracy (recall) for speed.

IVFFlatHNSW
IdeaSplit the space into clusters ("lists"). Search only the nearest few clusters.A layered graph of "friends". Hop from friend to nearer friend until you arrive.
BuildFaster and smaller, but should be built after data is loaded, because it learns the clusters from your rowsSlower and bigger, but can be created on an empty table
Query speed and recallGoodUsually better for read-heavy, low-latency search
Typical pickVery large data, memory is tightGood default for most apps

Supabase's own guide also recommends HNSW for read-heavy workloads where recall matters. Either way, tuning details change between versions, so read the pgvector README when you tune.

An index only helps if the query's ORDER BY uses the same distance operator the index was built for. An index made with vector_cosine_ops serves <=>, not <->. On a tiny table Postgres will ignore any index and scan everything, and that is the correct choice.

pgvector vs a dedicated vector database

pgvector is a Postgres extension. Your vectors live in a normal table beside your other columns, so you get SQL, joins, transactions, backups and row-level security for free. A dedicated vector database (Pinecone, Qdrant, Weaviate, Milvus and others) is built only for vector search.

pgvector (in your Postgres)Dedicated vector DB
OperationsOne database to run. Nothing new.One more system to pay for, secure and keep in sync
FilteringNormal SQL WHERE plus JOIN (for example "only this tenant's documents")Metadata filters, usually simpler but less flexible than SQL
ConsistencyThe vector and its row commit together (ACID)You must keep it in sync with your main DB
ScaleGreat up to a large size; very large or very high query rates may strain one PostgresBuilt to scale out for huge collections

When to use pgvector: you already use Postgres or Supabase, data is thousands to a few million chunks, and you need per-user filtering. When to look at a dedicated one: very large collections, very high query rates, or a team that wants managed vector features. Start simple, and move only when you can measure a problem.

Vectors are a good fit for "find things that mean the same". They are a poor fit for exact lookups (an order number, an email), where a normal index or keyword search is faster and exact. Many real systems combine both, called hybrid search.

Do it yourself (about 25 minutes)

You will use the Supabase SQL Editor. Do this in a throwaway table and delete it at the end. The SQL was run on a real Postgres with pgvector (PGlite) and the outputs below are real. Your row order for ties, or the exact decimals, may differ in the last digit.

A. Turn on vectors and create a tiny table

  1. Open supabase.com/dashboard, click your project, then click SQL Editor in the left bar (it may be shown as a ">_" icon). Click New query (it may say + or New snippet).
  2. Click Copy on the block below, click in the editor, press Ctrl + V, then click Run (or press Ctrl + Enter). 
    create extension if not exists vector with schema extensions;

create table items (
  id bigint generated always as identity primary key,
  name text not null,
  embedding extensions.vector(3)
);

insert into items (name, embedding) values
  ('samosa',        '[0.9, 0.1, 0.0]'),
  ('biryani',       '[0.8, 0.2, 0.1]'),
  ('train ticket',  '[0.1, 0.9, 0.1]'),
  ('flight to Goa', '[0.2, 0.8, 0.2]'),
  ('laptop',        '[0.0, 0.1, 0.9]'),
  ('smartphone',    '[0.1, 0.2, 0.8]');
  3. You should see "Success. No rows returned". If it says a table or extension already exists, that is fine, or change items to items2 everywhere. The three numbers mean "how food-like, travel-like, tech-like", which we made up. Real models do not label their dimensions.
  4. Optional check: Supabase also shows vector in Database then Extensions. Search "vector"; it should be enabled.

B. Find the nearest meaning

Our query vector [0.85, 0.15, 0.05] stands for "something to eat".

  1. Clear the editor (Ctrl + A, Delete), paste this, and click Run: 
    select name, embedding <=> '[0.85, 0.15, 0.05]' as distance
from items
order by embedding <=> '[0.85, 0.15, 0.05]'
limit 3;
  2. You should see these rows (decimals may differ in the last digits): 
    name            distance
samosa          0.0037184699510960373
biryani         0.004420605342517536
flight to Goa   0.5910695993991616
    Smaller distance = closer. The two food items are very close. The third place already belongs to a different topic, which shows that top-k always returns something even when nothing is really close.
  3. Turn distance into the friendlier similarity (1 minus distance): 
    select name,
       round((1 - (embedding <=> '[0.85, 0.15, 0.05]'))::numeric, 4) as similarity
from items
order by embedding <=> '[0.85, 0.15, 0.05]'
limit 3;
    Expected: samosa 0.9963, biryani 0.9956, flight to Goa 0.4089.
  4. Compare all three operators on the same query: 
    select name,
  round((embedding <-> '[0.85, 0.15, 0.05]')::numeric, 4) as euclidean,
  round((embedding <=> '[0.85, 0.15, 0.05]')::numeric, 4) as cosine,
  round((embedding <#> '[0.85, 0.15, 0.05]')::numeric, 4) as neg_inner_product
from items
order by 3
limit 6;
    Expected: 
    name            euclidean  cosine  neg_inner_product
samosa          0.0866     0.0037  -0.7800
biryani         0.0866     0.0044  -0.7150
flight to Goa   0.9314     0.5911  -0.3000
train ticket    1.0618     0.7143  -0.2250
smartphone      1.0618     0.7842  -0.1550
laptop          1.2031     0.9234  -0.0600
    Notice: samosa and biryani tie on straight-line distance but cosine separates them, because cosine compares direction. Row order for exact ties may differ on your screen.

C. Add an HNSW index and break a rule on purpose

  1. Run: 
    create index on items using hnsw (embedding vector_cosine_ops);
    It should succeed with no rows returned. (On Supabase the extensions schema is normally on the search path, so the bare operator class name works. If you get "operator class does not exist", write extensions.vector_cosine_ops.)
  2. Search for "travel" ([0.1, 0.85, 0.1]): 
    select name from items
order by embedding <=> '[0.1, 0.85, 0.1]'
limit 2;
    Expected: train ticket then flight to Goa.
  3. With only 6 rows Postgres would normally ignore the index. To see it used, run these two lines together: 
    set enable_seqscan = off;
explain select name from items order by embedding <=> '[0.1, 0.85, 0.1]' limit 2;
    The plan should include a line like Index Scan using items_embedding_idx on items. The cost numbers will differ. If the editor shows only the last result or complains, ignore this step. It is a nice-to-have.
  4. Break the dimension rule on purpose: 
    insert into items (name, embedding) values ('bad', '[1, 2]');
    You should get an error like expected 3 dimensions, not 2. That is why one embedding model per column matters.

D. Clean up

  1. Run drop table items;. Leave the extension on. You need it in the next lesson.

Quick quiz

In one sentence, what is an embedding?

A fixed-length list of numbers produced by a model, placed so that texts with similar meaning get nearby points.

pgvector's <=> returns 0.01 for one row and 0.60 for another. Which is the better match?

The 0.01 row. <=> is a distance (1 minus cosine similarity), so smaller means more similar.

Why can you not mix vectors from two different embedding models in one column?

Each model has its own coordinate system and often a different length. Distances between vectors from different models are meaningless.

What do you give up by using an ANN index like HNSW, and what do you get?

You give up a little accuracy (recall): the true nearest neighbour may occasionally be missed. You get much faster search on large tables, instead of comparing against every row.

A startup already runs Postgres, has 200,000 document chunks and needs "only this customer's documents" filtering. pgvector or a dedicated vector DB? Why?

pgvector. The data size is well within its range, it avoids running and syncing another system, and per-customer filtering is a plain SQL WHERE next to the vector search. Revisit only if measurements show a scale or latency problem.

Say it in the interview

An embedding turns text into a vector so that similar meaning means a small distance, and a vector database finds the nearest vectors quickly.
For small to medium data I start with pgvector in the Postgres I already run, with an HNSW index, and move to a dedicated vector store only when I can show it is the bottleneck.
Semantic search is great for fuzzy meaning but poor at exact matches, so I combine it with keyword search when users search for IDs or names.

Common follow-up question: "How do you choose between IVFFlat and HNSW?"

HNSW is usually my default: better query speed and recall, and it can be built on an empty table, at the cost of a slower build and more memory. IVFFlat builds faster and is smaller but needs data loaded first to make good clusters, so I consider it when memory or build time is the constraint. In both cases I measure recall against exact search on a sample before trusting it.
