Recipes that every cook already knows

When a cook makes dal, she does not invent cooking from scratch. She follows an old recipe: temper the spices, boil, add salt at the end. Other cooks know the same recipe, so they can say "make it the tadka way" and everyone understands.

A design pattern is a recipe for a problem that programmers meet again and again, with a name. Saying "use a Strategy here" is shorter than explaining a whole design. In this lesson you learn seven names that come up most in interviews.

Seven patterns, each with a tiny example

Patterns are tools, not goals. Use one when the problem is really there. The list below uses plain TypeScript and every block compiles with tsc --strict. The outputs are real.

1. Singleton: only one, ever

Like a school having one principal. The class makes sure only one object exists and gives everyone the same one. Use it for things that must be shared: configuration, one connection pool. Do not use it as a lazy global variable: hidden shared state makes tests hard and bugs strange.

class Config {
  private static instance?: Config;
  private constructor(public readonly appName: string) {}

  static get(): Config {
    if (!Config.instance) Config.instance = new Config("MyShop");
    return Config.instance;
  }
}

const a = Config.get();
const b = Config.get();
console.log(a === b); // true: same object every time
// new Config("x");   // compile error: constructor is private
true

You already used this: in Node, a module is loaded once, so export const db = createClient() is a singleton. Every import gets the same object.

2. Factory: ask by name, get the right object

Like ordering "one tea" and the tea stall decides the cup. A function creates the right object so callers do not write new everywhere. Use it when the type depends on input (email vs SMS) or creation is complicated. Do not use it when there is only one type: a plain constructor is clearer.

interface Notifier {
  send(msg: string): string;
}
class Email implements Notifier {
  send(msg: string): string { return `EMAIL: ${msg}`; }
}
class Sms implements Notifier {
  send(msg: string): string { return `SMS: ${msg}`; }
}

// The factory: callers ask by name, never write "new Email()".
function createNotifier(kind: "email" | "sms"): Notifier {
  switch (kind) {
    case "email": return new Email();
    case "sms": return new Sms();
  }
}

console.log(createNotifier("sms").send("OTP 4821"));
console.log(createNotifier("email").send("Welcome"));
SMS: OTP 4821
EMAIL: Welcome

You already used this: React.createElement("div") and document.createElement("div") return the right kind of thing for the name you give.

3. Strategy: swap the rule at run time

Like choosing speed post or normal post for the same parcel. Put each way of doing a job behind the same shape and let the caller pick. Use it when you have several interchangeable rules (shipping cost, sorting, pricing). Do not use it for two rules that never change; an if is fine.

type ShippingStrategy = (kg: number) => number;

const standard: ShippingStrategy = (kg) => 40 + kg * 10;
const express: ShippingStrategy = (kg) => 100 + kg * 25;

class Cart {
  constructor(private strategy: ShippingStrategy) {}
  setStrategy(s: ShippingStrategy): void { this.strategy = s; }
  shipping(kg: number): number { return this.strategy(kg); }
}

const cart = new Cart(standard);
console.log(cart.shipping(2)); // 60
cart.setStrategy(express);     // swap the rule at runtime
console.log(cart.shipping(2)); // 150
60
150

You already used this: array.sort((a, b) => ...). The comparison function is the strategy.

4. Observer: tell me when something happens

Like subscribing to a YouTube channel. One object announces events, and any number of listeners react. The announcer does not know who listens. Use it for notifications, UI updates, "order placed, now email and SMS". Do not use it when you need a strict order or a reply; too many hidden listeners are hard to trace. Remember to unsubscribe, or you leak memory.

type Listener<T> = (data: T) => void;

class EventHub<T> {
  private listeners = new Set<Listener<T>>();

  subscribe(fn: Listener<T>): () => void {
    this.listeners.add(fn);
    return () => this.listeners.delete(fn); // call this to unsubscribe
  }
  publish(data: T): void {
    for (const fn of this.listeners) fn(data);
  }
}

const orders = new EventHub<string>();
orders.subscribe((id) => console.log("Email service: order", id));
const stop = orders.subscribe((id) => console.log("SMS service: order", id));
orders.publish("A101");
stop();
orders.publish("A102");
Email service: order A101
SMS service: order A101
Email service: order A102

You already used this: button.addEventListener("click", ...), Node's EventEmitter, and React state updates.

5. Adapter: make two different plugs fit

Like a travel plug adapter. Your app expects one shape; an old library has another. Write a small class that translates. Use it to wrap third-party or legacy code. Do not use it if you can simply change the code yourself.

// What our app wants
interface PaymentGateway {
  pay(rupees: number): boolean;
}

// What the old vendor library gives us (cannot be changed)
class LegacyVendor {
  makePayment(paise: number, currency: string): { status: string } {
    console.log(`vendor charged ${paise} ${currency}`);
    return { status: "OK" };
  }
}

// The adapter translates between the two shapes
class VendorAdapter implements PaymentGateway {
  constructor(private vendor: LegacyVendor) {}
  pay(rupees: number): boolean {
    return this.vendor.makePayment(rupees * 100, "INR").status === "OK";
  }
}

const gateway: PaymentGateway = new VendorAdapter(new LegacyVendor());
console.log(gateway.pay(499));
vendor charged 49900 INR
true

You already used this: a small wrapper function that turns one API's response into the shape your React components expect.

6. Decorator: wrap an object to add a feature

Like adding ghee and papad around a thali. Each wrapper has the same shape as what it wraps, adds one thing and passes the call on. Use it to add logging, caching or auth without editing the core class, and to stack them in any order. Do not use it if the order of many wrappers gets confusing.

interface Handler {
  handle(req: string): string;
}
class Core implements Handler {
  handle(req: string): string { return `data for ${req}`; }
}

// Each decorator wraps another Handler and adds one thing.
class Logging implements Handler {
  constructor(private inner: Handler) {}
  handle(req: string): string {
    console.log("log: got", req);
    return this.inner.handle(req);
  }
}
class Auth implements Handler {
  constructor(private inner: Handler, private token: string) {}
  handle(req: string): string {
    if (this.token !== "secret") return "401 Unauthorized";
    return this.inner.handle(req);
  }
}

const good = new Logging(new Auth(new Core(), "secret"));
const bad = new Logging(new Auth(new Core(), "wrong"));
console.log(good.handle("/orders"));
console.log(bad.handle("/orders"));
log: got /orders
data for /orders
log: got /orders
401 Unauthorized

You already used this: Express middleware (app.use(logger), app.use(auth)) and React higher-order components. (TypeScript also has an @decorator syntax, which is a different language feature with a similar idea.)

7. Builder: assemble a complex object step by step

Like ordering a custom sandwich one choice at a time. Instead of a constructor with ten arguments, you call small named steps and then build(). Use it for objects with many optional parts (queries, HTTP requests, test data). Do not use it for simple objects with two or three fields.

class QueryBuilder {
  private table = "";
  private conditions: string[] = [];
  private max?: number;

  from(table: string): this { this.table = table; return this; }
  where(cond: string): this { this.conditions.push(cond); return this; }
  limit(n: number): this { this.max = n; return this; }

  build(): string {
    if (!this.table) throw new Error("from() is required");
    let sql = `SELECT * FROM ${this.table}`;
    if (this.conditions.length) sql += ` WHERE ${this.conditions.join(" AND ")}`;
    if (this.max !== undefined) sql += ` LIMIT ${this.max}`;
    return sql;
  }
}

const sql = new QueryBuilder()
  .from("orders")
  .where("city = 'Pune'")
  .where("paid = true")
  .limit(10)
  .build();
console.log(sql);
SELECT * FROM orders WHERE city = 'Pune' AND paid = true LIMIT 10

You already used this: Supabase's .from("orders").select().eq(...).limit(10) chain and new URLSearchParams() with .append().

Run it yourself (about 30 minutes)

A. Run three patterns in the Playground

  1. Open typescriptlang.org/play in Chrome. Click the left editor, press Ctrl + A then Delete.
  2. Click Copy on the Strategy block and paste it with Ctrl + V. Press Ctrl + Enter (or click Run). In the Logs tab you should see 60 then 150.
  3. Add a third strategy: const pickup: ShippingStrategy = () => 0;, call cart.setStrategy(pickup) and log cart.shipping(2). You should see 0.
  4. Repeat with the Observer block. You should see two lines for A101 and only the Email line for A102. Why? Because stop() removed the SMS listener.
  5. Repeat with the Decorator block. Notice that bad.handle prints a log line and returns 401 Unauthorized. Swap the order: new Auth(new Logging(new Core()), "wrong") (you must keep the token argument). The log line disappears. Order matters.

B. Try the Singleton guard

  1. Paste the Singleton block. Remove the // in front of new Config("x");. A red wavy line says the constructor is private. That is how the pattern stops a second instance.

C. Match the problem to the pattern (paper)

Quick quiz

Which pattern removes a long if/else on a "type" field?

Strategy (or Factory if the if/else is about which object to create). Each case becomes its own class or function behind the same shape.

Observer vs Decorator: what is the difference?

Observer: one event, many listeners who do not know each other. Decorator: a chain of wrappers around one object, where each wrapper adds a feature and passes the call on.

Why is Singleton often called an anti-pattern?

It is hidden global state. Code that quietly depends on it is hard to test and to change. It is fine for truly single resources such as config, but pass it in rather than reaching out for it.

Which pattern does Express middleware match, and why?

Decorator (a chain of handlers). Each one does one job, like logging or auth, and passes the request to the next.

You must support three payment gateways with different APIs. Which patterns would you combine and why?

An Adapter per gateway to give them one shared PaymentGateway interface, and a Factory (or a Strategy chosen by config) to pick the right one. The rest of the code only knows the interface.

Say it in the interview

I name the problem first, then the pattern: many interchangeable pricing rules means Strategy.
For notifications I use Observer, so the order service just publishes "order placed" and does not know about email or SMS.
I wrap third-party SDKs in an Adapter so a vendor change touches one class.

Common follow-up question: "What is the difference between Strategy and State?"

Both swap behaviour behind an interface. With Strategy the caller chooses the behaviour from outside, and it usually stays the same. With State the object changes its own behaviour as it moves through steps, like a vending machine going from idle to has-money. You will see State in the practice lesson.
