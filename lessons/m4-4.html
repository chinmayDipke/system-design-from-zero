The driving test

In a driving test, the examiner does not ask you to be a racing driver. She has a sheet: Did you check the mirror? Did you signal before turning? Did you stay calm at the roundabout? Marks are lost for small, predictable mistakes: forgetting the mirror, stalling, going too fast.

The design interview is the same. Interviewers have a sheet of areas, and candidates lose marks in the same few ways again and again. If you know the usual mistakes and what the sheet looks like, you can avoid them on purpose.

What goes wrong, and what the scorer looks for

The seven common mistakes

MistakeWhat it looks likeFix
Jumping into a solution"Design a URL shortener? OK, I'll use a hash and a database..." in the first 20 seconds.Pause. Repeat the problem. Ask questions first.
Not asking questionsNever asks about users, scale or priorities. Builds the wrong thing.Ask 5 to 8 requirement questions (step 1).
Over-engineeringKafka, Kubernetes, microservices and sharding for 40 writes a second.Start simple. Add each part only when a number or a requirement demands it.

How you are scored: a typical rubric

Every company has its own sheet. This is a common shape. Each area is scored from "no hire" to "strong hire".

AreaStrong looks likeWeak looks like
RequirementsAsks sharp questions, separates must-have from out of scope, confirms non-functional needs.Starts drawing at once; assumes everything.
EstimationRound numbers, states assumptions, links numbers to design choices.No numbers, or numbers that change nothing.
DesignA clear, correct high-level design that fits the requirements; each box has a reason.Boxes with no reason; missing pieces (no storage, no failure thinking).
DepthGoes deep on the hard parts: data layout, failure cases, algorithms. Knows how things work inside.Stays shallow; only names technologies.
Trade-offsStates options, picks one, says its cost, says when the other would win.One option, no downside mentioned.
CommunicationStructured, thinks aloud, checks in, draws tidy diagrams (diagrams).Silent or rambling; messy drawing.
OwnershipDrives the interview, manages time, takes hints well, admits gaps.Waits to be led; defensive or bluffs.

Phrases for trade-offs

Trade-offs are the single most scored skill, so learn a few sentence shapes:

  • "I'd choose X because reason. The cost is cost, which is acceptable here because why."
  • "The alternative is Y, which is better when condition, but it adds complexity."
  • "For this feature I'd favour consistency over availability, since a wrong balance is worse than a short error" (CAP).
  • "At this scale I'd keep it simple: one Postgres with a replica. If writes grow 10 times, I'd consider sharding."
  • "The first bottleneck will be the database writes. I'd watch this metric and then add this."
  • "I'm not sure about the exact numbers, but I'd measure first, then decide."

Trade-offs of "playing safe"

  • Being very structured can sound robotic. Keep the structure, but respond to the interviewer's face and hints.
  • Avoiding buzzwords completely is also a mistake: using the right term (queue, consistent hashing) is good, if you can explain it.
  • Over-asking questions wastes time. Ask the ones that change the design.

The usual fast self-check: after every box you add, ask "What problem does this solve, and what does it cost?" If you cannot answer, remove the box.

Do it yourself (about 30 minutes, reading and marking)

Below is a written sample answer to "Design a URL shortener". It has six deliberate mistakes. Your job is to find them. Remember the numbers from estimation: 100 million new URLs a month is about 40 writes a second.

A. Read the answer

  1. Copy these lines into a notes file, or print them. Read once, slowly: 
    [1]  Interviewer: Design a URL shortener.
[2]  Candidate:   OK. I'll use a hash of the long URL as the key and store it in a database.
[3]  Candidate:   For the database I'll use NoSQL, because it scales and relational databases don't.
[4]  Candidate:   The architecture: an API gateway, 12 microservices (URL service, user service,
                  analytics service, billing service and so on) on Kubernetes, Kafka between
                  all of them, and a sharded database across 20 regions.
[5]  Interviewer: How many users are we talking about?
[6]  Candidate:   Uh... a lot, I guess. It's like bit.ly.
[7]  Candidate:   We'll put Redis in front because Redis is fast.
[8]  (Candidate is silent for about two minutes while drawing.)
[9]  Interviewer: How do you handle two long URLs producing the same short code?
[10] Candidate:   I'm not sure. What would you like me to talk about next?

B. Find the six mistakes

  1. Get a pen and a fresh page. Write the numbers 1 to 6.
  2. For each mistake, write the line number, the name of the mistake (from the seven in the table) and a one-line fix.
  3. Do not open the answers until you have six. If you are stuck at four or five, re-read lines 2, 4, 6, 8 and 10.
  4. Open the answers:
    Show the six mistakes

    1. Line 2: jumped into a solution. No requirements, no questions. Fix: first ask who uses it, how many links, how long they last, whether custom aliases or analytics are needed.

    2. Line 3: a buzzword with no reason. "NoSQL because it scales and relational doesn't" is not a reason, and it is not even true. The load here is small. Fix: "At about 40 writes a second and 3 TB in five years, one Postgres with a replica fits, and a unique index on the code makes collisions easy to catch."

    3. Line 4: over-engineering. Twelve microservices, Kafka, Kubernetes and 20 regions for a tiny load. Fix: a simple service behind a load balancer, one database, one cache. Scale it only when numbers demand.

    4. Lines 5 and 6: no estimation and no non-functional requirements. "A lot" is not a number, so no design choice can be justified. Fix: estimate: 100 million a month is 40 writes a second, 4,000 reads a second, so read-heavy, so cache. (The non-functional side, such as availability of redirects and latency, was never discussed either.)

    5. Line 8: silence. Two minutes of silent drawing loses the interviewer. Fix: narrate: "I'm adding a cache here because reads are 100 times writes."

    6. Line 10: not driving, and no answer to a core problem. The candidate handed control back and had no plan for collisions in the hash. Fix: propose an answer even if unsure: "Generate a unique ID with a counter and encode it in base 62, which has no collisions; or retry on a unique-key conflict." Then offer where to go next: "I'd suggest we go deeper on code generation or on caching; which do you prefer?"

    Also noticeable: line 7 repeats the "because it is fast" buzzword for Redis. It is a seventh smaller flaw, and a good reason would be "because reads are 100 times writes and the same few links are requested again and again".

C. Rewrite the answer

  1. Write a corrected version of lines 2 to 4 in 6 to 8 lines. Include: two requirement questions, one number, a simple architecture, and one sentence that follows the pattern "I'd choose X because ..., the cost is ...".
  2. Save it as m4-4 rewrite.txt in your Module 4 folder.

D. Make your own checklist

  1. Write 7 short questions, one per mistake, to ask yourself before answering: "Did I ask? Did I give a number? Is every box justified? Did I talk? Did I name a cost?" and so on. Keep it beside you during mock interviews.

Quick quiz

Name four common design-interview mistakes.

Jumping into a solution, not asking questions, over-engineering, buzzwords without reasons, ignoring non-functional requirements, silence, and not driving the interview.

What does "driving the interview" mean?

Taking responsibility for the structure: announce the next step, manage time, propose deep-dive topics and ask for feedback, instead of waiting to be told what to do.

What is the sentence shape for stating a trade-off?

"I'd choose X because (reason). The cost is (cost), which is acceptable because (why). Y would be better if (condition)."

Why is "I'll use Kafka" a weak statement?

It names a technology without saying what problem it solves here or what it costs. A strong version says why a queue is needed (decoupling, buffering spikes) and the cost (extra moving part, at-least-once delivery).

You realise halfway that your design was wrong for the requirements. What do you do?

Say so openly, explain what changed my mind, and fix it. Interviewers value honest correction and adaptability far more than defending a bad design.

Say it in an interview

"I'd choose a single Postgres with a read replica because the load is about 40 writes a second. The cost is that it won't scale writes forever, so I'd plan to shard by user if that changes."
"I'm going to think out loud for a moment: I see two options, A and B."

Common follow-up question: What if you do not know the answer?

Say so, state what I do know, reason from first principles to a proposal, and say how I would verify it. For example: "I haven't used that, but I'd expect it to work like a queue, so I'd test it with a small load first." Bluffing is penalised more than a gap.
