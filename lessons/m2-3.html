Finding a topic in a 500-page book

You want to read about "photosynthesis" in a thick science book. You could flip every page from the start until you spot it. Or you open the index at the back: it lists topics in alphabetical order with page numbers. You find "photosynthesis, page 212", and you jump straight there.

The index costs something: it takes extra pages, and when the author adds a new chapter, the index must be updated too. But reading becomes hugely faster.

Now think about sending money on UPI. Your account is debited and your friend's account is credited. If the power goes out in the middle, you cannot have money vanish. Both steps must happen, or neither. Databases promise this too. This lesson covers both ideas.

Indexes, transactions and ACID

Indexes: the book index of a database

Without an index, a query like WHERE customer_id = 4242 makes the database read every row (a sequential scan). With 200,000 rows that is slow, with 200 million it is a disaster. An index is a separate, sorted structure that lets the database jump straight to matching rows.

Most databases use a B-tree: a shallow tree. The top node says which range to go to, the next node narrows it, and the bottom "leaf" holds the value and the location of the row. Three or four hops can find one row among millions, because each hop discards most of the remaining data.

The cost of indexes

  • Writes get slower. Every INSERT, UPDATE and DELETE must also update every index on the table.
  • Storage grows. Each index is a copy of some columns plus pointers.
  • So do not index everything. Index the columns you filter, join or sort on often. Primary keys are indexed automatically.

Composite indexes: the left-to-right rule

An index can cover several columns, like (city, created_at). It is sorted by city first, then by date inside each city, like a phone book sorted by surname then first name. So it helps queries on city, or on city AND created_at. It does not help a query on only created_at, just as a phone book does not help you find everyone named "Ravi". Order the columns with the most common filter first.

Transactions

A transaction groups several steps into one unit: BEGIN, do the steps, then COMMIT (make it permanent) or ROLLBACK (undo everything). It is "all or nothing".

AtomicityAll steps or noneDebit and credit both happen, or neither

Isolation levels and the problems they prevent

Perfect isolation is slow, so databases offer levels. Each level blocks more weird behaviour:

ProblemWhat happens
Dirty readYou read data another transaction has not committed yet, and it may be rolled back. You saw something that never really existed.
Non-repeatable readYou read a row twice in your transaction and get different values, because someone committed a change in between.
PhantomYou run the same query twice and the second time new rows appear (or vanish), because someone inserted or deleted matching rows.

The standard levels, from loosest to strictest: Read Uncommitted, Read Committed (Postgres default: no dirty reads), Repeatable Read (also no non-repeatable reads), Serializable (behaves as if transactions ran one at a time). Stricter means safer but slower and more likely to make one transaction retry. Default is fine for most apps; choose Serializable for things like seat booking or ledgers where a race would be costly.

The N+1 query problem

You load 50 orders (1 query), then for each order you fetch its customer (50 more queries). That is N+1 queries: 51 round trips instead of 1 or 2. It is the most common hidden slowness in apps that use an ORM. Fix: use a join, or fetch all needed customers in one query with WHERE id IN (...), or use your ORM's "include/eager load" option.

Trade-offs

  • Indexes speed reads and slow writes. Add the ones your real queries need, and check with EXPLAIN.
  • Transactions and high isolation give safety but reduce parallelism. Keep transactions short; never wait for a user or call a slow API inside one.
  • Many NoSQL stores relax ACID to scale out (the next lessons explain why).

Mention EXPLAIN ANALYZE in interviews. "I would not guess; I would look at the query plan" is exactly what interviewers want to hear.

Do it yourself (about 30 minutes)

Stay inside the free tier. The free Supabase database has a limited size (500 MB at the time of writing). The 200,000-row table below is only a few MB. Do not raise the number, and run the clean-up step at the end.

A. See a slow query, then fix it with an index

  1. Open your Supabase project (from the last lesson) and click SQL Editor, then New query.
  2. Create a table with 200,000 fake rows, then click Run (Ctrl + Enter). It may take a few seconds. If a popup asks about Row Level Security, you can run without it for this practice table. 
    create table demo_orders as
select
  g as id,
  (random() * 10000)::int as customer_id,
  (random() * 1000)::int as amount
from generate_series(1, 200000) g;

analyze demo_orders;
    generate_series(1, 200000) makes the numbers 1 to 200000, one per row.
  3. Confirm the count: new query, run select count(*) from demo_orders;. You should see 200000.
  4. Now ask the database to explain how it runs a filter. EXPLAIN ANALYZE actually runs the query and reports the plan and the real time: 
    explain analyze
select * from demo_orders where customer_id = 4242;
  5. Read the result lines. You should see Seq Scan on demo_orders with a Filter: (customer_id = 4242) line, and at the bottom Execution Time in milliseconds. Write that time down. (It will vary on your machine and project; a few to a few dozen ms is typical.)
  6. Add an index on that column and refresh the table statistics: 
    create index idx_demo_orders_customer on demo_orders (customer_id);
analyze demo_orders;
  7. Run the same explain analyze select ... again. Now the first line should say Index Scan or Bitmap Index Scan (both use the index) instead of Seq Scan, and Execution Time should be much smaller. Write it down next to the first number.
  8. Compare the two times in your notes, and write one sentence: "An index made this query about ___ times faster, but every insert now also updates the index." (At just 200,000 rows the gap is modest; imagine 200 million.)
  9. Try the left-to-right rule: create a composite index and test two queries. 
    create index idx_demo_orders_cust_amount on demo_orders (customer_id, amount);
analyze demo_orders;

explain analyze select * from demo_orders where customer_id = 4242 and amount = 500;
explain analyze select * from demo_orders where amount = 500;
    The grid shows the result of the last statement, so run the two explain lines one at a time. The first should use an index; the second filters on only the second column, so it will likely scan the whole table (the planner may also choose a full index scan; either way it cannot jump straight to the answer).

B. A transaction you can undo

  1. Create a tiny "bank" and run it: 
    create table demo_accounts (
  id int primary key,
  name text,
  balance int
);
insert into demo_accounts values (1, 'Asha', 1000), (2, 'Ravi', 500);
  2. Open a new query and run this whole block at once. It moves Rs 200 and then undoes it: 
    begin;
update demo_accounts set balance = balance - 200 where id = 1;
update demo_accounts set balance = balance + 200 where id = 2;
rollback;
  3. Check the balances in a separate query: select * from demo_accounts order by id;. You should see Asha 1000 and Ravi 500: nothing changed, because you rolled back. Atomicity at work.
  4. Run the block again but replace the last word with commit;. Check again: Asha 800, Ravi 700. Committed changes stay.
  5. Think: if the server crashed between the two update lines and there was no transaction, what would be wrong? (200 rupees would disappear from Asha but never reach Ravi.)

C. Clean up

  1. Remove the practice tables so they do not use up space: 
    drop table demo_orders;
drop table demo_accounts;
  2. Click Run. In Table Editor, confirm they are gone. Keep customers and orders from the last lesson if you want to reuse them.

Quick quiz

Why do indexes make reads fast but writes slower?

An index lets the database jump to rows instead of scanning all of them. But each insert, update or delete must also update every index on that table.

You have an index on (city, created_at). Which queries can use it well?

Filters on city, or on city and created_at together. Not a filter on created_at alone, because the index is sorted by city first (left-to-right rule).

Explain ACID with a UPI transfer in one sentence per letter.

Atomicity: debit and credit both happen or neither. Consistency: rules like "balance not negative" always hold. Isolation: simultaneous payments do not see each other's half-finished state. Durability: once confirmed, it survives a crash.

What is a phantom read?

Running the same query twice in one transaction and getting extra (or missing) rows the second time because another transaction inserted or deleted matching rows in between.

A page makes 1 query for 30 posts, then 30 queries for authors. What is wrong and how do you fix it?

It is the N+1 problem. Fix it with a join, one batched WHERE id IN (...) query, or the ORM's eager loading, giving 1 or 2 queries instead of 31.

A table gets 10,000 inserts a second and is rarely read. Would you add many indexes? Why?

No. Each index slows every insert. With a write-heavy, rarely-read table I would keep indexes minimal (maybe only the primary key).

Say it in an interview

"I would index the columns used in WHERE, JOIN and ORDER BY, check the plan with EXPLAIN, and remember every index slows writes."
"For the payment I would use a transaction so debit and credit are atomic, and a suitable isolation level to prevent double spending."

Common follow-up question: A query is slow. What do you do?

Run EXPLAIN ANALYZE to see the plan. If it does a sequential scan on a big table, add an index matching the filter and sort. Check for N+1 patterns, select only needed columns, and consider caching if the same result is read often.
