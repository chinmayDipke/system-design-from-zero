Five buckets per family

In a colony the water tanker comes once a day. There are 200 families and not enough water for everyone to take as much as they like. So the colony secretary stands at the tap with a notebook: each family may fill 5 buckets. When a family comes for the sixth, the secretary says, "Sorry, your turn is over. Come back after the next round."

A rate limiter is that secretary for a website. It counts how many requests each person has made in a short time, and says "no, slow down" when someone asks too often. It protects the tap (your servers) from one greedy person or a broken script, so everyone else still gets water.

The hard part is not the counting. The hard part is when many secretaries stand at many taps and must still agree on one notebook.

Design a distributed rate limiter

Before reading on, set a 10-minute timer and write your own requirements and a rough diagram. Then compare. If you only know "count requests in Redis", try to find the bug in that idea before you read the deep dive.

We follow the 7-step framework. The ideas of limiting were introduced in rate limiting; here we design the whole service.

1. Requirements

Functional:

  • Limit requests per client: by user id, by IP address, or by API key.
  • Different rules for different endpoints and plans (for example 5 per minute to create a link; 1,000 per minute to read; paid users get more).
  • When over the limit, reject with HTTP 429 Too Many Requests and tell the client when to retry.

Non-functional:

  • Very low added latency: a few milliseconds at most. It runs on every request.
  • Distributed: the limit must hold even though requests hit many servers (the "5 per minute" must not become "5 per minute per server").
  • Highly available: the limiter must not become the reason the whole API is down (availability).
  • Reasonably accurate. A few extra requests slipping through is acceptable. Letting through ten times the limit is not.
  • Rules are changeable without redeploying the app.

Out of scope: network-level DDoS protection (that belongs at a CDN or firewall), billing quotas (monthly usage caps), and bot detection.

2. Estimation

Assume 10 million daily active users, each making 100 API calls a day.

  • Total calls: 10,000,000 x 100 = 1,000,000,000 a day. At about 100,000 seconds a day that is 10,000 requests a second. Peak at 3x: 30,000 a second.
  • Limiter operations: one check per request, so 30,000 Redis operations a second at peak. A single Redis node handles on the order of 100,000 simple operations a second, so one node is enough to start; we shard for headroom.
  • Memory: a counter or token bucket is small, about 100 bytes with the key. 10,000,000 clients x 100 B = 1 GB. A sliding window log (one timestamp per request, say 100 per window at 8 bytes) is 10,000,000 x 800 B = 8 GB, eight times more. That is one reason to avoid the log version.

Conclusion: the load is small enough for Redis; the real challenges are correctness under concurrency and what to do when Redis fails.

3. API

The limiter is not called by users; it sits inside the request path. Its "API" is the decision and the headers the client sees:

Internal:  allow(key, rule) -> { allowed, remaining, reset_at }

Allowed response (from the real API) carries:
  X-RateLimit-Limit: 5
  X-RateLimit-Remaining: 3

Rejected response:
  HTTP/1.1 429 Too Many Requests
  Retry-After: 37                 (seconds until the client may try again)
  X-RateLimit-Limit: 5
  X-RateLimit-Remaining: 0

Admin:     PUT /rules/{rule_id}   { "match": "POST /shorten", "limit": 5, "window": "60s", "by": "ip" }

Retry-After is a standard HTTP header (see MDN in the reading list). The X-RateLimit-* names are a very common convention, not a rule every API follows exactly.

4. Data model

  • Counters live in Redis: key rl:{rule}:{client} (for example rl:shorten:203.0.113.7), value a number (or two numbers for a token bucket), and a TTL equal to the window so old entries delete themselves. Why Redis: in-memory, very fast, atomic operations, built-in expiry (Redis). The data is temporary, so losing it only means counters restart.
  • Rules live in a normal database or config store: rule_id, match (endpoint, plan), limit, window, key_by (ip | user | api_key), algorithm. They change rarely, so every gateway keeps a cached copy and refreshes it every minute.

5. High-level design

  1. A request arrives at the API gateway (or middleware in the app; see below).
  2. The limiter builds the key: the API key if present, else the user id, else the client IP.
  3. It reads the matching rule from its local rule cache.
  4. It makes one atomic call to Redis: "check and count this request".
  5. (a) Allowed: forward to the app server. (b) Over the limit: reply 429 with Retry-After immediately; the app server never sees it.
  6. On the way back the gateway adds the X-RateLimit-* headers to the response.

Where does it live?

PlaceProsCons
API gateway / edge (gateways)One place, any language behind it, rejected traffic never reaches your serversAnother hop; the gateway must scale and stay up
Middleware in each appNo extra hop; easy rules that need app knowledge (user plan)Each service re-implements it; rejected requests already cost you a server

A common answer: the gateway for coarse limits (per IP, per key), plus app middleware for fine ones (per user per action).

6. Deep dives

Deep dive A: which algorithm?

AlgorithmHow it worksProsCons
Fixed window counterCount requests per clock minute; reset at the next minuteSimplest; tiny memoryBoundary burst: 5 requests at 12:00:59 and 5 more at 12:01:00 is 10 in two seconds
Sliding window logKeep a timestamp for each request; count those in the last 60 sExactMemory grows with the limit (8 GB in our estimate)
Sliding window counterBlend this window's count with a weighted share of the previous window's countSmooth, tiny memory, good approximationApproximate, slightly harder to explain
Token bucketA bucket holds up to B tokens and refills at R per second; each request takes oneAllows short bursts but enforces the average rate; two numbers per clientTwo parameters to tune; needs atomic read-modify-write
Leaky bucketRequests enter a queue and leave at a fixed ratePerfectly smooth outputBursts wait or are dropped; queue adds delay

Pick: token bucket for an API where short bursts are normal (a mobile app fires 3 calls when a screen opens). Pick the sliding window counter when you want "no more than N in any 60 seconds" to look strict and simple. The build project uses a sliding window through a library.

Deep dive B: the atomicity problem in Redis

The tempting code is: count = GET key; if count < 5 then SET key count+1. It is broken. Say the count is 4 and two servers handle two requests at the same instant:

  1. Server A reads 4. Server B reads 4 (before A writes).
  2. A sees "4 is under 5", allows, and writes 5. B does the same and writes 5.
  3. Two requests were let through, but the counter says 5. The sixth and seventh request were allowed. Under load, many extra slip through.

This is a race condition: the read and the write are two steps, and another request can slip between them. The fix is to make check-and-update one indivisible step:

  • INCR adds 1 and returns the new value in one atomic command. Allow if the returned number is within the limit. For a fixed window: INCR key, and if the result is 1, also EXPIRE key 60. Careful: if the server crashes between those two commands, the key has no expiry and the client is blocked forever. Use one Lua script, or SET key 0 EX 60 NX first.
  • A Lua script run inside Redis is atomic: Redis runs it start to finish before anything else. Token bucket (read tokens, refill, subtract, write) needs this, because it is a read-modify-write.
  • A library that already did this correctly. @upstash/ratelimit sends such scripts for you, which is why the build project does not need to write any.

The bug only shows up under concurrency. It passes every test you run by hand, one request at a time. Interviewers love it for that reason.

Deep dive C: failure, many regions, and who is the client

  • Fail-open or fail-closed? If Redis is unreachable, either allow everything (fail-open) or block everything (fail-closed). For a normal API, fail-open: a short window without limits is better than a total outage, and you alert loudly. For sensitive actions (login attempts, OTP sending) fail-closed, or fall back to a rough in-memory limit per server, because an open door lets attackers guess passwords or run up your SMS bill.
  • Many regions: a single global Redis means every request in Mumbai waits for a round trip to Virginia, which is far too slow. Common choices: a Redis per region with the limit split between regions (accurate per region, loose globally), or regions sharing counts asynchronously (smoother globally, slightly stale). State the trade-off: accuracy versus latency. Most teams accept "limit is approximate across regions".
  • Who is the client? Logged-in traffic: user id or API key. Anonymous traffic: IP. But many people share one IP (an office, a college, a mobile carrier's NAT), so an IP limit can punish innocent users: keep IP limits generous, and add per-user limits after login. Behind a proxy, read the client IP from X-Forwarded-For, and only trust it if your own proxy set it, since a client can send a fake one.
  • Layered limits: use a short window to stop bursts (10 a second) plus a longer one to stop sustained abuse (1,000 an hour).

7. Trade-offs, bottlenecks and wrap-up

  • Accuracy versus speed: exact logs cost memory; approximations are cheap and good enough.
  • Strict versus friendly: token buckets are kinder to normal bursts; strict windows are easier to reason about.
  • Bottleneck: the Redis node. Shard counters by key (consistent hashing); a client's counter always lives on one shard.
  • Observe (observability): rate of 429s per rule, Redis latency and errors, and top limited keys. A sudden jump in 429s is either an attack or a rule set too low.
  • Tell clients clearly: Retry-After lets well-behaved clients back off instead of hammering. Good clients also add random jitter to their retries (retries).

At 10x scale (300,000 checks a second): shard Redis across many nodes, keep a small in-memory pre-check in each gateway to reject obvious abusers without calling Redis, do the coarse per-IP limits at the CDN edge, and accept approximate counts across regions.

B. Variation questions

1. Free users get 5 requests a minute, paid users get 100. What changes?

The rule depends on the plan, so the key or rule lookup uses the plan: gateway reads the user's plan (from the token or a cached lookup), picks the matching rule, and counts under a key such as rl:shorten:user:42. Rules stay in config, so changing a plan's limit needs no deploy. Use the user id, not the IP, once the user is logged in.

2. Limit login attempts: 5 wrong passwords per 15 minutes. How?

Count failures per account and per IP (an attacker may try one password on many accounts, or many on one). Use a 15-minute window, make the check fail-closed (if the limiter is down, do not allow unlimited guesses), and return a generic message. Consider a short lock or a CAPTCHA after the limit rather than blocking the real owner forever.

3. How would you test that your limiter really is atomic?

Fire many concurrent requests at the same key (for example 50 in parallel against a limit of 5) and assert that exactly 5 are allowed. A GET-then-SET version will let several extra through; an INCR or Lua version will not.

Build it (optional, about 30 to 45 minutes)

You will add a real limiter to the link shortener from the last lesson: POST /api/shorten allows 5 requests a minute per IP and then answers 429 with Retry-After. You need the finished project from lesson m5-1, with its .env.local and Upstash database. The steps were tested with Next.js 16 and @upstash/ratelimit 2.2 (with @upstash/redis 1.40).

Build step 1: add the library

  1. Open VS Code, choose File then Open Folder and open your shortener folder from lesson m5-1.
  2. Open a terminal with Ctrl + ` and run: 
    npm install @upstash/ratelimit
    It finishes with a line like added 1 package (the number may differ). The library reuses the Upstash Redis connection you already have in lib/clients.ts, so no new environment variable is needed.

Build step 2: the limiter file

  1. In the file list, right-click the lib folder, choose New File and name it ratelimit.ts. Paste: 
    import { Ratelimit } from "@upstash/ratelimit";
import { redis } from "@/lib/clients";

// At most 5 requests per 60 seconds, counted separately for each key (we use the IP)
export const shortenLimiter = new Ratelimit({
  redis,
  limiter: Ratelimit.slidingWindow(5, "60 s"),
  prefix: "rl:shorten",
});

export function clientIp(req: Request): string {
  // Behind Vercel (or any proxy) the real client address is the first item here
  const forwarded = req.headers.get("x-forwarded-for");
  return forwarded?.split(",")[0]?.trim() || "local";
}
    Ratelimit.slidingWindow(5, "60 s") means 5 requests in any rolling 60 seconds. The library does the atomic Redis work for you. Press Ctrl + S.

Build step 3: use it in the route

  1. Open app/api/shorten/route.ts. Select everything with Ctrl + A and replace it with this complete file. New parts are the import, the block at the top of POST, and the headers on the 201 reply: 
    import { NextResponse } from "next/server";
import { supabase } from "@/lib/clients";
import { makeCode } from "@/lib/code";
import { clientIp, shortenLimiter } from "@/lib/ratelimit";

export async function POST(req: Request) {
  // Rate limit first, before doing any real work
  const { success, limit, remaining, reset } = await shortenLimiter.limit(clientIp(req));
  const limitHeaders = {
    "X-RateLimit-Limit": String(limit),
    "X-RateLimit-Remaining": String(remaining),
  };
  if (!success) {
    const retryAfter = Math.max(1, Math.ceil((reset - Date.now()) / 1000));
    return NextResponse.json(
      { error: "Too many requests. Try again later." },
      { status: 429, headers: { ...limitHeaders, "Retry-After": String(retryAfter) } }
    );
  }

  let body: { url?: unknown };
  try {
    body = await req.json();
  } catch {
    return NextResponse.json({ error: "Send JSON like {\"url\":\"https://...\"}" }, { status: 400 });
  }

  // Accept only real http or https URLs
  let target: URL;
  try {
    target = new URL(String(body.url));
    if (target.protocol !== "http:" && target.protocol !== "https:") throw new Error("bad scheme");
  } catch {
    return NextResponse.json({ error: "url must be a valid http or https URL" }, { status: 400 });
  }

  // Try a few times: if a random code is already taken, the database says
  // "duplicate key" (error code 23505) and we simply draw another code.
  for (let attempt = 0; attempt < 3; attempt++) {
    const code = makeCode();
    const { error } = await supabase.from("links").insert({ code, url: target.toString() });
    if (!error) {
      const origin = new URL(req.url).origin;
      return NextResponse.json({ code, shortUrl: `${origin}/${code}` }, { status: 201, headers: limitHeaders });
    }
    if (error.code !== "23505") {
      console.error("insert failed", error);
      return NextResponse.json({ error: "Could not save the link" }, { status: 500 });
    }
  }
  return NextResponse.json({ error: "Could not find a free code, try again" }, { status: 503 });
}
    Press Ctrl + S.
  2. The limiter runs before anything else, so a blocked caller costs us almost nothing: no parsing, no database. The 429 carries Retry-After in seconds, worked out from the reset time the library returns.

Quick quiz

Why is "GET the count, then SET count+1" wrong in a distributed limiter?

Two servers can read the same value before either writes, so both allow the request and extra requests slip through. The read and write must be one atomic step: INCR, a Lua script, or a library that uses them.

What breaks if you run INCR and then EXPIRE as two separate commands and the server crashes between them?

The counter key stays without an expiry. Once it passes the limit, that client is blocked forever. Use one Lua script, or set the key with its TTL in the same step.

What is the weakness of a fixed window counter?

The boundary burst: a client can use the whole limit at the end of one window and the whole limit again at the start of the next, so up to twice the limit passes in a short time. A sliding window or token bucket fixes this.

What breaks if you rate limit by IP address only?

Many real users share one IP (office, college, mobile carrier), so they all get blocked together. Meanwhile an attacker with many IPs gets through. Use user id or API key when you have one, keep IP limits generous.

Redis goes down. Do you fail open or fail closed?

It depends on the endpoint. For a normal API, fail open (allow) and alert, because blocking everyone is a total outage. For login or OTP sending, fail closed or fall back to a small in-memory limit, because unlimited attempts are dangerous or expensive.

You must pick one algorithm for a public API where mobile apps fire a few calls at once. Which and why?

Token bucket: it allows short bursts up to the bucket size but enforces the average rate, and stores only two numbers per client.

Say it in an interview

"I would put the limiter at the API gateway, keyed by API key, then user, then IP. Counters live in Redis with a TTL equal to the window, and the check-and-increment is one atomic call so concurrent requests cannot race."
"On a rejection I return 429 with Retry-After. If Redis is down I fail open for normal endpoints and fail closed for login and OTP."

Common follow-up question: How do you make the limit work across many servers and regions?

All servers in a region share one Redis (sharded by key), so the count is global within the region. Across regions, a single global Redis is too slow, so each region gets a share of the limit or counts sync asynchronously. The limit becomes approximate; I would say that out loud as an accuracy versus latency choice.

Common follow-up question: Token bucket or sliding window?

Token bucket when bursts are normal and you care about the average rate. Sliding window counter when you want a strict "N per rolling minute" with low memory. Avoid the sliding window log at scale, since it stores every timestamp.
