The post office box number

Your friend lives at "Flat 402, Sunrise Heights, Road No. 7, Near the Big Banyan Tree, Pune 411001". Nobody wants to write that on every parcel. So the post office gives your friend a small box: PO Box 4821. Send the parcel to 4821 and the post office looks up the long address in its register and delivers it.

A URL shortener is that post office. You give it a very long web address. It gives back a tiny code like sho.rt/aZ3kP9q. When someone opens the short link, the shortener looks up the long address and sends the visitor there.

It sounds too easy to be an interview question. The fun starts when a billion people use it: how do you make sure two boxes never get the same number, and how do you look up the register so fast that nobody waits?

Design a URL shortener (like bit.ly)

Before reading on, set a 10-minute timer and write your own requirements and a rough diagram. Then compare. You will learn far more from the gap between your answer and this one than from reading it cold.

We follow the 7-step framework: requirements, estimate, API, data model, high-level design, deep dives, wrap-up.

1. Requirements

Functional:

  • Given a long URL, create a short URL.
  • Opening the short URL redirects to the long URL.
  • Optional: the user picks a custom alias; links can expire; the owner sees click counts.

Non-functional:

  • Very read-heavy: far more clicks than creations, say 100 to 1.
  • Fast redirects: under about 100 ms on the server side. A redirect is the user waiting for the real page, so it must feel instant.
  • Highly available (availability): if the shortener is down, every link on the internet that points to it is broken.
  • Short codes are unique, and ideally hard to guess one by one.
  • Slightly stale analytics are fine. A link that was just created may take a moment to work everywhere (eventual consistency is acceptable; see consistency models).

Out of scope today: user accounts and login, a dashboard UI, spam and malware scanning (mention it as a next step).

2. Estimation

Assumptions: 100 million new links a month, reads are 100 times writes. A month is about 2.6 million seconds (30 x 86,400), so we round to 2.5 million. A day is about 100,000 seconds (estimation).

  • Writes: 100,000,000 / 2,600,000 = about 40 per second. Peak at 3x: about 120 per second.
  • Reads: 40 x 100 = 4,000 per second. Peak at 3x: about 12,000 per second.
  • Storage per year: 100 million x 12 = 1.2 billion links. At about 500 bytes a row (code, long URL, dates, owner) that is 1.2 billion x 500 B = 600 GB a year. Over 5 years: about 3 TB. One big database can hold that, but we will want replicas.
  • Cache size: 4,000 reads a second x 86,400 = about 345 million reads a day. Links follow the 80/20 rule: a small share of links gets most clicks. Cache the hot 20%: 345 million x 0.2 = 69 million entries x 500 B = about 35 GB. That fits in a few Redis machines (caching).
  • Key space: in 5 years we create about 6 billion codes. Seven characters of base62 (0-9, a-z, A-Z) give 62^7 = about 3.5 trillion codes, so we would use only 0.2% of them. Six characters give 62^6 = 56.8 billion, still enough for 6 billion.

What the numbers tell us: 12,000 reads a second is too much to send to the database every time, so a cache is needed. Storage is modest, so no sharding on day one.

3. API

POST /api/v1/urls
  body: { "url": "https://long...", "alias": "my-link" (optional), "expires_at": "2027-01-01" (optional) }
  201 -> { "code": "aZ3kP9q", "short_url": "https://sho.rt/aZ3kP9q" }
  409 -> alias already taken

GET /{code}
  302 -> Location: https://long...        (404 if unknown or expired)

GET /api/v1/urls/{code}/stats
  200 -> { "clicks": 1234, "last_click": "..." }

DELETE /api/v1/urls/{code}
  204

Creating links needs an API key or login in real life, and a rate limiter to stop abuse (next lesson).

4. Data model

One main table:

links
  code        text  PRIMARY KEY      -- the short code, "aZ3kP9q"
  url         text  NOT NULL         -- the long URL
  created_at  timestamptz
  expires_at  timestamptz NULL
  owner_id    uuid  NULL

The only hot query is "find the row where code = X", and the primary key index makes it a fast point lookup (indexes). No joins. SQL or NoSQL? Both work. The access pattern is pure key-value, so a key-value store like DynamoDB or Cassandra fits at huge scale. At our size (about 3 TB in 5 years) PostgreSQL is perfectly fine and gives us a unique constraint for free, which we need for collision handling. Click events go in a separate store (deep dive below).

5. High-level design

Walk the redirect path, matching the numbers in the picture:

  1. The browser asks GET /aZ3kP9q.
  2. A load balancer picks one of several stateless app servers.
  3. The app server checks the cache (Redis) for the code.
  4. On a hit it jumps straight to step 6.
  5. On a miss it reads the database, then writes the answer into the cache with an expiry.
  6. It replies 302 with the long URL in the Location header.
  7. Off to the side, it drops a "click happened" message on a queue. A worker reads the queue and updates analytics. The user never waits for this.

The create path is simpler: app server makes a code, inserts the row, returns the short URL. Since reads outnumber writes 100 to 1, we can scale the two paths separately.

6. Deep dives

Deep dive A: how do we make the short code?

OptionHowProsCons
Hash + collision handlingHash the long URL (MD5/SHA), turn it to base62, keep the first 7 charactersSame URL gives the same code; no central counterDifferent URLs can collide. You must check the database and retry with a salt. Extra read on every create
Base62 of a counterA global counter 1, 2, 3 ... encoded in base62No collisions ever; short codes (6 characters reach 56 billion)A single counter is a bottleneck and a single point of failure; codes are guessable and countable by competitors
Pre-generated key service (KGS)A separate service generates random unused codes in advance and stores them. App servers grab a batch of, say, 1,000 into memoryFast creates, no collisions, no counter hot spot, codes look randomOne more service to run. Keys in a crashed server's batch are lost (fine, we have trillions). The KGS must itself be replicated
Snowflake-style IDA 64-bit ID built from time + machine ID + sequence, then base62Unique across many machines with no coordination64 bits is about 11 base62 characters: not "short". Time-ordered, so guessable

Our pick: random 7-character base62 codes, with the database primary key as the collision guard: generate, try to insert, and if the database says "duplicate key", draw another code. At 0.2% of the key space used, a retry is rare. That is exactly what the build project below does. At higher scale, move to a key generation service so creates need no retry and no extra database round trip. If the interviewer likes counters, the fix for the bottleneck is to hand each app server a block of numbers (say 1,000 at a time) and to scramble the bits so codes are not guessable in order.

Deep dive B: 301 or 302?

A 301 means "moved permanently". Browsers remember it and next time go straight to the long URL without asking us. A 302 means "found, temporarily": the browser asks us every time (see status codes).

301 Permanent302 Temporary
Server loadLower: repeat visitors skip usHigher: every click reaches us
AnalyticsLost for repeat clicksEvery click counted
Changing or expiring a linkHard: browsers cached the old targetEasy: next click gets the new answer

Pick 302 when the business sells analytics, expiry or editable links (most do). Pick 301 for a simple "make this URL shorter" tool where load and search-engine credit matter more. Say the trade-off out loud; that is the answer interviewers want.

Deep dive C: the read-heavy cache

Use cache-aside (caching 1): the app checks Redis first; on a miss it reads the database and fills Redis. Give every entry a TTL (say 1 hour) so memory does not fill with dead links and so a deleted or edited link stops being served within a known time. Evict with LRU when memory is full. Because short codes never change their target, stale data is rarely a problem; for an edited or deleted link, delete the cache key at the same time. Also cache "not found" for a short while (a few seconds) so a bot hammering random codes does not hit the database each time.

Smaller deep dives

  • Expiry: store expires_at. On every read, if the time has passed, return 404 (lazy check). Set the Redis TTL to the smaller of the default and the time left. A nightly cleanup job deletes expired rows in batches; never delete millions of rows in one go.
  • Custom aliases: insert with the alias as the code. The same primary key rule gives a clean 409 Conflict if it is taken. Reject reserved words (api, admin) and bad characters, and limit the length.
  • Click analytics through a queue: do not write a database row per click inside the redirect: 12,000 peak clicks a second would crush the main table. Instead publish an event (code, time, country, device, referrer) to a queue. Workers read in batches and add to an analytics store such as a columnar database, or into hourly counters. If the queue is slow, redirects are unaffected. If an event is lost, a count is off by one, which is acceptable for analytics.

7. Trade-offs, bottlenecks and wrap-up

  • Availability over consistency: a new link may take a moment to be visible on replicas. We accept that.
  • The database is the bottleneck on cache misses. Replicas help, and the cache absorbs most reads.
  • Abuse: attackers create millions of links, or point them at malware. Needs a rate limiter and a URL safety check.
  • Monitor (observability): cache hit rate (aim for 90%+), redirect latency, error rate, queue lag.

At 10x scale (400 million creations a month, 40,000 reads a second): add Redis nodes (shard keys by code with consistent hashing), shard the database by a hash of the code, move to a key generation service, serve hot links from a CDN-like edge cache, and run the app servers in several regions.

B. Variation questions

Try each on paper for 5 minutes before opening the answer.

1. Now support custom aliases. What changes?

The API gets an optional alias field. Insert with the alias as the primary key. The unique constraint turns a clash into 409 Conflict, with no race between "check" and "insert" (see next lesson for why that race matters). Validate the length and characters, block reserved words, and make sure generated codes cannot collide with aliases (the same table and the same primary key do that for free). A cache check before insert is not enough; the database is the source of truth.

2. The same long URL is submitted twice. Should it return the same code?

Depends on the product. If links are anonymous and share no analytics, returning the existing code saves space: hash the URL and keep an index on that hash. If each owner wants separate analytics, expiry or aliases, each creation needs its own code. State the choice. The default most services use is a new code per request.

3. A link goes viral: 50,000 clicks a second on one code. What do you do?

One cache key becomes a hot key. Keep the hot entry also in each app server's memory for a few seconds (a local cache in front of Redis). Or replicate that key across several Redis nodes. A CDN edge can serve it with a short TTL if you use 302 with Cache-Control: max-age=....

    import { randomInt } from "node:crypto";

const ALPHABET =
  "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";

// 7 random base62 characters, for example "aZ3kP9q" (62^7 is about 3.5 trillion)
export function makeCode(length = 7): string {
  let out = "";
  for (let i = 0; i < length; i++) {
    out += ALPHABET[randomInt(ALPHABET.length)];
  }
  return out;
}
  3. File app/api/shorten/route.ts (create a link; a duplicate code makes the database return error 23505, and we try another): 
    import { NextResponse } from "next/server";
import { supabase } from "@/lib/clients";
import { makeCode } from "@/lib/code";

export async function POST(req: Request) {
  let body: { url?: unknown };
  try {
    body = await req.json();
  } catch {
    return NextResponse.json({ error: "Send JSON like {\"url\":\"https://...\"}" }, { status: 400 });
  }

  // Accept only real http or https URLs
  let target: URL;
  try {
    target = new URL(String(body.url));
    if (target.protocol !== "http:" && target.protocol !== "https:") throw new Error("bad scheme");
  } catch {
    return NextResponse.json({ error: "url must be a valid http or https URL" }, { status: 400 });
  }

  // Try a few times: if a random code is already taken, the database says
  // "duplicate key" (error code 23505) and we simply draw another code.
  for (let attempt = 0; attempt < 3; attempt++) {
    const code = makeCode();
    const { error } = await supabase.from("links").insert({ code, url: target.toString() });
    if (!error) {
      const origin = new URL(req.url).origin;
      return NextResponse.json({ code, shortUrl: `${origin}/${code}` }, { status: 201 });
    }
    if (error.code !== "23505") {
      console.error("insert failed", error);
      return NextResponse.json({ error: "Could not save the link" }, { status: 500 });
    }
  }
  return NextResponse.json({ error: "Could not find a free code, try again" }, { status: 503 });
}
  4. File app/[code]/route.ts (the redirect: cache first, then the database): 
    import { NextResponse } from "next/server";
import { redis, supabase } from "@/lib/clients";

const TTL_SECONDS = 60 * 60; // keep a link in the cache for 1 hour

function go(url: string, cache: "HIT" | "MISS") {
  const res = NextResponse.redirect(url, 302);
  res.headers.set("x-cache", cache); // see this with: curl.exe -i
  return res;
}

export async function GET(
  _req: Request,
  { params }: { params: Promise<{ code: string }> }
) {
  const { code } = await params;
  const key = `link:${code}`;

  // 1. Ask the cache first (fast)
  const cached = await redis.get<string>(key);
  if (cached) {
    console.log(`cache HIT  ${code}`);
    return go(cached, "HIT");
  }

  // 2. Miss: ask the database (slower)
  console.log(`cache MISS ${code}`);
  const { data, error } = await supabase
    .from("links")
    .select("url")
    .eq("code", code)
    .maybeSingle();

  if (error) {
    console.error("select failed", error);
    return new NextResponse("Something went wrong", { status: 500 });
  }
  if (!data) {
    return new NextResponse("Short link not found", { status: 404 });
  }

  // 3. Fill the cache for next time, with an expiry (TTL)
  await redis.set(key, data.url, { ex: TTL_SECONDS });
  return go(data.url, "MISS");
}

Quick quiz

Why is a URL shortener "read-heavy", and what does that lead us to add?

People click far more links than they create, roughly 100 to 1. So a cache (Redis) in front of the database serves most redirects, and the read path is scaled separately from the write path.

Compare a base62 counter with a pre-generated key service.

A counter never collides and gives short codes, but one counter is a bottleneck and single point of failure, and codes are guessable. A key service pre-makes random unused codes and hands out batches, so creates are fast and codes look random, at the cost of one more service to run and replicate.

What breaks if you use a 301 redirect and the business wants click counts?

Browsers cache a 301, so repeat visitors skip your server and those clicks are never counted. You also cannot change or expire the link for people who already cached it. Use 302.

What breaks if two app servers both check "is this code free?" and then insert?

Both can see "free" and both insert, so one overwrites the other or two links share a code. The fix is to let the database primary key decide: just insert, and on a duplicate-key error pick another code.

What breaks if the Redis cache has no TTL and the cache goes down for an hour, then returns empty?

Without a TTL, memory fills with dead links over time. When Redis returns empty, all 12,000 reads a second fall on the database at once (a cache stampede), which may overload it. Use TTLs, replicate Redis, and consider a short local cache or request coalescing.

What would you choose for expiry: delete rows on the minute, or check on read? Why?

Check on read, plus a nightly batch cleanup. Deleting rows exactly on time needs a heavy scheduler for little benefit; the read check is cheap and always correct.

Say it in an interview

"It is a read-heavy key-value problem: about 40 writes and 4,000 reads a second. So I would put Redis in front of the database with cache-aside, and the database only needs a primary key on the code."
"For codes I would use random 7-character base62 with the primary key as the collision guard, moving to a key generation service at higher scale. I would redirect with 302 so we can count clicks and expire links."

Common follow-up question: How do you stop two servers generating the same code?

Let the database enforce it: the code is the primary key, so a second insert fails with a duplicate-key error and the server draws another code. With a counter, give each server its own block of numbers. With a key generation service, each key is handed to only one server.

Common follow-up question: How do you count clicks without slowing redirects?

Publish a click event to a queue after deciding the redirect, and let workers update analytics in batches. The redirect never waits for analytics, and a slow worker only delays the numbers.
