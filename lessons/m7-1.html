The very fast, very forgetful writer

Imagine a writer sitting behind a counter. You slide a note under the glass. He reads it, then writes his reply one small piece at a time, each piece based on everything written so far. He is fast and he has read a huge number of books. But he has no memory of you. Every time you come back, you must slide the whole conversation under the glass again.

He also charges by the piece: a few paise for every piece he reads and a bit more for every piece he writes. And his desk is small. If your pile of notes is too big, it does not fit.

That writer is a large language model (LLM). The "pieces" are called tokens, the small desk is the context window, and the bill is the cost per request. An LLM app is a normal app that talks to this writer over the internet.

The moving parts of an LLM app

An LLM is a stateless API, just like the stateless servers in scaling. You send text in, you get text out, and it remembers nothing. Your app supplies the memory, the data and the safety. Providers such as OpenAI, Anthropic, Google Gemini, or open models served by Groq or Hugging Face all work this way.

Tokens

The model does not read letters or words. It reads tokens: chunks of text, often a short word or a piece of a long word. A common rule of thumb for English is about 4 characters, or about three-quarters of a word, per token. So 100 tokens is roughly 75 words. This is only a rule of thumb. Code, numbers and rare words use more tokens. Indian-language text usually needs more tokens for the same meaning, because the tokenizer saw less of it while it was built. That means Hindi, Tamil or Marathi users can cost more and also fill the context window sooner. You will measure this yourself below.

Context window

The context window is the maximum number of tokens the model can look at in one call, input and output together. Your system prompt, the chat history, any documents you paste in, the user's question and the answer being written all share it. Window sizes differ by model and change often, so always read the provider's docs for the model you use. Never design around a number you remember.

Temperature

The model picks the next token from a list of likely options. Temperature controls how adventurous the pick is. Low (near 0): it picks the most likely token, so answers are steadier and repeat more. High: more variety and more surprises. Use low for extraction, classification and code. Use higher for brainstorming. Even at low temperature, do not assume two calls give identical text.

Latency: two numbers, not one

MeasureMeaningWhy you care
Time to first token (TTFT)Wait until the first piece of the answer arrivesThis is when the user feels "it is working"
Total timeWait until the whole answer is doneGrows with the length of the answer

Tokens are produced one after another, so a longer answer takes longer. Example with made-up round numbers: TTFT 0.5 s, then 50 tokens per second. A 300-token answer takes 0.5 + 300 / 50 = 6.5 seconds. If you wait for the full answer, the user stares at a spinner for 6.5 s. If you stream, the first words appear after about 0.5 s and the user starts reading while the rest arrives. Streaming usually uses server-sent events or a similar long-lived connection (compare the options in the APIs lesson). It does not make the model faster, it makes the wait feel shorter.

Cost per request

Providers charge per token, usually a price per million tokens, with output tokens costing more than input tokens. The prices below are invented example numbers. Check the provider's pricing page for real ones.

Example prices (NOT real):  Rs 250 per 1M input tokens,  Rs 1000 per 1M output tokens
One request: 1500 input tokens + 300 output tokens
  input  = 1500 x 250  / 1,000,000 = Rs 0.375
  output =  300 x 1000 / 1,000,000 = Rs 0.300
  total                            = Rs 0.675
100,000 requests a day  = Rs 67,500 a day  = about Rs 20.25 lakh in 30 days

Small per call, large at scale. And chat apps have a trap: because the model has no memory, every turn re-sends the whole history. With the same example prices, a 5-turn chat where each question is 100 tokens and each answer 200 tokens sends 100, 400, 700, 1000 and 1300 input tokens on the five turns, and costs Rs 1.875, not the Rs 1.125 you would guess from "5 small calls". Long chats get expensive turn by turn.

Why an LLM call is not like a database call

Database queryLLM call
Typical timeMillisecondsSeconds
Same input againSame outputMay differ
CostAlmost free per queryPaid per token
FailureRare, clear errorsTimeouts, rate limits (429), overload (5xx), refusals, cut-off answers
OutputExact dataPlausible text that may be wrong

So you design around it: set timeouts, retry with backoff (see idempotency and retries), put long jobs on a queue, and treat the answer as untrusted input. Scaling LLM apps covers these in detail.

Trade-offs: when to use an LLM, when not to

  • Good fit: messy language in or out: summaries, drafting, extraction from free text, question answering over documents, classification with fuzzy rules.
  • Bad fit: exact arithmetic, anything that must be 100% correct and auditable (money, permissions), or anything a plain if, a regex or a SQL query already does cheaply and instantly.
  • Bigger model vs smaller model: bigger usually reasons better but is slower and costs more. Many apps send easy requests to a cheap model and hard ones to a strong one.
  • Long context vs retrieval: pasting everything is simple but pays for every token on every call. Retrieval (RAG) sends only the relevant pieces.

Your app is the brain around the model: it holds the memory (history), the data (retrieval), the rules (system prompt, guardrails) and the bill. The model is one slow, paid, slightly random function call inside it.

Do it yourself (about 25 minutes)

A. See tokens with your own eyes

  1. In Chrome, open a new tab with Ctrl + T and go to platform.openai.com/tokenizer. (OpenAI's tokenizer page. If it asks you to sign in, or is missing or moved, search the web for "LLM tokenizer online" and use any free one. Each tool counts a little differently, which is fine.)
  2. Click the text box and paste this English sentence: Please send my order status on WhatsApp.
  3. Read the token count and character count the page shows. Divide characters by tokens. For English it is usually somewhere around 4.
  4. Clear the box and paste the same meaning in Hindi: कृपया मेरे ऑर्डर की स्थिति व्हाट्सएप पर भेजें।
  5. Compare. For similar meaning, the Hindi text usually has more tokens per character and more tokens overall. Write both numbers on paper. If the page offers a colour view, notice that Hindi words are cut into many small pieces.
  6. Try one more: paste a line of code, such as const total = items.reduce((a, b) => a + b.price, 0);. Write down the count.

B. Do the cost math in the browser Console

  1. Press F12 in Chrome, then click the Console tab.
  2. Click Copy on the block below, click in the Console, press Ctrl + V and then Enter. If Chrome asks you to type "allow pasting" first, type it, press Enter, and paste again. 
    const inPerM = 250;   // example: rupees per 1 million input tokens
const outPerM = 1000; // example: rupees per 1 million output tokens

function costRupees(inputTokens, outputTokens) {
  return (inputTokens * inPerM + outputTokens * outPerM) / 1_000_000;
}

const one = costRupees(1500, 300);
console.log("one request: Rs", one.toFixed(3));
console.log("100,000 requests a day: Rs", Math.round(one * 100000));
console.log("30 days: Rs", Math.round(one * 100000 * 30));

// Chat history: every turn re-sends all earlier turns.
let history = 0, total = 0;
for (let turn = 1; turn <= 5; turn++) {
  const input = history + 100;   // old history + new question (100 tokens)
  const output = 200;            // answer
  total += costRupees(input, output);
  history = input + output;
  console.log("turn", turn, "input tokens", input);
}
console.log("5-turn chat: Rs", total.toFixed(3));

Quick quiz

Why must a chat app send the whole conversation on every turn?

The LLM API is stateless: it remembers nothing between calls. The app stores the history and re-sends it each time, which is also why cost grows turn by turn.

What is the difference between time to first token and total time?

TTFT is the wait until the first piece of the answer arrives. Total time is the wait for the whole answer and grows with its length. Streaming improves how fast the user sees something, not the total time.

A request has 2,000 input tokens and 500 output tokens. With example prices of Rs 200 per million input tokens and Rs 800 per million output tokens, what does it cost?

Input: 2000 x 200 / 1,000,000 = Rs 0.40. Output: 500 x 800 / 1,000,000 = Rs 0.40. Total Rs 0.80.

Why might the same support bot cost more for Hindi users than for English users?

Indian-language text usually needs more tokens for the same meaning, so both input and output bills are higher and the context window fills sooner.

Your feature needs to total an invoice exactly and check a user's permission. LLM or ordinary code? Why?

Ordinary code. Arithmetic and permissions must be exact, fast, cheap and auditable. An LLM is slow, paid, may vary between calls and can be confidently wrong. Use the LLM only for the messy-language parts, for example reading a free-text complaint.

Say it in the interview

An LLM API is stateless and billed per token, so my app owns the memory, the data and the guardrails, and I design for seconds of latency and occasional failures.
I stream responses so the user sees the first token fast, and I track input and output tokens per request because output tokens usually cost more.
I only use an LLM where the input or output is messy language. Exact, cheap, auditable work stays in normal code.

Common follow-up question: "How would you keep LLM costs under control?"

Measure tokens per request first. Then trim the prompt and the history (summarise old turns), cache repeated answers, route easy requests to a cheaper model, cap the output length, and set per-user token budgets. Retrieval instead of pasting whole documents also cuts input tokens. Details are in Scaling LLM apps.
