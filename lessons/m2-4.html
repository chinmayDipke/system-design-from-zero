One chai stall, then many

Rajan runs a chai stall. Business booms and the queue grows. Option one: buy a bigger stove and hire one super-fast helper. That works until the stove cannot get any bigger. Option two: open three more stalls and let customers go to any of them.

The second option has a catch. If Rajan remembers every regular's order in his own head ("Meena likes less sugar"), then Meena must always go back to his stall. The fix is to write regular customers' notes in a shared register that all the stalls can read. Then any stall can serve anyone.

Scale up or scale out

Vertical scaling (scale up)

Give the same machine more power: more CPU, RAM, a faster disk. Easy: no code change. But it has limits: the biggest machine is expensive and finite, upgrading often needs downtime, and it is still one machine: if it dies, everything dies.

Horizontal scaling (scale out)

Add more machines and spread the work. In theory the ceiling is very high, it is usually cheaper (many small machines), and if one dies the others carry on. The cost is complexity: you need something to split the traffic (a load balancer, next lesson), and your servers must be built the right way.

Why stateless servers matter

State is anything a server remembers between requests: who is logged in, what is in your cart, a half-uploaded file. A stateless server keeps nothing about the user between requests; each request carries or looks up everything it needs.

Why it matters: with three servers behind a load balancer, your first request may hit server A and your second hit server B. If your login lived only in A's memory, B says "who are you?" and logs you out. If servers are stateless, any server can handle any request, so adding or removing servers is easy.

Where does the state go?

  • Database: permanent data such as users, orders, carts you want to keep.
  • Shared cache (Redis): fast, temporary data such as sessions, rate-limit counters.
  • Sessions: either a session id in a cookie that points to data stored in Redis or the database, or a JWT (a signed token the client carries, so the server stores nothing). JWT is easy to scale, but you cannot easily revoke one before it expires.
  • Files: uploads go to object storage (a later lesson), never to one server's local disk.

Autoscaling

Autoscaling adds or removes servers automatically based on a signal, such as CPU above 70% or requests per second. You save money at night and survive a sudden spike (a sale, an IPL final). It needs stateless servers and takes a minute or two to start new ones, so a very sharp spike can still hurt; keep some spare capacity.

The database is usually the real bottleneck

App servers are easy to clone because they hold no state. The database holds the truth, so it is hard to clone. When traffic grows, the app tier scales out happily and then all those servers hammer one database. That is why the next lessons are about caching, replication and sharding: ways of taking pressure off the database.

Trade-offs

  • Scale up first if the system is small: it is the cheapest in effort. Scale out for availability and growth.
  • Stateless design costs extra lookups (Redis or database on each request), a small price for flexibility.
  • More machines means more things to monitor, deploy and debug.

In an interview, never just say "we scale horizontally". Say what makes it possible: "the app tier is stateless, sessions are in Redis, and the database is the part we handle with replicas and caching."

B. Spot the state

For each item, decide: can the app server keep it in its own memory or disk safely when there are 3 servers? Write "yes" or "no, move it to ___".

  1. A logged-in user's session. (No: use Redis, the database, or a JWT.)
  2. A profile picture the user just uploaded, saved to the server's /uploads folder. (No: object storage; another server will not have that file.)
  3. A cached copy of the product list that expires in 60 seconds. (Mostly yes, if a stale copy is fine and each server may differ slightly. For exact shared consistency, use Redis.)
  4. The shopping cart of a logged-in user. (No: database or Redis, so it is the same on every server and survives restarts.)
  5. A counter of "requests per minute for this user" used for rate limiting. (No: if each server counts separately, a user gets three times the limit; use Redis.)
  6. The compiled application code and config. (Yes: every server has the same copy; that is how they are deployed.)

Quick quiz

What is the difference between scaling up and scaling out?

Up: a bigger single machine. Out: more machines sharing the load.

Why must servers be stateless to scale out?

Because the load balancer may send any request to any server. If a server keeps user data in its own memory, other servers do not have it and the user's experience breaks.

Where do sessions live in a scaled-out system?

In a shared store such as Redis or the database (session id in a cookie), or inside a signed JWT that the client carries.

Why is the database usually the bottleneck?

App servers are easy to clone but they all depend on the one database, which holds the shared truth and is harder to copy or split.

A startup with 500 users asks whether to build a 10-server cluster. What do you advise?

No. Start with one reasonably sized server (scale up) and a managed database. Keep the code stateless so scaling out is easy later. Do not pay the complexity cost before you need it.

Say it in an interview

"I would keep the app servers stateless, put sessions in Redis, and scale them horizontally behind a load balancer, with autoscaling on CPU or request rate."
"The database is the harder part to scale, so I would add caching and read replicas first, and shard only if I must."

Common follow-up question: When would you scale vertically instead?

When the system is small or the bottleneck is a single stateful component like the primary database. A bigger machine is the quickest fix with no code change. I would still plan for horizontal growth because a single machine is a single point of failure.
