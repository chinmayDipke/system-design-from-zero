Five godowns and a notebook in each

A big grain merchant has five godowns in five towns. Customers say "store this sack under the name Ramesh-42" and later "give me Ramesh-42". Keeping everything in one godown is risky: if it floods, everything is lost, and one godown can only handle so many trucks.

So the merchant decides: every sack is kept in three godowns, picked by a fixed rule based on the name. To store a sack, the clerk phones the three godowns and is happy when two say "done". To read it, he asks two and trusts the newer answer. Why does this work even if one godown has a power cut? Because any two godowns out of three must overlap with the two that stored the sack, so the clerk always meets at least one that knows the latest.

When the sleeping godown wakes up, it is behind. Another godown that wrote a small note, "this sack was for you", hands it over. And from time to time the godowns compare their ledgers to catch anything missed. This lesson is those ideas: spread, copy, agree by counting, and catch up.

Design a distributed key-value store (like DynamoDB or Cassandra)

Before reading on, set a 10-minute timer and write your own requirements and a rough diagram. Then compare. In your own words: if one machine dies, how can the data still be read, and how will the machine catch up when it comes back?

We follow the 7-step framework. This design is built from ideas you already know: consistent hashing, replication and quorum and consistency models. It is also the shape of the "database behind the database" in many other lessons.

1. Requirements

Functional:

  • put(key, value) and get(key), and delete(key). Keys and values are small blobs (up to about 1 MB; our estimate uses 1 KB).
  • Data is spread across many machines and survives machine failures.

Non-functional:

  • Highly available: reads and writes keep working when some nodes fail (favouring the "A" over the "C", see CAP).
  • Scalable: add machines to add capacity, with only a little data moving.
  • Low latency: a few milliseconds per operation.
  • Tunable consistency: the caller chooses between "fast and maybe slightly stale" and "slower but latest" for each request.
  • Eventual consistency by default; no single master that can fail.

Out of scope: multi-key transactions, joins, secondary indexes, range queries across the whole cluster, security, and multi-region replication (we mention it at 10x scale).

2. Estimation

Assume 100 billion items of 1 KB, and a peak of 1 million operations a second, 80% reads and 20% writes. Replication factor N = 3.

  • Unique data: 100,000,000,000 x 1 KB = 100,000,000,000 KB = 100 TB. With 3 copies: 300 TB.
  • Nodes for storage: a node might have 4 TB of disk, but we should keep a disk less than about half full so there is room for compaction (explained below). So 2 TB usable: 300 / 2 = 150 nodes.
  • Operations: reads 800,000 a second and writes 200,000 a second. Each write goes to 3 replicas: 600,000 replica writes a second. Each read asks 2 replicas (R = 2): 1,600,000 replica reads a second. Total 2,200,000 / 150 nodes = about 14,700 operations a second per node. A modern node with SSDs handles this, so the cluster is sized by storage, not by operations.
  • Write bandwidth in: 200,000 x 1 KB = 200 MB a second from clients, and 600 MB a second between nodes after replication.

Conclusion: roughly 150 nodes, and a node failing should be normal, not an emergency: with 150 machines, some machine is always down for some reason.

3. API

PUT    /kv/{key}   body: value      Consistency: QUORUM
  200 -> { "version": "v17" }

GET    /kv/{key}                       Consistency: ONE | QUORUM | ALL
  200 -> { "value": "...", "version": "v17" }
  404 -> not found

DELETE /kv/{key}
  200 -> ok   (stored as a "tombstone" marker, see below)

The Consistency option is the tunable part: it says how many replicas must answer.

4. Data model

key       -> bytes (hashed to a position on the ring)
value     -> bytes, plus metadata: timestamp (or vector clock), tombstone flag

On each node:
  commit log    append-only file, on disk
  memtable      sorted structure, in memory
  SSTables      immutable sorted files on disk, each with an index and a Bloom filter

Why not SQL: we want simple key lookups at huge scale with no single point of failure. We give up joins and multi-row transactions to get easy scaling and always-on writes (see SQL versus NoSQL).

5. High-level design

Numbers match the picture. Every node can do every job; there is no special master.

  1. A client sends a request to any node. That node becomes the coordinator for this request.
  2. The coordinator hashes the key to find its position on the ring. The node that owns that position and the next two nodes clockwise are the 3 replicas. It sends the write (or read) to all three and waits for W (or R) answers.
  3. On each replica, a write is appended to the commit log, then applied to the memtable; later the memtable is flushed to an SSTable on disk.

6. Deep dives

Deep dive A: partitioning and replication

Put the machines on a hash ring (see consistent hashing). Hash each key to a point on the ring; the first node clockwise owns it. For replication factor N = 3, the next two nodes clockwise also store a copy. This list is the key's preference list. Adding a node takes a slice from its neighbours only; removing one hands its slice to its neighbours. To spread load more evenly, each physical machine takes many small slices of the ring (virtual nodes), so a new or recovering node can fetch data from many peers at once, and a bigger machine can take more slices.

ChoiceMeaningTrade-off
N (replication factor)Copies of each itemHigher N survives more failures but costs storage and write work. N = 3 is the common default
W (write quorum)Replicas that must acknowledge a writeHigher W means safer but slower writes, and a write fails if too many replicas are down
R (read quorum)Replicas that must answer a readHigher R means fresher reads but slower, and reads fail if too many are down

Deep dive B: quorums, tunable consistency and conflicts

The rule from consistency models: if R + W > N, any read set and any write set share at least one node, so a read always meets a replica that saw the latest acknowledged write. With N = 3, W = 2, R = 2 we get 4 > 3, which is the usual setting.

N, W, RBehaviourUse for
3, 1, 1Fastest. A read may be stale (R + W = 2, not above 3). Writes survive 2 dead nodesCounters, session data, "likes", anything that can be a little old
3, 2, 2Strong enough. Tolerates 1 dead node for both reads and writesThe default for most data
3, 3, 1Fast reads, but one dead node blocks writesRead-mostly, rarely written data
3, 1, 3Fast writes, but one dead node blocks readsWrite-heavy logs that are rarely read

Conflicts. If two clients write the same key at nearly the same time on different coordinators, replicas may hold different values. We have to decide which one wins:

ApproachHowProsCons
Last-write-wins (LWW)Every write has a timestamp; the highest timestamp winsSimple; no work for the clientClocks on different machines are not perfectly equal, so a genuinely newer write can lose; the losing write is silently dropped
Vector clocksEach value carries a small list of counters, one per node that updated it. Comparing two lists tells whether one is a descendant of the other (newer) or whether they are concurrent (neither saw the other)Detects real conflicts; nothing is lost silentlyThe client must merge concurrent versions (for example, a shopping cart merged by union); lists grow and need pruning; more complex

Pick: LWW for most data (simple and good enough when overwrites are rare or the last value really is the right one); vector clocks (or application-level merge) where silently losing a write would hurt, such as a shopping cart. Deletes are written as a tombstone (a marker that says "deleted at time T") rather than removing the data, so that replicas that missed the delete do not bring the value back. Tombstones are cleaned out after a safe period.

Deep dive C: failures: gossip, hinted handoff and anti-entropy

  • Gossip for membership and failure detection. There is no central list of who is alive. Every second, each node picks a random peer and they swap what they know: "node C: heartbeat counter 4021". Information spreads through the cluster like a rumour, reaching everyone in a few rounds. If a node's counter has not increased for a while, others suspect it is down (a smarter detector gives a suspicion score from how late the heartbeats are, instead of a fixed timeout). Gossip also spreads news of nodes joining or leaving, so every node learns the ring layout.
  • Hinted handoff. If a replica is down during a write, the coordinator keeps a hint: "this write is for C". It stores the hint for a limited time. When gossip says C is back, the coordinator hands the write over. So a short outage heals itself quickly. Hints are best effort; they may be lost or expire.
  • Read repair. When a read finds that replicas disagree, the coordinator returns the newest value and writes it to the stale replica in the background.
  • Anti-entropy with Merkle trees. For everything else (a long outage, lost hints), replicas periodically compare their data. Comparing every key would be huge, so each replica builds a Merkle tree: a tree of hashes where each leaf is the hash of a small range of keys and each parent is a hash of its children. Two replicas compare their root hashes; if the roots match, they are identical and nothing more is done. If not, they go down only the branches whose hashes differ, find the exact ranges that differ, and copy just those keys. This is idea level; you do not need the algorithm details.

Deep dive D: the write path and compaction

Each node stores data using a design called a log-structured merge tree (LSM). It turns random writes into sequential ones, which is fast on any disk.

  1. Commit log: append the write to a log file on disk. Appending is fast and gives durability: after a crash, replay the log.
  2. Memtable: insert into a sorted in-memory structure. Reads check here first. The write is now acknowledged to the coordinator.
  3. Flush to SSTable: when the memtable is full (say 100 MB), write it out as a sorted, immutable file called an SSTable (sorted string table), and start a new memtable. The commit log part for it can then be dropped.
  4. Reads check the memtable and then SSTables from newest to oldest. To avoid opening every file, each SSTable has a Bloom filter (the same idea as in the crawler lesson) that says "this key is definitely not here", and an index.
  5. Compaction: over time, many SSTables pile up. A background job merges several into one bigger sorted file, keeping only the newest value of each key and dropping tombstones that are old enough. This keeps reads fast, and it needs free disk space while it runs (the reason we keep disks under half full).

7. Trade-offs, bottlenecks and wrap-up

  • Availability against consistency: this design chooses to keep answering during failures, and to repair differences afterward (see CAP and PACELC). If you need strict, transaction-like consistency, use a different system.
  • Latency against freshness: lower R and W mean faster operations but possibly stale reads. The caller decides per request.
  • Write speed against read cost: LSM storage makes writes very fast but reads may check several files (Bloom filters and compaction reduce this). A B-tree database reads faster per key but writes slower.
  • Hot keys: one popular key lands on the same 3 nodes. Cache it in front, or split it across several keys.
  • Bottlenecks: compaction using disk and CPU, repair traffic after an outage, and uneven data per node (virtual nodes help).
  • Monitor (observability): read and write latency p99 per node, hinted-handoff backlog, compaction backlog, number of SSTables per read, nodes marked down, disk usage.

At 10x scale: more nodes with more virtual nodes, racks and zones considered when choosing the 3 replicas (never all 3 in one rack), replication across regions with a "local quorum" so that most operations stay in one region, and rate limiting on repairs so that recovery does not hurt live traffic.

B. Paper simulation: five nodes, one failure (20 minutes)

You need a piece of paper (or an Excalidraw canvas) and a pen. Nothing to install. Settings: N = 3, W = 2, R = 2.

  1. Draw the ring. Draw a big circle. Mark five nodes on it, going clockwise, and write their ring positions (the ring has positions 0 to 99): A = 10, B = 30, C = 50, D = 70, E = 90. A key belongs to the first node at or after its position, going clockwise, and the next two nodes also hold copies.
  2. Place a key. The key k1 hashes to position 25. Going clockwise from 25 the first node is B (30). So the owner is B, and the copies go to the next two nodes: C (50) and D (70). The replicas of k1 are B, C, D. Write that down. Now find the replicas of a second key k2 that hashes to position 95 (hint: after 95 the ring wraps around past 99 to 0).
    Show answer

    Going clockwise from 95 the first node is A (at 10), then B (30), then C (50). So the replicas of k2 are A, B, C. The wrap-around is the point of a ring: E at 90 is before 95, so it is skipped.

  3. Start state. Make a small table with one row per replica of k1: 
    node   value   timestamp
B      v1      5
C      v1      5
D      v1      5
    All three agree on k1 = v1.
  4. C fails. Put a big cross on node C. It has crashed and cannot answer.
  5. A client writes k1 = v2 at time 10. It happens to contact node B, so B is the coordinator. B sends the write to B (itself), C and D.
    • B writes locally and acknowledges: that is 1 ack.
    • D writes and acknowledges: that is 2 acks.
    • C does not answer.
    W = 2 and we have 2 acks, so B tells the client success without waiting for C. Update your table: B = v2 (ts 10), D = v2 (ts 10), C still v1 (ts 5, and it is down). B also writes a hint: "for C: k1 = v2, ts 10".
  6. Read while C is still down (R = 2). Another client reads k1 through some coordinator. It asks the replicas and needs 2 answers. Only B and D can answer. Both return v2 (ts 10). The coordinator returns v2. Correct and fresh, even though one node is down.
  7. C comes back before the hint is delivered (it is stale). Now a read asks C and D. C answers v1 (ts 5), D answers v2 (ts 10). The coordinator compares timestamps, returns v2 (the newer one), and in the background repairs C by writing v2 to it (this is read repair). Cross out C's v1 and write v2 (ts 10).
  8. Check the overlap rule. The write was acknowledged by {B, D}. List every possible pair of replicas a read could ask: {B, C}, {B, D}, {C, D}. Which pairs contain a node that has v2?
    Show answer

    {B, C} contains B (v2). {B, D} contains both. {C, D} contains D (v2). Every pair contains at least one node with the latest value, which is exactly what R + W > N means: 2 + 2 = 4, which is more than 3. The coordinator picks the highest timestamp and so always returns v2.

  9. Without the read repair, the hint. Suppose instead C came back and nobody read k1. Node B, learning from gossip that C is up, delivers the hint, and C is updated to v2. Nobody had to do anything. Write "hinted handoff" next to this step.
  10. What if the hint is lost? Suppose B also crashed before delivering the hint, and C stayed stale (v1). Nobody reads the key for a week. Replicas of this key range (C and D) run their regular comparison with Merkle trees. Their root hashes differ, so they compare child hashes, narrow down to the small range that contains k1, and copy the newer value. Write "anti-entropy (Merkle tree)" next to this step.
  11. Two nodes down. Now cross out both C and D, and write k1 = v3 at time 20 through coordinator B. How many acks can B collect? Only B's own: 1 ack. W = 2, so the write fails (the client gets an error or a timeout) and should retry later. B may hold the value locally but the system does not promise it. This is the price of choosing W = 2: it tolerates one failure, not two.
    What changes with W = 1?

    B alone gives 1 ack, so the write succeeds, even with C and D down. But now R + W = 2 + 1 = 3, which is not greater than N = 3. A later read of C and D (once they are back) can return the older v2 or v1. This is the "fast but maybe stale" setting.

  12. Finally write three sentences in your own words: why W = 2 and R = 2 stay correct with one failure; what hinted handoff does; what a Merkle tree is for.

C. Variation questions

1. Two clients write k1 at almost the same time through coordinators B and D, with different values. What happens?

Each replica stores whichever write it saw, so replicas may disagree for a moment. With last-write-wins, the write with the higher timestamp wins everywhere after repair, and the other is silently lost. With vector clocks, the system sees that neither write knew about the other, keeps both as siblings, and returns both on the next read, so the application can merge them.

2. You add a sixth node F at ring position 60. What data moves?

Keys that hash between 50 and 60 now belong first to F (before, D owned them). F also becomes the second or third copy holder for the two ranges just before it (10 to 30 and 30 to 50), because it is now among the next nodes clockwise. So F receives three ranges of data, about one sixth of all stored copies, and the nodes that held those copies before (D, E and A for some ranges) drop them afterwards. Nothing else moves, which is the benefit of consistent hashing. With virtual nodes F fetches from many peers at once.

3. Reads are slow because each key is in 12 SSTable files. What do you do?

Run (or tune) compaction so files are merged into fewer, larger ones. Make sure each SSTable has a Bloom filter so that most files are skipped, and cache hot keys in memory. If it keeps happening, the write rate may exceed compaction speed, so add nodes or give compaction more disk speed.

Quick quiz

What do N, W and R mean, and what rule makes a read see the latest write?

N is the number of copies, W the number of replicas that must acknowledge a write, R the number that must answer a read. If R + W > N, every read set overlaps every write set, so a read meets at least one replica with the latest write.

What breaks if you set W = 1 and R = 1 with N = 3, and why might you still choose it?

A read can hit a replica that has not yet received the last write, so it returns stale data (1 + 1 is not more than 3). You may choose it for data where being slightly old is fine, such as view counters, because it is the fastest and survives the most failures.

What breaks if a node is down for a day and you rely only on hinted handoff?

Hints are kept only for a limited time and can be lost, so the node may stay stale. Anti-entropy with Merkle trees (and read repair) finds and fixes what remains.

Why is a delete stored as a tombstone and not by removing the data?

If a replica missed the delete and the data is simply gone elsewhere, repair would copy the old value back and the deleted item would reappear. The tombstone is a newer record that says "deleted", so it wins during repair, and it is cleaned up later after a safe time.

Why are writes fast in an LSM-tree design, and what is the cost?

A write is one sequential append to the commit log plus an insert into memory, with no random disk seeks. The cost is that reads may check several SSTables, and background compaction uses disk and CPU.

Would you choose last-write-wins or vector clocks for a shopping cart? Why?

Vector clocks (or an application merge). With last-write-wins, two devices adding different items at the same time could lose one of them. Detecting the concurrency and merging the two carts keeps both items.

Say it in an interview

"I would partition with consistent hashing and virtual nodes, and replicate each key to the next N = 3 nodes on the ring. With W = 2 and R = 2, reads and writes overlap, so we get strong-enough consistency and tolerate one node failure."
"Failures are handled without a master: gossip detects dead nodes, hinted handoff replays missed writes, read repair fixes stale replicas, and Merkle-tree anti-entropy repairs the rest. Each node writes to a commit log and memtable, flushes SSTables, and compacts in the background."

Common follow-up question: How do you handle conflicting writes?

Last-write-wins by timestamp is the simple default but can lose a write when clocks differ. Where loss is unacceptable, use vector clocks to detect concurrent versions and let the application merge them, as in a shopping cart.

Common follow-up question: Why not use one big SQL database?

A single primary becomes both a scale limit and a failure point. A key-value store scales out by key, stays available when nodes fail and is simpler per operation, at the price of giving up joins, multi-row transactions and strong consistency by default.
