The warehouse and the neighbourhood shops

A company makes notebooks in one big warehouse in Delhi. If every customer in India had to order from that warehouse, delivery to Chennai would take days. So the company places a few notebooks in a local shop in every big city. The first customer in Chennai waits for the shop to fetch stock from Delhi. After that, everyone in Chennai buys from the nearby shop in minutes.

That local shop is a CDN edge. Inside the warehouse, the packer also keeps today's most-asked items on a table right next to the door instead of walking to the back shelves each time. That table is Redis: a very fast memory shelf for the things you need all the time.

CDN and Redis

CDN: a cache spread around the world

A CDN (content delivery network) is many servers in many cities, called edge locations. They keep copies of your files, so a user is served from a nearby edge rather than from your faraway origin server. This cuts the round-trip time you saw in Module 1 and takes load off the origin. Examples: Cloudflare, Amazon CloudFront, Akamai, Vercel's network.

  • Pull CDN: the edge fetches a file from your origin the first time someone asks (a miss), then keeps it for next time. Easy: you change nothing. Most common.
  • Push CDN: you upload files to the CDN ahead of time. More control, and good for rarely changing big files, but you must manage the uploads.
  • Cache key: what the CDN uses to decide "is this the same request?". Usually the URL, sometimes plus chosen headers or query strings. /logo.png?v=2 and /logo.png?v=3 are different keys, which is a neat trick to force fresh files.
  • Purge (invalidate): tell the CDN to drop a file now, when you cannot wait for its TTL. Powerful but slow across the globe and sometimes costs money. Better: put a version or hash in file names (app.3f9a2.js) so a new file is a new key and no purge is needed.

CDNs are great for static files (images, CSS, JS, video) and increasingly for whole pages. They are a poor fit for data that is personal or changes every second.

Redis: the in-memory shelf

Redis is an in-memory key-value store: a giant dictionary that lives in RAM. It is not just strings; its values can be rich data types:

TypeWhat it isUse it for
StringText or numberCached values, counters
HashA small object of fields and valuesA user profile
ListOrdered items, add at either endRecent activity, simple queues
SetUnique items, no orderTags, unique visitors
Sorted setUnique items, each with a score, kept in orderLeaderboards, rankings

Why it is fast: data sits in RAM (not on disk), operations are simple, and the structures are built for speed. One Redis can handle very large numbers of operations per second, with answers in well under a millisecond on the same network.

Persistence in one line: Redis can save snapshots or a write log to disk so data survives a restart, but treat it as a cache first, not your main database.

When to use, when not to

Use Redis forDo not use it for
Caches, sessions, counters, rate limits, leaderboards, short queuesThe only copy of important data, large datasets that exceed RAM, complex queries and joins
  • Trade-off: RAM is fast but costly and limited, so you cache only hot data and set TTLs.
  • Trade-off: a separate cache server adds a network hop (tiny compared with a database query) and one more thing to keep running.
  • Trade-off: cached data can be stale. Plan invalidation, as the last lesson said.

Redis is not only a cache. Its counters, sorted sets and expiry make it the standard tool for rate limiting and leaderboards too (you will use it for rate limiting soon).

Do it yourself (about 30 minutes)

A. Create a free Redis database on Upstash

  1. Open console.upstash.com and log in.
  2. Find the Redis section (a tab or a menu item named Redis) and click Create Database.
  3. In Name, type sysdesign-practice.
  4. For the region (it may be called Primary Region), pick one near India if offered, for example Mumbai (ap-south-1) or else Singapore. Near means faster, as in Module 1.
  5. Choose the Free plan. Leave other options as they are, then click Create.
  6. After a few seconds the database page opens. Look for a tab named CLI and click it. (If your console shows a Data Browser with a command box instead, that works too. Labels may differ a little.) You will see a text box where you type commands, and results appear below.

B. Strings, expiry and counters

Type each command in the CLI box and press Enter. After each, compare with what you should see.

  1. SET greeting "hello" shows OK.
  2. GET greeting shows "hello".
  3. EXPIRE greeting 60 shows 1 (it worked: the key will vanish after 60 seconds).
  4. TTL greeting shows the seconds left, for example 57. (-1 means no expiry; -2 means the key does not exist.)
  5. Set a value with an expiry in one go: SET session:42 "asha" EX 30, then TTL session:42.
  6. Wait 30 seconds and run GET session:42. It shows (nil) (or an empty value): the key expired by itself. That is TTL, from the last lesson.
  7. Counters: INCR visits shows 1. Run it three more times: 2, 3, 4. INCR creates the key at 0 if needed and is safe even when many clients call it at once.
  8. Remove a key: DEL greeting shows 1; GET greeting shows (nil).

C. Hash, list, sorted set

  1. A hash (a small object): HSET user:1 name Asha city Pune, then HGETALL user:1. You see the fields and values: name, Asha, city, Pune.
  2. A list (recent items): run these three one at a time: LPUSH recent "page-a", LPUSH recent "page-b", LPUSH recent "page-c". Then LRANGE recent 0 -1. You see them with the newest first: page-c, page-b, page-a. (0 -1 means "from the first to the last".)
  3. A sorted set (a leaderboard): ZADD leaderboard 100 asha 250 ravi 175 meera shows 3 (three members added).
  4. ZRANGE leaderboard 0 -1 WITHSCORES lists lowest score first: asha 100, meera 175, ravi 250.
  5. For top scores first, run ZRANGE leaderboard 0 -1 REV WITHSCORES. (If your console complains about REV, use ZREVRANGE leaderboard 0 -1 WITHSCORES instead.) Ravi is first. Redis keeps the order for you; no sorting code needed.
  6. Update a score: ZINCRBY leaderboard 100 asha, then list again. Asha is now 200 and moves up.

D. A cache-aside walkthrough, in commands

Pretend the "database" is a slow place that holds the product named "Laptop" with id 7. You play the app.

  1. Check the cache first: GET product:7 shows (nil). That is a miss.
  2. On a miss, the app reads the database (imagine it takes 80 ms) and gets Laptop, Rs 52000.
  3. The app saves it in the cache with a 60-second TTL: SET product:7 "Laptop,52000" EX 60.
  4. The next request: GET product:7 shows "Laptop,52000". That is a hit, no database needed.
  5. Look at how long the copy has left: TTL product:7.
  6. The price changes in the database. To stay fresh, the app deletes the cached copy: DEL product:7. The next GET misses and reloads the new value. That is invalidation.
  7. Write in your notes: which command did each of these jobs: look up, store with expiry, invalidate. (GET, SET ... EX, DEL.)

E. Clean up

  1. Delete the practice keys: DEL visits user:1 recent leaderboard product:7. Or just leave the database for the rate-limiting lesson, which uses it again.

Quick quiz

What is the difference between a pull CDN and a push CDN?

Pull: the edge fetches from your origin on the first request and then caches it. Push: you upload files to the CDN ahead of time.

How can you update a file on a CDN without purging it?

Put a version or content hash in the file name or URL (like app.3f9a2.js or ?v=3), so the new file has a new cache key.

Why is Redis fast?

It keeps data in RAM, and its operations and data structures are simple and built for speed. No disk read is needed for most requests.

Which Redis type would you use for a leaderboard, and which command adds a player?

A sorted set; ZADD leaderboard score name.

Your cached product page shows an old price after an update. What would you change?

Delete (or update) the cache key whenever the product is written, and keep a TTL as a safety net. Optionally lower the TTL for price data.

Say it in an interview

"Static files go through a CDN so users are served from a nearby edge, with versioned file names to avoid purges."
"For dynamic data I use Redis with cache-aside and a TTL. Sorted sets give leaderboards and INCR gives atomic counters."

Common follow-up question: What happens if Redis goes down?

The app should fall back to the database, slower but correct. Then the database must survive the extra load, so I would protect it with a connection limit, and run Redis with a replica so it fails over quickly.
