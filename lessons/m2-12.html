The Tatkal counter and the one-sweet rule

At a railway reservation counter, one person cannot book 50 tickets in a row while 100 others wait. The clerk says: "Four tickets per person, then go to the back of the line." Everyone gets a fair turn, and the clerk does not collapse.

At a wedding buffet, the caterer tells the kids: "One sweet each for now. Come back in ten minutes for more." Nobody is starved, and the sweets do not run out in the first five minutes.

A rate limiter is that clerk. It says "you may make this many requests in this much time", and politely refuses the extra ones.

Saying "slow down" to clients

Why limit

  • Abuse: stop bots that guess passwords or scrape your whole site; blunt simple denial-of-service floods.
  • Fairness: one heavy user should not slow everyone else.
  • Cost and safety: each call may cost money (an AI model, an SMS) or load (a database). A limit protects both.

The algorithms

AlgorithmHow it worksProsCons

Where to put it

  • At the gateway or edge (API gateway, reverse proxy, CDN): cheap to enforce, protects everything behind it, one place for rules. Best for blunt per-IP or per-API-key limits.
  • In the app: when the rule needs business knowledge, such as "5 password attempts per account per hour" or "free users get 10 AI requests a day".
  • Often both: coarse at the edge, specific in the app.

What the client sees: 429 and Retry-After

When blocked, reply 429 Too Many Requests. Add a Retry-After header saying how many seconds to wait, and many APIs also send headers showing the limit and what remains. A good client backs off and retries after that time instead of hammering.

Distributed counters in Redis

With many app servers, a per-server counter is wrong: three servers would each allow the full limit. The counter must be shared, and Redis is the usual place, because it is fast and INCR is atomic (two servers incrementing at the same moment never lose a count). A fixed-window limiter is just two commands: INCR a key that includes the window, and EXPIRE it so old windows clean themselves up. For more exact algorithms people use small Lua scripts so check-and-update happens in one step.

Trade-offs

  • Strict vs smooth: fixed window is simplest but bursty at the edges; token bucket is friendlier to real traffic.
  • Extra hop: each request now needs a Redis call. Keep it fast, and decide what happens if Redis is down: fail open (allow, risking abuse) or fail closed (block, risking an outage).
  • Who is "a user": IP addresses are shared (offices, mobile networks) and easy to change; an API key or account id is fairer.

Always name the key you limit on (user id, API key, IP), the limit (for example 100 per minute), and the response (429 with Retry-After).

Do it yourself (about 20 minutes)

You will act as a rate limiter that allows 5 requests per minute for user1, using the Upstash Redis database from the CDN and Redis lesson. (If you do not have one, create it with the steps in that lesson first.)

A. Open the CLI

  1. Open console.upstash.com, click your Redis database, and open its CLI tab (or the command box in the Data Browser).
  2. Look at the clock on your screen and note the current time as hours and minutes. We use it in the key so each minute gets its own counter. For example, if it is 10:15, the key is rl:user1:1015. Use your own number in all commands below.

B. Count requests

  1. Request 1 arrives. Type INCR rl:user1:1015. The result is 1.
  2. This is the first request of the window, so set the key to expire after 60 seconds: EXPIRE rl:user1:1015 60. The result is 1. (Normally you set the expiry only when INCR returns 1.)
  3. Request 2: INCR rl:user1:1015 gives 2. Do not set EXPIRE again.
  4. Do the same for requests 3, 4 and 5. You get 3, 4, 5. The rule is "allow if the number is 5 or less", so all five were allowed.
  5. Request 6: INCR rl:user1:1015 gives 6. That is over the limit, so the limiter would answer 429 Too Many Requests. Try a 7th: 7, blocked again.
  6. Check how long the block lasts: TTL rl:user1:1015. It shows the seconds left, for example 31. That is your Retry-After.

C. Watch it reset

  1. Wait until the TTL reaches 0 (re-run TTL rl:user1:1015 now and then). When the key expires, TTL returns -2 (no such key).
  2. Run GET rl:user1:1015. The result is (nil): the counter vanished by itself.
  3. Run INCR rl:user1:1015 again. It is back to 1, and the user is allowed again. The window has reset.

A real limiter puts the minute in the key automatically. That is why we typed the time into the key: a new minute means a new key and a fresh counter, and the old one disappears through EXPIRE.

D. Find the weakness

  1. Imagine the window changes at 10:16:00. A user sends 5 requests at 10:15:59 and 5 more at 10:16:00. Is each window within its limit? (Yes, 5 and 5.) How many requests arrived in those 2 seconds? (10, twice the limit.) This is the fixed window edge burst.
  2. Write which algorithm from the table fixes it (sliding window counter, sliding window log or token bucket) and its price (more memory or more logic).
  3. Think: what if the app crashed right after INCR and before EXPIRE? (The key would never expire, and the user would be blocked forever. Real code does both steps in one atomic step, for example with a small script, or checks that the TTL is set.)

E. Clean up

  1. Delete the test key: DEL rl:user1:1015.

Quick quiz

Give two reasons to rate limit.

Protect against abuse and bots, ensure fairness between users, and control cost or load on expensive resources.

What is the weakness of the fixed window algorithm?

A burst at the boundary of two windows can let through up to twice the limit within a short time.

How does token bucket differ from leaky bucket?

Token bucket allows bursts up to the bucket size while keeping an average rate. Leaky bucket releases requests at a constant steady rate, smoothing bursts, and drops overflow.

What should the server return when a client is limited?

429 Too Many Requests, with a Retry-After header telling how long to wait.

Why do you need Redis for rate limiting with several app servers?

The counter must be shared. Per-server counters would each allow the full limit. Redis is fast and INCR is atomic.

Where would you enforce "100 requests per minute per IP", and where "5 password attempts per account"?

The IP limit at the gateway or edge (cheap, blunt, protects everything). The password limit in the app, because it needs account knowledge.

Say it in an interview

"I would rate limit per API key at the gateway with a token bucket kept in Redis, and return 429 with Retry-After."
"For sensitive actions like login I add a stricter, per-account limit inside the app."

Common follow-up question: What if Redis is down?

Decide per endpoint. For abuse-prone ones such as login, fail closed (block) or fall back to a small local limit. For normal reads, fail open so users are not locked out. Either way, alert on it, and run Redis with a replica.
