The newspaper boy and the celebrity

In a colony, a newspaper boy delivers a morning paper to each flat. Now imagine every neighbour writes a tiny letter each day, and every flat wants the letters of just their own friends, newest on top. There are two ways to do it.

Way 1 (deliver in advance): the moment a neighbour writes a letter, a helper runs and slips a copy into the box of every friend. When you wake up, your box is already full and sorted. Reading is instant, but writing makes lots of running around.

Way 2 (collect when asked): letters stay with the writer. When you want your news, a helper goes to each of your friends and collects their latest letters. Writing is easy, but reading is slow if you have 500 friends.

Now one neighbour is a film star with 10 million fans. With Way 1, one letter means 10 million slips. So for the star we switch: fans collect the star's letters when they ask. A news feed uses both ways at once. That is the whole lesson.

Design a news feed (like Instagram or Twitter)

Before reading on, set a 10-minute timer and write your own requirements and a rough diagram. Then compare. Decide in your own words: when someone posts, do you do the work now or when a follower opens the app?

We follow the 7-step framework. This design uses caching, queues, sharding and object storage with a CDN.

1. Requirements

Functional:

  • A user can create a post (text and images or video).
  • A user can follow and unfollow other users.
  • The home feed shows recent posts from people you follow, newest (or most relevant) first, with infinite scroll.
  • Posts show their images quickly.

Non-functional:

  • Feed loads fast (under about 200 ms for the first page). It is the main screen.
  • Very read-heavy: far more people read the feed than post.
  • Highly available. Eventual consistency is fine: a new post may show up for followers a few seconds late (consistency).
  • Must cope with celebrities who have millions of followers.

Out of scope: likes and comments, search, ads, stories, direct messages, and the machine-learning details of ranking.

2. Estimation

Assume 200 million daily active users. Each opens the feed 10 times a day. 10% of users post once a day. Average followers: 200.

  • Feed reads: 200,000,000 x 10 = 2,000,000,000 a day, divided by 100,000 s = 20,000 a second. Peak at 3x: 60,000 a second.
  • Posts: 200,000,000 x 10% = 20,000,000 a day, divided by 100,000 s = 200 a second; peak about 600.
  • Fan-out writes (if we push to every follower): 20,000,000 x 200 = 4,000,000,000 feed inserts a day, which is 40,000 a second. Large, but each is a tiny write.
  • The celebrity: one post by a user with 10 million followers would need 10,000,000 writes at once. At 40,000 a second that is over four minutes of the whole system's write capacity for one post. This is why pure push fails.
  • Feed cache size: keep the latest 500 post ids per user. An entry (id plus score) is about 16 bytes, so 500 x 16 B = 8 KB per user. 200,000,000 x 8 KB = 1.6 TB of memory across a Redis cluster (for example 25 machines with 64 GB each). We only keep feeds for active users.
  • Storage: 20,000,000 posts a day x 1 KB of text and metadata = 20 GB a day, about 7 TB a year. Media: if half the posts have a 2 MB image, that is 10,000,000 x 2 MB = 20 TB a day, in object storage and CDN.

Conclusion: reads dominate, so precompute the feed and keep it in memory; but protect the write path from celebrities.

3. API

POST /posts                 { "text": "...", "media_ids": ["m1"] }
  201 -> { "post_id": "p_8841", "created_at": "..." }

POST /users/{id}/follow     DELETE /users/{id}/follow

GET  /feed?limit=20&cursor=p_8790
  200 -> { "posts": [ ... 20 posts ... ], "next_cursor": "p_8741" }

GET  /users/{id}/posts?limit=20&cursor=...     (a profile page)
POST /media/upload-url      -> pre-signed URL for uploading an image

The feed uses a cursor, not "page 2" (see deep dive B).

4. Data model

users    (user_id, name, ...)
follows  (follower_id, followee_id, created_at)     PK (follower_id, followee_id)
                                                    INDEX (followee_id)  -- "who follows X?"
posts    (post_id, author_id, text, media_keys, created_at)
                                                    INDEX (author_id, post_id DESC)
Redis    feed:{user_id}  = sorted set of post_id, score = post time / id

Post ids should be time-sortable (Snowflake-style ids from the URL shortener lesson), so sorting by id is sorting by time. Why these stores: users and follows are relational, but at hundreds of millions of rows they are sharded by user id (sharding). Posts are append-mostly and read by author, so they shard by author_id. The precomputed feed is a cache, and losing it is fine because it can be rebuilt from follows and posts. We want the follow index in both directions: "who do I follow?" (reading) and "who follows me?" (fan-out).

5. High-level design

Write path (creating a post):

  1. The client posts text and the keys of images already uploaded to object storage.
  2. The post service saves the post in the posts database.
  3. It publishes a "post created" event to a queue.
  4. Fan-out workers read the event and ask the follow database for the author's followers.
  5. They add the post id to each follower's feed in Redis (skipping celebrities, see below).

Read path (opening the feed):

  1. The app calls GET /feed.
  2. The feed service reads the user's list of post ids from Redis.
  3. It adds the latest posts of any celebrities the user follows (pulled live), and fetches the post details and author names for all ids (from a post cache, then the database).
  4. It ranks, trims to 20 posts, and returns them with a next_cursor. Images load from the CDN by URL.

The two paths are separate on purpose. The write path may take a few seconds and nobody waits for it; the read path must be fast.

6. Deep dives

Deep dive A: fan-out on write, on read, or both

ApproachOn a postOn opening the feedProsCons
Fan-out on write (push)Copy the post id into every follower's feedJust read your listVery fast reads; simple read pathCelebrity posts cause millions of writes; wasted work for followers who never log in
Fan-out on read (pull)Only save the postFetch recent posts from everyone you follow and mergeCheap writes; no wasted workSlow reads (500 lookups per feed); heavy load at 60,000 reads a second
HybridPush for normal users; skip celebritiesRead your pushed list and merge in the recent posts of celebrities you followFast reads and bounded write costTwo code paths; needs a rule for "who is a celebrity"

Pick the hybrid. Use a follower threshold (say above 100,000 followers, tuned by watching real numbers) to mark a celebrity. For everyone else, push. At read time, merge: most users follow only a few celebrities, so that is a handful of cheap lookups, each served from a cache. Also, only push to recently active users: if someone has not opened the app in 30 days, skip them and rebuild their feed on their next visit.

Deep dive B: the feed cache and cursor pagination

The feed for each user is a Redis sorted set: key feed:{user_id}, member the post_id, score the post's time or id. ZADD inserts, and range commands read the newest first (Redis). After each insert, trim the set to the newest 500 or so, so memory stays bounded. If a user scrolls past 500, fall back to pulling from the database.

Why a cursor, not "page 2"? With offset pagination ("skip 20, take 20"), new posts arriving between page 1 and page 2 push everything down, so the user sees the same post twice. Large offsets are also slow. A cursor says "give me 20 posts older than this id", which is stable however many new posts arrive, and is fast with an index. The response returns next_cursor = the id of the last post sent. You will try this in Redis below.

Fetching details: the sorted set holds only ids, so the feed service uses a multi-get to load the 20 post objects from a post cache (fast), falling back to the database, and loads author data the same way. This "hydration" step is often the real latency cost, so cache it hard.

Deep dive C: ranking and media

  • Ranking, just the idea: the simplest feed is newest first. A ranked feed scores each candidate post (how recent, how much you interact with this author, how many likes) and sorts by score. The feed service gathers candidates (your pushed ids plus celebrity posts), a ranking service scores them, and we return the top 20. Start simple; add ranking when the product needs it. Ranking must be fast, so it uses precomputed features.
  • Media through a CDN: the phone uploads the image straight to object storage with a pre-signed URL; the post stores only the file key. A background worker makes smaller sizes and thumbnails. The feed returns CDN URLs with long cache times, so image bytes never pass through our servers (CDN).
  • Unfollow and delete: removing entries from millions of feeds is expensive, so filter on read: the feed service drops ids whose post is deleted or whose author you no longer follow.

7. Trade-offs, bottlenecks and wrap-up

  • Write cost against read speed: push moves work to the write side so the read side stays fast. The hybrid caps the damage from celebrities.
  • Freshness: a post may appear a few seconds late, and feeds for celebrities' followers are slightly different in timing. Acceptable for a feed, not for money.
  • Memory cost: 1.6 TB of Redis is real money, so keep feeds only for active users.
  • Bottlenecks: fan-out queue lag after a big post, hot celebrity post rows (cache them), the follow database.
  • Monitor (observability): feed latency p99, fan-out queue lag, cache hit rate, delay between "post created" and "visible in followers' feeds".

At 10x scale (2 billion DAU): shard the feed cache by user id with consistent hashing, partition the fan-out queue by author, lower the celebrity threshold, cache hydrated posts per region, and serve feeds from regional data centres close to users.

B. Feel a feed cache and a cursor in Upstash (15 to 20 minutes)

You will use a Redis sorted set as a tiny feed. This uses your Upstash account (the free plan is fine). Commands may be written in any letter case.

  1. Open console.upstash.com, click your Redis database (create one as in the URL shortener lesson if you have none) and open the CLI tab (you may see a terminal-like box at the bottom of the page).
  2. Type this line and press Enter. It puts 7 posts into the feed of user 42, using the post id as the score (bigger id means newer): 
    ZADD feed:42 1001 p1001 1002 p1002 1003 p1003 1004 p1004 1005 p1005 1006 p1006 1007 p1007
    It should print 7 (seven new members).
  3. Read "page 1" (the newest 3): 
    ZREVRANGE feed:42 0 2
    You should see p1007, p1006, p1005, newest first.
  4. A new post arrives while the user is reading page 1: 
    ZADD feed:42 1008 p1008
  5. Offset-style page 2 (skip 3, take 3). This is the buggy way: 
    ZREVRANGE feed:42 3 5
    You should see p1005, p1004, p1003. Look: p1005 was already on page 1. The new post pushed everything down, so the user sees a duplicate.
  6. Cursor-style page 2 ("older than the last post I saw, which was 1005"). The round bracket means "not including 1005": 
    ZRANGE feed:42 (1005 -inf BYSCORE REV LIMIT 0 3
    You should see p1004, p1003, p1002. No duplicate, no gap. (If the console says the command is unknown, use the older spelling ZREVRANGEBYSCORE feed:42 (1005 -inf LIMIT 0 3, which gives the same answer.)
  7. Now trim the feed to the newest 5 so memory stays bounded: 
    ZREMRANGEBYRANK feed:42 0 -6
    It prints 3 (three old entries removed). Check with ZCARD feed:42, which should print 5, and ZREVRANGE feed:42 0 -1, which should show p1008 down to p1004.
  8. Clean up: DEL feed:42. It prints 1.
  9. Write two sentences in your notes: "A cursor is stable when new items arrive; an offset is not." and "The feed cache is a sorted set of ids, trimmed to a fixed size."

C. Variation questions

1. A user with 5,000 followers becomes a celebrity with 500,000 overnight. What happens?

A follower count threshold flips the user to "pull" mode. New posts stop being pushed. Posts already pushed stay in existing feeds (harmless). From then on, followers' feed services merge this author's recent posts at read time. The threshold check runs in the post service when it decides whether to publish a fan-out event.

2. How do you delete a post that is already in 10,000 feeds?

Mark it deleted in the posts database and post cache. The feed service drops any id whose post is deleted when it hydrates, so the stale id in the sorted sets does nothing. A background job may clean the ids later. Do not try to scrub 10,000 feeds synchronously.

3. Add "show posts ranked by what I like most". What changes?

Only the read path: after collecting candidate ids, a ranking step scores them with precomputed features (author affinity, recency, engagement) and sorts by score. The cursor now must encode the score as well as the id, or the app asks for a fixed-size ranked batch and pages within it. The write path does not change.

Quick quiz

What is fan-out on write, and what is its main benefit?

When a user posts, copy the post id into every follower's precomputed feed. The benefit is a very fast read, because the feed is already built.

What breaks if you use pure fan-out on write and a user with 50 million followers posts?

One post triggers 50 million feed writes, which floods the queue and workers and delays everyone else's posts. Use the hybrid: do not push for celebrities, and merge their posts when a follower reads.

What breaks if you use pure fan-out on read for 60,000 feed reads a second?

Each read must query hundreds of followed authors and merge them, so the database gets millions of lookups a second and the feed becomes slow. Precompute feeds for normal users.

Why is cursor pagination better than offset for a feed?

New posts shift offsets, causing duplicates or skipped items, and big offsets are slow. A cursor ("older than id X") is stable and uses the index.

The Redis feed cache loses all its data. What happens, and what should you do?

Feeds are only a cache, so no data is lost. Rebuild each feed on demand from follows and posts (fan-out on read for that user) and refill the cache. Expect a database spike, so rebuild gradually and limit concurrent rebuilds.

Would you choose push, pull or hybrid for a small company-internal app with 2,000 users? Why?

Pull is enough: at that size a join over a few hundred posts is fast and there is no celebrity problem. Hybrid solves a scale problem you do not have yet.

Say it in an interview

"Reads outnumber writes about 100 to 1, so I would precompute feeds: when a user posts, workers push the post id into each follower's Redis sorted set. For celebrities I skip the push and merge their recent posts at read time, a hybrid."
"The feed is paginated with a cursor, the id of the last post seen, because offsets shift when new posts arrive. Images are uploaded to object storage and served through a CDN."

Common follow-up question: How do you decide who counts as a celebrity?

A follower count threshold (for example 100,000), tuned from real fan-out cost. It can also consider posting frequency. The post service checks it when deciding to fan out, and the feed service uses the same rule when deciding whose posts to pull.

Common follow-up question: How do you keep the feed from growing forever in memory?

Trim each sorted set to a fixed length (say 500 ids), keep feeds only for recently active users, and fall back to pulling from the posts database when someone scrolls beyond the cached part.
