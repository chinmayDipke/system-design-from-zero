The busy dhaba on the highway

A highway dhaba gets a rush of truck drivers at lunch. The head chef is excellent, but slow and expensive. If every driver orders a different dish and the chef cooks each one from scratch, the queue reaches the road.

So the owner makes rules. Dal tadka is the most common order, so a big pot is already made (a cache). Each table may order only so much at a time (a limit). A big party order gets a token number and a "we will call you" (a queue). Plain chai is made by the helper boy, and only tricky dishes go to the head chef (routing). And if the gas runs out, the owner has a second stove next door (a fallback).

Scaling an LLM app is exactly this: the model is slow, costly and sometimes unavailable, so you do everything you can to call it less, call a cheaper one, and survive when it fails.

Making an LLM app fast, cheap and sturdy

A normal database call takes a few milliseconds and costs almost nothing. An LLM call takes seconds, costs real money per token, and the provider limits how many you may send per minute (lesson 1 showed why). Classic scaling tricks still apply, but cost and provider limits become the main enemies, not just server CPU.

1. Response caching: exact and semantic

An exact cache stores the answer under a key made from the full prompt (plus model name and settings). The same input again gives the same answer instantly, with no model call. It is simple and safe, but it only hits when the text is identical. Use the ideas from caching: TTL, eviction, and a key that includes everything that changes the answer.

A semantic cache embeds the question (embeddings) and looks for a similar earlier question: "how do I reset my password" and "forgot password, what to do" can share one answer. It hits more often, but it can hit wrongly: "cancel my order" and "cancel my subscription" are close in meaning and different in action.

Never share cached answers between users when the answer depends on the user (their orders, their account) or on private documents. Put the user or tenant in the cache key, or do not cache that path at all. A semantic cache needs a strict similarity threshold, which you tune on real questions (evals).

Separately, some providers offer prompt caching: if the start of your prompt (a long system prompt or document) is identical across calls, repeated tokens are processed faster or billed cheaper. The rules and discounts differ by provider, so read their docs. The design lesson: put the stable part of the prompt first and the changing question last.

2. Rate limits and token budgets

There are two limits. The provider limits you (requests and tokens per minute). You limit your users, otherwise one user, or one bug, can burn your whole bill overnight. Count tokens, not only requests, because one request can be 100 tokens or 100,000. Cap the output with a maximum-output-tokens setting, cap the input length, and keep a per-user daily token budget in Redis. The counting methods are in rate limiting and the rate limiter design. Return a clear "limit reached" message rather than failing quietly.

3. Queues for long jobs

If a task takes 30 seconds to many minutes (summarise 200 pages, generate a report), do not hold an HTTP request open. Accept the job, put it on a queue, answer "job accepted, id 123", and let workers process it. The user polls, or you push the result by webhook or notification. Workers also let you control concurrency: ten workers means at most ten model calls at once, which keeps you under the provider's limits.

4. Streaming

For chat, the first words matter more than the last. Stream tokens to the browser as they are produced, using server-sent events, so the user sees text after the time-to-first-token instead of waiting for the whole answer. Streaming does not make the model cheaper or finish sooner; it makes the app feel faster. Note that a stream cut halfway is awkward to retry: you have already shown part of an answer.

5. Timeouts and retries with backoff

Set a timeout on every call (stricter for the time to first token than for the whole answer) so a hung request does not pin a server. Retry only errors that may pass by themselves: rate-limit errors (429), server errors (5xx) and timeouts. Never retry a bad request (400) or an auth failure; it will fail the same way. Wait longer after each failure (exponential backoff) and add jitter (a random part) so a thousand clients do not all retry in the same second. Respect a Retry-After header if the provider sends one, and stop after a small number of tries or a total deadline. More background: retries and idempotency and circuit breakers and timeouts.

async function withRetry(fn, { maxTries = 4, baseMs = 200, capMs = 5000 } = {}) {
  for (let attempt = 1; ; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (!err.retryable || attempt === maxTries) throw err; // give up
      const wait = Math.random() * Math.min(capMs, baseMs * 2 ** (attempt - 1)); // "full jitter"
      console.log(`attempt ${attempt} failed, waiting ${Math.round(wait)} ms`);
      await new Promise((resolve) => setTimeout(resolve, wait));
    }
  }
}

Here fn is "call the model" and your code marks an error retryable for 429, 5xx and timeouts. This snippet is provider-neutral on purpose. Many official SDKs already retry for you, so check before adding a second layer (retries multiplied by retries make a storm).

6. Fallbacks between models and providers

Providers have outages and slow hours. A fallback sends the request to a second model, or a second provider, when the first keeps failing or times out. A circuit breaker stops you from hammering a provider that is clearly down. Costs of fallbacks: the second model may answer a little differently, may need a slightly different prompt, may have a different privacy policy, and you must test it before the bad day arrives. Aggregator gateways exist that do this routing for you; they add convenience and one more dependency.

7. Cheap-model routing

Most questions are easy. A router sends easy ones to a small, cheap, fast model and only hard ones to a strong, expensive model. The router can be simple rules (short question, known intent), a small classifier, or the cheap model itself saying "I am not sure, escalate". The risk is routing a hard question to a weak model, so measure answer quality on both paths with a golden set.

The numbers: what these tricks are worth

Example prices only (check the provider's page for real ones): Rs 200 per million input tokens, Rs 800 per million output tokens. Say a support bot gets 10,000 requests a day, each with 1,500 input and 400 output tokens.

  • One request: input 1,500 x 200 / 1,000,000 = Rs 0.30. Output 400 x 800 / 1,000,000 = Rs 0.32. Total Rs 0.62.
  • Per day: 10,000 x 0.62 = Rs 6,200.
  • With a cache that answers 30% of requests: only 7,000 reach the model, 7,000 x 0.62 = Rs 4,340.
  • With routing instead (example: 60% of requests go to a model that costs one tenth as much): 0.4 x 0.62 + 0.6 x 0.062 = Rs 0.2852 per request, so 10,000 x 0.2852 = Rs 2,852.

These percentages are invented to show the method. Your real hit rate and routing split come from your own traffic.

When to use, when not to

  • Early on, do not build everything. Start with timeouts, a retry, an output-token cap and a per-user limit. Those four prevent most disasters.
  • Add a cache when many users ask the same thing (an FAQ bot). Skip it when every question is unique or personal.
  • Add a queue when work is long or bursty. Skip it for a short chat where streaming is enough.
  • Add routing and fallbacks when the bill or the downtime hurts. Both need an eval set to stay safe.

Watch the cost per request on a dashboard from day one (observability). You cannot reduce what you do not measure.

Quick quiz

Why count tokens, not only requests, when you rate-limit an LLM app?

Requests differ hugely in size. One request can use 100 tokens or 100,000, and the bill and the provider's limits are in tokens. A request-count limit lets one big request cost as much as hundreds of small ones.

What is the difference between an exact cache and a semantic cache?

An exact cache hits only when the whole prompt is identical. A semantic cache embeds the question and hits on a similar one. It gets more hits but can return the wrong answer for a near-miss, so it needs a strict threshold.

Which errors should you retry, and which not?

Retry errors that may pass by themselves: 429, 5xx and timeouts, with exponential backoff and jitter, and a limit on tries. Do not retry 400-type errors or auth failures; they will fail again.

What breaks if a thousand clients all retry after exactly 1 second, then 2, then 4?

They retry in waves at the same moments, so each wave hits the provider (or your own server) together and the overload continues. Jitter spreads the retries out.

What breaks if a semantic cache is shared across all users of a bank chatbot?

"What is my balance?" is similar to another user's "what is my balance?", so one customer could be shown another's cached answer. Personal answers must never be cached across users: include the user in the key or skip caching.

Your bot costs too much and the answers are mostly easy FAQs. What would you try first and why?

First an exact or semantic cache for repeated FAQs, since a hit costs nothing. Then cheap-model routing for the rest. Both are measured against a golden set so quality does not quietly drop. Rate limits and an output cap protect the worst case in the meantime.

Say it in the interview

An LLM call is slow, expensive and rate-limited, so I call it less: cache repeated answers, route easy questions to a small model, and set per-user token budgets.
I put a timeout on every call, retry only 429s, 5xx and timeouts with exponential backoff and jitter, and keep a fallback model behind a circuit breaker for provider outages.
Long jobs go on a queue with a fixed number of workers, which also keeps me under the provider's rate limit. Chat streams tokens so the first word appears quickly.

Common follow-up question: "What is the risk of a semantic cache?"

It can return a confident answer to a question that only looks similar, and it can leak personal answers between users. I use a strict similarity threshold, keep the user or tenant in the key for personal data, set a TTL, and check hit quality on a golden set.
