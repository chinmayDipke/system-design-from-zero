The school library that outgrew its room

A school library has so many books that one room cannot hold them. So the librarian splits them: books with titles A to H in room 1, I to P in room 2, Q to Z in room 3. Now each room has a smaller load, and three librarians work at once.

But new troubles appear. Everybody wants the "Harry Potter" shelf, so room 1 is crowded and room 3 sits empty. A student who wants "all books by one author" has to visit three rooms. And if the school opens a fourth room, the librarian must carry a lot of books around to rebalance.

That is sharding: splitting one big database into pieces on different machines. This lesson is about how to split, and how to avoid moving everything when you add a room.

Splitting data across machines

Replication (last lesson) copies the same data to many machines, which helps reads. It does nothing when the data is too big for one machine, or when there are too many writes for one leader. For that you split the data so each machine holds only a part.

Partitioning vs sharding

Partitioning means splitting a big table into parts, often inside one database server (for example one partition per month). Sharding means the parts live on different servers, each called a shard. People often use the words loosely. Each shard is usually also replicated for safety.

The shard key

The shard key is the column that decides which shard a row goes to (for example user_id). It is the most important choice: it decides which queries are fast and whether the load is even.

RangeShard by value range: ids 1-1M, 1M-2M, ...Range queries are easy and fastHot spots: newest ids all land on the last shard

Hot shards: the celebrity problem

Even with a fair hash, some keys are far busier than others. One celebrity with 100 million followers makes their shard a hot shard while others idle. Fixes: split that key's data further (add a random suffix so one celebrity is spread over many shards), cache their data heavily, or give hot keys dedicated machines.

The pain of cross-shard work

  • Cross-shard queries: "top 10 products across everything" needs a question to every shard and a merge of the answers.
  • Cross-shard joins are slow and awkward. Designs often denormalize, or keep related rows on the same shard by choosing the key carefully (for example all of a customer's orders share the customer's shard).
  • Transactions across shards are hard and slow. Avoid them if you can.
  • Resharding (changing the number of shards) means moving large amounts of data while the system is live. It is expensive and risky. That is why you only shard when you truly must, after trying a bigger machine, caching, indexes and replicas.

Why hash mod N hurts

With shard = hash(key) mod N, going from 3 servers to 4 changes the answer for most keys, so almost everything must move (you will count it below). In a cache, that means nearly all cached data suddenly "misses". We need a scheme where adding a server moves only a small share of keys.

Consistent hashing

Picture a ring (a circle) of positions from 0 to a huge number. You hash each server to a spot on the ring, and each key to a spot too. A key belongs to the first server you meet walking clockwise from the key's spot. Add a new server: it takes over only the keys between it and the previous server. Everything else stays put. Remove a server: only its keys move to the next server. On average only about 1/N of the keys move.

Virtual nodes: with only a few servers on the ring, the arcs can be very uneven. So each real server appears at many points (say 100-200 virtual nodes, such as A#1, A#2, ...). The load evens out, and when a server leaves, its many small arcs are spread across all the other servers rather than dumped on one neighbour. Consistent hashing is used by Cassandra, DynamoDB-style stores, and many cache clusters and CDNs.

Trade-offs

  • Sharding gives huge capacity for data and writes, but costs simplicity: no easy joins, harder transactions, more operations work.
  • Choose the key from your access pattern: what do most queries filter by? A bad key causes hot shards or scatter-gather queries on every request.
  • Delay it. Many successful products never shard.

A good one-line answer: "Shard by user id with consistent hashing, so a user's data is on one shard, and adding servers moves only a small fraction of the data."

Do it yourself (about 30 minutes, paper or Excalidraw)

No tools needed beyond paper or Excalidraw. We use a small ring from 0 to 99 and a made-up hash so you can calculate by hand.

A. Put 8 users on a hash ring

  1. Draw a big circle. Mark 0 at the top and write 25 on the right, 50 at the bottom and 75 on the left (clockwise).
  2. Place three servers on the ring: S1 at 10, S2 at 40, S3 at 70. (Real systems hash the server name; we pick spots to keep the maths easy.)
  3. The hash of a user is (user_id × 13) mod 100. Calculate for the user ids 1 to 8 and write the results in a table:
    User12345678
    Hash132639526578914
    (For user 8: 8 × 13 = 104, and 104 mod 100 = 4.)
  4. Mark each user on the ring at its hash spot (for example user 1 at 13, a little clockwise of S1).
  5. For each user, walk clockwise to the first server at or after that spot (after 99 you wrap round to 0). Write who owns whom. You should get: S2 owns users 1, 2, 3; S3 owns users 4, 5; S1 owns users 6, 7, 8 (78 and 91 wrap past 99 round to S1 at 10; 4 reaches S1 at 10).

B. Add a server and count the moves

  1. Add S4 at 55 on the ring.
  2. Redo the walk for all 8 users. Which owners changed? Only user 4 (hash 52): its next server clockwise is now S4 at 55 instead of S3 at 70.
  3. Write: 1 of 8 keys moved.

C. Compare with hash mod N

  1. With 3 servers, the shard of a user is hash mod 3. Using the same hashes, fill the row:
    User12345678
    hash mod 312012011
    hash mod 412301230
    (Work out each number yourself first, then check the table. For example 52 mod 3 = 1, and 52 mod 4 = 0.)
  2. Count the users whose shard number changed when going from 3 to 4 servers. You should find 6 of 8 changed (users 3, 4, 5, 6, 7, 8).
  3. Write one sentence: "Consistent hashing moved 1 of 8 keys, hash mod N moved 6 of 8. In a cache, 6 of 8 means a flood of misses hitting the database."

Eight keys is a tiny sample, but the pattern is real: with N servers, hash mod N moves roughly N/(N+1) of the keys when you add one (3 → 4 servers: about 3 in 4 keys), while consistent hashing moves about 1/(N+1).

D. Virtual nodes

  1. On a fresh circle, place S1 at 10, 50 and 90, S2 at 25, 65 and 95, S3 at 5, 35 and 80 (three virtual spots each).
  2. Notice that the arcs are now shorter and mixed. If S2 disappears, who takes over its keys? Different neighbours for different arcs, so the load spreads, instead of one server taking all of it.
  3. Save the drawings as m2-10 hash-ring-exercise.excalidraw.

Quick quiz

How is sharding different from replication?

Replication copies the same data to many machines (helps reads and safety). Sharding splits the data so each machine holds a different part (helps data size and write volume).

Name three shard strategies and one weakness of each.

Range (hot spots on the newest range), hash (range queries scatter; resharding moves much data), directory/geo (the lookup table becomes another thing to keep fast and available).

What is the celebrity problem?

One key (like a hugely popular user) gets far more traffic than others, making its shard hot even if the data was split evenly by hash.

Why is hash mod N bad when you add a server?

Changing N changes the result for most keys, so almost all data must move (or most cache entries miss).

What problem do virtual nodes solve?

They even out the load on the ring and, when a server leaves, spread its keys across many servers rather than one neighbour.

A single Postgres handles your load fine. Should you shard? Why?

No. Sharding adds big complexity (cross-shard joins, transactions, resharding). Try indexes, caching, a bigger machine and read replicas first. Shard only when data size or write volume truly exceeds one machine.

Say it in an interview

"Replicas scale reads; to scale writes and storage I would shard, choosing a shard key like user_id that matches the main access pattern, so a user's data lives on one shard."
"I would place shards on a consistent-hash ring with virtual nodes, so adding a server moves only about 1/N of the keys."

Common follow-up question: How do you handle a hot shard?

First cache the hot key's data. Then split the hot key across several shards (for example by adding a small random suffix and merging reads), or move it to a dedicated machine. Also review the shard key: a better key may avoid the skew.
