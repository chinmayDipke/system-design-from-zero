The phone line that stays open

Imagine two friends, Asha and Ravi, on a long phone call. The line stays open, so the moment Asha speaks, Ravi hears. Nobody has to keep dialling to ask "anything new?". That is a chat app: a line that stays open.

Now picture a big telephone exchange with a million open lines. When Asha talks, the exchange must find Ravi's line, which may be connected to a different desk, and pass the words along. If Ravi's phone is off, the exchange writes the message on a slip and keeps it until he is back. When he is back, he gets all the slips in the right order. In a group call with 200 people, one voice must reach 199 others.

Chat design is about three things: keeping lots of lines open, finding the right line fast, and never losing or scrambling a message, even when someone is offline.

Design a chat app (like WhatsApp)

Before reading on, set a 10-minute timer and write your own requirements and a rough diagram. Then compare. Try to draw what happens when Ravi is offline: where does the message wait?

We follow the 7-step framework. Realtime delivery builds on WebSockets and the pub/sub idea.

1. Requirements

Functional:

  • One-to-one chat and group chat (up to a few hundred members).
  • Send and receive text messages in real time; send images, video and files.
  • Delivery and read receipts (one tick sent, two ticks delivered, blue ticks read).
  • Online status ("online", "last seen").
  • Messages sent while you are offline arrive when you come back. Chat history syncs.

Non-functional:

  • Low latency: a message should arrive in well under a second.
  • No message lost, none duplicated on screen, and in the right order within a conversation.
  • Highly available and scalable to hundreds of millions of users.
  • Private: end-to-end encryption.

Out of scope: voice and video calls, status/stories, payments, message search.

2. Estimation

Assume 100 million daily active users, each sending 40 messages a day.

  • Messages: 100,000,000 x 40 = 4,000,000,000 a day. At about 100,000 seconds a day: 40,000 messages a second average, about 120,000 at peak (3x).
  • Storage: assume 200 bytes a message (text plus metadata). 4,000,000,000 x 200 B = 800 GB a day, which is about 290 TB a year (800 GB x 365). Very large, and it only grows.
  • Connections: assume 20% of users are online at once: 20 million open WebSockets. A well-tuned server can hold on the order of 100,000 idle connections, so 20,000,000 / 100,000 = about 200 connection servers. We plan for more for safety.
  • Media: assume 10% of messages carry media of 200 KB: 400,000,000 x 200 KB = 80 TB a day. That goes to object storage and a CDN, never through the chat servers.

Conclusions: we need servers that hold many long-lived connections, a storage engine built for huge append-only writes, and media outside the message path.

4. Data model

  • Users, conversations, group members: relational (PostgreSQL). Small compared with messages, and relationships and constraints matter (SQL vs NoSQL).
  • Messages: a wide-column store such as Cassandra or HBase. The key: partition key = conversation_id, clustering key = seq. That keeps one conversation's messages together on disk in order, so "latest 50 messages" or "everything after seq 118" is a quick read from one partition. 
    messages
  conversation_id  (partition key)
  seq              (clustering key, increasing)
  sender_id, body, media_key, created_at
  • Presence and sessions: in Redis with short TTLs: presence:{user} and session:{user} (which connection server holds this user's connection).
  • Media: files in object storage, only the key in the message row.

Why wide-column here? The workload is a flood of appends, reads of recent ranges by one key, no joins, and the data must spread over many machines (sharding). Wide-column stores are made for that. The cost: no joins, limited query flexibility, eventual consistency by default (consistency). We accept that because we only ever query a conversation by its id. Very busy conversations can grow huge partitions, so split a partition by time bucket (for example conversation plus month).

5. High-level design

  1. Asha's phone sends a message over its open WebSocket to a connection server.
  2. The connection server passes it to the chat service (a normal stateless service).
  3. The chat service checks the session registry (Redis) to learn which connection server holds Ravi's connection.
  4. It gives the message the next sequence number for the conversation and saves it in the message store.
  5. It forwards the message to Ravi's connection server, which writes it down Ravi's WebSocket. Ravi's phone replies with a "delivered" ack, later a "read" ack, and both travel back to Asha as receipts.
  6. If Ravi is offline (no session), the message just stays stored and the chat service asks the push service (Apple or Google) to show a notification.

When Ravi comes back, his app connects and says "my last seq in this chat is 118". The server sends everything after 118.

6. Deep dives

Deep dive A: connections and presence

Why WebSockets and not polling? Polling asks "any news?" every few seconds: wasteful and slow. A WebSocket stays open so the server pushes the instant something arrives. The catch: connection servers are stateful. User 7 is "stuck" to server C14 for as long as the line is open. So:

  • Put a load balancer (layer 4 is fine) in front to spread new connections; it does not need to route messages (load balancers).
  • When a client connects, the connection server writes session:{user} = server id into Redis. When it disconnects, it deletes it.
  • To deliver to Ravi, the chat service looks up his server and sends the message to just that server (through an internal RPC or a pub/sub topic per server).
  • When a connection server is restarted or crashes, its users reconnect elsewhere, and clients must reconnect with backoff and jitter so they do not all arrive at once.

Presence ("online"): the client sends a small heartbeat every 15 to 30 seconds, and the server sets presence:{user} in Redis with a TTL of about 30 to 60 seconds. If heartbeats stop, the key expires and the user shows offline; the last-seen time is saved. Do not broadcast every presence change to every contact: a person with 500 contacts flickering online would create a storm. Send presence only to people who currently have that chat open or visible, or let clients fetch it when needed.

Deep dive B: ordering, groups and receipts

Messages must appear in the same order for everyone in a conversation. We do not need a global order across all of WhatsApp, only per conversation. Clock timestamps are unreliable (phones disagree by seconds), so we use a per-conversation sequence number: the Nth message in conversation X gets seq = N. To hand out numbers without gaps or duplicates, one component must own each conversation's counter at a time: route a conversation always to the same chat-service shard (hash of conversation_id), or use an atomic increment in the store. Clients sort by seq. If a client sees 118 then 120, it knows 119 is missing and asks for it.

Retries: the sender's app tags each message with a client_msg_id. If the network drops and the app resends, the server sees the same id and returns the original seq rather than storing a second copy (idempotency).

Receipts: "sent" means the server stored it. "Delivered" means Ravi's device acked. "Read" means the app was open on that chat. Receipts are tiny messages going the other way and are compressed as "up to seq N".

Deep dive C: offline sync, media, encryption

  • Offline: messages are already stored by sequence. Each device remembers the last seq it has per conversation and syncs "after_seq" on reconnect. A push notification wakes the phone. Keep delivered-but-not-yet-synced messages until acked.
  • Media: the phone asks for a pre-signed URL, uploads the file straight to object storage, then sends a normal chat message containing the file's key and a small thumbnail. The receiver downloads it from the CDN. The chat servers never carry the heavy bytes.
  • End-to-end encryption, in one paragraph: each device makes a key pair and shares only its public key with the server. The sender's app encrypts every message with keys that only the recipient's device can use, so the server stores and forwards ciphertext and cannot read it, not even for a court order or a hacker. The Signal protocol, used by WhatsApp, also changes keys as messages go, so one stolen key does not expose the past. The costs: the server cannot search or moderate content, adding a new device or restoring backups is harder, and groups need extra key handling.

7. Trade-offs, bottlenecks and wrap-up

  • Stateful connection servers are the hardest to scale and deploy. Drain them slowly, and expect reconnection spikes.
  • At-least-once delivery plus dedupe (by client_msg_id and seq) instead of the myth of exactly-once.
  • Eventual consistency on the message store is fine because messages are append-only and ordered by seq.
  • Bottlenecks: hot group chats (one partition, one sequence counter), presence traffic, and the session registry.
  • Monitor (observability): connection count per server, message delivery latency (p99), undelivered backlog, reconnect rate.

At 10x scale (1 billion users): shard the session registry and presence by user id, split big groups into smaller delivery shards, run connection servers in many regions with the chat service close to them, use more partitions and time buckets, and push heavy media entirely via CDN.

B. Variation questions

1. The same user is logged in on a phone and a laptop. What changes?

The session registry holds a set of connections per user, one per device. The chat service delivers to every connected device. Each device tracks its own last seen seq per conversation, so each can sync independently. Receipts: "delivered" can mean "delivered to at least one device"; "read" when any device reads it.

2. Two messages arrive at the phone in the order seq 121 then seq 120. What does the app do?

It sorts by seq when drawing the screen, so 120 shows above 121. If a number is missing (it got 122 but never 121), the app asks the server for the missing range with after_seq. It never trusts arrival order or phone clocks.

3. How would you add "typing..." indicators?

Send a tiny, ephemeral event over the WebSocket that is forwarded but never stored, and drops silently if the other user is offline. Throttle it (at most one every few seconds) and auto-expire it on the receiver after a few seconds. Never queue or retry it.

Build it (optional, about 30 to 45 minutes)

You will build a tiny live chat in one HTML file, with no build tools. Two Chrome tabs will chat with each other through Supabase Realtime Broadcast, which sends a message to everyone subscribed to a named channel. The code uses supabase-js version 2.118.0 loaded from a CDN script tag. It was syntax-checked with node --check, and the CDN address was confirmed to load.

This is a learning demo. It uses only your project's publishable (anon) key, which is safe to put in a browser page. There is no login, and anyone who knows your project URL, key and the channel name can join the room. Never put a secret or service_role key in this file. Also, Broadcast does not store messages: a message exists only for people connected at that moment, which is exactly why a real chat app needs the message store from deep dive A.

Quick quiz

Why do chat apps use WebSockets instead of polling?

A WebSocket stays open so the server can push a message the instant it arrives. Polling asks repeatedly "anything new?", which wastes requests and adds delay.

How does the chat service know which server holds the recipient's connection?

Each connection server records user to server id in a shared session registry (Redis) when a user connects and removes it when they disconnect. The chat service looks it up and forwards the message to that server.

What breaks if you order messages by the phone's clock timestamp?

Phone clocks differ by seconds or more, so two people could see messages in different orders or a reply before the question. Use a per-conversation sequence number assigned by the server.

What breaks if a message is only held on the connection server and that server crashes?

The message is lost. Messages must be saved in the durable message store before the server says "sent", and delivered messages are kept until acked, so reconnecting clients can sync from their last seq.

Why is partition key = conversation_id a good choice for the message store, and what could go wrong?

All messages of a conversation sit together in order, so reading recent history is one fast partition read. A huge group chat can make one partition very large and hot; split it by time bucket.

You must decide between Postgres and Cassandra for messages at 40,000 writes a second. What do you choose?

A wide-column store like Cassandra: append-heavy writes, access always by conversation id and range, easy horizontal spread, no joins needed. Postgres stays for users and group membership. For a small app, plain Postgres is fine; the choice follows the scale.

Say it in an interview

"Clients hold a WebSocket to a connection server. A Redis session registry maps user to server, so the chat service can forward a message straight to the recipient's connection server. Every message gets a per-conversation sequence number and is stored before we acknowledge it."
"Messages live in a wide-column store partitioned by conversation id and ordered by sequence number. Offline users sync from their last seen sequence number when they reconnect, and media goes through object storage and a CDN, not through the chat servers."

Common follow-up question: How do you guarantee ordering and no duplicates?

Order comes from the per-conversation sequence number, not clocks. Duplicates are avoided with a client-generated message id that makes retries idempotent, and the receiver ignores a seq it already has. Delivery is at-least-once.

Common follow-up question: How does a group message reach 200 people?

It is stored once for the conversation, then the chat service fans out to each member's connection server. Offline members get a push notification and sync later. I would cap group size, because the fan-out cost grows with members.
