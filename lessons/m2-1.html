The restaurant menu and the waiter

In a restaurant you never walk into the kitchen. You read a menu, tell the waiter what you want, and the waiter brings the food. The menu lists what you are allowed to ask for, and the waiter carries your request to the kitchen and the answer back.

An API is that menu and waiter for programs. One program (your app) asks, another program (a server) answers, and both follow agreed rules, so neither needs to know how the other works inside.

But there are different kinds of restaurants. Some give a fixed thali. Some let you pick each item. Some call you when your table is ready. APIs have the same styles.

Six ways programs talk

In Module 1 you saw that a client sends an HTTP request and the server sends a response. All the styles below sit on top of that idea, except where noted. Learn what each one is, and more importantly when to pick it.

REST: resources and verbs

REST is the most common style. You think in resources (things with a name): users, posts, orders. Each has a URL, and the HTTP verb says what to do:

VerbExampleMeaning
GET/posts/1Read post 1
POST/postsCreate a new post
PUT / PATCH/posts/1Replace / change part of post 1
DELETE/posts/1Delete post 1

Status codes tell the result: 200 OK, 201 created, 400 you sent something wrong, 401 not logged in, 403 not allowed, 404 not found, 429 too many requests, 500 the server broke. Data usually travels as JSON.

Pagination: never return a million rows. Return a page, such as /posts?page=2&limit=20, or better for big data a cursor (?after=id123) that means "continue after this item". Cursors stay correct even when new rows arrive.

Versioning: once apps depend on your API you cannot change it freely. Put a version in the URL (/v1/posts) or a header, so old apps keep working while new ones use /v2.

GraphQL: one endpoint, you pick the fields

REST has many URLs. GraphQL has one endpoint, and the client sends a query describing exactly the fields it wants. This fixes two REST pains: over-fetching (the server sends 30 fields, your screen needs 3) and under-fetching (one screen needs 4 REST calls to assemble). The cost: caching is harder (every request is a POST to the same URL), and a careless query can be very expensive for the server.

gRPC: fast and binary, for service to service

gRPC sends compact binary messages (using protobuf, a schema file that both sides share) over HTTP/2. It is smaller and faster than JSON, and it generates client code for you. Browsers do not speak it natively, so it is mostly used between backend services, not from a web page.

WebSockets: a phone call instead of letters

HTTP is letters: ask, then answer. A WebSocket is a phone call: one connection stays open and either side can speak at any time. Good for chat, live cricket scores, multiplayer games, live dashboards. The cost: every open connection uses server memory, so a million users means a million open connections to manage.

Long polling and Server-Sent Events (SSE)

Polling is asking "anything new?" every few seconds. Wasteful. Long polling improves it: the server holds your request open until there is news (or a timeout), answers, and you immediately ask again. SSE keeps one HTTP connection open and the server pushes a stream of events, one way only (server to client). It is simpler than WebSockets when you only need updates flowing down, like notifications or a live log.

Webhooks: they call you

A webhook turns it around: the server calls your URL when something happens. Example: a payment provider calls https://yourapp.com/payment-done after the customer pays. You do not keep asking "did it pay yet?". Rules: check the signature (so nobody fakes the call), answer fast with 200, and expect retries, so handle the same event twice safely.

Trade-offs

  • REST is easy but can over/under-fetch. GraphQL fixes that but moves complexity to the server.
  • Persistent connections (WebSocket, SSE) feel instant but cost memory and make scaling harder (see the scaling lesson).
  • Do not default to the fancy one. In an interview, start with REST and move to another only when you can name the problem it solves.

Make writes safe to retry. A client may resend a POST after a timeout. An idempotency key (a unique id sent with the request) lets the server notice "already done" and not charge twice.

Do it yourself (about 25 minutes)

You will call a free practice API, jsonplaceholder.typicode.com. It holds fake blog posts. Nothing you do there changes anything real.

A. Call it from Command Prompt with curl

  1. Press ⊞ Win, type cmd, press Enter.
  2. Type this and press Enter. (Use curl.exe, with the .exe, so you do not hit a different command of the same name in PowerShell.) 
    curl.exe https://jsonplaceholder.typicode.com/posts/1
    You should see a block of JSON with userId, id, title and body. That is a REST GET on the resource "post number 1".
  3. Now see the status code and headers too. The -i flag means "include the headers": 
    curl.exe -i https://jsonplaceholder.typicode.com/posts/1
    The first line should say HTTP/... 200 OK.
  4. Ask for a page of results (pagination). The _limit part is how this practice API pages: 
    curl.exe "https://jsonplaceholder.typicode.com/posts?_limit=3"
    You get only 3 posts.
  5. Ask for something that does not exist: 
    curl.exe -i https://jsonplaceholder.typicode.com/posts/99999
    The first line should say 404 Not Found.
  6. Create a post with POST. In Command Prompt, the quotes inside the JSON must be escaped with a backslash, exactly like this: 
    curl.exe -i -X POST -H "Content-Type: application/json" -d "{\"title\":\"hello\",\"body\":\"my first post\",\"userId\":1}" https://jsonplaceholder.typicode.com/posts
    You should see 201 Created and a post with "id": 101. The site only pretends to save it; asking for post 101 afterwards will give 404. That is expected.

B. Call the same API from the browser

  1. In Chrome, open https://jsonplaceholder.typicode.com (a normal page is better than a blank tab).
  2. Press F12 and click the Console tab.
  3. Copy the line below from this page (use its Copy button). 
    fetch('https://jsonplaceholder.typicode.com/posts/1').then(r=>r.json()).then(console.log)
  4. Click inside the Console next to the > and press Ctrl + V. Chrome may refuse and show a warning: "Warning: Don't paste code into the DevTools Console that you don't understand or haven't reviewed yourself... type 'allow pasting'". It does this to protect people from scams.
  5. This code is yours and safe, so type allow pasting in the Console and press Enter. Then paste again and press Enter. (If Chrome pasted it without a warning, just press Enter.)
  6. You should see a Promise line and then an object. Click the small triangle to open it: the same title and body as in cmd. fetch is how your React code calls REST APIs.
  7. Click the Network tab, run the line once more, and click the new 1 row. Under Headers find Request Method (GET) and Status Code (200).
Never paste code into the Console just because a stranger told you to. It can steal your logged-in sessions. Paste only code you have read and understood.

  2. Check with the table above. Suggested answers: (a) SSE or WebSocket, (b) webhook, (c) gRPC, (d) REST.

Quick quiz

What does POST /orders normally mean, and which status code should come back on success?

Create a new order. 201 Created (or 200 in simple APIs).

What are over-fetching and under-fetching?

Over-fetching: the response has far more data than the screen needs. Under-fetching: one screen needs several calls to get all its data. GraphQL lets the client ask for exactly the fields it wants in one call.

Why is gRPC rarely called straight from a browser page?

Browsers do not natively speak its binary HTTP/2 format. It shines between backend services.

How does a webhook differ from polling?

In polling you keep asking "done yet?". With a webhook the other side calls your URL once when it is done, saving requests. You must verify the signature and handle retries.

You are building a live notification bell that only needs server-to-browser updates. What do you choose and why?

SSE: one-way push over plain HTTP, simpler than WebSockets. If the client also had to send frequent messages (chat), I would move to WebSockets.

Say it in an interview

"I would start with a REST API with JSON, versioned like /v1, paginated with cursors. If clients struggle with over-fetching I would consider GraphQL."
"For live two-way features I would use WebSockets; for one-way updates SSE is simpler. Between internal services I would consider gRPC. For third-party events I would take a webhook."

Common follow-up question: What goes wrong with webhooks and how do you handle it?

The sender may retry, so you can receive the same event twice, and events may arrive out of order. I verify the signature, return 200 quickly, store the event id to ignore duplicates, and do the heavy work in the background.
