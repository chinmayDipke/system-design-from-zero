The lift button and the impatient uncle

You press the lift button. Nothing seems to happen, so you press it again, and again. Does the lift come three times? No. Pressing the button many times has the same effect as pressing once. The lift knows you want to go to floor 5.

Now picture a "Pay Rs 500" button. The network is slow, so you tap it twice. If the shop's computer treats each tap as a new payment, you lose Rs 1000. That would be a terrible lift.

In distributed systems, messages get lost, delayed and repeated all the time. The safe design is: doing it twice must be the same as doing it once. That property is called idempotency.

Retrying safely

A network call can end in three ways: success, failure, or "no idea" (a timeout). On "no idea", the sender cannot tell if the server did the work. The only safe move is to try again. But trying again is only safe if the operation is idempotent.

Idempotent operations

An operation is idempotent if running it many times leaves the same result as running it once.

IdempotentNot idempotent
Set the user's city to "Pune"Add Rs 100 to the balance
Delete order 42Create a new order
PUT /users/7 with the full recordPOST /payments

HTTP methods GET, PUT and DELETE are meant to be idempotent (HTTP lesson). POST is not. To make a POST safe we add an idempotency key.

Idempotency keys (payments)

Payment APIs like Razorpay's and Stripe's let the client send a unique key, for example in an Idempotency-Key header. (Check each provider's docs for exact names and rules; the idea is the same.) The flow:

  1. The client makes a random unique key (a UUID) once per intended payment and sends it with the request.
  2. The server looks the key up. If it has never seen it, it does the work and stores the key with the result.
  3. If the key is already stored, the server does not charge again. It returns the stored result.
  4. If the client times out, it retries with the same key. Whatever happened the first time, the customer is charged once.

The key lives in the database behind a unique constraint, so even two simultaneous requests cannot both succeed. You will try this below.

Retries: backoff and jitter

When a call fails, do not retry instantly in a loop. That hammers a server that is already struggling.

  • Exponential backoff: wait longer after each failure: 1 s, 2 s, 4 s, 8 s... and stop after a limit.
  • Jitter: add a random amount to each wait. Without it, 10,000 clients that failed together all retry together at 1 s, then 2 s, then 4 s: the server is hit in waves.
  • Retry only what is safe and worth it: timeouts and 503s, yes. A 400 (bad request) will fail again, so no. Only retry non-idempotent calls if you have an idempotency key.

Retry storm: a server slows down, clients time out and retry, the retries add load, the server slows more, more retries. A small problem becomes an outage. Backoff, jitter, a retry limit and a retry budget (for example "retries may add at most 10% extra traffic") prevent this. See circuit breakers for the next layer of defence.

At-least-once delivery and idempotent consumers

Queues (message queues) usually promise at-least-once delivery: if the consumer does not confirm in time, the message is delivered again. So duplicates will happen. "Exactly once" end to end is very hard. The practical answer: at-least-once delivery + an idempotent consumer. The consumer remembers processed message IDs, or uses an operation like "set status = shipped" that can safely repeat.

Dead-letter queues

Some messages fail every time: bad data, a bug. If retried forever they block the line. After a set number of attempts (say 5), the message is moved to a dead-letter queue (DLQ): a side box for failed messages. A person or tool examines them, fixes the cause and can replay them. Always alert when the DLQ is not empty.

The outbox pattern

Problem: after saving an order you must also publish an "order placed" event. If you write to the database and then publish, a crash between the two loses the event. If you publish first and the write fails, you announced an order that does not exist. The database and the queue cannot share one transaction.

Fix: in one database transaction write the order and also a row in an outbox table ("event to publish"). Both succeed or both fail. A separate relay process reads unpublished outbox rows, publishes them to the queue, and marks them sent. If the relay crashes after publishing but before marking, the event is sent twice, which is fine because consumers are idempotent.

Trade-offs

  • Idempotency keys need storage and a policy (how long to keep keys; what if the same key arrives with a different amount, which should be rejected).
  • Retries improve reliability but can cause storms and delay failures from being noticed.
  • The outbox adds a table and a relay, and gives at-least-once publishing with small delay.

Rule of thumb: assume every message and every request can arrive twice. Design so that is harmless.

Do it yourself (about 25 minutes, Supabase SQL Editor)

You will build a tiny payments table that refuses duplicates. Use a throw-away project or a scratch table: nothing here touches your real data, and we remove the table at the end.

A. Create the table

  1. Open supabase.com/dashboard and click your project.
  2. In the left sidebar click SQL Editor. Click New query (it may say + New query or open a blank tab).
  3. Paste this and click Run (or press Ctrl + Enter): 
    create table lesson_payments (
  id bigint generated always as identity primary key,
  idempotency_key text not null unique,
  amount_paise integer not null,
  status text not null default 'created',
  created_at timestamptz not null default now()
);
  4. You should see "Success. No rows returned". The unique on idempotency_key is what blocks duplicates. (Amounts are in paise, so 49900 means Rs 499.00. Money is stored as whole numbers to avoid rounding errors.)

B. Send the same payment twice

  1. Clear the editor (Ctrl + A, Delete) and paste: 
    insert into lesson_payments (idempotency_key, amount_paise)
values ('order-1001-try-1', 49900)
on conflict (idempotency_key) do nothing
returning id, idempotency_key, amount_paise;
  2. Click Run. You should see one row in the result with an id (probably 1).
  3. Click Run again, with the exact same text. This time the result should be empty (no rows, or "Success. No rows returned"). The database saw the key already existed and skipped the insert, instead of charging again.
  4. Run once more if you like. Same empty result.

C. Prove only one row exists

  1. Replace the text with: 
    select * from lesson_payments;
  2. Click Run. You should see exactly one row, even though you ran the insert three times.
  3. Now see what happens without the safety. Run this: 
    insert into lesson_payments (idempotency_key, amount_paise)
values ('order-1001-try-1', 49900);
    You should get a red error mentioning a duplicate key and the unique constraint. The database refuses it. (Your app would catch that error and return the stored result.)
  4. A new key is a new payment. Run the first insert again, changing only 'order-1001-try-1' to 'order-1002-try-1'. Then select * from lesson_payments; shows two rows.

D. Clean up

  1. Run: 
    drop table lesson_payments;
  2. If the editor warns that the query has a destructive operation, read it, make sure it names only lesson_payments, and confirm. You should see "Success".

E. On paper: backoff with jitter

  1. A client retries after 1 s, 2 s, 4 s, 8 s. What is the total wait after the 4th retry? 1 + 2 + 4 + 8 = 15 seconds.
  2. Now say 1,000 clients all failed at 12:00:00 with no jitter. At what times do they all retry? Together at 12:00:01, then 12:00:03 (1 + 2), then 12:00:07 (1 + 2 + 4), and so on: spikes of 1,000 at once.
  3. Write in your notes how adding a random 0 to 1 second to each wait would spread each spike over a second.

Quick quiz

What does idempotent mean?

Doing the operation many times has the same effect as doing it once.

Why does a payment API need an idempotency key?

If the client times out it cannot know whether the charge happened. It retries with the same key, and the server charges only once and returns the stored result.

Why add jitter to exponential backoff?

Without it, many clients that failed together retry together in waves. Randomness spreads the load out.

What is a dead-letter queue for?

It holds messages that keep failing after a set number of attempts, so they stop blocking the queue and a human or tool can inspect and replay them.

What problem does the outbox pattern solve?

Writing to the database and publishing an event cannot be one transaction. Writing the event into an outbox table in the same transaction, and publishing it later by a relay, means neither is lost.

A queue delivers each message at least once. How do you stop a duplicate from charging a customer twice?

Make the consumer idempotent: store processed message IDs or an idempotency key under a unique constraint, and skip work that has been done.

Say it in an interview

"I assume messages and requests can repeat, so writes carry an idempotency key enforced by a unique constraint, and consumers are idempotent."
"Retries use exponential backoff with jitter and a cap, and messages that keep failing go to a dead-letter queue with an alert."

Common follow-up question: Can you get exactly-once delivery?

Not reliably across a network. The practical approach is at-least-once delivery plus idempotent processing, which gives the same effect as exactly-once. The outbox pattern covers the gap between the database write and publishing the event.
