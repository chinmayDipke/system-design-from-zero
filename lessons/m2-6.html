The receptionist and the personal assistant

Imagine a big office building. Visitors do not walk to any desk they like. They go to the reception. The receptionist checks who they are, says "Sales is on floor 3, Accounts on floor 5", turns away people without an appointment, and gives them a visitor pass. The staff upstairs never deal with the crowd at the door.

Now picture a school student whose teacher passes all her letters to outside people so nobody learns her home address. That is the opposite direction: someone standing in front of the sender.

Both are "someone in the middle". They are called proxies.

Forward proxy, reverse proxy, API gateway

A proxy is a server that passes requests along on behalf of someone else. Which side it stands in front of decides its name.

Forward proxy: stands in front of clients

Your laptop talks to the proxy, and the proxy talks to the internet for you. The website sees the proxy's address, not yours. Companies use it to filter sites at the office; people use VPN-like tools to hide their location. The server does not know the real client.

Reverse proxy: stands in front of servers

Users talk to the reverse proxy, which talks to your real servers. The client does not know the real servers. You already met one: a load balancer is a kind of reverse proxy. A reverse proxy usually does more than forward:

  • TLS termination: it handles HTTPS encryption once, so the servers behind it can speak simple HTTP on a private network and need no certificates.
  • Compression: it shrinks responses (gzip or Brotli) before sending them.
  • Caching: it keeps copies of common responses and answers them without bothering the app.
  • Routing: /api to the API servers, / to the web servers, /images to the file servers.
  • Protection: hides internal servers, blocks bad traffic, can serve a friendly error page when the app is down.

API gateway: a reverse proxy for APIs, with extra jobs

When you split a system into many small services (microservices), clients should not need to know about each one. An API gateway is the single front door that adds API-specific features on top of reverse proxying:

  • Authentication and authorization: check the API key or token once, at the door, instead of in every service.
  • Rate limiting: stop one client from sending too many requests (covered in a later lesson).
  • Routing to microservices: /users/* goes to the users service, /orders/* to the orders service.
  • Request shaping: change versions or formats, combine several service answers into one response, add headers.
  • Logging and metrics in one place.

Examples: AWS API Gateway, Kong, and Nginx used as a gateway. Many cloud platforms and CDNs also bundle gateway features.

Reading a reverse proxy config (reading only, no install)

This is a small Nginx configuration. You do not need to run it. Just read the comments to see how little is needed to build a reverse proxy.

# Two app servers that sit behind the proxy
upstream app_servers {
    server 10.0.0.11:3000;   # app server 1
    server 10.0.0.12:3000;   # app server 2
}

server {
    listen 443 ssl;                       # users connect with HTTPS
    server_name example.com;
    ssl_certificate     /etc/certs/example.crt;   # TLS ends here
    ssl_certificate_key /etc/certs/example.key;

    gzip on;                              # compress responses

    location /api/ {
        proxy_pass http://app_servers;    # forward to the app servers
        proxy_set_header Host $host;      # keep the original host name
    }

    location /static/ {
        root /var/www;                    # serve files directly
        expires 7d;                       # tell browsers to cache them
    }
}

Reading it: HTTPS arrives at the proxy (TLS termination), /api/ requests are forwarded to one of two app servers (a tiny load balancer), static files are served directly with caching, and responses are compressed.

Trade-offs

  • One more hop adds a little latency, and one more thing that can fail (so run it redundantly).
  • A gateway is a choke point. If it is slow or down, everything is. If you put too much business logic in it, it becomes a hidden monolith.
  • Benefits are central security, simpler clients, and the freedom to change what is behind the door.
  • For a small app, one Nginx or the platform's built-in front door is plenty. A full API gateway pays off with many services or many outside API users.

A quick memory trick: forward = for the client, reverse = for the server.

Do it yourself (about 20 minutes)

A. Spot a proxy or CDN from the response headers

  1. Open Chrome, go to https://www.wikipedia.org, then press F12 and click Network.
  2. Reload with Ctrl + R. Click the first row (type document).
  3. Open the Headers tab and scroll to Response Headers.
  4. Look for clues of a middle layer: server (which software answered), via (proxies passed), x-cache (cache hit or miss), age (how long a cached copy has been held), cf-ray (Cloudflare). Not all will be there; headers differ per site and over time.
  5. Write in your notes: "Header ___ shows a proxy/cache sits in front, because ___."
  6. Repeat for https://www.cloudflare.com and one more site of your choice (for example a news site). Which one has the most clues?
  7. Reload each one twice. Does age or x-cache change? A growing age means you are getting an older, cached copy from the proxy, not a fresh one from the app.

B. Draw a gateway in front of microservices

  1. Open excalidraw.com and start a clean page (☰, Reset the canvas).
  2. Draw an ellipse (O) labelled Mobile app and another labelled Web app on the left.
  3. Draw one rectangle in the middle: API gateway. Under its name, write four short lines with the text tool: TLS, Auth, Rate limit, Routing.
  4. On the right, draw three rectangles: Users service, Orders service, Payments service.
  5. Draw arrows from both clients to the gateway, and from the gateway to each service. Label the three arrows /users, /orders, /payments.
  6. Answer in a text note: "Where is the login token checked?" (At the gateway, once.) "What breaks if the gateway dies?" (Everything: so run several copies behind a load balancer.)

Quick quiz

Forward proxy or reverse proxy: which one hides the identity of the client?

The forward proxy. A reverse proxy hides the servers.

Name four things a reverse proxy can do.

TLS termination, compression, caching, routing by path, hiding internal servers, load balancing.

What does an API gateway add over a plain reverse proxy?

API-specific features: authentication, rate limiting, routing to microservices, request shaping and central logging.

What is TLS termination and why is it useful?

The proxy decrypts HTTPS once, so backend servers handle plain HTTP and do not each need certificates and the CPU cost of encryption.

You have one small web app on a single server. Do you need an API gateway?

No. At most an Nginx reverse proxy (or the hosting platform's built-in one) for HTTPS and static files. A gateway pays off with many services or many external API clients.

Say it in an interview

"A forward proxy stands in front of clients; a reverse proxy stands in front of servers, handling TLS, caching and routing."
"With microservices I would put an API gateway at the edge for authentication, rate limiting and routing, and keep business logic out of it."

Common follow-up question: Is a load balancer the same as a reverse proxy?

A load balancer is a kind of reverse proxy whose main job is spreading traffic across servers. A reverse proxy is the wider idea: it can also terminate TLS, cache, compress and route. In practice one tool such as Nginx often does all of these.
