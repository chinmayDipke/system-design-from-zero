Ordering a parcel to a new friend's house

You want to send a gift to a friend. You know only her name. First you look up her address in your phone. Then you call to check she is home and agree on a secret word so nobody else opens the parcel. Then you send the parcel with a note: "Please send me your photo album." She posts it back, and you open it. Inside there are more notes: "Also see the other album", so you ask again.

Your browser does exactly this, in less than a second, every time you type a web address and press Enter.

The most famous interview question

"What happens when you type https://www.example.com into the browser and press Enter?" is asked everywhere because one answer touches DNS, networking, security, servers and the browser. Here are the steps. Learn them in order.

1. The browser reads the URL

A URL has parts: the protocol (https), the host (www.example.com), an optional port (default 443 for https) and the path (/products?id=7). The browser first checks if it already has a saved copy that is still fresh. If it does, the trip may end here.

2. DNS: find the IP

The browser needs a number, not a name. It goes through the chain from the last lesson: browser cache, OS cache, resolver, and if needed root, TLD and authoritative servers. Result: an IP address.

3. TCP handshake: open a connection

TCP is the reliable-delivery layer under HTTP. Before any data, both sides do a three-step greeting: "Hello?" (SYN), "Hello, I hear you" (SYN-ACK), "Great" (ACK). This costs one round trip of waiting. (HTTP/3 uses QUIC instead and merges some of these steps.)

4. TLS handshake: make it secure

For HTTPS, the browser and the server then agree on encryption. The server shows its certificate, the browser checks it, and both create a shared secret key. After this, everything is encrypted. This costs about one more round trip with modern TLS.

5. HTTP request

Finally the browser sends: GET /products?id=7 plus headers (including cookies for that site).

6. The server does its work

The request may not go to a single machine directly. Often it first meets a CDN (a network of nearby copy-holders for static files) or a load balancer (a traffic police that spreads requests across many servers). Both come in Module 2; for now, just know the names. A backend server runs the code, may ask a database, and builds a response.

7. The response travels back

A status code (200), headers and a body, usually HTML.

8. The browser renders

It reads the HTML top to bottom and builds the page structure (the DOM). When it meets <link> for CSS, <script> for JavaScript or <img> for pictures, it makes more requests. Styles and layout get applied, scripts run, and the page is painted on screen. JavaScript may then call APIs for more data, which is yet another request.

Trade-offs

  • Distance hurts: each round trip across the globe costs 100+ ms, and steps 2 to 5 need several. That is why we put servers and CDNs near users.
  • Reusing connections (keep-alive) saves handshakes but holds resources on the server.
  • Caching makes things fast but risks showing stale data. Deciding what to cache and for how long is a recurring design question.

In an interview, speak the steps in order, then say which ones you would optimise and how (cache DNS, reuse connections, add a CDN, compress). That is what turns a memorised list into a design answer.

Do it yourself (about 25 minutes)

A. Read the Timing tab

  1. Open Chrome. Open a new Incognito window: Ctrl + Shift + N. (This starts with a cleaner cache, so you see more of the steps.)
  2. Press F12, click the Network tab. Keep the panel open.
  3. Click the address bar, type https://www.wikipedia.org and press Enter. Rows fill the list.
  4. Click the very first row: its type is document. It is the HTML page itself.
  5. In the detail pane click the Timing tab. You see a list of timed phases with a bar for each. Match them:
    • DNS Lookup: step 2, finding the IP.
    • Initial connection: step 3, the TCP handshake.
    • SSL: step 4, the TLS handshake. (Chrome counts it inside "Initial connection".)
    • Request sent then Waiting for server response (also called TTFB, time to first byte): steps 5 and 6, the request and the server thinking.
    • Content Download: step 7, the response travelling back.
    If DNS, connection or SSL are missing or zero, Chrome reused an existing connection. That is normal; open a different site to see them.
  6. Look at the other rows below: scripts, images, styles. These are step 8, the "more requests".
  7. Write in your notes the time of each phase and which was the longest.

B. Walk the route with tracert

  1. Press ⊞ Win, type cmd, press Enter.
  2. Type this and press Enter (paste with Ctrl + V or right-click): 
    tracert google.com
  3. It prints a numbered list. Each line is one "hop": a router your packet passes through, with three timings. The first hop is your own router. Some lines show * and "Request timed out"; many routers simply do not reply, and that is normal.
  4. It can take up to a minute or two. To stop early, press Ctrl + C.
  5. Notice how the time generally grows as you go farther along. That is the distance cost from the trade-offs section.

C. Explain out loud

  1. Close this page. Set a timer for 2 minutes. Say the 8 steps out loud, as if the interviewer is in front of you. Then open the lesson and check what you missed. Repeat until you do not miss any.

Quick quiz

Why does the browser need DNS before it can send the request?

Networks route by IP address, not by name. DNS turns the host name into an IP.

What is the point of the TCP handshake and the TLS handshake?

TCP sets up a reliable connection between the two machines. TLS then agrees on encryption and checks the server's certificate, so the data is private.

Which Timing bar do you look at to judge how slow the server itself is?

"Waiting for server response" (TTFB).

Why are later requests to the same site often faster than the first?

DNS is cached and the connection (with TCP and TLS already done) is reused. Some files may also come from the browser cache.

Your page's first byte takes 1.5 seconds. Where do you start looking, and why?

On the server side: slow code, slow database queries, or no caching, since TTFB is mostly server time plus network. I would also check whether a CDN or cache could answer instead.

Say it in an interview

"The browser parses the URL, resolves the domain through DNS, opens a TCP connection, does a TLS handshake, sends the HTTP request, and the server responds, usually via a CDN or load balancer. Then the browser renders the HTML and fetches CSS, JS and images."
"Each round trip costs real time, so we cache DNS, reuse connections and put content close to the user."

Common follow-up question: How would you make that page load faster?

Reduce round trips and bytes. Use a CDN so content is near the user, keep connections alive, use HTTP/2 or HTTP/3, cache static files with sensible headers, compress responses, load fewer or smaller files, and make the server's own work (queries, code) faster. I would measure first, using TTFB and the Network timing, then fix the biggest piece.
