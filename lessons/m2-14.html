The index at the back of the book, again

You are looking for every page that mentions "monsoon" in a 400-page cookbook. Reading every page takes an hour. Instead you open the index at the back: it is sorted by word, and next to each word it lists the pages: "monsoon: 12, 87, 203". Done in ten seconds.

The normal order of a book is page to words. The index flips it: word to pages. That flip is the heart of how search engines work. A good index also treats "pakora" and "pakoras" as the same entry, and lists the most useful pages first.

Why LIKE is slow, and what replaces it

The problem with LIKE '%word%'

A query such as WHERE body LIKE '%monsoon%' has to look inside every row's text, because the word could be anywhere. A normal B-tree index cannot help when the pattern starts with %. On a million articles it reads a million texts. It also has no idea of relevance (which result is best), and it does not know that "run", "runs" and "running" are the same word.

The inverted index

A search engine does the work once, when a document is saved, so that searching is cheap. It builds an inverted index: a dictionary of words, each pointing to the list of documents that contain it (a posting list).

  • Tokenizing: split the text into words: "Fast bowling, again!" becomes fast, bowling, again.
  • Normalizing: lowercase everything, remove punctuation, drop very common stop words (the, a, is).
  • Stemming: chop words to a root so "running", "runs" and "run" match: bowling becomes bowl. It is rough: "runners" may become "runner", not "run".
  • Lookup: to search "fast bowl", find the lists for each word and intersect them: the documents that contain both.

Ranking

Many documents may match, so the engine sorts them by relevance. TF-IDF scores a document higher if the search word appears often in it (term frequency) and the word is rare across all documents (inverse document frequency). BM25 is the modern refinement of that idea and is the default in most engines. In one line: frequent in this document, rare in general, and not just because the document is very long.

Elasticsearch and OpenSearch as a concept

Elasticsearch (and its fork OpenSearch) is a server built around inverted indexes, spread over many machines (using ideas from the sharding and replication lessons). It gives full-text search, typo tolerance, filters, highlighting, and "facets" (counts by category) over an HTTP API. You usually do not make it your main database: you keep the truth in your main database and copy data into the search engine. Smaller options exist (Meilisearch, Typesense), and Postgres has built-in full-text search that is enough for many apps.

Keeping search in sync with the main database

Now there are two copies of the data, so they can disagree. Two approaches:

ApproachHowProsCons
Dual writesThe app writes to the database and the search engine in the same code pathSimple to startIf one write fails, they drift apart; no transaction spans both; race conditions
Change data capture (CDC)The database's change log is read by a tool and streamed (often through a queue like Kafka) into the search indexOne source of truth; reliable; replayableMore moving parts; the index is slightly behind (eventually consistent)

A simpler middle road: write to the database only, push an "updated" message to a queue, and have a worker update the index (with retries), plus an occasional full re-index to repair drift.

Trade-offs

  • Speed vs freshness: a search index is quick to read but updated slightly after the main data, so a new item may appear in search a moment late.
  • Extra system: a search cluster costs money and time to operate. Start with the database's own full-text search; move to Elasticsearch/OpenSearch when you need scale, typo tolerance or rich ranking.
  • Storage: the index is extra data on top of the original.

Do not say "just use Elasticsearch" first. Say "Postgres full-text search for now; a dedicated engine when search becomes a core feature or outgrows the database", then explain how you would keep it in sync.

Do it yourself (about 25 minutes)

You will use Postgres's built-in full-text search in the Supabase SQL Editor. Open your practice project, click SQL Editor and New query for each step. (If a popup asks about Row Level Security, running without it is fine for this practice table.)

A. Make a small table

  1. Paste and run: 
    create table articles (
  id bigint generated always as identity primary key,
  title text,
  body text
);

insert into articles (title, body) values
 ('Cricket match report', 'India won the match by five wickets after a fast bowling spell'),
 ('Running shoes guide', 'Best running shoes for beginners who run every morning'),
 ('Monsoon recipes', 'Hot pakoras and chai are perfect when the rain keeps falling'),
 ('Fast bowling tips', 'How fast bowlers train to bowl quickly and stay fit'),
 ('Morning routine', 'Runners wake early to run before the city wakes up');
    You should see "Success. No rows returned".

B. The slow way, and its limits

  1. Run: 
    select title from articles where body ilike '%run%';
    (ilike is a case-insensitive LIKE.) It matches the "Running shoes", "Morning routine" rows, but also anything containing the letters "run" inside another word. It checks every row's text, and it has no ranking.

C. See what tokenizing and stemming do

  1. Run: 
    select to_tsvector('english', 'The runners were running quickly');
    You should get something like 'quick':5 'run':4 'runner':2. Notice: "the" and "were" (stop words) are gone, "quickly" became quick, "running" became run, and each word has a position number. This is what goes into the inverted index. "runners" became runner, not run: stemming is rough.
  2. Run: 
    select to_tsquery('english', 'running');
    The query word is stemmed the same way and shows as 'run'. That is why it can match "run" in a document.

D. Search with a tsvector column and a GIN index

  1. Add a search column that is filled automatically, and index it. GIN is the index type made for inverted-index style lookups: 
    alter table articles add column search tsvector
  generated always as (
    to_tsvector('english', coalesce(title, '') || ' ' || coalesce(body, ''))
  ) stored;

create index articles_search_idx on articles using gin (search);
    Run it. Then open Table Editor, open articles, and look at the new search column: each row has its words and positions.
  2. Search for two words that must both appear. The & means AND : 
    select id, title
from articles
where search @@ to_tsquery('english', 'fast & bowl');
    You should get "Cricket match report" and "Fast bowling tips". The operator @@ means "this document matches this query".
  3. Search for "run": 
    select id, title
from articles
where search @@ to_tsquery('english', 'run');
    "Running shoes guide" and "Morning routine" match (they contain run or running). "Runners" on its own would not, since it stems to "runner". That is how stemming can surprise you.

E. Rank the results

  1. Run: 
    select title,
       ts_rank(search, query) as rank
from articles,
     to_tsquery('english', 'fast | bowl') as query
where search @@ query
order by rank desc;
    The | means OR. Rows that contain more of the words, or more often, get a higher rank and come first. Look at the numbers: the "Fast bowling tips" article should rank at or near the top. (Exact numbers may differ; the order is what matters.) ts_rank is Postgres's relevance score, in the spirit of TF-IDF and BM25.
  2. Try a friendlier query style that handles plain text typed by users: 
    select title
from articles
where search @@ websearch_to_tsquery('english', 'fast bowling');

With only 5 rows Postgres will not bother with the index, since scanning is cheaper. The GIN index pays off with thousands or millions of rows. Use explain on a big table to see it.

F. Clean up

  1. Run drop table articles; to remove the practice table.

Quick quiz

Why is LIKE '%word%' slow on a big table?

A leading wildcard stops a normal index from being used, so the database scans and reads the text of every row. It also gives no relevance ranking.

What is an inverted index?

A map from each word to the list of documents that contain it, built when documents are saved, like the index at the back of a book.

What do tokenizing and stemming do?

Tokenizing splits text into words. Stemming reduces words to a root (running to run) so different forms of a word match.

What is BM25 in one line?

A relevance score favouring documents where the word appears often, the word is rare across all documents, and length does not unfairly help. A refinement of TF-IDF.

Compare dual writes with change data capture for syncing a search index.

Dual writes are simple but can drift apart if one write fails. CDC reads the database's change log and streams it to the index, so the database stays the single source of truth, at the cost of more infrastructure and a small delay.

You run a small blog with 5,000 posts on Postgres. Elasticsearch or Postgres full-text search?

Postgres full-text search with a GIN index. It is enough, adds no extra system to operate and stays automatically in sync. Move to a dedicated engine if search becomes central or needs typo tolerance and heavy ranking.

Say it in an interview

"LIKE with a leading wildcard scans every row. I would use an inverted index, either Postgres full-text search with a GIN index or Elasticsearch, with BM25 ranking."
"The database stays the source of truth; I would feed the search index with change data capture or a queue and accept that it is eventually consistent."

Common follow-up question: A new product does not show up in search for a few seconds. Is that a bug?

No. The index is updated after the main write, so it is eventually consistent. I would keep the delay small and monitored, show the product by direct link immediately, and rebuild the index periodically to fix any drift.
