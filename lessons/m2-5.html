The traffic police at the crossing

Picture a busy junction in front of a mall with three entrance gates. If every car goes to Gate 1, a huge queue forms there while Gates 2 and 3 stay empty. So a traffic policeman stands at the junction and waves cars: "You to Gate 2, you to Gate 3." If Gate 3 is closed for repairs, he stops sending cars there.

A load balancer is that policeman for web requests. The mall gates are your servers. Users only know the one road; they never see which gate they were sent to.

But what if the policeman falls sick? The whole junction jams. So smart cities keep a second policeman standing by.

What a load balancer does

A load balancer (LB) sits in front of several identical servers. It receives every request and forwards it to one healthy server. Three benefits: more capacity (many servers share the work), availability (a dead server is skipped), and easy changes (add or remove servers without users noticing). It is the piece that makes horizontal scaling from the last lesson work.

L4 vs L7

Network traffic has layers. An LB can look at different layers:

L4 (transport)L7 (application)
Looks atIP addresses and ports onlyThe HTTP request: URL path, headers, cookies
Can doForward raw connections very fastRoute /api to one group and /images to another, terminate TLS, rewrite headers

Use forNon-HTTP traffic, huge throughputMost web apps and APIs

How it picks a server: the algorithms

AlgorithmHowGood whenWeakness
Round robinA, B, C, A, B, C, ...Servers equal, requests similarIgnores how busy a server is
Weighted round robinStronger servers get more turns (for example 3:1)Servers of different sizesWeights are set by hand

Health checks

The LB regularly pings each server (for example GET /health every 10 seconds). If a server fails a few checks in a row, the LB marks it unhealthy and stops sending traffic. When it passes again, it comes back. This is how failures stay invisible to users. Make the health endpoint cheap and honest: it should check what the server truly needs (for example it can reach the database), not just return "OK".

Sticky sessions, and why to avoid them

Sticky sessions (session affinity) make the LB send the same user to the same server every time, usually using a cookie. It is a quick patch for servers that keep session data in memory. Problems: load becomes uneven (a heavy user pins one server), and if that server dies the user loses their session. The better fix is what you learned last lesson: stateless servers with sessions in Redis. Use stickiness only as a short-term crutch, or for things like WebSockets where a connection must stay on one server.

The load balancer is itself a single point of failure

If all traffic goes through one LB and it dies, your site is down however many servers you have. The fix is a pair: an active LB and a passive (standby) one that watches the active one with a heartbeat and takes over its address if it stops. Cloud providers do this for you, and large systems also put several LBs behind DNS or a shared IP.

Examples you will meet

  • AWS Application Load Balancer (ALB): a managed L7 balancer. (The AWS Network Load Balancer is its L4 sibling.)
  • Nginx (and HAProxy): free software you run yourself, can act as an L7 balancer.
  • Cloudflare: a global network that can balance traffic across servers and regions, and also acts as a CDN.

Trade-offs

  • An LB adds one extra network hop (a few milliseconds) and one more thing to run and watch.
  • L7 is flexible but costs more CPU than L4.
  • Smarter algorithms need more tracking. Round robin is simple and fine when requests are alike; least connections shines when some requests are long.

Also say "TLS termination": the LB can handle HTTPS decryption once, so the servers behind it speak plain HTTP on a private network. The next lesson covers this.

Do it yourself (about 30 minutes)

A. Spot the load balancer clues in a big site's headers

Big sites hide their servers, but response headers leave footprints. Look for headers like server, via, cf-ray and x-cache or similar. What you see differs from site to site and changes over time, so do not expect an exact match.

  1. Open Chrome and go to https://www.cloudflare.com.
  2. Press F12 and click the Network tab.
  3. Press Ctrl + R to reload so the requests are recorded.
  4. Click the first row in the list (type document, the page itself).
  5. In the right pane click the Headers tab and scroll down to Response Headers.
  6. Look for these names and write down their values:
    • server: often names the software or provider at the front (for example a CDN or web server name).
    • cf-ray: an id added by Cloudflare. Its presence means the request passed through Cloudflare's network, and the code at the end usually shows which city handled it.
    • via: lists proxies the request passed through.
    • x-cache or x-served-by: tells a cache hit from a miss, or which machine answered.
    Not every header will be present; that is normal.
  7. Repeat with https://www.wikipedia.org and https://github.com. For each site, note: which clue tells you a middle layer exists in front of the real server?
  8. Reload the same page 3 times and compare. If you see something like a server or machine id header, does it ever change? If so, different machines answered you: a load balancer in action.

B. Whiteboard: round robin vs least connections

You will act as the load balancer. Use paper or Excalidraw.

  1. Draw three boxes A, B, C (servers) and a timeline from 0 to 7 seconds along the bottom.
  2. Six requests arrive, one each second. Request R1 is heavy (takes 6 seconds); R2 to R6 are light (2 seconds each).
    RequestR1R2R3R4R5R6
    Arrives at0s1s2s3s4s5s
    Takes6s2s2s2s2s2s
    A request is "active" from its arrival until arrival + takes (R2 is active from 1s up to, but not including, 3s).
  3. Round robin: send R1 to A, R2 to B, R3 to C, R4 to A, R5 to B, R6 to C. Draw each as a bar on the server's row. Look at second 3 to 5: A is serving R1 and R4 at the same time, while the others may be free.
  4. Least connections: before each request, count active requests on A, B, C and send it to the lowest (if tied, pick the earlier letter). Walk through:
    • R1 at 0s: all 0, goes to A.
    • R2 at 1s: A has 1, B and C have 0, goes to B.
    • R3 at 2s: A 1, B 1, C 0, goes to C.
    • R4 at 3s: R2 just finished, so A 1, B 0, C 1, goes to B.
    • R5 at 4s: A 1, B 1, C 0 (R3 finished), goes to C.
    • R6 at 5s: A 1, B 0, C 1, goes to B.
  5. Compare: with least connections, the busy server A got no extra work while it handled the heavy R1; with round robin, R4 was stuck sharing A with R1. Write one sentence on which you would choose when request durations vary a lot.
  6. Extra: add a fourth server D that is twice as powerful. Which algorithm lets you say "D gets double the traffic"? (Weighted round robin.)
  7. Save as m2-5 round-robin-vs-least-conn.excalidraw.

Quick quiz

What is the difference between an L4 and an L7 load balancer?

L4 routes using only IP and port, so it is fast and simple. L7 reads the HTTP request (path, headers, cookies), so it can route by URL and do things like TLS termination, at higher cost.

When is least connections better than round robin?

When requests differ a lot in how long they take. Round robin may keep adding work to a server stuck on a heavy request; least connections avoids it.

What does a health check do?

It periodically tests each server. After failures the LB stops sending traffic to it, and resumes when it recovers, hiding failures from users.

Why are sticky sessions discouraged?

They cause uneven load and lose the session if that server dies. Keeping servers stateless with sessions in Redis is better.

How do you stop the load balancer being a single point of failure?

Run an active and a standby (or several), with a heartbeat so the standby takes over; managed cloud balancers already do this behind the scenes.

You have two servers: one has 4 CPUs, one has 8. Which algorithm and why?

Weighted round robin (weights 1:2), or least connections, so the bigger server receives proportionally more requests.

Say it in an interview

"I would put an L7 load balancer in front of stateless app servers, with health checks, using least connections because request times vary."
"The load balancer itself must not be a single point of failure, so I would run it as an active-passive pair or use a managed one."

Common follow-up question: Where does the load balancer sit, and can you have more than one?

Yes. Commonly one in front of the web tier, and another internal one in front of a service tier. Global traffic can first be steered by DNS or a CDN to the nearest region, where a regional LB takes over.
