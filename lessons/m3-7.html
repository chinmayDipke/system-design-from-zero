The doctor, the pulse and the X-ray

You feel unwell. A good doctor does three things. She reads your diary of symptoms ("fever on Tuesday, cough on Wednesday"). She checks numbers: temperature, pulse, blood pressure. And if needed she takes an X-ray to follow the problem through the body to find exactly where it is.

A running system also gets sick, and nobody can open it up and look. So we make it tell us how it feels: a diary (logs), vital signs (metrics) and a way to follow one request through every part (traces). Having these three is called observability.

Seeing inside a running system

Monitoring tells you that something is wrong. Observability lets you ask why, even for a problem you did not predict.

The three pillars

PillarWhat it isGood atWeak at
LogsTime-stamped records of eventsDetail about one event: the exact errorBig volume and cost; hard to see trends
MetricsNumbers over time (counts, rates, percentiles)Dashboards, trends, alerts. Cheap.No detail on one request
TracesThe path of one request across services, with timingsFinding which service is slowNeeds setup in every service; usually sampled

Logs: structured, with a request ID

A log line like Something went wrong! helps nobody. Write structured logs: one JSON object per line, with named fields, so tools can search and filter them. Always include:

  • timestamp and level (info, warn, error);
  • a request ID (also called correlation ID): generated at the edge, passed to every service and written in every log line, so you can pull up everything that happened for one user click;
  • who and what: user id, route, status, duration, error message.

Never log passwords, tokens or full card numbers.

Metrics: what to measure

You cannot watch everything. Use short checklists:

  • RED (for services, from the request's view): Rate (requests per second), Errors (failed share), Duration (latency).
  • USE (for resources like CPU, disk, queue): Utilisation (how busy), Saturation (how much is waiting), Errors.
  • Four golden signals (from Google's SRE book): latency, traffic, errors, saturation. It combines the two lists.

For latency, use percentiles (p50, p95, p99), not the average, as in the latency lesson. An average of 100 ms can hide the 1% of users waiting 5 seconds.

Distributed tracing

When one request passes through the gateway, an orders service, a payments service and the database, a trace follows it. Each unit of work inside is a span, with a start time, a duration and a parent. Drawn on a timeline, the spans show which step took the time. The trace ID is passed along with the request (in headers), which is the same idea as the request ID.

Alerts and dashboards

  • Alert on symptoms, not causes. Users feel "checkout is failing" or "pages take 5 s". Alert on that (error rate, latency, SLO burn). Do not page someone at 3 a.m. because "CPU is 80%" when users are fine.
  • Every alert should be actionable: someone knows what to do. Too many noisy alerts teach people to ignore them (alert fatigue).
  • Dashboards: one overview page per service with the RED numbers; deeper pages for resources. They are for looking during an incident, not a replacement for alerts.

Tools, by name

  • Prometheus: collects and stores metrics. Grafana: draws dashboards and alerts from them.
  • OpenTelemetry: a standard way for your code to produce logs, metrics and traces for many backends.
  • Sentry: catches application errors with stack traces and groups them.
  • Hosted platforms and cloud providers offer the same ideas (for example the logs tab of your database host).

Trade-offs

  • More data means more cost and noise. Log less at info, sample traces (keep 1 in 100, plus all errors).
  • High-cardinality labels in metrics (a label per user id) can overload the metrics store; put those details in logs.
  • Instrumentation costs a bit of performance and developer time, but you pay far more without it during an outage.

The usual debugging path: an alert says error rate is up (metric), a dashboard shows which route, a trace shows which service is slow, and the logs for that request ID show the exact error.

Do it yourself (about 30 minutes)

A. Find your own request in the Supabase logs

The Supabase dashboard changes its layout from time to time, so a menu may have a slightly different name from the one below. Look for the same idea.

  1. Open supabase.com/dashboard and click a project. In the left sidebar click Settings (gear icon) → Data API (it may say API) and copy the Project URL. It looks like https://abcdefgh.supabase.co.
  2. In a new browser tab, type that URL followed by a path and a unique marker, then press Enter. Replace the first part with yours: 
    https://YOUR-PROJECT.supabase.co/rest/v1/?lesson=m3-7
    You will probably see a short error message (for example saying no API key was given). That is fine: the request still reached the server and was logged. Do it 2 or 3 times.
  3. Go back to the dashboard. In the left sidebar click Logs (older versions: Logs & Analytics, or Logs Explorer).
  4. Pick the log source for the API: look for API Gateway, Edge Logs or API Edge. Click it.
  5. Set the time range (top right) to Last hour. Click a refresh button if there is one.
  6. In the search or filter box type lesson=m3-7 (or just m3-7) and press Enter. Logs may take up to a minute to appear; if the list is empty, wait, refresh and try again.
  7. Click one row to open its details. Find and write down: the method (GET), the path, the status code (probably 401 or 404), the timestamp and any request ID (it may be named x-request-id or request_id) and the latency if shown.
  8. Now remove your filter and look at other rows. Which has the most rows? Which status codes do you see? This is a metric in disguise: counting log lines by status.

B. Write 3 structured log lines

  1. Open a notepad file called m3-7 observability.txt.
  2. Copy these three example lines of an orders service. Notice that the request_id ties them together: 
    {"ts":"2026-11-02T10:15:01.120Z","level":"info","service":"orders","request_id":"req-8f3a","route":"POST /orders","user_id":"u_42","msg":"order created","order_id":"o_901","duration_ms":84}
{"ts":"2026-11-02T10:15:01.150Z","level":"warn","service":"payments","request_id":"req-8f3a","msg":"gateway slow","upstream":"card-gateway","duration_ms":2300}
{"ts":"2026-11-02T10:15:03.480Z","level":"error","service":"payments","request_id":"req-8f3a","msg":"payment failed","error":"timeout after 3000ms","order_id":"o_901"}
  3. Answer in the file: if a customer says "my order o_901 failed", what do you search for, and how do the lines tell the story? (Search request_id = req-8f3a and read the lines in time order: created, then slow gateway, then timeout.)
  4. Write 3 more lines of your own, for a login service: a successful login, a wrong password (warn, with no password in the line) and a database error.

C. Write 3 alert rules

  1. In the same file, write each rule as: condition, duration, who is told, what they do first. Example for you to copy the style: 
    1. Error rate on checkout above 2% for 5 minutes -> page on-call -> check the latest deploy, roll back if needed.
  2. Write two more of your own. Good candidates: p99 latency of the product page above 1 s for 10 minutes; payment success rate below 98% over 5 minutes; the dead-letter queue has more than 0 messages (DLQ).
  3. Check each rule: does it describe something a user would feel (symptom)? Rewrite any that say only "CPU above 90%" unless you can say why that hurts users.

Quick quiz

What are the three pillars of observability, and one strength of each?

Logs: detail of one event. Metrics: cheap trends, dashboards and alerts. Traces: following one request across services to find the slow step.

Why include a request ID in every log line?

So you can find every line from every service for one user request, by searching one ID.

What do RED and USE stand for?

RED: Rate, Errors, Duration (for services). USE: Utilisation, Saturation, Errors (for resources).

Why alert on symptoms instead of causes?

Symptoms are what users actually feel and catch many causes, including unknown ones. Cause-based alerts (high CPU) often fire when nobody is hurt and miss problems they did not think of.

Users say checkout is slow. In what order would you use metrics, traces and logs?

Metrics first to confirm and scope it (which route, since when). Then a trace of a slow request to find the slow service. Then the logs for that request ID to read the exact error or slow query.

Say it in an interview

"I would instrument with structured logs carrying a request ID, RED metrics per service, and distributed tracing, and alert on user-visible symptoms like error rate and p99 latency."
"Metrics tell me something is wrong, traces tell me where, and logs tell me why."

Common follow-up question: How do you avoid alert fatigue?

Alert only on symptoms that need a human now, tie each alert to a runbook, route low-urgency items to a ticket or a daily review rather than a page, and delete or tune any alert that fires without action.
