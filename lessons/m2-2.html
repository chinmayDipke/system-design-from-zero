The kirana shop's two notebooks

A kirana shop owner keeps a customer notebook: name, phone, address, one line per customer. She keeps a separate sales notebook: date, item, price, and the customer's name beside it.

She does not rewrite the customer's address next to every sale. If Asha moves house, she changes one line in the customer notebook. When she wants to know "where do I deliver this sale?", she looks up Asha's name in the first notebook. That is a database with tables, and the "look up" is a join.

Another shopkeeper keeps one big loose page per customer, with everything about that customer stapled together. Faster to read in one go, but changing one fact may mean fixing many pages. That is the other family: NoSQL.

Tables, keys, and the NoSQL families

The relational (SQL) world

A table is a grid. Each row is one thing (one customer). Each column is one fact about it (name, city). You talk to it with SQL. Examples: PostgreSQL, MySQL.

  • Primary key (PK): a column that is unique for every row, like an Aadhaar number. Usually id.
  • Foreign key (FK): a column that holds another table's primary key. orders.customer_id points at customers.id. The database refuses an order for a customer that does not exist.
  • Join: combine rows from two tables by matching the key. "Give me each order with the customer's name."

Normalization in plain words

Normalization means "store each fact in exactly one place". Three steps:

  • 1NF: one value per cell, no lists crammed into a column. Not phones = "999, 888"; make a row per phone.
  • 2NF: every column must depend on the whole key. If the key is (order, product), the product's name belongs in a products table, not in each order line.
  • 3NF: columns must depend on the key and nothing else. Do not store both pincode and city in the customer row if the pincode already decides the city; that is a separate fact.

Payoff: change a fact once, and it is right everywhere. No contradictions.

When to denormalize: joins cost time. For a read-heavy page (a product listing viewed a million times) you may copy data on purpose, for example storing the customer name inside each order. Reads get faster; writes get more work and the copies can drift apart. Do it only after you measure a real problem.

The NoSQL families

NoSQL means "not only SQL": databases that choose different trade-offs, often to scale across many machines more easily or to fit a different data shape.

Trade-offs

  • SQL: strong rules, joins, transactions, flexible questions. Scaling one huge database across machines is harder (later lessons: replication, sharding).
  • NoSQL: scales out easily and fits some shapes well, but you often give up joins and multi-row transactions, and you must design around the queries you will run.
  • Real systems often use both: Postgres for the money and the users, Redis for caching, a search engine for search.

Safe interview default: "I would start with PostgreSQL. It handles relations and transactions, and one well-indexed Postgres goes a very long way. I would add NoSQL only for a specific need."

Do it yourself (about 30 minutes)

A. Create a free Supabase project

If you already made a practice project, you can reuse it and skip to B. Otherwise:

  1. Open supabase.com/dashboard and log in.
  2. Click New project. If it asks which organization, pick your personal one.
  3. In Name, type sysdesign-practice.
  4. In Database password, type a strong password (or use the generate button) and save it in your password manager or notes now. You usually cannot read it again later.
  5. For Region, choose the one closest to India, for example Mumbai (Asia South) if it is offered, otherwise Singapore. Closer means lower latency, as you learned in Module 1.
  6. Pick the Free plan if asked, and click Create new project.
  7. Wait 1 to 2 minutes while it says "Setting up your project". When the dashboard appears, you are ready. (The labels may look slightly different from this lesson; the idea is the same.)

B. Create two tables with a foreign key

  1. In the left sidebar click SQL Editor, then New query (or the + button).
  2. Paste this into the big editor box: 
    create table customers (
  id bigint generated always as identity primary key,
  name text not null,
  city text
);

create table orders (
  id bigint generated always as identity primary key,
  customer_id bigint not null references customers(id),
  item text not null,
  amount_inr int not null,
  created_at timestamptz default now()
);
  3. Click Run (or press Ctrl + Enter). A popup may ask about Row Level Security for the new tables. For this practice project you can choose to run the query without it. You should see "Success. No rows returned".
  4. Click Table Editor in the sidebar. Both tables are listed, both empty.

C. Insert rows

  1. Back in SQL Editor, open a new query and paste: 
    insert into customers (name, city) values
  ('Asha', 'Pune'),
  ('Ravi', 'Chennai'),
  ('Meera', 'Delhi');

insert into orders (customer_id, item, amount_inr) values
  (1, 'Laptop', 52000),
  (1, 'Mouse', 700),
  (2, 'Keyboard', 1500);
  2. Click Run. Open the tables in Table Editor and check you see 3 customers and 3 orders. Note that id filled itself in: 1, 2, 3.

D. Join them, and test the foreign key

  1. New query, paste, run: 
    select c.name, o.item, o.amount_inr
from orders o
join customers c on c.id = o.customer_id
order by c.name;
    The results grid should show 3 rows: Asha Laptop, Asha Mouse, Ravi Keyboard. Meera is missing because she has no orders (a plain join only keeps matches).
  2. Now keep Meera too. Run: 
    select c.name, o.item
from customers c
left join orders o on o.customer_id = c.id;
    Meera appears with an empty (null) item. That is a LEFT JOIN: "all customers, with orders if any".
  3. Try to break the rule: 
    insert into orders (customer_id, item, amount_inr) values (999, 'Ghost', 1);
    You should get an error mentioning a foreign key constraint. The database refused an order for a customer that does not exist.

Keep these tables. The next lesson builds on the same project.

  1. On paper, write how one MongoDB-style document for Asha would look with her orders nested inside it (a JSON object with an orders array). Then write one advantage (one read gets everything) and one disadvantage (an order is also needed in a "all orders today" view, so you must copy or query across documents).

Quick quiz

What is the difference between a primary key and a foreign key?

A primary key uniquely identifies a row in its own table. A foreign key is a column that stores another table's primary key, linking the two.

What does normalization achieve?

Each fact is stored in one place, so updates happen once and cannot contradict each other.

Why would you ever denormalize?

To avoid costly joins on a very read-heavy path. You trade extra write work and the risk of copies drifting apart for faster reads.

Name the four NoSQL families with one product each.

Key-value (Redis), document (MongoDB), wide-column (Cassandra), graph (Neo4j).

You are building a payments ledger. SQL or NoSQL, and why?

SQL (such as PostgreSQL). Money needs transactions across rows, strict constraints and flexible reporting queries, which relational databases do best.

Say it in an interview

"I would start with PostgreSQL because the data is relational and I need transactions. I would normalize the schema, then denormalize only specific hot read paths after measuring."
"NoSQL is a family, not one thing. I pick key-value for sessions and counters, document for flexible shapes, wide-column for massive writes, graph for relationship queries."

Common follow-up question: Does NoSQL scale better than SQL?

Many NoSQL systems were designed to spread data across machines from day one, so scaling out is easier. But they gain that by dropping joins or cross-row transactions. SQL can scale too, with read replicas, caching and sharding, just with more work. It depends on the access pattern, not on the label.
