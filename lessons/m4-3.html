The railway map and the plate of noodles

Look at a metro map. Every line has its own colour, stations are in a neat row, and you can read it in seconds, even in a hurry. Now picture a plate of noodles: the same lines, but tangled in a heap. Both contain the same information. Only one can be understood.

In an interview the diagram is how the interviewer follows your thinking. A messy diagram makes them think you are confused, even when you are not. A tidy one makes you look clear. And tidy is not about being an artist: it is a few simple rules, plus practice.

Rules for a diagram anyone can read

1. Layout: a direction and a place for things

  • Users on the left, data on the right. Requests travel left to right; the database ends up at the far right.
  • Or top to bottom: users at the top, storage at the bottom. Pick one direction and keep to it. Mixing both makes arrows cross.
  • Put things in rows and columns. Align boxes of the same kind (all app servers in one column).
  • Leave gaps. Cramped drawings cannot be edited. Start with the main flow in the middle and add side parts around it.
  • Avoid crossing arrows. If two cross, move a box.

2. Standard shapes

ThingShape
Users, clients (browser, phone)Ellipse, or a box labelled "Client"
Services, servers, load balancersRectangle
Database, storageCylinder, or a rectangle labelled "DB". (Excalidraw has no cylinder key; a labelled box is fine.)
QueueA long thin box (like a line of people), labelled "Queue"
CacheA small rectangle next to the thing it caches, labelled "Cache"
Group (one data centre, one region)A big dashed rectangle around the members

The exact shape matters less than consistency: the same kind of thing always looks the same, and every box has a name.

3. Label the arrows with what flows

An arrow without a label means "something goes here". Write what: GET /feed, order event, image bytes. Use a solid arrow for a request that waits for an answer, and a dashed arrow for async (events and queues). If you use dashed, say so once.

4. Number the request path

Put small numbers on the arrows: 1, 2, 3 ... Then walk the interviewer along them: "The user's request goes (1) to the CDN, which on a miss (2) forwards to the load balancer, then (3) to an app server ..." Numbers turn a picture into a story, and stop you from forgetting a step. Keep a separate numbering, or letters, for the background path (a, b, c).

5. Colour sparingly

Use at most two or three colours, with a meaning each: for example, one for the main flow, one for async or background parts, and one (red) to mark a problem or a bottleneck you want to discuss. Colour by mood is noise. Black and white also works well.

6. Build it up in stages while you talk

  1. Stage 1: the simplest version. Client, one server, one database. Say, "Here is the bare minimum."
  2. Stage 2: fix the first problem. "One server is a single point of failure and cannot scale, so I add a load balancer and more servers" (SPOF).
  3. Stage 3: add what the numbers need. Cache for reads (caching), CDN for static files (CDN), a queue for slow background work (queues).
  4. Stage 4: only then deep dives. Zoom on one box and draw its insides separately, rather than cramming everything into one picture.

Drawing silently for five minutes loses the interviewer. Draw one thing, say why you added it, then draw the next.

Trade-offs

  • Detail versus clarity: a diagram with 25 boxes is unreadable. Show only what the discussion needs; mention the rest in words.
  • Drawing early versus asking first: do the requirements first (the 7 steps), so the diagram has a purpose.
  • Fancy icons look nice but cost time. Plain labelled boxes are enough.

Shortcuts you will use all the time in Excalidraw: R box, A arrow, O ellipse, T text, Ctrl + D duplicate, Shift for straight lines, and double-click on a shape or arrow to type its label (the Excalidraw lesson).

Do it yourself (about 30 minutes, Excalidraw)

A timed drill: redraw the web architecture from the picture, from memory, in under 5 minutes. Do it three times.

A. Prepare the timer and the canvas

  1. Open excalidraw.com. If an old drawing is there, click ☰ → Reset the canvas → confirm. (Save the old one first if you want it: ☰ → Save to….)
  2. Open the Windows Clock: press ⊞ Win, type Clock, press Enter, click Timer and set 5 minutes. Do not start it yet.
  3. Study the picture above for one minute. Then do not look at it again during the run.

B. Run 1: boxes first, then arrows

  1. Click the timer's play button.
  2. Press R and draw the first box on the far left. Double-click it and type Client, then Esc.
  3. With the box selected press Ctrl + D to copy it, and drag the copy to the right. Double-click, select the old text with Ctrl + A, type CDN, then Esc. Repeat for Load balancer and App servers in one row.
  4. Make the right-hand column the same way: Cache above, Database below. Then Queue and Workers underneath.
  5. Press A. Draw an arrow from each box to the next in the order above. Add numbers 1 to 6 beside the main-path arrows (T, click, type).
  6. Make the background arrows (app to queue to workers to database) dashed: press V, click the arrow, and choose the dashed Stroke style in the left panel.
  7. Stop the timer. Write down your time and what you forgot.

C. Checklist against the rules

  1. Tick each: users on the left? Data on the right? Every box named? Arrows labelled or numbered? No crossing arrows? Dashed used only for async?
  2. Fix one problem you find. If it takes more than a minute, note that you need to place boxes better the first time.

D. Runs 2 and 3: build in stages while talking

  1. Clear the canvas and restart the 5-minute timer.
  2. This time say out loud, as you draw: "Stage 1: a client and one server with a database. Stage 2: one server is a single point of failure, so a load balancer and two app servers. Stage 3: reads dominate, so a cache and a CDN. Stage 4: slow jobs go on a queue with workers."
  3. You should finish in under 5 minutes. If you did not, practise the shortcuts again: the fast way to make more boxes is Ctrl + D and drag.
  4. Save your best run as m4-3 drill.excalidraw.

Quick quiz

Where do users and data usually go in a diagram?

Users on the left (or top), data stores on the right (or bottom), so requests flow in one direction.

Why label arrows?

An unlabelled arrow does not say what flows. Labels such as "GET /feed" or "order event" make the diagram a precise statement.

Why number the request path?

Numbers turn the picture into a story you can walk the interviewer through, and make sure you do not skip a step.

How many colours should you use?

Two or three at most, each with a meaning (for example main flow, async path, problem area).

Should you draw the final design right away? Explain.

No. Start with the simplest version, then add parts one at a time as you explain the problem each part solves. It keeps the interviewer with you and shows reasons for each box.

Say it in an interview

"Let me start with the simplest version and add components as the requirements need them."
"I've numbered the request path: one, the client hits the CDN; two, on a miss it goes to the load balancer; and so on."

Common follow-up question: Can you zoom into this component?

Yes. I'd draw it separately, with its own inputs and outputs, and keep the main diagram unchanged. For example, for the queue I'd show producers, the queue, consumers, retries and a dead-letter queue.
