The family tree of your code

Think of a family tree on the wall at a wedding. Boxes are people. Lines say who is related to whom: "parent of", "married to", "cousin of". You understand the whole family in ten seconds without reading a long story.

A class diagram is the family tree of your code. Boxes are classes. Lines say how they relate: "is a kind of", "owns", "uses". In an interview you draw this before writing code, so the interviewer can check your thinking early.

How to read and draw a class diagram

UML (Unified Modeling Language) is a standard way to draw software. You only need one part of it: the class diagram. Learn the box and six kinds of lines.

The class box

A class is a rectangle with three parts: the name, the attributes (data) and the methods (actions). A sign in front of each line says who can see it:

SignMeaningTypeScript
+public: anyone can use itpublic (the default)
-private: only this classprivate or #
#protected: this class and its childrenprotected

An interface or abstract class gets a label «interface» (or «abstract») above its name. Write abstract names in italics if you like; on a whiteboard the label is enough.

The six lines

LineNamePlain meaningLooks like this in code
Solid line, open arrowAssociation"knows about" or "has a reference to"A field that points to another class
Dashed line, open arrowDependency"uses for a moment"A method parameter or local variable of that type
Hollow diamond at the ownerAggregation"has a", but the parts can live aloneParts are passed in through the constructor
Filled diamond at the ownerComposition"is made of"; parts die with the wholeThe class creates its parts with new
Solid line, hollow triangle at the parentInheritance"is a kind of"extends
Dashed line, hollow triangle at the interfaceRealisation"promises to do what the interface says"implements

The same relations in TypeScript. Real output underneath:

interface PaymentMethod {                        // «interface»
  pay(rupees: number): boolean;
}
class UpiPayment implements PaymentMethod {      // realisation (dashed + hollow triangle)
  pay(rupees: number): boolean {
    console.log(`UPI paid Rs ${rupees}`);
    return true;
  }
}

class OrderItem {
  constructor(public sku: string, public qty: number) {}
}
class Order {
  // Composition (filled diamond): Order creates its items and owns them.
  private items: OrderItem[] = [];
  // Association (plain arrow): Order keeps a reference to a payment method.
  constructor(public readonly customerId: string, private payment: PaymentMethod) {}

  addItem(sku: string, qty: number): void {
    this.items.push(new OrderItem(sku, qty));
  }
  checkout(rupees: number): boolean {
    return this.items.length > 0 && this.payment.pay(rupees);
  }
}

class Player {
  constructor(public name: string) {}
}
class Team {
  // Aggregation (hollow diamond): players are passed in and live on without the team.
  constructor(private players: Player[]) {}
  size(): number { return this.players.length; }
}

const order = new Order("cust-7", new UpiPayment());
order.addItem("TSHIRT-M", 2);
console.log(order.checkout(998));
console.log(new Team([new Player("Asha"), new Player("Ravi")]).size());

Multiplicity: how many?

Write numbers near the ends of a line: 1 exactly one, 0..1 zero or one, * or 0..* many, 1..* one or more. "A customer places 0..* orders; an order belongs to exactly 1 customer."

When to draw, and how much

  • Do: draw it in the interview after you list the entities. Keep only the important fields and methods. Show every relationship that matters, with multiplicity.
  • Do not: list every getter, every field, or every tiny helper class. A cluttered diagram hides your thinking.
  • Do not agonise over aggregation versus composition. If you are unsure, use a plain association and say "the order owns its items" out loud. Inheritance, interface and association are the lines you need most.
  • Trade-off: a diagram is quick to change but does not show behaviour over time (the order of calls). For that, interviewers sometimes ask for a sequence diagram, which is a separate drawing.

Tip: prefer a short sentence next to a line ("places", "contains") over a clever symbol. Words always win in an interview.

Draw it yourself (about 30 minutes)

You will draw a small shopping system: a customer places orders, an order has items, an order is paid by a payment method (UPI or card).

A. Open a fresh page

  1. Open excalidraw.com in Chrome. If an old drawing is there, click ☰ → Reset the canvas → Confirm.

B. Draw the first class box

  1. Press R and drag a rectangle about 200 pixels wide and 150 pixels tall, like a small card.
  2. Press T (text tool) and click near the top inside the box. Type Order. Press Esc.
  3. Press L (line tool). Hold Shift and drag a straight horizontal line under the name, from the left edge of the box to the right edge. Draw a second line a bit lower.
  4. Press T, click in the middle part and type - items: OrderItem[]. Press Esc. Click in the bottom part and type + addItem(), Enter, + checkout(). Press Esc.
  5. If it feels slow, that is normal. In the interview you can write just the name and two or three important members.

C. Copy the box for the other classes

  1. Press V. Drag a selection around the whole box (box, lines and texts). Press Ctrl + D to duplicate. Drag the copy to a new spot.
  2. Double-click each text in the copy and replace it. Make these boxes (one name each, members optional): Customer, OrderItem, Product, «interface» PaymentMethod, UpiPayment, CardPayment.
  3. Place them like this: Customer on the left, Order in the middle, OrderItem to its right, Product to the right of OrderItem; PaymentMethod below Order; UpiPayment and CardPayment below PaymentMethod.

D. Draw the lines

  1. Press A (arrow tool). Drag from the Customer box to the Order box. Add the words places and the multiplicities 1 (near Customer) and 0..* (near Order) using the text tool. This is an association.
  2. Draw an arrow from OrderItem to Order. Click it with V. In the left panel find the arrowhead choices (look for Arrowheads, one for each end). Set the end at Order to a filled diamond and the other end to nothing. Add 1 at the Order end and 1..* at the OrderItem end. This is composition: an order owns its items.
  3. Draw an arrow from OrderItem to Product. Keep the plain arrowhead. Label it refers to. Multiplicity * to 1.
  4. Draw an arrow from Order to PaymentMethod (plain association). Label it paid by.
  5. Draw an arrow from UpiPayment up to PaymentMethod. Select it and set Stroke style to dashed and the arrowhead to a hollow triangle (it may be called "triangle outline"). Do the same for CardPayment. This is realisation.
  6. If your Excalidraw version has no hollow triangle or diamond option, use the closest shape and write the name of the relationship next to the line, for example implements. Interviewers care more about the words than the exact tip.

E. Check your own diagram

  1. Say out loud for each line: "An A ... a B". For example "a Customer places zero or more Orders" and "a UpiPayment is a PaymentMethod". If a sentence sounds wrong, the line is wrong.
  2. Save: ☰ → Save to… → Save to disk, name it m6-4 uml.

F. Optional: match the code

  1. Open typescriptlang.org/play, paste the code block from this lesson and press Ctrl + Enter. In the Logs tab you should see UPI paid Rs 998, true and 2.
  2. Find the line in the code that matches each of your arrows.

Quick quiz

What do the signs +, - and # mean before a member?

+ public, - private, # protected.

What is the difference between aggregation and composition?

Both mean "has a". In aggregation (hollow diamond) the parts can exist without the whole, like players without a team. In composition (filled diamond) the parts belong to the whole and die with it, like items in an order.

Which line means "implements an interface"?

Realisation: a dashed line with a hollow triangle pointing at the interface.

What does "1..*" at the end of a line mean?

One or more. For example an order must have at least one item.

In the interview you have 5 minutes for the diagram. What would you include and what would you leave out?

Include the main classes, two or three key fields or methods each, every important relationship with a short word and multiplicity, and any interfaces. Leave out getters, setters, helper classes and the aggregation-versus-composition debate; say the ownership out loud instead.

Say it in the interview

Let me list the entities first, then draw the relationships and their multiplicities.
An order owns its items, so that is composition. Items do not exist without the order.
Payment is an interface with UPI and card implementations, so adding a wallet later needs no change to Order.

Common follow-up question: "How do you decide between inheritance and an interface in the diagram?"

I use an interface when classes share a promise but not code, like PaymentMethod. I use inheritance only when children truly share data and behaviour with a parent and the "is a" relation is stable. When in doubt I choose the interface and put shared code in a helper that classes hold as a part.
