One apartment building, many families

Think of one big apartment building. Fifty families live in it. They share the lift, the water tank, the watchman and the electricity connection, so each family pays far less than if each had built its own house. But every family has its own locked door. Nobody can walk into another family's flat, and nobody should see another family's bills.

A software product that serves many businesses at the same time, such as many restaurants using one billing app, is the same. The restaurants are the tenants. They share the same servers and database (the building), but each must see only its own data (its own door).

Three things can go wrong in a building. A neighbour can leave the door unlocked (a data leak, the worst one). A neighbour can run a loud party all night and use all the water (a noisy neighbour). And a very big family may want its own separate house (a dedicated database). This lesson is about building the locks, the water meter and the option to move out.

Design a multi-tenant SaaS (restaurant billing, POS or any B2B app)

Before reading on, set a 10-minute timer and write your own requirements and a rough diagram. Then compare. Decide: if one developer forgets WHERE tenant_id = ... in one query, what stops a customer seeing another customer's data?

We follow the 7-step framework. This design uses database indexes and transactions, rate limiting, caching and auth basics. The product is imaginary and generic: an app that restaurants use to take orders and print bills.

1. Requirements

Functional:

  • A business can sign up (be onboarded) and gets its own workspace with its own users, menu and orders.
  • Staff of a business can create and view orders (the main data), run reports, and change settings.
  • Each tenant can have its own configuration and feature flags (for example a new report switched on for some tenants only).
  • The platform measures usage and bills each tenant.
  • A tenant can export all its data and can ask for it to be deleted when it leaves.

Non-functional:

  • Strong isolation: a tenant must never read or change another tenant's data. This is the number one rule.
  • Fair performance: one tenant's heavy use must not slow down the others.
  • Low cost per tenant: thousands of small tenants should be cheap to serve.
  • Easy upgrades: one code version and one schema change should reach all tenants.
  • Available during meal rushes, with order writes strongly consistent (ACID).

Out of scope: the payment gateway, the internals of the kitchen printer, mobile app design, and the identity provider (login itself is in the auth lesson).

2. Estimation

Assume 10,000 tenants (restaurants), averaging 100 orders a day, with a few big chains doing 100 times that. Each tenant has about 5 staff devices.

  • Orders: 10,000 x 100 = 1,000,000 orders a day, divided by 100,000 s = 10 a second. Most come in the meal rush, so peak is perhaps 5 to 10 times: about 50 to 100 a second. Tiny for a database.
  • Reads: 50,000 staff devices refreshing the order screen every 10 seconds = 5,000 reads a second. These need to be cheap and cacheable.
  • Storage: 1,000,000 orders x 1 KB = 1 GB a day, about 365 GB a year. One database server handles this for years. That is the big surprise: the data is small, so the hard parts are isolation, fairness and operations, not capacity.
  • The per-tenant cost of the wrong model: with a schema per tenant and 50 tables each, 10,000 tenants means 500,000 tables, and a schema change must be run 10,000 times. With a database per tenant, there would be 10,000 databases to connect to, back up and upgrade. This is why the tenancy model matters.

3. API

POST /orders                 (tenant is taken from the login token, never from the request body)
  { "table": "T4", "items": [ { "sku": "dosa", "qty": 2 } ] }
  201 -> { "order_id": 8841 }

GET  /orders?status=open&limit=50     -> only this tenant's orders
GET  /settings                         -> this tenant's configuration and enabled features
PUT  /settings                         -> change it
POST /exports                          -> start a full data export  (202, then a download link)
DELETE /tenant                         -> start deletion (admin only, with confirmation)
GET  /usage                            -> metered usage this month (orders, staff accounts)

Rule: the tenant id comes from the verified token (a claim signed by the server), never from a URL or JSON field that the client can change. This is the first defence against leaks.

4. Data model

tenants      (id, name, plan, status, created_at, region, shard)
users        (id, tenant_id, email, role)
orders       (id, tenant_id, table_no, status, total_paise, created_at)   INDEX (tenant_id, created_at)
tenant_config(tenant_id PK, settings jsonb, feature_flags jsonb)
usage_events (tenant_id, metric, quantity, at)                           -- for billing

Every table that holds tenant data has a tenant_id column, and every index that serves common queries starts with tenant_id, so that each tenant's rows sit together in the index and queries stay fast as the table grows. Why SQL: orders, bills and reports need transactions, joins and exact numbers, and our volume is small.

5. High-level design

Numbers match the picture.

  1. A staff member's app sends a request with a login token to the API gateway. The gateway verifies the token and learns the tenant id.
  2. The gateway applies per-tenant rate limits (counters keyed by tenant) and forwards the request, with the tenant id attached, to the app service.
  3. The app service loads the tenant's config and feature flags (cached) to decide what this tenant may do.
  4. It checks a tenant-aware cache, where every key starts with the tenant id.
  5. On a miss, it queries the shared database. Before the query, the app tells the database who the tenant is (set local app.tenant_id), and row-level security makes the database itself filter rows.
  6. Very large or regulated tenants are routed to their own dedicated database (the "silo"), chosen from the tenant's record.
  7. Usage counters feed metering and billing.

Pick: start with shared tables with a tenant_id column and row-level security, because at our scale it is the cheapest and easiest to run. Keep the option to move a big tenant into its own database: that is the hybrid (often called pool plus silo). The tenant record says where its data lives, and the gateway or app routes accordingly. To make a later move possible, never write code that assumes one database, and always carry the tenant id.

Deep dive B: isolation with row-level security

The most common leak is human: one query somewhere forgets WHERE tenant_id = .... Row-level security (RLS) in PostgreSQL is a safety net inside the database itself. You enable it on a table and add a policy: a rule that every query must satisfy, added automatically. Even if the app code forgets the filter, the database adds it.

  • The policy compares each row's tenant_id with the current tenant. A simple way to know the current tenant is a session setting: the app runs set local app.tenant_id = '42' at the start of each transaction, and the policy reads it with current_setting('app.tenant_id', true). (Supabase apps often read it from the login token's claims instead, which works the same way.)
  • Use set local (lasts only until the end of the transaction), never a plain set. With a connection pool, a plain set sticks to the connection and leaks the tenant to the next request that borrows it. This is a serious real-world bug.
  • The gotcha: the table owner bypasses RLS by default, and so do superusers and roles with the BYPASSRLS attribute. If your app connects as the owner, the policy is never applied and everything seems to work, while nothing is protected. Fixes: connect the app as a non-owner role with only the permissions it needs, or run alter table ... force row level security so that even the owner is subject to the policy (this still does not apply to superusers or BYPASSRLS roles). You will see the owner bypass in the exercise.
  • A query with no tenant set should return nothing, not everything. Write the policy so a missing setting matches no rows. The exercise shows this.
  • RLS is a second lock, not the only lock. Keep the explicit WHERE tenant_id = ... in your code too (it helps the query planner and is obvious to readers). The two together mean one mistake is not enough to leak.

Deep dive C: noisy neighbours, caching, config and flags

  • Noisy neighbours. One tenant running a huge report or an import script can slow everyone. Defences: per-tenant rate limits and quotas at the gateway (a token bucket or sliding window keyed by tenant id, see the rate limiter lesson), per-tenant limits on concurrent requests and on queries' running time, fair queues for background jobs (one queue per tenant, or round-robin between tenants, so one tenant's 100,000 jobs do not block others), and the last resort: move the heavy tenant to its own database or machine. Report big queries on a read replica, not the main database. Rate limits by plan (small plan 10 requests a second, large plan 100) double as a pricing tool.
  • Tenant-aware cache keys. In a shared cache, a key like menu:today would mix tenants: the first tenant to fill it serves its menu to everybody. Always include the tenant id in the key: t:42:menu:today. Treat a cache key without a tenant prefix as a bug, and build a small helper function that makes keys, so nobody writes them by hand. The same goes for search indexes, file storage paths (tenant-42/receipts/...), queues and logs.
  • Per-tenant config and feature flags. Store settings (currency, tax rules, logo, enabled modules) in one row per tenant and cache it with a short TTL. A feature flag is an on/off switch evaluated per tenant: "new report: on for tenants 42 and 77". It lets you release to a few tenants first, turn a feature off without a deploy, and sell features by plan. Keep flags few and remove them when the rollout is done.

Deep dive D: onboarding, billing, export and deletion

  • Onboarding must be fully automatic, since thousands of tenants cannot each need an engineer: create the tenant row, the first admin user, default config and sample data, and (for a silo plan) provision a database. Make each step idempotent so a retry after a failure does not create a second tenant.
  • Metering and billing. Record usage events (an order created, a staff seat in use) with the tenant id, either by counting in Redis and saving totals, or by writing events to a queue and aggregating in a daily job. Bill from the aggregated totals, and keep the raw events for disputes. The plan limits (for example 500 orders a month) are enforced with the same counters.
  • Export. A tenant should be able to take its data out (it is their data, and often a legal requirement). Run it as a background job that reads only that tenant's rows, writes files to a private storage path, and gives a time-limited download link. It must not slow the live system, so run it against a replica and rate limit it.
  • Deletion. When a tenant leaves, delete its rows from every store: database, cache, search index, file storage, backups (by expiry) and logs where it is allowed. Use a soft delete first (mark the tenant as pending deletion for a grace period such as 30 days, then hard delete). With one table per tenant model, it is a drop; with shared tables it is a careful DELETE ... WHERE tenant_id = ... in batches. Keep a record of what was deleted and when.

Testing for cross-tenant leaks

The worst bug in this system is invisible: everything works, but one tenant can see another's data. Test for it on purpose:

  • Two-tenant tests: in the test database create tenants A and B with data. For every endpoint, call it as A and assert that no row, id, name or count from B appears. Run it on every build.
  • Guess the id: as A, request B's order by its id (GET /orders/8841). The answer must be "not found", not B's order. This is called an insecure direct object reference, and it is the classic mistake.
  • Test the database rules as the app does: run the policy tests while connected as the non-owner app role (as in the exercise below), because tests run as the owner pass even when the policy is wrong.
  • A missing tenant returns nothing, and a wrong tenant on INSERT is rejected.
  • Review every place that bypasses the normal path: background jobs, exports, admin tools, reports and caches, since these often skip the tenant filter.

7. Trade-offs, bottlenecks and wrap-up

  • Cost against isolation: shared tables are cheapest and least isolated; a database per tenant is the opposite. The hybrid lets each tenant be in the right place for its size and its contract.
  • Simplicity against safety: RLS adds a little complexity and a small cost per query, but turns a catastrophic mistake into a harmless empty result.
  • Fairness against utilisation: strict per-tenant limits protect everyone but can throttle a tenant who is paying and has a real spike, so allow bursts and make limits depend on the plan.
  • Bottlenecks: the single shared database as tenants grow (shard it by tenant id into several databases, with a lookup table from tenant to shard), one huge tenant (move it out), and cache memory.
  • Monitor (observability): requests, errors and latency per tenant (add the tenant id to every log line and metric), top tenants by load, queue age per tenant, rate-limit hits, and automated leak-test results.

At 10x scale (100,000 tenants): several shared database clusters with a tenant-to-shard directory so tenants can be moved between them, dedicated silos for the biggest tenants, a per-region setup so tenants' data stays in their own country, automated per-tenant migrations with a staged rollout, and a "cell" design: independent copies of the whole stack, each serving a few thousand tenants, so a failure affects only one cell.

B. Row-level security in the Supabase SQL Editor (25 to 30 minutes)

Use a scratch project, not a real one. This script creates tables called tenants and orders. If your project already has tables with those names, stop and use a different project (or rename them everywhere in the script). Run each block on its own: select all the old text with Ctrl + A, paste the new text, press Run (or Ctrl + Enter). The names, rows and tenants here are made-up examples.

If a result seems to be missing. Depending on the editor version, the results panel may show one tab per statement, or only the result of the last statement. In Part 3 and 4 our blocks end with commit;, which returns nothing. If you only see Success. No rows returned and no rows, the select result is hidden. Use this variant, which saves the rows in a temporary table and reads them after the commit (use a new table name each time, for example seen_2): 

begin;
set local role authenticated;
set local app.tenant_id = '1';
create temp table seen_1 as select id, tenant_id, item from orders order by id;
commit;
select * from seen_1;
We tested the plain blocks and this variant on a real Postgres; the rows are the same either way.

Part 1: tables and data

  1. Open your Supabase dashboard in Chrome and open a project. Click SQL Editor in the left sidebar, then + New query (it may be a plus icon).
  2. Paste this and press Run: 
    create table tenants (
  id   int  primary key,
  name text not null
);

create table orders (
  id           bigint generated always as identity primary key,
  tenant_id    int  not null references tenants (id),
  item         text not null,
  amount_paise int  not null
);

create index orders_tenant_idx on orders (tenant_id);

insert into tenants (id, name) values (1, 'Tenant One'), (2, 'Tenant Two');

insert into orders (tenant_id, item, amount_paise) values
  (1, 'Masala dosa', 9000), (1, 'Filter coffee', 4000), (1, 'Idli', 6000),
  (2, 'Paneer tikka', 21000), (2, 'Naan', 5000);

select tenant_id, count(*) as orders
from orders group by tenant_id order by tenant_id;
    You should see two rows: tenant_id 1 with orders 3, and tenant_id 2 with orders 2. There are 5 orders in total.

Part 2: turn on RLS and write the policy

  1. Paste this and press Run: 
    alter table tenants enable row level security;
alter table orders  enable row level security;

-- A row is visible (and writable) only if its tenant_id equals the tenant
-- named in the session setting app.tenant_id.
-- nullif(..., '') turns an empty or missing setting into NULL, which matches no row.
create policy tenant_isolation on orders
  using      (tenant_id = nullif(current_setting('app.tenant_id', true), '')::int)
  with check (tenant_id = nullif(current_setting('app.tenant_id', true), '')::int);

create policy own_tenant on tenants
  using (id = nullif(current_setting('app.tenant_id', true), '')::int);

-- Let the app role use the tables. (Supabase usually grants this already; running it again is harmless.)
grant usage on schema public to authenticated;
grant select, insert, update, delete on orders to authenticated;
grant select on tenants to authenticated;

select count(*) as orders_seen_by_owner from orders;
    You should see orders_seen_by_owner equal to 5. That is the gotcha, in action: you are running as the owner of the tables (the postgres role in the editor). Owners bypass row-level security, so RLS is switched on and the owner still sees everything. Never test RLS as the owner.
    What the policy says: using is the rule for rows that a query may see (and update or delete), and with check is the rule for rows a query may write. current_setting('app.tenant_id', true) reads a custom setting; the true means "return empty instead of an error if it was never set".

Part 3: see each tenant's own rows

We now pretend to be the app. In one run we start a transaction, switch to the non-owner role authenticated, name the tenant, query, and commit. set local lasts only until the transaction ends, so nothing leaks into the next run.

  1. Tenant 1. Paste and run: 
    begin;
set local role authenticated;
set local app.tenant_id = '1';
select id, tenant_id, item from orders order by id;
commit;
    You should see exactly 3 rows: 1 Masala dosa, 2 Filter coffee, 3 Idli, all with tenant_id 1. There was no where tenant_id = 1 in the query. The database added it.
  2. Tenant 2. Same block, with the tenant changed to '2': 
    begin;
set local role authenticated;
set local app.tenant_id = '2';
select id, tenant_id, item, amount_paise from orders order by id;
commit;
    You should see 2 rows: 4 Paneer tikka 21000 and 5 Naan 5000. Tenant 2 cannot see tenant 1's orders.
  3. The tenants table too. Run: 
    begin;
set local role authenticated;
set local app.tenant_id = '1';
select id, name from tenants;
commit;
    You should see one row: 1 Tenant One. Tenant 1 does not even learn that tenant 2 exists.
  4. Forget to set the tenant. This is the "developer forgot" case: 
    begin;
set local role authenticated;
select count(*) as visible_orders from orders;
commit;
    You should see visible_orders 0. With no tenant named, nothing is visible. A missing tenant fails closed (shows nothing), not open (shows everything). That is the behaviour you want.
  5. The owner trap again. Run this and notice what you get: 
    begin;
set local app.tenant_id = '1';
select count(*) as orders_without_role_switch from orders;
commit;
    You should see 5, not 3. The tenant is set, but we did not switch to authenticated, so we are still the owner and the policy is skipped. This is exactly what happens in real apps that connect as the table owner. The fix is to connect as a non-owner role, or to run alter table orders force row level security;, which makes even the owner follow the policy. (Even force does not apply to superusers or roles with the BYPASSRLS attribute, so in your editor, where you may be one of those, the role switch above is the reliable test.)

Part 4: tenants cannot write into each other's data

  1. Try to insert an order for the wrong tenant. We are tenant 1, trying to create an order for tenant 2: 
    begin;
set local role authenticated;
set local app.tenant_id = '1';
insert into orders (tenant_id, item, amount_paise) values (2, 'Sneaky order', 100);
commit;
    You should see a red error with the text new row violates row-level security policy for table "orders" (it may be shown with a code like 42501). That error comes from the with check part. If the next thing you run complains current transaction is aborted, run rollback; on its own once, and then continue.
  2. Try to change another tenant's rows. Tenant 1 tries to zero out tenant 2's prices: 
    begin;
set local role authenticated;
set local app.tenant_id = '1';
update orders set amount_paise = 0 where tenant_id = 2 returning id;
commit;
    You should see Success. No rows returned: zero rows were updated, because tenant 2's rows are invisible to tenant 1. There is no error, since from tenant 1's point of view those rows simply do not exist.
  3. Check that nothing changed. Back as the owner, run: 
    select tenant_id, count(*) as n, sum(amount_paise) as total
from orders group by tenant_id order by tenant_id;
    You should see tenant 1 with n 3, total 19000 and tenant 2 with n 2, total 26000. (9000 + 4000 + 6000 = 19000, and 21000 + 5000 = 26000.) The sneaky insert and update did nothing.
  4. A legitimate insert works. Tenant 1 adds its own order: 
    begin;
set local role authenticated;
set local app.tenant_id = '1';
insert into orders (tenant_id, item, amount_paise) values (1, 'Vada', 3000) returning item, tenant_id;
commit;
    You should see one row: Vada, 1.
  5. Check that the setting did not leak out. Run: 
    select current_user, current_setting('app.tenant_id', true) as leftover;
    You should see current_user as postgres and leftover as an empty value (or null). The role switch and the tenant setting disappeared at the end of each transaction, which is why we used set local.

Part 5: clean up

  1. Run the lines below. The editor may ask you to confirm a "destructive" query; confirm it: 
    drop table orders;
drop table tenants;
    You should see Success. No rows returned. Dropping the tables also removes their policies.
  2. Write three sentences in your notes: "RLS is a lock inside the database that works even when app code forgets a filter." "The table owner bypasses it, so test as a non-owner role." "Use set local and keep it inside a transaction."

C. Variation questions

1. One restaurant chain has 200 outlets and does 100 times the traffic of a normal tenant. What do you do?

First give it higher limits for its plan, and move its reports to a read replica. If it still affects others, move it to a dedicated database (the silo): copy its rows, switch its tenant record to point to the new database, and let the gateway route to it. The app code does not change, since it already carries the tenant id and asks "where does this tenant live?".

2. A tenant asks for "delete all our data" the day they leave. What do you do?

Mark the tenant as pending deletion (soft delete) and block logins. After a grace period, delete in batches: all rows with that tenant id in every table, the cache keys with its prefix, its search index documents, its files under its storage path, and its queued jobs. Backups expire on their own schedule. Keep an audit record of when and what was deleted, and confirm completion to the tenant.

3. Add a "super admin" screen that shows data across all tenants, for support staff. How do you do it safely?

Do not weaken the tenant policy. Use a separate role (or a separate service) with its own permission and its own policy or the bypass attribute, reachable only from an internal network and only for a few authenticated staff. Log every access, and prefer read-only views or tools that show only what support needs, with the ability to act "as" one tenant at a time.

Quick quiz

What is row-level security and why use it when the app already filters by tenant?

It is a rule inside the database that adds a tenant filter to every query automatically. App code can forget a filter in one query; RLS makes that mistake return nothing instead of leaking another tenant's data. It is a second lock.

What breaks if the app connects to Postgres as the table owner?

The owner bypasses RLS by default, so the policies are never applied and every tenant can see all rows, even though RLS looks enabled. Connect as a non-owner role, or use force row level security (which still does not bind superusers or BYPASSRLS roles).

What breaks if you use a plain set app.tenant_id = ... with a connection pool?

A session-level setting stays on the pooled connection after the request ends, so the next request that borrows it may run as the previous tenant. Use set local inside a transaction so the setting disappears at commit.

What breaks if the cache key is just menu:today in a shared cache?

The first tenant to fill the key stores its menu, and every other tenant is served that menu: a cross-tenant leak that also looks like a plain caching bug. Always prefix keys with the tenant id, such as t:42:menu:today.

What breaks if one tenant runs a huge import on the shared database and nothing limits it?

It uses the CPU, connections and I/O that the other tenants share, so everyone slows down (a noisy neighbour). Use per-tenant rate limits and quotas, fair job queues, replicas for reports, and as a last resort move that tenant to its own database.

For 5,000 small restaurants, would you pick shared tables, schema per tenant, or database per tenant? Why?

Shared tables with a tenant_id and RLS. Thousands of tiny tenants make per-tenant schemas or databases too costly to run and migrate (thousands of copies of every change). Keep the ability to move a big or regulated tenant into its own database later.

Say it in an interview

"I would start with shared tables and a tenant_id column on every table, with indexes that start with tenant_id, and enforce isolation twice: in the app with a tenant context taken from the verified token, and in the database with row-level security policies."
"For fairness I would add per-tenant rate limits and quotas at the gateway, tenant-prefixed cache keys, and fair job queues. A very large or regulated tenant can be moved to its own database, so the model is a hybrid."

Common follow-up question: How do you make sure there is no data leak between tenants?

Defence in depth: tenant id from the signed token only, RLS in the database with the app connecting as a non-owner role, tenant-aware cache and file paths, and automated tests that create two tenants and assert that every endpoint and every direct-id request returns nothing from the other tenant. Also add the tenant id to logs so that any suspicious access is visible.

Common follow-up question: How do you onboard thousands of tenants without manual work?

Automate it as an idempotent workflow: create the tenant record, admin user, default config and sample data, and only for premium plans provision a dedicated database. Shared tables mean a new tenant is just rows, so onboarding takes seconds and costs almost nothing.
