The class monitor and the notice board

A school has three notice boards: one in the corridor, one in the canteen, one in the library. When the principal changes the exam date, a peon walks to each board and updates it. For a few minutes, the corridor board says "Monday" while the library board still says "Friday".

If you read the corridor board you are right. If you read the library board you are briefly wrong, but soon it catches up. How strict should the school be? It could make you wait until all three boards agree (always right, but slow). Or let you read any board (fast, but sometimes old).

Those are consistency models: promises about how fresh and how orderly the data you read is.

How fresh is "fresh enough"?

Once data is copied to several machines (replication), a read may hit a copy that has not received the latest write yet. A consistency model is the promise the database makes about that. Stronger promise means simpler for you but slower, as PACELC said.

The models, strongest to weakest

ModelPromiseExample
Strong (linearizable)Once a write is done, every later read, from anywhere, sees it. It behaves like one single copy.Bank balance, seat booking
CausalIf B happened because of A (a reply to a comment), everyone sees A before B. Unrelated things may appear in any order.A comment never shows before the post it answers
Read-your-writesYou always see your own updates, though others may still see old data.You change your profile photo and refresh: you see the new one
Monotonic readsYou never see data go backwards in time. Once you saw version 5, you will not then see version 4.A post count that jumps 10, 9, 10 would be confusing
EventualIf no new writes come, all copies end up the same, "eventually". No promise about when.Likes count, DNS, follower counts

The classic bugs these fix

  • You post a comment, refresh, and it vanishes. The write went to the leader, the read to a lagging replica. Fix: read-your-writes, for example by reading your own recent changes from the leader, or by sticking you to one replica.
  • You refresh twice and see newer data, then older. Two reads hit two replicas at different lag. Fix: monotonic reads, by always sending the same user to the same replica.
  • A reply appears before the question. Fix: causal ordering.

Quorums: N, R, W

Some databases (Cassandra, DynamoDB-style systems) let you choose how strict each operation is using three numbers:

  • N: how many copies (replicas) of each item exist.
  • W: how many replicas must confirm a write before it counts as successful.
  • R: how many replicas you ask on a read before answering.

The rule: if R + W > N, every read set overlaps every write set in at least one replica, so the read must meet at least one replica holding the newest value. Each value carries a version number (or timestamp); the reader takes the highest.

Worked example, N = 3.

WRR + WGreater than 3?Result
224YesAlways sees the latest write. Balanced.
314YesFast reads, slow writes (all 3 must answer; one down blocks writes).
134YesFast writes, slow reads.
112NoFastest, but a read can miss the latest write: eventual consistency.

With W = 2, R = 2, N = 3 you can lose one replica and still read and write. That is a common default.

Trade-offs

  • Higher W or R means more consistency but slower answers and less availability (more nodes must be up).
  • Lower W or R means faster and more available but possibly stale reads.
  • R + W > N is not magic: it does not help if replicas are clocks-skewed, or while a write is only half-finished. Real databases add extra repair steps. Treat it as the idea to explain, not a full guarantee of strong consistency.

Choose the weakest model that does not hurt the user. Strong everywhere is expensive. A like count can be eventual; your own profile edit needs read-your-writes; money needs strong.

Do it yourself (about 25 minutes, paper only)

You are a database with 3 replicas, A, B and C. N = 3, W = 2, R = 2. Each holds a value balance with a version number.

A. Set up the board

  1. On paper (or Excalidraw), draw three boxes labelled A, B, C, side by side.
  2. Write inside each box: balance = 100, v1.
  3. Make a "log" column on the right where you will write each step.

B. A write that one replica misses

  1. A client sends write balance = 70 (version 2) to all three replicas.
  2. A receives it. Update box A to 70, v2. Write in the log: "A acks".
  3. B receives it. Update box B to 70, v2. Log: "B acks".
  4. C is slow: the message is delayed. Leave box C as 100, v1.
  5. Two acks have arrived and W = 2, so tell the client: write succeeded. Log it. Note that C is still stale.

C. Read from every possible pair

  1. A read asks any R = 2 replicas. There are three possible pairs. Try each one and write the answer in the log:
    Pair askedValues returnedHighest versionClient gets
    A and B70 v2, 70 v2v270
    A and C70 v2, 100 v1v270
    B and C70 v2, 100 v1v270
    Cover the last two columns first and work them out yourself.
  2. Write one sentence: "Every pair of 2 replicas out of 3 includes at least one of A or B, the two that have v2, so a read always meets the latest write."

D. Break the rule

  1. Reset the boxes to the state after step B (A and B at v2, C at v1).
  2. Change to W = 1, R = 1. Imagine the write had been acked by A only, so only A has v2 and B and C hold v1.
  3. Now a read asks only C. What does the client get? 100 (old). Write down why: R + W = 2, which is not greater than 3, so the read set and the write set need not overlap.
  4. Now try W = 3, R = 1: the write needs all three acks. Confirm any single replica read is now up to date (R + W = 4 > 3). What happens to writes if C is down? They cannot complete. Write that cost down.

E. Match the model to the bug

  1. For each, write which model fixes it (strong, causal, read-your-writes, monotonic reads, eventual):
    1. You post a comment, refresh, and it is gone.
    2. A friend's reply shows up before the message it replies to.
    3. The follower count of a celebrity is slightly old. Acceptable?
    4. You see 12 comments, refresh, see 10, refresh again, see 12.
  2. Check: 1 read-your-writes; 2 causal; 3 eventual is fine; 4 monotonic reads.
  3. Save your boxes as m3-2 quorum-simulation.excalidraw.

Quick quiz

What is the difference between strong and eventual consistency?

Strong: after a write completes, every read sees it. Eventual: reads may see old data for a while, but all copies converge if writes stop.

What does read-your-writes guarantee, and what does it not?

You always see your own updates. It does not promise that other users see them immediately.

N = 5, W = 3, R = 3. Does a read always see the latest write?

Yes by the rule: R + W = 6, which is greater than N = 5, so the sets overlap in at least one replica.

N = 3, W = 1, R = 1. What do you gain and lose?

Gain: the fastest reads and writes, and the system survives two failures. Lose: R + W = 2 is not greater than 3, so reads can be stale.

A news site shows article view counts, and a banking app shows balances. Which consistency would you choose for each, and why?

View counts: eventual, being a little off is harmless and it keeps the system fast. Balances: strong, a wrong balance can cause real harm, and the extra latency is acceptable.

Say it in an interview

"For money I would use strong consistency. For feeds and counters, eventual consistency is fine, with read-your-writes so a user sees their own post."
"With N replicas, if R + W is greater than N the read and write sets overlap, so a read sees the latest write. I tune R and W to trade speed against safety."

Common follow-up question: Why not make everything strongly consistent?

It costs latency and availability: more replicas must agree before answering, and if some are unreachable the system may have to refuse requests. Most data does not need it, so I use the weakest model that keeps the user experience correct.
