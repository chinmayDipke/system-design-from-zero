The school office that talks to 5,000 parents

A big school has one office that must reach parents. Some news is urgent: "School closed today because of heavy rain." Some is routine: "Fee due on the 10th." Some is just a newsletter. Parents like different ways: one wants a WhatsApp message, one reads email, one only answers a phone call, and a few said "please stop sending me the newsletter".

The clerk cannot shout at everyone at once. So the office uses a system: write the message once, check each parent's wishes, put the messages in trays (urgent tray first), and give them to different helpers: one for SMS, one for email, one for calls. If a helper cannot reach a parent, they try again later, and if it keeps failing, the note goes to a "problem pile" for a human.

That is a notification system. It is less about sending a message and more about sending the right message, to the right person, on the right channel, once, even when things go wrong.

Design a notification system (SMS, email, push, WhatsApp)

Before reading on, set a 10-minute timer and write your own requirements and a rough diagram. Then compare. Ask yourself especially: what happens if the SMS provider is slow, and what if the same message is sent twice?

We follow the 7-step framework. This design leans on queues and retries, idempotency and dead-letter queues, so skim those if they are fuzzy.

1. Requirements

Functional:

  • Send notifications over four channels: SMS, email, mobile push, WhatsApp.
  • Triggered by events (OTP, order shipped), by campaigns (a promo to 5 million users) and scheduled for later.
  • Templates with variables ("Hi {name}, your order {id} has shipped"), in several languages.
  • User preferences: a user can turn channels or categories (marketing, updates) on or off, and opt out entirely.
  • Track delivery status per message: queued, sent, delivered, failed, read.

Non-functional:

  • Priority: an OTP must arrive in seconds, even while a marketing blast is running.
  • Reliable: no message is silently lost. At least once delivery, with duplicates prevented where we can.
  • Scalable to big bursts (a campaign) and highly available.
  • Respects provider limits and legal rules (opt-outs, quiet hours, sender registration).

Out of scope: building our own SMS network (we buy that from providers), the in-app inbox screen, A/B testing of campaigns.

2. Estimation

Assume 10 million users, about 5 notifications each per day: 50 million a day.

  • Average: 50,000,000 / 100,000 s = 500 per second.
  • Peak is driven by campaigns, not by users. A marketing blast to 5 million users finished in 10 minutes (600 s) needs 5,000,000 / 600 = about 8,300 per second. Designing for about 10x average, 5,000 to 10,000 a second, is right.
  • Storage of delivery logs: about 300 bytes a row. 50,000,000 x 300 B = 15 GB a day, which is about 5.5 TB a year (15 GB x 365). Keep 90 days hot (about 1.4 TB) and archive older data.
  • Channel mix (assumption): 60% push, 20% email, 10% SMS, 10% WhatsApp. SMS and WhatsApp cost real money per message, push and email are almost free, so we must not send them carelessly.

What the numbers say: thousands per second with sharp spikes means a queue must sit between "someone wants to notify" and "we actually send". The database for logs needs good write throughput.

3. API

POST /v1/notifications
  { "user_id": 42, "template": "order_shipped", "data": { "order_id": "A91" },
    "category": "transactional", "priority": "high",
    "channels": ["push", "sms"],           (optional: otherwise use user prefs)
    "idempotency_key": "order-A91-shipped",
    "send_at": "2026-12-01T10:00:00+05:30"  (optional: schedule) }
  202 -> { "notification_id": "n_123" }       (accepted, not yet sent)

GET  /v1/notifications/{id}        -> status per channel
PUT  /v1/users/{id}/preferences    { "sms": false, "marketing": false }
POST /v1/campaigns                 { "segment": "...", "template": "...", "send_at": "..." }
POST /webhooks/{provider}          (callback from the SMS/email/WhatsApp provider)

The send call returns 202 Accepted, not 200: "we took it, we will send it". The caller must not wait for the SMS. The idempotency_key lets a caller retry safely (idempotency).

4. Data model

templates      (id, channel, locale, version, body)
preferences    (user_id, channel, category, enabled, updated_at)
device_tokens  (user_id, platform, token)           -- for push
notifications  (id, user_id, template, category, priority,
                idempotency_key UNIQUE, created_at)
deliveries     (id, notification_id, channel, provider, provider_msg_id,
                status, attempts, last_error, updated_at)
scheduled      (id, notification_id, send_at)  INDEX on send_at

Why these stores: templates, preferences and the idempotency key need correctness and uniqueness, so they go in a relational database (PostgreSQL; SQL vs NoSQL). The deliveries table is a huge, append-heavy log queried mostly by id or user; at 15 GB a day a time-partitioned table or a wide-column store works. Redis helps for short-lived things: dedupe keys and provider rate counters.

5. High-level design

  1. A service (orders, auth) or the campaign tool calls the Notification service.
  2. It validates the request and dedupes using the idempotency key.
  3. It checks the user's preferences and renders the template for each allowed channel.
  4. It puts one message per channel on a queue, chosen by channel and priority.
  5. A channel worker pulls messages, respects the provider's rate limit and calls the provider (SMS gateway, email service, push service, WhatsApp API).
  6. If the call fails, the message goes back with a delay (retry with backoff), and after too many tries into a dead-letter queue for a human to look at.
  7. Later the provider calls our webhook with "delivered" or "failed", and a status updater writes it to deliveries.

A scheduler scans the scheduled table and puts due messages onto the same queues at the right time, so scheduled traffic follows the same path.

6. Deep dives

Deep dive A: retries, duplicates and dead letters

Providers fail: timeouts, 5xx errors, rate limits. We retry, but not instantly and not forever. Use exponential backoff with jitter: wait 1 s, 2 s, 4 s, 8 s ... plus a random bit so thousands of failed messages do not all retry at the same instant. After, say, 5 attempts, move the message to the DLQ and alert.

Retries create the danger of duplicates: the worker sends the SMS, the provider accepts it, but the worker crashes before writing "sent". The queue redelivers, and the user gets two OTPs. We cannot get perfect exactly-once with an outside provider, so we aim for at-least-once plus dedupe:

  • Callers send an idempotency key; a unique index on it rejects the second copy.
  • Each queue message has a stable id (notification_id, channel). Before sending, the worker records "attempt started" with that id and skips if it is already marked sent.
  • Where a provider supports its own idempotency key or client reference, pass ours.

For an OTP a duplicate is harmless; for a "payment received" message it is confusing but not harmful. For a marketing offer it is annoying. Match the effort to the damage.

Deep dive B: priorities and provider limits

If OTPs and a 5-million-user promo share one queue, the OTPs wait behind the promo and users cannot log in. So use separate queues (and separate worker pools) per priority:

QueueExampleTargetWorkers
HighOTP, password resetsecondsAlways reserved, never starved
NormalOrder shipped, payment receivedunder a minuteScaled to load
LowMarketing, newslettersminutes to hoursThrottled on purpose

Providers also limit how fast you may send (for example X messages a second) and charge per message. Put a rate limiter (token bucket) in the worker, per provider, and keep low-priority throughput below the cap so there is always room for OTPs. For safety use two providers for SMS and email, with a circuit breaker that moves traffic to the second one when the first fails.

Deep dive C: preferences, opt-outs and status webhooks

  • Preferences are checked at send time, not just at enqueue time. A user may opt out while a campaign message waits in the queue. Cache preferences in Redis for speed, and update the cache when the user changes them.
  • Categories matter. Security messages (OTP) and transactional ones are allowed even if marketing is off; marketing must honour opt-out. Add quiet hours, and limit how many promos one user gets a day.
  • Rules vary by channel. In India, bulk SMS needs registered sender IDs and approved message templates (the telecom "DLT" rules) and respects a do-not-disturb list. WhatsApp business messages need pre-approved templates when you start the chat. Check the provider's current rules rather than guessing.
  • Status via webhooks. When the provider says "accepted", it means only "I took it", not "the phone received it". Delivery results arrive later as webhooks. Verify the webhook's signature, handle duplicates (providers resend), and let statuses only move forward (a late "sent" must not overwrite "delivered"). If webhooks go missing, poll the provider for old messages.
  • Scheduling: an index on send_at and a scheduler that every few seconds takes due rows (marking them as taken inside the same transaction so two schedulers do not both send). For "10am in the user's own time zone" store the user's time zone and compute send_at per user.

7. Trade-offs, bottlenecks and wrap-up

  • At-least-once beats at-most-once for most messages: a duplicate is better than a lost OTP. We reduce duplicates with dedupe instead of trying for the impossible exactly-once.
  • Asynchronous means delay: the API answers 202 quickly, but the actual send takes a moment. The price of reliability.
  • Bottlenecks: provider rate limits and cost (not our servers); the preference lookup on every send; the delivery-log writes.
  • Fallback channels: try push first; if not delivered in a minute, send SMS. Costs more but improves reach for important messages.
  • Monitor (observability): queue depth and age per priority, success rate per provider, DLQ size, time to deliver an OTP (p95).

At 10x scale (500 million a day): partition queues by user id, shard the delivery log by user and month, add more worker pools per channel, contract with multiple providers per country, and precompute audience segments for campaigns instead of looking up users one by one.

C. Variation questions

1. Send a push first, and if it is not delivered in one minute, send an SMS. How?

After sending the push, the worker schedules a "check" message with a one-minute delay (a delayed queue or the scheduler table). When it fires, it reads the delivery status. If the push is not delivered, it sends the SMS; if it is, it does nothing. Use the same idempotency key family so a late push callback cannot trigger a second SMS.

2. Marketing must go out at 10 am local time for every user across India and abroad. How?

Store each user's time zone. For a campaign, compute each user's send_at (10:00 in their zone converted to UTC) and write them as scheduled rows in batches. The scheduler releases them as they come due, into the low-priority queue, so the blast is spread over the day instead of arriving at once.

3. The main SMS provider is returning errors. What happens?

Retries with backoff first. If the failure rate stays high, a circuit breaker opens and the SMS worker routes new messages to the backup provider. High-priority OTPs switch first. When the main provider recovers, the breaker lets a few test messages through before sending everything back.

Quick quiz

Why does the send API return 202 and not 200?

Because the message is only accepted, not sent yet. The real sending happens later through queues and workers, and the caller must not wait for slow providers.

What breaks if OTPs and marketing share a single queue?

A marketing blast of millions of messages sits ahead of the OTPs, so users wait minutes for a login code. Use separate queues and worker pools per priority.

What breaks if a worker sends an SMS and crashes before recording "sent"?

The queue redelivers the message and the user gets a duplicate. We reduce this with idempotency keys and a stable message id checked before sending, accepting at-least-once delivery.

Why add random jitter to retry backoff?

Without jitter, thousands of messages that failed at the same moment retry at the same moment, hitting the provider in waves. Randomness spreads them out.

A user opts out of marketing while their message sits in the queue. How do you honour it?

Check preferences again at send time (a cached lookup), not only when the message was enqueued.

What breaks if you treat the provider's "accepted" response as "delivered"?

You would show "delivered" for messages that later fail (phone off, number invalid) and never retry or fall back. Delivery status must come from the provider's webhook, with statuses only moving forward.

Say it in an interview

"I would decouple with queues: the API validates, dedupes by idempotency key, checks preferences and renders a template, then publishes to per-channel, per-priority queues. Workers send through providers and retry with exponential backoff and jitter, with a dead-letter queue at the end."
"OTPs get their own high-priority queue and reserved workers so a marketing campaign cannot delay them, and each worker rate limits itself to the provider's cap."

Common follow-up question: How do you avoid sending a duplicate notification?

The caller supplies an idempotency key with a unique index, and each queue message has a stable id that the worker checks before sending. Since exactly-once with an external provider is not possible, I accept at-least-once and make a rare duplicate harmless.

Common follow-up question: How do you know a message was really delivered?

The provider's "accepted" only means it took the message. Final status arrives later by webhook (delivered, failed, read). I verify the webhook signature, handle repeats, let statuses move only forward, and poll the provider for messages whose webhook never arrived.
