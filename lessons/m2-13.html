The godown and the token slip

A shop keeps its small, often-used things (a notebook of prices) on the counter. But the big stuff, like sacks of rice and cartons of TVs, goes to a godown (a warehouse) outside. Putting a TV on the counter would block everything.

When you leave a parcel in a godown, you get a token slip with a number. Anyone with the slip can collect that parcel, but nobody can wander in and pick things. And if the owner wants to let a friend collect it only this evening, he gives the friend a slip that stops working after 6 pm.

Object storage is the godown for files. The database keeps the notebook, and files live in the godown.

Where files live

Files, blocks and objects

Object storageWhole files stored with a key and some metadata, accessed through an HTTP APIAmazon S3, Cloudflare R2, Supabase StorageImages, videos, backups, user uploads

Buckets and keys

In object storage you create a bucket, a top-level container (like user-uploads). Inside, each file (an object) is saved under a key, such as avatars/user-42.png. The slashes look like folders but the store is really flat: the key is just a long name. Each object also carries metadata (size, content type, and so on). You can put, get and delete objects, and normally not edit part of a file in place.

Object stores are built to be very durable (copies in several places), practically unlimited in size, and cheap per gigabyte.

Why images and videos never go in the database

  • Size: a 5 MB photo is millions of times larger than a typical row. It bloats tables, backups and replicas.
  • Speed: the database is your scarcest, most expensive resource; streaming big files through it slows real queries.
  • Cost: database storage costs more per GB than object storage.
  • Delivery: object storage plus a CDN is made for serving files.

The pattern: store the file in the bucket, and store only its URL or key in the database, for example users.avatar_key = 'avatars/user-42.png'.

Pre-signed (signed) URLs and direct upload

Suppose users upload videos. If the video passes through your app server, that server's bandwidth and memory are tied up. Better: the user's browser sends the file straight to the storage. But the bucket is private, so how is the browser allowed to? With a signed URL:

  1. The browser asks your app: "I want to upload a file."
  2. Your app (which holds the secret credentials) checks the user is allowed, and creates a signed URL: a normal link with a cryptographic signature and an expiry time baked in.
  3. The browser uploads (or downloads) using that link. After it expires, the link stops working.

This keeps secrets off the browser, saves your servers' bandwidth, and limits damage if a link leaks.

CDN in front

For public files, put a CDN in front of the bucket. Popular images are then served from nearby edges (last lessons), cutting latency and storage bandwidth bills.

Lifecycle rules

Lifecycle rules are automatic housekeeping: "delete temporary uploads after 24 hours", "move files not read for 90 days to cheaper cold storage", "delete old versions". They keep costs from growing silently.

Trade-offs

  • Public vs private buckets: public is simple and cacheable but anyone with the URL can read it. Private needs signed URLs (a bit more code) and is right for personal or paid files.
  • Object storage has higher latency per request than memory or a local disk, and you cannot append to or edit parts of an object cheaply. Great for big whole files, wrong for a database.
  • Your database row and your file can get out of sync (a row with no file, or a file with no row). Plan clean-up for orphan files.

Check what you store: always validate size and file type on upload, and never trust the file name the user sends.

Do it yourself (about 25 minutes)

You will do this in the Supabase dashboard. The labels may look a little different from what is written here, so look for the closest match.

A. A public bucket

  1. Open your Supabase project and click Storage in the left sidebar.
  2. Click New bucket (it may be a + button or "Create a new bucket").
  3. In the name box type public-images. Switch on the option named Public bucket. Click Create (or Save).
  4. Click your new bucket to open it. Click Upload file and choose any small image from your computer (a screenshot is fine; keep it under about 1 MB). Click Open. The image appears in the list.
  5. Click the image's row (or the three dots ⋮ beside it) and choose Get URL or Copy URL.
  6. Open a new Incognito window: Ctrl + Shift + N. Paste the link into the address bar with Ctrl + V and press Enter. Your image shows even though you are not logged in. That is a public bucket: anyone with the URL can see it.
  7. Look at the URL. Find the parts: your project address, the word public, the bucket name public-images and then the file name (the key).
  8. Open F12 in that Incognito tab, click Network, reload with Ctrl + R, click the image row and look at the response headers for cache-control and anything that shows a CDN in front. (Headers vary; note what you find.)

B. A private bucket and a signed URL that expires

  1. Back in Storage, click New bucket again. Name it private-files. Leave Public bucket switched off. Click Create.
  2. Open private-files and upload an image the same way.
  3. Click the file's row or its ⋮ menu. Choose Get URL and see what it offers. For a private file you should get a choice like Create signed URL with a box for how long it should last.
  4. Set the expiry to a short time. If you can type a number, enter 60 (seconds). If there are only preset choices, pick the shortest one. Click Create URL or Get URL, then copy the link.
  5. Paste it into an Incognito tab and press Enter. The image shows. Look at the end of the link: a long token=... part. That is the signature, and it also carries the expiry time.
  6. Wait past the expiry time, then reload the same tab with Ctrl + R. You should now see an error message (JSON text mentioning the link being invalid or expired) instead of the image.
  7. Now try the plain, unsigned address of that private file. Edit the signed link: change the word after storage/v1/object/ from sign to public and remove everything from ?token= onwards. Press Enter. It should be refused (not found), because the bucket is private.
  8. Write in your notes: "Signed URL = a normal link plus a signature plus an expiry. My app server creates it; the browser uses it."

C. Clean up and think

  1. Delete the test files: open each bucket, tick the file's checkbox, and click Delete. Then delete the buckets (use the ⋮ menu next to the bucket name, then Delete bucket). The free tier has a storage limit, so tidy up.
  2. On paper, write the database table you would create for user profile pictures. Suggested: users(id, name, avatar_key), where avatar_key is something like avatars/42.png, not the image itself.
  3. Write one lifecycle rule you would set for this app, for example "delete files in tmp/ after 1 day".

Quick quiz

What are the three kinds of storage, in one line each?

File: folders and files. Block: raw disk chunks for databases and operating systems. Object: whole files stored by key through an HTTP API, ideal for images, video and backups.

Why not store images in the database?

They are large, bloat tables, backups and replicas, slow the database that serves real queries, and cost more per GB. Store the file in object storage and keep only its key or URL.

What is a signed URL and why is it useful?

A link with a signature and an expiry that grants temporary access to a private object. It lets browsers upload or download directly without exposing secrets or passing the file through your server.

What does a CDN in front of a bucket give you?

Faster loading from a nearby edge and less traffic to the storage itself.

Users upload 200 MB videos. Do you accept them through your API server? What would you do?

No. Give the browser a signed upload URL so the video goes straight to object storage, then store the key in the database. That keeps the app servers free.

Say it in an interview

"I keep large files in object storage like S3, store only the key in the database, and serve public files through a CDN."
"For uploads, the app issues a short-lived signed URL so the client uploads directly to storage and the app servers never carry the bytes."

Common follow-up question: How do you handle a failed upload that leaves an orphan file?

Upload into a temporary prefix, only save the key in the database when the upload is confirmed, and use a lifecycle rule that deletes anything left in the temporary prefix after a day. A periodic job can also find files with no database row.
