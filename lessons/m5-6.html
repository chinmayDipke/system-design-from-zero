One window, one last seat

At a railway station there is one ticket window and one chart on the wall. The clerk looks at the chart, sees "Seat 42: empty", writes your name and stamps your ticket. Simple. Now add a second window. Two clerks look at the chart at the same moment. Both see "Seat 42: empty". Both write a name. Two passengers walk to the train with a ticket for the same seat.

The fix is a rule everyone follows: only one clerk can write on a seat at a time, and a seat you are "thinking about" is marked with a sticky note that falls off after five minutes if you do not pay.

Now it is 10 am on Tatkal day and a million people rush to the windows at once. You also need a waiting room outside, with a guard letting people in a few at a time. This lesson is all about those three ideas: never sell a seat twice, hold seats while paying, and survive the rush.

Design a ticket booking system (BookMyShow, IRCTC Tatkal)

Before reading on, set a 10-minute timer and write your own requirements and a rough diagram. Then compare. Write down in one sentence how you would stop two people booking the last seat. We will test your answer in the SQL editor below.

We follow the 7-step framework. This lesson leans on transactions and ACID, idempotency, and rate limiting.

1. Requirements

Functional:

  • Browse shows (or trains) and see a seat map with free and taken seats.
  • Select seats; the system holds them for a few minutes while you pay.
  • Pay, and on success the seats are booked and you get a ticket. On failure or timeout the seats are released.
  • Cancel a booking (and release the seats).

Non-functional:

  • No double booking, ever. This is the one hard guarantee. It needs strong consistency for seat inventory (the "C" side of CAP).
  • Browsing can be slightly stale (a seat map that is 2 seconds old is fine).
  • Survive huge spikes: a blockbuster opening or Tatkal at 10 am, maybe 50 to 100 times normal traffic.
  • Fair: first come, first served as far as possible. Low latency for hold and book.

Out of scope: how the payment itself works (see the payment lesson), pricing and offers, recommendations, the theatre's own admin tools.

2. Estimation

Assume 2 million bookings a day on an ordinary day.

  • Bookings: 2,000,000 / 100,000 s = 20 a second on average. For a big opening, 50x: 1,000 a second.
  • Browsing: about 100 seat-map views per booking: 2,000 a second on average and 100,000 a second at the spike. This is mostly reads and can be cached.
  • Seat rows: 5,000 venues x 3 screens x 4 shows a day x 7 days of advance sales = 420,000 shows. At 200 seats each that is 84,000,000 seat rows. At about 100 bytes a row: 8.4 GB. That fits on one ordinary database.
  • Contention: one hot show has 200 seats and 50,000 people trying in one minute: about 250 people for every seat.

The surprise: data size is tiny. The problem is not storage, it is many people fighting over the same few rows. So the design is about correctness under contention, and about protecting the database from the rush.

3. API

GET  /shows/{id}/seats
  200 -> { "seats": [ { "no": "A1", "status": "free" }, ... ] }     (cached for ~2 s)

POST /shows/{id}/holds        Idempotency-Key: k1
  { "seats": ["A1", "A2"] }
  201 -> { "hold_id": "h9", "expires_at": "..." }
  409 -> { "error": "seat A2 is no longer available" }

POST /bookings                Idempotency-Key: k2
  { "hold_id": "h9", "payment_ref": "pay_77" }
  201 -> { "booking_id": "b5" }          (409 if already booked, 410 if the hold expired)

DELETE /holds/{id}            release seats early
GET    /queue/status          -> { "position": 12043, "admitted": false }  (waiting room)

Both write calls carry an idempotency key, so a retry after a timeout cannot create a second hold or a second booking (idempotency).

4. Data model

shows          (show_id, movie, starts_at, venue_id)
seats          (show_id, seat_no, status [free|held|booked],
                held_by, held_until, version)           PK (show_id, seat_no)
bookings       (booking_id, user_id, show_id, amount_paise, status,
                idempotency_key UNIQUE)
booking_seats  (booking_id, show_id, seat_no)           UNIQUE (show_id, seat_no)

Why SQL: we need real transactions (book three seats all-or-nothing), row locks and unique constraints that the database enforces for us. That is exactly what ACID databases are good at, and the data is small. NoSQL stores that give up multi-row transactions would make the hard part harder. Redis helps on the side for holds with expiry, the cached seat map and the waiting room.

Notice UNIQUE (show_id, seat_no) on booking_seats. It is the last line of defence: even if every other layer has a bug, the database refuses a second booking of the same seat.

5. High-level design

  1. Users arrive through a virtual waiting room (a queue page served from a CDN). It admits people at a rate the backend can handle.
  2. Admitted users call the booking service. The seat map comes from a short-lived cache, not the database.
  3. The user picks seats. The booking service holds them: one atomic database step marks the seats held with a held_until time. If any seat is taken, nothing is held and the user gets 409.
  4. The user is sent to pay at the payment provider (about 5 to 10 minutes allowed).
  5. The provider calls our webhook with the result. On success, in one transaction the hold becomes a booking. On failure the seats are freed.
  6. A release job frees expired holds (and correctness does not depend on it, see deep dive B).
  7. A confirmation goes out through a notification system.

6. Deep dives

Deep dive A: how do we prevent double booking?

The danger is a read-then-write race: two requests both read "free", then both write "booked". Every fix below makes the check and the write happen as one step the database controls.

OptionHowProsCons
Row lock (pessimistic)BEGIN; SELECT ... FOR UPDATE; locks the seat rows. Others wait until you commit. Then update and commitSimple to reason about; good for booking several seats all-or-nothingWaiters queue up and hold connections; locks held too long hurt throughput; risk of deadlock
Conditional update (compare-and-set)UPDATE seats SET status='held' WHERE seat='A1' AND status='free'. If it changed 1 row you won, if 0 rows you lostOne statement, no explicit lock, very fast, no waitingMulti-seat requests need a transaction around several updates
Optimistic locking (version column)Read the row and its version; update WHERE version = :seen and add 1. 0 rows means someone changed it, so retry or failNo locks held while the user thinksUnder heavy contention many attempts fail and retry, wasting work
Unique constraintUNIQUE (show_id, seat_no) on bookings; the second insert failsCannot be bypassed; works for any code pathYou only find out at the end, so you still need holds for a good user experience
Redis holdSET hold:show:seat user NX EX 300: set only if absent, auto-expiresFast; built-in expiry; takes load off the databaseA second source of truth; if Redis loses data a hold vanishes (the database constraint still saves you)

Pick: a conditional update for holding (it is the simplest correct thing and avoids waiting), wrapped in a transaction for multi-seat requests that locks the seats in a fixed order (for example seat number ascending), so two people grabbing A1+A2 and A2+A1 cannot deadlock each other. Keep the unique constraint on booking_seats as the final guard. For very hot shows, use SELECT ... FOR UPDATE only for the short moment of confirming, not while the user is choosing. The optimistic version is good when contention is low (random seats in a big hall), poor for the first-day rush.

Deep dive B: holds, payment timeout and release

A hold must expire by itself. If a user closes the tab with seats held, nobody else should be locked out forever. Store held_until on the seat. A seat counts as free if status = 'free' or held_until < now(), so correctness does not depend on a background job running on time. The job just tidies up. The hold update can take over an expired hold in the same conditional statement.

The awkward case: the user pays at minute 5:01, a second after the hold expired, and meanwhile somebody else grabbed the seat. The payment is real money, so the webhook handler first tries to re-acquire the same seats if they are still free; if not, it must refund automatically and tell the user (refunds). Never silently keep the money without a ticket. Also limit how many seats and how many simultaneous holds one user can have, or a bot can hold a whole theatre.

Deep dive C: the waiting room, idempotency and read load

  • Virtual waiting room: when 1,000,000 people arrive at 10:00, the database cannot serve them all. Put a queue in front. Each visitor gets a position (Redis sorted set by arrival time, or a hosted queue service), and sees a static "you are number 12,043" page from the CDN. A controller admits N people per second based on what the booking service can handle, handing out a signed admission token that the API checks. This turns a vertical wall of traffic into a steady stream. Combine it with a rate limiter per user, and CAPTCHA or login to slow bots.
  • Fairness: queue by arrival time, or use a random draw among people who arrived in the first minute, so that a faster connection is not the only winner. Say which you chose.
  • Idempotent booking: the client generates an Idempotency-Key; bookings has a unique index on it. If the request is retried (timeout, double-click, webhook delivered twice), the second attempt finds the existing row and returns the same booking instead of creating another.
  • Read scaling: the seat map is served from a cache refreshed every second or two. If a seat looks free on a stale map but is taken, the hold call returns 409 and the app refreshes the map. The database is always the truth; the cache is only a hint.

7. Trade-offs, bottlenecks and wrap-up

  • Consistency over availability for seats: if the database primary is unreachable we reject bookings rather than risk selling a seat twice (CAP). Browsing from cache can keep working.
  • Pessimistic versus optimistic: locks are safe under high contention; version checks are cheaper under low contention. Hot shows are high contention.
  • Hold time: short holds free seats quickly but annoy slow payers; long holds let seats sit idle (and enable hoarding). 5 to 10 minutes is typical.
  • Bottleneck: all the contention for one hot show lands on a few rows of one database primary. Shard by show_id (sharding) so different shows live on different machines, and give a blockbuster its own capacity.
  • Monitor (observability): hold success rate, 409 rate, number of holds expiring, payment-after-expiry count (should be near zero), queue length and admit rate.

At 10x scale (10 million bookings a day, bigger spikes): shard seats by show, run read replicas for browsing, move holds into Redis with the database as the final guard, run the waiting room entirely at the CDN edge, and pre-warm capacity before known sale times.

B. Prevent double booking in the Supabase SQL Editor

Be honest about what the editor does. Each time you press Run, the editor sends your text to the database, and a single statement is committed (made permanent) straight away. This is called auto-commit. So a lone SELECT ... FOR UPDATE would take a lock and release it a moment later, and you would see nothing. That is why Part 3 below puts begin; ... commit; and a 15-second pause inside one run. Use a scratch project, not a real one. Everything here uses tables named demo_... and you drop them at the end.

Part 1: create the tables

  1. Open your Supabase dashboard in Chrome and open a project. Click SQL Editor in the left sidebar, then + New query (it may be a plus icon).
  2. Paste this, then press Run (or Ctrl + Enter). You should see Success. No rows returned: 
    create table demo_bookings (
  id        bigint generated always as identity primary key,
  show_id   int  not null,
  seat_no   text not null,
  user_name text not null,
  unique (show_id, seat_no)   -- one booking per seat per show
);

create table demo_seats (
  show_id    int  not null,
  seat_no    text not null,
  status     text not null default 'free',   -- free | held | booked
  held_by    text,
  held_until timestamptz,
  booked_by  text,
  version    int  not null default 0,
  primary key (show_id, seat_no)
);

insert into demo_seats (show_id, seat_no)
values (1, 'A1'), (1, 'A2'), (1, 'A3');

-- Good habit: no public API access to these tables
alter table demo_bookings enable row level security;
alter table demo_seats    enable row level security;
  3. Click Table Editor in the left sidebar. You should see demo_bookings (empty) and demo_seats with three rows: A1, A2, A3, all free. (It may show an RLS enabled badge; that is what we want.)
  4. Go back to the SQL Editor.

Part 2: the unique constraint stops a second booking

Run each statement below on its own: select all the old text with Ctrl + A, paste the new text over it, press Run.

  1. Asha books seat A1: 
    insert into demo_bookings (show_id, seat_no, user_name)
values (1, 'A1', 'asha')
returning *;
    You should see one row: seat_no A1, user_name asha.
  2. Ravi tries the same seat: 
    insert into demo_bookings (show_id, seat_no, user_name)
values (1, 'A1', 'ravi')
returning *;
    You should see a red error like duplicate key value violates unique constraint "demo_bookings_show_id_seat_no_key". The database refused the second booking. Even if Asha and Ravi had clicked in the same millisecond, one of them would have had to wait for the other to finish, and then got this error. That is the last line of defence.
  3. Real code usually does not want an error. Try the polite form: 
    insert into demo_bookings (show_id, seat_no, user_name)
values (1, 'A1', 'ravi')
on conflict (show_id, seat_no) do nothing
returning *;
    You should see Success. No rows returned: zero rows came back, which is how your app learns "someone else got it" and shows the "seat taken" message.
  4. Open the Table Editor, click demo_bookings: only Asha's row exists.

Part 3: compare-and-set, version check and holds

  1. Optimistic version check. Seat A3 starts at version 0. Run this: 
    update demo_seats
set status = 'booked', booked_by = 'asha', version = version + 1
where show_id = 1 and seat_no = 'A3' and version = 0
returning seat_no, booked_by, version;
    You should see one row: A3, asha, version 1. Now press Run again without changing anything. This time you should get no rows, because the seat is now at version 1, not 0. A second person working from the old version loses cleanly.
  2. Hold with an expiry. Asha holds A1 for 5 minutes. The where says: free, or held but expired. 
    update demo_seats
set status = 'held', held_by = 'asha', held_until = now() + interval '5 minutes'
where show_id = 1 and seat_no = 'A1'
  and (status = 'free' or (status = 'held' and held_until < now()))
returning seat_no, held_by, held_until;
    You should see one row with held_until about 5 minutes from now. (Seat A1 is free in demo_seats; the booking in Part 2 was in the other table.)
  3. Ravi tries to hold A1 (same text with the name changed): 
    update demo_seats
set status = 'held', held_by = 'ravi', held_until = now() + interval '5 minutes'
where show_id = 1 and seat_no = 'A1'
  and (status = 'free' or (status = 'held' and held_until < now()))
returning seat_no, held_by, held_until;
    You should get no rows: A1 is held and the hold has not expired.
  4. Pretend 5 minutes have passed, by moving the expiry into the past: 
    update demo_seats
set held_until = now() - interval '1 minute'
where show_id = 1 and seat_no = 'A1'
returning seat_no, held_by, held_until;
    Then run Ravi's hold again (the text from the previous step). This time one row comes back with held_by ravi. An expired hold is simply treated as free, so correctness does not depend on a cleanup job.

Part 4: a row lock across two query tabs

The plan: Tab 1 starts a transaction, locks seat A2, then sleeps 15 seconds while holding the lock. Tab 2 tries the same seat meanwhile, and must wait.

  1. You need two query tabs. In the SQL Editor press + New query twice, so you have two. Rename them if you like.
  2. In Tab 2 paste this and do not run it yet: 
    begin;

select seat_no, status from demo_seats
where show_id = 1 and seat_no = 'A2'
for update;

update demo_seats
set status = 'booked', booked_by = 'ravi', version = version + 1
where show_id = 1 and seat_no = 'A2' and status = 'free';

commit;

select seat_no, status, booked_by from demo_seats
where show_id = 1 and seat_no = 'A2';
  3. In Tab 1 paste this and press Run. It will run for about 15 seconds: 
    begin;

select seat_no, status from demo_seats
where show_id = 1 and seat_no = 'A2'
for update;

select pg_sleep(15);

update demo_seats
set status = 'booked', booked_by = 'asha', version = version + 1
where show_id = 1 and seat_no = 'A2' and status = 'free';

commit;

select seat_no, status, booked_by from demo_seats
where show_id = 1 and seat_no = 'A2';
  4. Quickly (within 15 seconds) switch to Tab 2 and press Run. Tab 2 should appear to hang: its SELECT ... FOR UPDATE is waiting for Tab 1's lock.
  5. When Tab 1 finishes (commit), Tab 2 wakes up. Its result should show seat A2 as booked by asha, not ravi. Tab 2's update changed zero rows because, after waiting, it saw the seat was no longer free.
  6. If it does not wait: if Tab 2 answers instantly with the same final result, your editor ran the two requests one after the other instead of at the same time (it may share one database connection). You still saw the correct outcome (only Asha got A2), but not the waiting. If you see a timeout error in Tab 1, change 15 to 5 and try again. In your real app, each user has their own connection, so the waiting is real.
  7. Reset the seat if you want to try again: 
    update demo_seats
set status = 'free', booked_by = null, version = 0
where show_id = 1 and seat_no = 'A2';

C. Variation questions

1. A family wants 6 seats together. How do you hold them?

All-or-nothing in one transaction: update the six seats where each is free (or expired), and check that the count of updated rows is 6; if not, roll back so no seat stays held. Lock or update the seats in a fixed order (by seat number) so two groups going for overlapping seats cannot deadlock. Return 409 naming the seat that failed.

2. The user pays successfully but the hold expired a minute ago. What now?

The webhook handler tries to re-acquire the same seats. If they are still free, book them. If someone else has them, refund automatically and tell the user clearly. Never keep the money without a ticket. Also log these cases; if they are common, the hold time is too short.

3. At 10:00 sharp, 1 million people hit "Book". What do you do?

Put a virtual waiting room in front, served from a CDN, and admit users at a rate the booking service can handle. Rate limit each user, use login and CAPTCHA against bots, cache the seat map, and keep the database path short: one conditional update per hold. Shed load with a friendly message instead of letting the database fall over.

Quick quiz

What is the read-then-write race in booking, and how do you stop it?

Two requests both read "seat is free" and both write "booked". Stop it by making the check and the write a single step the database enforces: a conditional update, a row lock (FOR UPDATE), or a unique constraint.

What breaks if you only check availability in your app code and have no unique constraint?

Two app servers can both pass the check at the same moment and both insert, so the seat is sold twice. The unique constraint in the database is the guard that works no matter which code path or server runs.

What breaks if holds never expire and a user closes the tab?

Their seats stay held forever, so nobody can buy them and the show sells out only on paper. Holds need a held_until time (or a Redis TTL) and expired holds count as free.

What breaks if two requests lock seats A1,A2 and A2,A1 in opposite orders?

Each holds one lock and waits for the other: a deadlock, and the database aborts one. Always lock seats in a fixed order, such as ascending seat number.

When would you choose optimistic locking over FOR UPDATE, and when not?

Optimistic suits low contention (people picking random seats in a big hall), since nothing is locked while the user thinks. For a hot show, with hundreds of people per seat, optimistic attempts fail and retry constantly, so use a conditional update or a short row lock.

Why is the seat map allowed to be stale, but the hold is not?

The map is only a hint to help the user choose, and stale data costs at most a refreshed screen. The hold is where the seat is actually claimed, so it must hit the database, the single source of truth.

Say it in an interview

"Data size is small, contention is the problem. I would keep seats in PostgreSQL and claim them with a conditional update inside a transaction, with a unique constraint on show and seat as the final guard against double booking."
"Seats are held for a few minutes with a held_until time, so an abandoned hold frees itself. For the 10 am rush I would put a virtual waiting room in front and admit users at a rate the booking service can handle."

Common follow-up question: Why not just use a distributed lock in Redis?

A Redis hold is fine for speed and expiry, but it is a second source of truth and can lose data on failover. I would still keep the unique constraint in the database as the final guard. The database transaction is what makes the booking itself safe.

Common follow-up question: How do you make booking idempotent?

The client sends an idempotency key with the booking request, and the bookings table has a unique index on it. A retry or a duplicate webhook finds the existing row and returns the same result, so one payment never creates two bookings.
