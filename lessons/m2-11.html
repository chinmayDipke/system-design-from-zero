The tiffin pick-up and the notice board

A restaurant kitchen gets 200 orders in the lunch rush. The cook cannot cook 200 dishes at once, and the waiter cannot stand and wait for each dish. So orders are pinned on a rail: the waiter drops a slip and goes back to work, and cooks take slips one by one. The rail is a queue. If a cook is sick, the slips just wait; nothing is lost.

Now picture the school notice board: "Sports day on Friday". The principal pins it once, and every class that follows the board reads its own copy. That is pub/sub: one announcement, many listeners.

Doing work later, and telling many

Why asynchronous?

Without a queue, a request does everything while the user waits: save the order, send the email, make the invoice PDF, update analytics. If the email service is slow, the user waits too, and if it is down, the whole request fails. With a message queue, the request saves the order, drops a message "send email for order 7" in a queue, and replies at once. A separate worker does the email later. Benefits:

  • Decoupling: sender and receiver need not be up at the same time or even know each other.
  • Buffering spikes: 10,000 messages in a minute are stored and handled at the workers' own pace. The database is not flooded.
  • Retries: if a worker fails, the message goes back to be tried again.

Producer and consumer

A producer puts messages in. A consumer (worker) takes messages out and processes them. You can run many consumers on one queue to work faster; each message goes to one of them.

Many systems combine them: a topic fans out into one queue per subscribing service, and each service's workers share that queue.

Delivery guarantees

GuaranteeMeaningRisk
At-most-onceDelivered zero or one times; never retriedMay lose a message
At-least-onceDelivered one or more times; retried until acknowledgedMay deliver duplicates
Exactly-onceProcessed exactly one timeVery hard in reality; usually built from at-least-once plus idempotent handling

The practical rule: assume at-least-once and make consumers idempotent (doing it twice has the same effect as once, for example by storing a message id and skipping ids you have already handled).

Ordering, dead letters, backpressure

  • Ordering: one queue is mostly first-in, first-out, but with many consumers or retries, messages can finish out of order. If order matters per customer, route all of a customer's messages to the same consumer or partition.
  • Dead-letter queue (DLQ): a message that fails again and again (a "poison message") is moved to a separate queue after N attempts, so it does not block everything. Humans or tools look at it later.
  • Backpressure: if producers are faster than consumers, the queue grows without end. Watch the queue length, add consumers, slow producers, or reject new work when it is too full.

A Postgres table as a simple queue

You do not always need a new product. A table plus the clause FOR UPDATE SKIP LOCKED makes a decent queue. Each worker grabs the next unclaimed row and locks it; other workers skip locked rows instead of waiting:

-- one worker claims one job
update jobs set status = 'processing'
where id = (
  select id from jobs
  where status = 'pending'
  order by id
  for update skip locked
  limit 1
)
returning *;

Good for modest volumes with no extra infrastructure; at very high volume a dedicated broker is better.

Trade-offs

  • Queues add complexity (another thing to run, monitor, and debug) and make results eventual: the user is told "we are processing", not "done".
  • You must design for duplicates, retries, poison messages and a growing backlog.
  • Do not use a queue when the user needs the answer in the same response, for example a login check.

The best interview line: "I would move the slow, non-urgent work to a queue, so the user gets a fast response and spikes are absorbed."

Do it yourself (about 25 minutes)

You will use pgmq, a queue that lives inside Postgres, offered by Supabase as "Queues". Use your practice project from the SQL lessons.

A. Enable the queue extension

  1. Open your project in the Supabase dashboard.
  2. Easiest way: click SQL Editor, New query, paste the line below, and click Run: 
    create extension if not exists pgmq;
    You should see "Success. No rows returned". If you get an error that the extension is not available or you lack permission, enable it from the dashboard instead: look for Integrations (older dashboards: Database, then Extensions), find Queues (the module for pgmq), and switch it on. The dashboard menus change over time, so look around if names differ.

B. Create a queue and send messages

  1. In a new query, run: 
    select pgmq.create('jobs');
    This makes a queue named jobs. (Keep queue names to lowercase letters, hyphens and underscores.) You should see a success result with an empty cell.
  2. Be the producer. Send a message (it is JSON): 
    select pgmq.send('jobs', '{"email":"a@b.com"}');
    The result shows a number: the message id, for example 1. Write it down.
  3. Send two more, one at a time, changing the email each time (for example c@d.com and e@f.com).

C. Be the consumer: read, visibility timeout, delete

  1. Read one message: 
    select * from pgmq.read('jobs', 30, 1);
    The three arguments are the queue name, the visibility timeout in seconds (30) and how many messages to fetch (1). You get a row with msg_id, read_ct (how many times it has been read, now 1), vt (the time until which the message is hidden) and your message JSON.
  2. The visibility timeout: the message is not deleted. It is just hidden for 30 seconds so other workers do not grab the same job. If your worker crashes and never deletes it, the message reappears after 30 seconds and another worker retries. That is how at-least-once delivery works.
  3. Prove it. Run the same select * from pgmq.read('jobs', 30, 1); again right away. You get the next message, not the first one, because the first is hidden.
  4. Wait over 30 seconds and read with a bigger count: select * from pgmq.read('jobs', 30, 10);. The first message is back, and its read_ct is now 2: it was delivered a second time.
  5. Now finish a job. Replace 1 with a real msg_id from your results: 
    select pgmq.delete('jobs', 1);
    It returns true. That message is gone for good. Doing the work and then deleting it is the "acknowledge" step.
  6. Read again with a count of 10: the deleted message no longer appears.

D. Clean up

  1. Remove the practice queue: 
    select pgmq.drop_queue('jobs');
    It returns true. (If a function name or result looks different in your version, check the Supabase Queues docs linked above; the ideas stay the same.)

E. Think

  1. Write on paper: what would happen if the visibility timeout was 2 seconds and the job takes 10 seconds? (The message reappears while still being worked on, so a second worker does it again: a duplicate. So the timeout must be longer than the job, and the job should be idempotent.)

Quick quiz

Give three reasons to use a queue.

Decoupling producer and consumer, absorbing traffic spikes, and retrying failed work without making the user wait.

What is the difference between a queue and pub/sub?

In a queue each message is handled by one consumer. In pub/sub every subscriber to the topic gets a copy.

Why make consumers idempotent?

Most systems deliver at-least-once, so the same message may arrive twice. An idempotent consumer gives the same result for duplicates.

What is a dead-letter queue?

A separate queue for messages that keep failing after several tries, so they do not block the main queue and can be inspected later.

What does the visibility timeout in pgmq.read do?

It hides the message from other consumers for that many seconds. If it is not deleted by then, it becomes visible again and is retried.

You need to run background jobs on a small app already using Postgres. What do you pick?

A Postgres-based queue (a jobs table with FOR UPDATE SKIP LOCKED, or pgmq). No new infrastructure; move to Kafka, RabbitMQ or SQS only when the volume or features demand it.

Say it in an interview

"I would put slow, non-critical work like emails behind a queue, so the API replies fast and traffic spikes are buffered."
"I assume at-least-once delivery, so consumers are idempotent, and failing messages go to a dead-letter queue after a few retries."

Common follow-up question: How do you pick between Kafka and SQS?

SQS if I want a simple managed job queue on AWS with little to operate. Kafka if I need very high throughput, several independent consumers reading the same events, or the ability to replay history, and I can afford its operational cost.
