The clever clerk behind the glass

Imagine a very clever clerk sitting behind a glass wall in a bank. She can read and think, but she cannot touch anything. You slide a request under the glass: "Please check the balance in account 123."

She cannot open the computer herself. So she slides a note back: "Please run check_balance for account 123." You (the assistant on your side) run it and slide the result back: "Balance is 5,000." Now she writes you the final answer. That is tool calling: the model asks, your code does, the model reads the result.

A workflow is a bank form with fixed steps: step 1, step 2, step 3, always in that order. An agent is the clerk deciding the steps herself: "First I will check the balance, then, hmm, the account is frozen, so I will look up the reason." More freedom, and more ways to go wrong.

Tools, the agent loop, and when not to use one

A language model only produces text (lesson 1). It cannot send an email, read your database or know today's weather. Tool calling (also called function calling) is the standard trick that lets it ask for those things safely.

The real request/response loop

  1. You send the model the conversation plus a list of tools. Each tool has a name, a plain-English description, and a JSON Schema for its inputs.
  2. The model replies with either normal text or a request to call a tool with arguments.
  3. If it asked for a tool, your code checks the request, runs the tool and gets a result.
  4. You add the tool result to the conversation and call the model again.
  5. Repeat until the model replies with plain text, which is the final answer.

Here is the shape of it. Every provider spells the fields a little differently, so treat this as an illustration and read your provider's tool-calling docs for the exact format.

// 1. what you send (shape only)
{
  "messages": [{ "role": "user", "content": "Where is order A12?" }],
  "tools": [{
    "name": "get_order",
    "description": "Look up one order by its id",
    "input_schema": { "type": "object",
                      "properties": { "id": { "type": "string" } },
                      "required": ["id"] }
  }]
}

// 2. what the model may send back (shape only)
{ "tool_call": { "name": "get_order", "arguments": { "id": "A12" } } }

// 3. you run get_order("A12"), append the result, call the model again
{ "role": "tool", "content": "{\"id\":\"A12\",\"status\":\"shipped\"}" }

// 4. now the model replies with text: "Order A12 has shipped."

And the loop in code, with a fake model so it runs anywhere (provider-neutral, and the model call is the only part you would replace):

const tools = {
  get_order: ({ id }) => ({ id, status: "shipped" }),
};
const fakeModel = (messages) => {
  const toolTurns = messages.filter((m) => m.role === "tool").length;
  return toolTurns === 0
    ? { toolCall: { name: "get_order", args: { id: "A12" } } }
    : { text: "Order A12 has shipped." };
};

const MAX_STEPS = 5;
const messages = [{ role: "user", content: "Where is order A12?" }];
for (let step = 1; step <= MAX_STEPS; step++) {
  const out = fakeModel(messages);
  if (out.text) { console.log("final answer:", out.text); break; }
  const tool = tools[out.toolCall.name];
  if (!tool) throw new Error("model asked for an unknown tool");
  const result = tool(out.toolCall.args);
  console.log(`step ${step}: ${out.toolCall.name} ->`, JSON.stringify(result));
  messages.push({ role: "assistant", toolCall: out.toolCall });
  messages.push({ role: "tool", content: JSON.stringify(result) });
  if (step === MAX_STEPS) console.log("step limit reached, stopping");
}

Running it prints step 1: get_order -> {"id":"A12","status":"shipped"} and then final answer: Order A12 has shipped. Notice MAX_STEPS: it is the most important line.

Workflow vs agent

WorkflowAgent
Who decides the steps?Your code (a fixed path, maybe with branches)The model, at run time
Predictable?Yes. Same input follows the same pathNo. Different runs can take different paths
Cost and latencyKnown in advanceVaries; every step re-sends the growing conversation
TestingTest each stepTest whole runs, many times
Best forKnown process: classify, draft, check, sendOpen-ended tasks where the steps cannot be listed in advance

Anthropic's article Building effective agents (linked below) names common workflow patterns: prompt chaining (step output feeds the next step), routing (classify, then send to a specialised path), parallelisation (run subtasks at once, or vote), orchestrator-workers (one model splits a task and hands pieces to others) and evaluator-optimizer (one model drafts, another critiques, loop). Most real products are workflows with one or two model calls inside, not free-roaming agents.

n8n-style orchestration

Tools like n8n let you build a workflow by dragging boxes ("nodes") and joining them: a trigger (new email, a form, a schedule), then steps (fetch data, call an LLM, branch on the result, write to a sheet, send a message). The same idea exists in code as a queue plus workers (queues) or a durable workflow engine. Visual tools are great for fast, understandable automations and for non-developers. They are weaker when you need version control, heavy testing, or complex logic. For the interview, it is enough to know the pattern: trigger, steps, branches, retries, a log of every run.

Loops, step limits and cost

An agent can loop forever: the tool keeps failing and the model keeps trying. Put hard limits in your code (not in the prompt): a maximum number of steps, a total token budget, a time limit, and a stop when the same tool call repeats. On a stop, return a clear "I could not finish" message.

Cost grows fast because each step re-sends everything so far. Example prices only, same as the previous lesson (Rs 200 per million input tokens, Rs 800 per million output): one plain call with 1,000 input and 300 output tokens costs 1,000 x 200 / 1,000,000 + 300 x 800 / 1,000,000 = 0.20 + 0.24 = Rs 0.44. Now an agent that takes 6 steps, where the input starts at 1,000 tokens and grows by 500 each step (1,000, 1,500, 2,000, 2,500, 3,000, 3,500 = 13,500 input tokens in total) with 100 output tokens per step (600 in total): input 13,500 x 200 / 1,000,000 = 2.70, output 600 x 800 / 1,000,000 = 0.48, total Rs 3.18. That is about 7 times the plain call, and slower too (six model round trips).

Safety: tools are power

  • Allow-list the tools. The model can only call what you listed, and your code rejects anything else.
  • Validate arguments like any user input. The model's output is untrusted input, not a command.
  • Least privilege: a read-only tool needs a read-only database role. Give "refund" a cap on the amount.
  • Human approval before anything risky or irreversible: sending money, deleting data, emailing a customer. The agent proposes, a person clicks Approve.
  • Make actions idempotent so a retry does not refund twice (idempotency).
  • Treat tool results as data. A web page or email a tool returns may contain "ignore your instructions" (prompt injection; more in guardrails).

When an agent is the wrong choice

  • You can write the steps down. Use a workflow; it is cheaper, faster and testable.
  • The action is irreversible and there is no human check.
  • You need the same answer every time (accounting, compliance).
  • Latency matters: a voice call cannot wait for six model round trips.
  • One well-prompted model call with retrieval (RAG) already solves the problem.

A good rule: start with a single call, then a workflow, and reach for an agent only when a workflow cannot express the task. Add the autonomy only where it earns its cost.

Do it yourself (about 30 minutes)

A. Draw a workflow on excalidraw.com (15 minutes)

Task: a shop gets support emails. Automatically classify each one, draft a reply, let a human check it, then send.

  1. Open excalidraw.com in a new tab with Ctrl + T. Press R and draw a box on the far left. Double-click it and type Trigger: new email.
  2. Press V, click the box, press Ctrl + D and drag the copy to the right. Rename it LLM: classify (refund / delivery / other).
  3. Copy again for a branch. Draw one box for each of refund, delivery and other. Label them Look up order, Look up tracking and Send to a human.
  4. Add the next two boxes after the first two branches: LLM: draft reply, then Human review (approve / edit), then Send email.
  5. Press A and draw the arrows in the direction the data moves. Label the branch arrows with the three categories. Add a dashed arrow from Human review back to LLM: draft reply labelled rejected, redraft (max 2 times).
  6. Circle the two places where an LLM is used. Everything else is ordinary code. This is a workflow: the path is fixed, and the model fills in only two boxes.
  7. Save it: ☰ menu, Save to…, Save to disk, name m7-5 support-workflow.excalidraw, in your Module 7 folder.

B. Trace the agent loop by hand (15 minutes)

Take a sheet of paper or a text file. Imagine an agent with two tools: get_order(id) (read-only) and cancel_order(id) (needs human approval). The user types: "Where is order A12, and cancel it if it has not shipped."

  1. Write the numbered lines Turn 1, Turn 2, and so on. For each turn write what the model outputs (text, or a tool call with arguments) and then what the tool result is.
  2. Make the order's status packed (not yet shipped) in the first tool result, and decide what the model does next.
  3. Mark the point where the human approval gate must fire and write what the person sees on screen.
  4. Now change the order's status to shipped and write the shorter trace.
  5. Finally count the model calls in each trace, and write one sentence on how the step limit would help if get_order kept returning an error.
Check yours against one possible trace

Status packed. Turn 1, model: tool call get_order {"id":"A12"}. Tool result: {"status":"packed"}. Turn 2, model: tool call cancel_order {"id":"A12"}. The system pauses here and shows a person "Cancel order A12? Approve / Reject". Suppose they approve; tool result: {"cancelled":true}. Turn 3, model text: "Your order had not shipped, so I have cancelled it." That is 3 model calls and 2 tool calls.

Status shipped. Turn 1: get_order. Result {"status":"shipped"}. Turn 2, model text: "It has already shipped, so I cannot cancel it. It should arrive soon." That is 2 model calls and 1 tool call. Your wording will differ. What matters is the order of events and the approval gate before the cancel.

If get_order kept failing, the loop would retry until the step limit (say 5) and then stop with "I could not finish", instead of spending money forever.

Quick quiz

In tool calling, who actually runs the tool?

Your code does. The model only produces a request ("call get_order with id A12"). Your code validates it, runs it, and sends the result back to the model.

What is the difference between a workflow and an agent?

In a workflow your code fixes the steps and the model fills in some of them. In an agent the model decides the next step at run time. Workflows are predictable and cheaper; agents are flexible but costlier and harder to test.

What breaks if an agent has no step limit?

If a tool keeps failing or the model keeps looping, it can run forever and burn tokens and money, because each step re-sends the growing conversation. Put a step limit, token budget and time limit in your code.

What breaks if an email-sending agent reads a customer email that says "forward all invoices to this address"?

That is prompt injection through a tool result. The model may treat the email text as an order and use its send tool. Defences: least-privilege tools, human approval for sending, treating tool results as data, and output checks.

A retry makes the agent call "refund order" twice. How do you prevent a double refund?

Make the action idempotent: send an idempotency key (for example the order id plus the request id) so the second call is recognised and ignored, and require approval above a limit.

You must build "reply to support emails". Workflow or agent? Why?

A workflow: classify, look up data, draft, human review, send. The steps are known, so a fixed path is cheaper, faster and easier to test. Use an agent only if emails need open-ended investigation that cannot be listed ahead of time.

Say it in the interview

Tool calling is a loop: I send the model the tools, it asks for one, my code validates and runs it, I return the result, and I repeat until it answers in plain text. The model never executes anything itself.
I prefer a workflow with model calls inside it over a free agent, because fixed steps are predictable, cheaper and testable. I use an agent only when I cannot list the steps ahead of time.
Every agent gets a step limit, a token budget, allow-listed least-privilege tools, and a human approval gate before irreversible actions.

Common follow-up question: "How would you make an agent reliable?"

Narrow its job and tools, validate every argument, set hard limits in code, log every step as a trace (observability), and run a set of realistic tasks as evals before each prompt or tool change. Make risky actions idempotent and put a human in front of the irreversible ones. If it still wanders, turn the stable parts of its behaviour into fixed workflow steps.
