The college gate, the ID card and the library

At a college gate the guard asks, "Who are you?" You show your ID card. He checks the photo and the stamp, and lets you in. That is authentication: proving who you are.

Inside, you walk to the library. The librarian does not ask who you are again: she looks at your card, sees "Student, Year 2", and lets you borrow books, but not enter the staff room. That is authorization: deciding what you are allowed to do.

A good ID card is hard to fake (stamp, hologram), has an expiry date, and carries just enough information. A JWT is exactly that kind of card for websites.

Proving who you are, and what you may do

Authentication vs authorization

QuestionExampleFailure code
Authentication (authn)Who are you?Login with password or Google401 Unauthorized

(Status codes: the name "Unauthorized" for 401 is historic; it really means "not authenticated".)

Sessions with cookies

After login, the server creates a session: a record in its memory or database (session abc123 = user 42) and gives the browser a cookie with only the random ID. Every request carries the cookie, and the server looks the ID up.

  • Plus: the server can end a session instantly (logout, banned user).
  • Minus: every server must reach the session store (often Redis, Redis), which is extra state to scale.

JWT (JSON Web Token)

A JWT is a self-contained token with three parts, separated by dots: header.payload.signature. Each of the first two is JSON, encoded in base64url.

  • Header: the signing algorithm (for example HS256 or RS256).
  • Payload (claims): data such as sub (user id), role, iat (issued at) and exp (expiry time).
  • Signature: a hash made with a secret (or private key) over the header and payload. Anyone with the matching key can check that nobody changed it.
Signed is not encrypted. Base64 is just a way of writing, not a lock. Anyone who holds a JWT can read its payload (you will do it below). Never put secrets or private data in it. The signature only guarantees it has not been changed.

Because the server can verify it with the key alone, it does not need to look anything up. That suits many servers and many services (microservices). The cost: you cannot easily cancel a JWT before it expires.

Expiry and refresh tokens

Make the access token short-lived (for example 15 minutes), so a stolen one stops working soon. Alongside it, issue a longer-lived refresh token (days or weeks), stored more carefully and kept on the server side so it can be revoked. When the access token expires, the app swaps the refresh token for a new access token without asking for the password again.

OAuth 2.0 and "Login with Google"

OAuth 2.0 lets a user give an app limited access without giving their password. (Logging in with Google is OAuth with an identity layer on top, called OpenID Connect.) The roles: you (the user), the app, and Google (the authorization server). Simple steps:

  1. You click "Continue with Google" in the app.
  2. The app redirects your browser to Google with its client ID and the permissions it wants (scopes, like "email").
  3. You log in at Google (the app never sees your password) and click Allow.
  4. Google redirects back to the app with a short-lived code.
  5. The app's server sends the code and its client secret to Google, and receives tokens (an access token, and an ID token telling who you are).
  6. The app logs you in and creates its own session or token.

Other basics

  • HTTPS everywhere: encrypts traffic so nobody on the Wi-Fi can read or change it (HTTP and HTTPS).
  • Hash passwords, never store them. Use a slow, salted password hash: bcrypt, argon2 or scrypt. Not plain text, and not plain SHA-256 or MD5 (too fast to attack). A hash cannot be turned back into the password; at login you hash what was typed and compare.
  • Secrets in environment variables (or a secrets manager), never in code or git. Rotate them if leaked. Different secrets for dev and production.

OWASP Top 10: common risks in one line each

OWASP publishes a list of the most common web security risks. A few to know:

  • Broken access control: a user reaching data they should not (change /orders/5 to /orders/6 and see someone else's). Always check authorization on the server.
  • Injection (SQL): user input becomes part of a command. Use parameterized queries.
  • Cryptographic failures: no HTTPS, weak hashing, secrets in plain sight.
  • Authentication failures: weak passwords, no rate limit on login (rate limiting).
  • Security misconfiguration: default passwords, open buckets, debug mode in production.
  • Vulnerable components: old libraries with known holes. Keep dependencies updated.
  • XSS (cross-site scripting): attacker script runs in the victim's page. Escape output.

Row-level security: authorization inside the database

Instead of trusting every query in your app to add where user_id = ..., the database itself can enforce it. In Postgres and Supabase this is row-level security (RLS): policies that say which rows each user may see or change.

alter table notes enable row level security;

create policy "users read own notes"
on notes for select
using (auth.uid() = user_id);

Now even a bug in the app cannot leak another user's notes through that table. In Supabase, auth.uid() comes from the user's JWT.

Trade-offs

  • Sessions: easy revocation, but needs a shared store. JWT: no lookup, but hard to revoke, so keep them short-lived.
  • Rolling your own login is risky. Prefer a proven provider or library.
  • Defence in depth: HTTPS + checks in the app + database policies. Any one layer can fail.

Do it yourself (about 20 minutes)

Never paste a real production token, password or API key into any website, including debugger sites. Anyone running the site, or anyone who can read its logs, could use it. For real tokens, decode them on your own machine. The token below is made up and harmless.

B. Try to break the signature

  1. On the same page, find the Verify signature area (it has a box for a secret). Type exactly demo-secret-not-real. The page should say the signature is valid (the wording may differ).
  2. Now edit the payload: change "role": "student" to "role": "admin". The encoded token on the left changes, but the page should now say the signature is invalid, because the signature no longer matches. This is why you cannot just edit a JWT to make yourself admin.
  3. Write one sentence: "Signed means tamper-evident, not secret."

C. Paper exercise: protect an endpoint

  1. For GET /orders/6, write the checks a server must do, in order: (1) is there a valid token (authentication, otherwise 401)? (2) has it expired? (3) does order 6 belong to sub from the token, or does the role allow it (authorization, otherwise 403)?
  2. Write which of these a row-level security policy could also enforce in the database.

Quick quiz

Authentication or authorization: "can this user delete this post?"

Authorization. Authentication is proving who the user is.

What are the three parts of a JWT?

Header (algorithm), payload (claims such as user id and expiry) and signature (proof it was not changed).

Is a JWT encrypted?

No, normally it is only signed. Anyone with the token can read the payload, so never put secrets in it.

Why use short-lived access tokens with refresh tokens?

A stolen access token stops working soon. The longer-lived refresh token is kept more safely and can be revoked on the server.

How should you store passwords?

As salted hashes made with a slow algorithm such as bcrypt or argon2. Never in plain text.

Would you use sessions or JWTs for a new web app, and why?

For a single web app, server sessions in an HttpOnly cookie are simple and easy to revoke. JWTs suit many services or mobile clients that need stateless checks, if kept short-lived. Either way I would prefer a proven auth provider over writing my own.

Say it in an interview

"Authentication proves who you are; authorization decides what you may do. I check both on the server for every request."
"I would use short-lived signed access tokens with refresh tokens, HTTPS everywhere, hashed passwords with bcrypt or argon2, and secrets in environment variables."

Common follow-up question: How do you log a user out if JWTs are stateless?

Keep access tokens short-lived, and revoke the refresh token on the server so no new access token is issued. For immediate cut-off, keep a small deny list of revoked token IDs that servers check.
